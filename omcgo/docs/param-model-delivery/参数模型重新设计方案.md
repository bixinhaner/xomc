# 参数模型（ParamModel）重新设计方案

> 本文档定义参数树导入/管理功能的重新设计，将标准路径↔私有路径映射能力整合进系统，完全替换旧的 DataModel 体系。
> 更新日期：2026-04-29

---

## Context

当前 `data_model_definitions` 表存储 TR-069 参数树（JSONB 大对象），按 carrier/tech/oui/product_class/scope 三级回退解析。该设计缺少**标准路径 ↔ 私有路径映射**能力——不同厂商产品使用不同私有路径，OMC 需要统一标准路径进行跨产品管理。

已有 17 个产品映射 XML 文件（MongoDB + MySQL 数据源生成），定义了 standardPath ↔ privatePath 映射关系。本次重新设计将映射能力整合进参数树管理系统，**完全替换**旧的 DataModel 体系。

**核心运行时流程**（来自 TODO.md）：
1. 系统启动：加载 XML → 每个产品类型的默认参数模型
2. 基站连接：productClass → 正则匹配 → 确定产品类型(paramModel) + 软件版本
3. 基站上传参数模型 → 与默认模型取交集 → 按 (paramModel, softwareVersion, standardPath) 存储
4. 参数操作时：standardPath → 查找 privatePath → TR-069 消息使用 privatePath

## 1. 数据库 Schema

### 1.1 `param_models` — 产品参数模型

存储参数模型的顶层定义。每个模型包含一组标准路径↔私有路径的映射关系（如 RTS、QRTB、BaiBNQ），由 XML 文件导入生成。路由表将基站 productClass 解析到具体的 param_model_id，再从本表加载对应的映射集。一个参数模型可服务多个产品子型号（如 QRTB-CA/DC/SC 共用 QRTB 模型）。

| 列 | 类型 | 说明 |
|----|------|------|
| id | UUID PK | |
| name | VARCHAR(64) UNIQUE | "RTS", "QRTB", "BaiBNQ" 等 |
| total_entries | INT | 对象+参数总数 |
| total_objects | INT | 对象数 |
| total_params | INT | 参数数 |
| description | TEXT | |
| is_active | BOOLEAN DEFAULT true | |
| loaded_from | VARCHAR(256) | XML 文件名 |
| created_at / updated_at | TIMESTAMPTZ | |

### 1.2 `param_mappings` — 参数映射（核心表）

系统的核心表，存储每个参数模型下标准路径与私有路径的双向映射。`software_version` 为 NULL 时表示默认模型，非空时为特定软件版本的覆盖映射。运行时通过 Translator 做 O(1) 路径翻译：下发配置时 standardPath → privatePath，解析响应时 privatePath → standardPath。预估 17 个模型约 13,600 条默认映射。

| 列 | 类型 | 说明 |
|----|------|------|
| id | UUID PK | |
| param_model_id | UUID FK → param_models | CASCADE 删除 |
| software_version | VARCHAR(64) | NULL=默认模型，具体值=设备特定 |
| standard_path | TEXT NOT NULL | 标准路径 |
| private_path | TEXT NOT NULL | 产品私有路径 |
| entry_type | VARCHAR(8) CHECK ('object','parameter') | |
| access | VARCHAR(16) | READ_ONLY / READ_WRITE |
| data_type | VARCHAR(16) | STRING/INT/U_INT/BOOLEAN/DATE_TIME |
| change_applies | VARCHAR(16) | Immediate / OnReboot |
| min_value | BIGINT | |
| max_value | BIGINT | |
| is_active | BOOLEAN DEFAULT true | |
| created_at / updated_at | TIMESTAMPTZ | |

**唯一约束**（两个 partial unique index 处理 NULL）：
```sql
CREATE UNIQUE INDEX idx_pm_default ON param_mappings (param_model_id, standard_path) WHERE software_version IS NULL;
CREATE UNIQUE INDEX idx_pm_versioned ON param_mappings (param_model_id, software_version, standard_path) WHERE software_version IS NOT NULL;
```

**查询索引**：
```sql
CREATE INDEX idx_pm_lookup_std ON param_mappings (param_model_id, software_version, standard_path) WHERE is_active;
CREATE INDEX idx_pm_lookup_priv ON param_mappings (param_model_id, software_version, private_path) WHERE is_active;
```

预估行数：17 模型 × ~800 条 ≈ 13,600 默认行 + 设备特定覆盖。

### 1.3 `product_name_routing` — 产品名路由

将基站 Inform 上报的 productClass 字符串通过正则匹配解析为产品显示名（1:1 映射）。匹配结果用于 UI 展示和设备列表的产品名显示。按 sort_order 升序遍历，首次命中即返回，确保具体规则优先于宽泛兜底规则。

| 列 | 类型 | 说明 |
|----|------|------|
| id | UUID PK | |
| product_class | TEXT NOT NULL UNIQUE | 正则表达式，支持精确/锚定/通配符三种模式（详见 §1.4.1） |
| product_name | VARCHAR(128) NOT NULL | 产品显示名，与 product_class 一对一 |
| sort_order | INT NOT NULL | 匹配顺序，加载时按 XML 元素位置自动赋值，查询 ORDER BY sort_order ASC |
| is_active | BOOLEAN DEFAULT true | |
| created_at / updated_at | TIMESTAMPTZ | |

### 1.4 `param_model_routing` — 参数模型路由

将基站 productClass 字符串通过正则匹配解析到参数模型（N:1 映射，多个产品子型号可指向同一参数模型）。匹配结果是 param_model_id，运行时据此加载对应的双向映射集。同样按 sort_order 升序遍历，首次命中即返回。

| 列 | 类型 | 说明 |
|----|------|------|
| id | UUID PK | |
| param_model_id | UUID FK → param_models | CASCADE 删除 |
| product_class | TEXT NOT NULL | 正则表达式，多个规则可指向同一 param_model（详见 §1.4.1） |
| sort_order | INT NOT NULL | 匹配顺序，加载时按 XML 元素位置自动赋值，查询 ORDER BY sort_order ASC |
| is_active | BOOLEAN DEFAULT true | |
| created_at / updated_at | TIMESTAMPTZ | |

共 42 条路由规则（product_name_routing + param_model_routing 各 42 条）。具体改名映射和废弃排除规则参见 `TR069参数映射-实施计划.md`。

### 1.4.1 正则匹配规则详解

路由表中的 `product_class` 列存储正则表达式，运行时对基站 Inform 上报的 productClass 字符串做 `regexp.MatchString`（子串匹配）。42 条规则按正则形态分为三类：

**A. 精确匹配**（无通配符，~20 条）

productClass 字符串固定不变，主要是第三方厂商（京信、大唐、CICT、华为等）。

| productClass 正则 | productName | paramModel | 说明 |
|---|---|---|---|
| `CHINA_TELECOM` | CHINA_TELECOM | CHINA_TELECOM | 电信专用 |
| `FDD-LTE-Enterprise` | FDD-LTE-Enterprise | ENB_DEFAULT_098 | 第三方 FDD |
| `femto_au` | JX-femto_au | ENB_DEFAULT_098 | 京信澳大利亚版 |
| `fBS3251-B01` | DT-fBS3251-B01 | ENB_DEFAULT_181 | 大唐 B01 |
| `fBS3251-Q01` | DT-fBS3251-Q01 | ENB_DEFAULT_181 | 大唐 Q01 |
| `SC3400(L1821)` | CICT-SC3400(L1821) | ENB_DEFAULT_181 | CICT |
| `HM-TCELL-*-2100` / `HM-TCELL-*-1800`（8 条） | HM-TCELL-* | ENB_DEFAULT_098 | 华为 TCELL 系列 |
| `LTE-FDD_N1` ~ `LTE-FDD_N4`（4 条） | JX-LTE-FDD_N* | ENB_DEFAULT_098 | 京信 FDD 系列 |

**B. 锚定路径匹配**（`^...$`，~10 条）

用 `^` 和 `$` 锚定完整字符串，精确匹配已知路径格式。主要是 Baicells 自有产品的已知子型号。

| productClass 正则 | productName | paramModel | 说明 |
|---|---|---|---|
| `^FAP/MLN/SC$` | MLN-SC | MLN | MLN 单载波 |
| `^FAP/MLN/CA$` | MLN-CA | MLN | MLN 载波聚合 |
| `^FAP/MLN/DC$` | MLN-DC | MLN | MLN 双连接 |
| `^FAP/MLQ/SC$` | MLQ | MLQ | MLQ 单载波 |
| `^FAP/PGSM$` | BSC | BSC | 皮基站网关 |
| `^FAP/BTS$` | BTS | BTS | 基站传输 |
| `^FAP/BU1810$` | BM | BM | BM 型号 |
| `^FAP/pBS41010/SC$` | QRTB-SC | QRTB | QRTB 特定子型号 |
| `^FAP/BAIBLQ/SC$` | BAIBLQ | QA_V3.1 | Baicells BLQ 系列 |
| `^FAP/BaiBLX-(QRTB\|BLQ)/SC` | BLX | BLX | BLX 系列，QRTB 或 BLQ 子型号 |

**C. 通配符模式匹配**（`\w+` / `\w*`，~12 条）

用 `\w+`（1+ 字母数字）和 `\w*`（0+ 字母数字）匹配中间的设备型号部分。通过芯片型号 + 射频模式组合识别产品。

| productClass 正则 | productName | paramModel | 说明 |
|---|---|---|---|
| `FAP/\w*BSC\w+` | BaiBNQ | BaiBNQ | BSC 芯片组 |
| `FAP/\w+(BS31)\w+/CA` | QRTB-CA | QRTB | BS31 芯片 + 载波聚合 |
| `FAP/\w+(BS31)\w+/DC` | QRTB-DC | QRTB | BS31 芯片 + 双连接 |
| `FAP/\w+(BS31)\w+/SC` | QRTB-SC | QRTB | BS31 芯片 + 单载波 |
| `FAP/\w+(BS32)\w+/SC` | QAFB | QAFB | BS32 芯片 |
| `FAP/\w+(BS41)\w+/SC` | QATA | QAFA | BS41 芯片 |
| `FAP/\w+(BS42\|RS43)\w+/SC` | QAFA | QAFA | BS42 或 RS43 芯片 |
| `FAP/\w+(BS81)\w+/(DC\|SC)` | RTD | RTS | BS81 芯片 |
| `FAP/\w+CRB\w+/CA` ~ `/TC`（4 条） | CR-B4860-* | CR-B4860 | CRB 板 |
| `FAP/\w+PMB\w+` | PM-B4860 | PM-B4860 | PMB 板 |
| `HeNB-\w+` | DXDF | DXDF | 华为 HeNB |
| `(FAP/\w+BU2210)\|^001$\|^003$\|^5G BBU-F1$` | BaiBNX | BaiBNX | 多选一：BU2210 或固定编码 |
| `FAP` | RTS | RTS | **兜底规则**——任何含 "FAP" 的字符串 |

### 1.4.2 匹配顺序

**正则是子串匹配**（Go 的 `regexp.MatchString`），不是全匹配，因此匹配顺序至关重要。

关键约束：**`FAP` 这条规则能匹配所有包含 "FAP" 的字符串**（如 `FAP/pBS7430/DC`、`FAP/MLN/SC` 等）。如果它排在前面，所有 Baicels 产品都会被错误识别为 RTS。

**排序机制**：

1. 生成脚本 `generate_routing.py` 按正则特异性（锚点 `^$` > 通配符 `\w+` > 纯字符串）排序后输出 XML，确保具体规则在前、宽泛兜底在后
2. 加载器按 XML 元素位置依次赋 `sort_order = 1, 2, 3...` 写入数据库
3. 运行时 `ORDER BY sort_order ASC` 逐条遍历，首次 `regexp.MatchString` 命中即返回

**product_name_routing vs param_model_routing 的关系**：

| 维度 | product_name_routing | param_model_routing |
|---|---|---|
| 映射目标 | productName（UI 显示名，1:1） | paramModel（参数集，N:1） |
| 唯一性 | 42 条 → 42 个不同显示名 | 42 条 → 17 个参数模型 |
| 典型例子 | QRTB-CA / QRTB-DC / QRTB-SC 各自独立 | 三个都路由到 QRTB 参数集 |

同一套 TR-069 参数可以服务多个产品子型号（如 QRTB-CA/DC/SC 共用 QRTB.xml），但 UI 上需要按射频模式分别显示。

### 1.5 `standard_params` — 标准参数树

定义 OMC 统一的标准参数路径，独立于任何厂商的私有实现。约 2555 条标准路径，用于参数配置模板、KPI 定义等跨产品场景——所有操作面向标准路径，由 param_mappings 在运行时翻译为具体厂商的私有路径。

| 列 | 类型 | 说明 |
|----|------|------|
| id | UUID PK | |
| standard_path | TEXT NOT NULL | |
| entry_type | VARCHAR(8) | object / parameter |
| access / data_type / change_applies | VARCHAR(16) | |
| min_value / max_value | BIGINT | |
| created_at / updated_at | TIMESTAMPTZ | |

~2555 条标准路径。

## 2. Go 后端架构

### 2.1 新包 `internal/config/parammodel/`（9 个文件）

```
internal/config/parammodel/
├── model.go         — 领域类型
├── repository.go    — 接口定义
├── pg_repository.go — PostgreSQL 实现
├── handler.go       — HTTP 端点（Gin）
├── registry.go      — 路由解析 + 映射缓存
├── translator.go    — standardPath ↔ privatePath 翻译（新能力）
├── loader.go        — XML 文件加载（启动时从文件系统读取）
├── intersect.go     — 基站模型与默认模型交集逻辑
└── cache.go         — Redis L2 缓存
```

### 2.2 核心类型（model.go）

- **ParamModel** — 对应 param_models 表
- **ParamMapping** — 对应 param_mappings 表
- **ProductNameRoute** — 对应 product_name_routing 表
- **ParamModelRoute** — 对应 param_model_routing 表
- **StandardParam** — 对应 standard_params 表
- **TranslationResult** — 翻译结果：`{Original, Translated, Found, Mapping}`

### 2.3 Registry 解析流程

**替代旧的三级回退**，更简单直接：

```
基站 Inform → productClass 字符串（如 "FAP/pBS7430/DC"）

  Step 1: productName 路由
    → 按 sort_order ASC 遍历 product_name_routing
    → 首次 regexp.MatchString 命中 → 得到 productName（如 "QRTB-DC"，用于 UI 显示）

  Step 2: paramModel 路由
    → 按 sort_order ASC 遍历 param_model_routing
    → 首次 regexp.MatchString 命中 → 得到 param_model_id（如 "QRTB"）
    → 多条同时命中时报错（需要调整正则精确度）

  Step 3: 加载参数模型
    → GetParamModel(paramModelId, softwareVersion)
    → L1 sync.Map → L2 Redis → L3 PostgreSQL
    → 返回该 paramModel 的双向映射（standardToPrivate + privateToStandard）
```

**匹配示例**：productClass = `"FAP/pBS7430/DC"`

| 步骤 | 遍历到的正则 | 是否命中 | 说明 |
|------|-------------|---------|------|
| productName #1 | `FAP/\w*BSC\w+` | ✗ | 无 BSC |
| productName #2 | `FAP/\w+(BS31)\w+/CA` | ✗ | 无 BS31 |
| ... | ... | ✗ | 跳过其他具体规则 |
| productName #N | `FAP/\w+(BS31)\w+/DC` | ✓ | 命中，返回 "QRTB-DC" |
| paramModel #1 | `FAP/\w*BSC\w+` | ✗ | 无 BSC |
| ... | ... | ✗ | 跳过 |
| paramModel #N | `FAP/\w+(BS31)\w+/DC` | ✓ | 命中，加载 QRTB 参数模型 |

注意：兜底规则 `FAP` 排在最后，只在前面的具体规则都未命中时才生效（匹配到 RTS）。

### 2.4 Translator 路径翻译（新能力）

```
TranslateToPrivate(ctx, paramModelId, softwareVersion, standardPath) → TranslationResult
TranslateToStandard(ctx, paramModelId, softwareVersion, privatePath) → TranslationResult
```

- O(1) 查找（map 查询），用于 ACS 运行时翻译
- SetParameterValues：模板用 standardPath 定义 → 翻译成 privatePath 下发
- GetParameterValues 响应：privatePath → 翻译回 standardPath 存储

### 2.5 XML 加载器（loader.go）

**启动时从文件系统加载**：
1. 配置目录路径（`ParamModelConfig.XMLDirectory`）
2. 扫描 `*.xml` 文件
3. 解析四种格式：产品映射 XML、product-name-routing.xml、param-model-routing.xml、standard-model.xml
4. Upsert 语义：存在则更新映射，不存在则新建
5. 每个 XML 在事务中处理（删旧映射 → 批量插入新映射）
6. 加载完毕后预热 L1 缓存

### 2.6 交集逻辑（intersect.go）

基站首次连接时上报自身的完整参数模型，需要与系统预定义的默认模型取交集，得到该基站实际支持的参数子集。默认 paramModel 的获取方式：通过 §2.3 的 Registry 路由解析得到 param_model_id，加载 `param_mappings` 中 `software_version IS NULL` 的映射行（即启动时从 XML 导入的全量映射）。

```
基站上传参数模型 XML → 解析得到 privatePath 集合
默认 paramModel → 遍历 privateToStandard 反向索引
交集 = 默认 paramModel 中 privatePath 存在于 基站集合的条目
以 softwareVersion 存储交集结果
```
