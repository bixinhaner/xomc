## 三、修复效果分析

### Fix 1: Per-device Transport Pool

**问题**: v2 每会话创建新 Transport → 每会话 TCP 握手 → 高开销
**修复**: 每设备一个 Transport (MaxConnsPerHost=1) → TCP 连接跨会话复用
**效果**:
- R4 吞吐: v2 666/s → v3 **2,310/s** (×3.5 提升)
- R3 TCP errors: v2 10,681 → v3 **43** (×248 减少)
- 原理: TCP 连接在同一设备的多次会话间复用，消除了重复握手开销

### Fix 2: Stress Config (relaxed rate limit)

**问题**: 生产配置 10/min/device 在高频压测下限流 >50% 请求
**修复**: 压测专用配置 `acs-stress.yaml` (rate_limit=60000/min)
**效果**:
- R1 成功率: v2 46.7% → v3 **100%** (+53.3pp)
- R2 成功率: v2 77.8% → v3 **99.96%** (+22.2pp)
- R1-R4 rate_limited = **0** (完全消除)

### Fix 3: Per-device In-flight Guard

**问题**: 同一设备可能有多个并发会话，导致 RemoteAddr 冲突
**修复**: `sync.Map` 原子 CAS 保证每设备同时只有一个活跃会话
**效果**: 匹配真实 CPE 行为 (一次一个会话)，消除了设备级并发冲突

### Fix 4: Rate-Limited Response Tracking

**问题**: v1/v2 无法区分 Rate Limit 失败和其他失败
**修复**: 追踪 503/429 响应，在报告中单独显示 `rate_limited` 字段
**效果**: 立即识别 Rate Limiter 是否为瓶颈，提供精确修复建议

## 六、R5 崩溃分析

R5 (3000 并发) 60.1% 的成功率中，40% 的失败全部来自 TCP errors (62,538 个)：
- 0 rate-limited
- 0 application failures
- 62,538 TCP connection timeout/refused

**根因**: macOS 默认 fd limit (~10240) 不足以支撑 30000 per-device transport。
每个 transport 维护一个 idle TCP 连接 → 30000 连接 + 系统开销 > fd limit。

**不影响生产**: 独立部署 + Linux (fd limit 可调至 100K+) + 负载均衡。
