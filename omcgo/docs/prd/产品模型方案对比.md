## 0. 一句话摘要

| 方案 | 一句话定位 | 文档形态 | 代码就绪度 |
|------|-----------|---------|----------|
| **A 老方案** | "如何把 17 个 XML 落地为 5 张表 + 完整 CRUD 系统"——**短平快的实施手册** | 含 SQL / Go 文件路径 / REST 端点 / 前端页面 / 5 阶段实施步骤 | ★★★★★ 可立即开工 |
| **B 新方案** | "把 Product 抽出为一等公民，加生命周期 / 灰度 / RBAC / 观测"——**架构演进蓝图** | 含实体关系 / 状态机 / 流程边界 / 开源借鉴 / 7 阶段演进路线 | ★★☆☆☆ 缺 SQL / API / 前端 / 启动加载细节 |

**核心差异**：A 把"产品（Product）"概念合并进 `param_models` 表 + 两张并列路由表表达；B 把 Product 提升为独立实体，并在其上叠加版本生命周期、灰度发布、RBAC、可观测等运营能力。

**最佳实施路径**：A 提供 short-term 落地模板，B 提供 long-term 演进目标。两者**不冲突**，B 是 A 的超集演进。

## 1. 实体模型对比

### 1.1 核心实体清单

| 概念 | 方案 A（老）| 方案 B（新） |
|------|-----------|-------------|
| 模型抽象 | `param_models` 表（一行 = 一个产品族，如 RTS / QRTB / BaiBNQ）| `Model` 实体（与厂商 / 型号无关的标准 path 集合）|
| 产品概念 | **隐含在 `param_models.name` 字段**（无独立实体）| `Product` 实体（一等公民，绑定 Model）|
| 版本管理 | `param_mappings.software_version` 列（NULL = 默认）| `ProductVersion` 实体（独立行 + 生命周期）|
| 软件版本归属 | 列中精确字符串匹配 | `SoftwareVersionRange` 表（区间 + 优先级）|
| 设备路由规则 | 两张并列全局表：`product_name_routing` + `param_model_routing`（各 42 条）| 每 Product 一组 `ProductMatchingRule`（per-product 局部）|
| 设备 | `devices` 表（不变）| 设备运行时动态绑定到 (Product, ProductVersion) |
| 标准参数全集 | `standard_params` 表（~2555 条）| 隐含在 Model 内部 |
| 路径映射 | `param_mappings`（核心表，N 行 / paramModel）| ProductVersion 的映射表 |

### 1.2 实体数对比

| 维度 | 方案 A | 方案 B |
|------|--------|--------|
| 表数量 | **5 张**（param_models / param_mappings / product_name_routing / param_model_routing / standard_params）| **6+ 张**（Model / Product / ProductVersion / ProductMatchingRule / SoftwareVersionRange / param_model_audit_log + 隐含 mapping 表）|
| 一等概念 | 5 个 | 6 个 |
| 路由规则归属 | 全局共享 | 隶属 Product |
| 版本号语义 | 无生命周期，仅区分"默认 / 特定版本" | SemVer + 状态机 + 灰度 |

### 1.3 实体关系图对比

**A 老方案的关系**：
```
product_name_routing ─────┐
param_model_routing ──┐   │  （两表并列，结构相同，输出不同）
                      ▼   ▼
                  param_models ───── param_mappings (含 software_version 列)
                                              │
                                  standard_params (全局独立)
```

**B 新方案的关系**：
```
              Model ←─ N ── Product ←─ N ── ProductVersion
                              │              │
                              │ 1:N          │ 1:N
                              ▼              ▼
                  ProductMatchingRule  SoftwareVersionRange
                              ▲              ▲
                              │ regex 命中    │ version 命中
                              └────── Device ───────┘
```

**结构差异**：A 是"模型 + 平行路由"两层结构；B 是"模型 ← 产品 ← 版本"三层有向树。B 的 Product 充当聚合根（DDD 意义上），运维变更在 Product 边界内闭合，A 的全局路由表是跨 Product 共享，调整任一行可能影响多产品。

## 3. 优缺点分析

### 3.1 方案 A 老方案

**优点**：

1. **可立即开工**：5 张表 SQL 完整、9 个 Go 文件路径明确、7 个 REST 端点列全、5 个前端 Tab 描述到位，团队拿到即可拆分任务并行
2. **改动量小**：基本只在 `internal/config/parammodel/` 新增包；现有消费者修改清单明确（6 个文件）
3. **数据库设计紧凑**：5 张表覆盖全部 XML 内容，索引设计针对热路径（`idx_pm_lookup_std` / `idx_pm_lookup_priv`）
4. **加载流程清晰**：XML 扫描 → 事务内 Upsert → L1 预热，每步可验证（启动后 `SELECT count(*)` ≈ 13,600）
5. **REST API 完备**：CRUD + import/export + 路由测试 + 翻译调试全覆盖
6. **前端规划具体**：5 个 Tab + 文件路径 + 主要交互全部列出
7. **验证可量化**：每阶段都给出验证方法（行数、单元测试、curl、UI 手测、grep 扫描）

**缺点**：

1. **"Product"概念缺失**：`param_models` 行同时承担"模型"和"产品"两种语义；运营心智上把 RTS / QRTB / BaiBNQ 当成"模型"，但它们其实是产品族
2. **路由分两表，运营成本高**：`product_name_routing` 与 `param_model_routing` 各 42 条独立维护，添加新产品时需要在两个地方各加一条，容易遗漏
3. **路由是全局共享**：调整任一规则可能影响所有产品；Product 边界不清晰
4. **版本管理弱**：`software_version` 是字符串列，**无生命周期**、无灰度、无回滚、无审批
5. **缺冲突处理**：§2.3 说"多条同时命中时报错"，但报错给谁、怎么降级、未识别设备如何兜底，全部空白
6. **缺路径转换边界**：找不到映射时 panic？返回空？降级用标准 path？文档未答
7. **缺类型校验**：`param_mappings.data_type` 列存在但发布前不校验"私有 path 类型 == 标准 path 类型"
8. **缺 RBAC**：谁能创建 / 修改 / 导入 XML？
9. **缺审计**：变更哪些字段？谁改的？为什么？
10. **缺观测**：翻译延迟、缓存命中率、路由匹配分布？
11. **缺多实例同步协议**：列了 `parammodel:cache_version` 但没说怎么用
12. **样本数据已过期**：方案写"17 模型 / 42 路由"，但实测当前 XML 是 9 模型 / 27 路由（参见 [产品模型.md §8.3](./产品模型.md)）

### 3.2 方案 B 新方案

**优点**：

1. **概念模型干净**：Model / Product / ProductVersion / MatchingRule 各司其职；运维心智模型与商业语言一致（"我们家 MLN 产品的 v1.2 版本"）
2. **Product 是聚合根**：路由规则、版本族都属于 Product，调整不外溢，多团队并行修改不冲突
3. **完整生命周期**：4 状态 + 状态机约束（同 Product 单 active），杜绝"线上同时跑两套配置"
4. **灰度发布**：4 种策略（immediate / percent / device_group / scheduled）+ 自动回滚，借鉴 Hawkbit 已验证模式
5. **路径转换鲁棒**：4 类边界明确（双源合并 / 缺私有 path / 未知 path / 类型不一致），并且类型校验阻塞发布
6. **运营保障齐全**：RBAC 矩阵 + 审计日志 + 评审流程 + 默认策略
7. **可观测性完整**：5 个 Prometheus 指标 + 关键日志 + 4 条告警规则 + 灰度看板
8. **未知设备兜底**：Default Product 模式（借鉴 ThingsBoard），保证设备永远可接入
9. **多实例同步协议清晰**：cache_version 写入 + 30s 轮询，未来可平滑升级到 Pub/Sub
10. **OSS 借鉴有据**：每个开源项目都给出"具体借鉴哪一点"和"借鉴到本方案的哪一节"
11. **远期演进留接口**：Function Block / 三要素 / desired-reported 都已纳入路线图

**缺点**：

1. **缺 SQL 细节**：6 个新实体只有 1 个（SoftwareVersionRange）列出列，其余仅口头描述；落地需要补完
2. **缺 Go 代码结构**：未给包路径、文件清单、接口签名（除 Translator）
3. **缺 REST API**：CRUD 端点未列；前端无法对接
4. **缺前端规划**：页面、组件、交互全部缺失
5. **缺 XML 启动加载流程**：与现有 9 个 XML 文件如何对接？是直接 import 现有数据还是新建？
6. **缺与现有代码迁移路径**：现有 `internal/config/datamodel/` 包如何过渡？哪些文件改、哪些删？
7. **缺验证方案**：每阶段如何确认完成？
8. **实施阶段偏抽象**：7 阶段无具体里程碑、无验证标准、无 Owner
9. **复杂度引入风险高**：6 实体 + 状态机 + 灰度 + RBAC + 审计同时上，团队学习成本陡峭
10. **第 6 实体半成品**：`software_version_ranges` 只列了 4 列；多区间命中按 priority 取最大，但 priority 的赋值规则没说
11. **MatchingRule 边界未细化**：每 Product 的 sort_order 是局部还是全局？跨 Product 命中冲突时，sort_order 怎么排？
12. **Default Product 实现细节缺**：兜底设备如何后续手工分配？怎么"重新路由"？
13. **回滚自动化未细化**：1h 观察期内基于什么指标判断"失败"自动回退？

## 5. 兼容性与演进关系

### 5.1 表结构兼容关系

| A 的表 | B 中对应实体 | 兼容方式 |
|--------|-------------|---------|
| `param_models` | Model + Product 拆分 | A 表的一行 = B 中一个 (Model, Product) 对 |
| `param_mappings` (default) | Product 默认 ProductVersion 的映射 | software_version IS NULL 的行 → ProductVersion `v0` |
| `param_mappings` (versioned) | ProductVersion 的映射 | software_version 值 → 创建对应 ProductVersion |
| `product_name_routing` | Product 的 display_name + 部分 MatchingRule | 拆分到 Product 表（display_name）和 MatchingRule（regex） |
| `param_model_routing` | Product 的 MatchingRule | 直接迁移，加 product_id |
| `standard_params` | Model 内嵌 | 直接迁移，加 model_id |

**结论**：A 的所有表都可以**无损迁移**到 B，迁移过程是"拆分 + 关联补齐"，不存在数据丢失。

### 5.2 推荐的双阶段演进路径

```
阶段 1（按 A 落地）:
  按 A 完整实施（5 张表 + 9 个 Go 文件 + 7 个 REST 端点 + 5 个前端 Tab）
  ↓
  落地后线上跑 1-2 个月，验证基本能力
  ↓
阶段 2（按 B 演进）:
  迁移 1: 拆 param_models → (models, products) 两表
  迁移 2: 拆 param_mappings 的 software_version 列 → product_versions 表
  迁移 3: 路由表加 product_id，迁为 per-product
  ↓
  在新结构上叠加：
  - 生命周期状态字段
  - 灰度发布
  - RBAC + 审计
  - 可观测性指标
```

**字段命名预防**：阶段 1 落地时建议字段名提前向 B 对齐：
- `param_models.name` → 新方案中"Product code"，沿用即可
- `param_mappings.software_version` → 阶段 2 时拆出 `product_version_id` 外键，老列保留作为冗余列以便回滚
- 路由表新增 `applies_to_product_name VARCHAR(64)` 冗余列，阶段 2 时改为 `product_id UUID FK`

### 5.3 风险等级评估

| 直接按 A 实施 | 直接按 B 实施 |
|--------------|--------------|
| 风险等级：**低**（5 表 + 已有完整 spec） | 风险等级：**高**（6+ 实体同时引入 + 状态机 + 灰度 + RBAC） |
| 团队学习成本：**低** | 团队学习成本：**高** |
| 短期欠债：**多**（缺生命周期 / 灰度 / RBAC / 观测） | 短期欠债：**多**（缺 SQL / API / 前端 / 加载流程） |
| 长期演进：需要二次迁移 | 长期演进：直接到位 |

**推荐**：阶段 1 按 A 落地（快），阶段 2 增量演进到 B（稳）。

## 6. 决策建议

### 6.1 如果"业务方要求 1 个月内出可用版本"

→ **采用方案 A**。
- 数据建模 + REST + 前端齐备，可拆分 4-5 人并行
- 接受短期欠债（生命周期 / 灰度 / RBAC / 观测）
- 落地后开 backlog，逐项补齐 B 的能力

### 6.2 如果"业务方要求一次到位、3-6 个月窗口"

→ **以 B 为目标，但以 A 的施工细节为施工模板**：
- B 缺的 SQL / API / 前端，按 A 的同等粒度补完（实质是把 B 的 6 个实体写出 A 那样的完整 spec）
- 一次迁移到位，避免阶段 2 的二次重构成本
- 引入风险高，需保证团队对状态机 / 灰度 / RBAC 的实施经验

### 6.3 如果"团队人手紧 + 长期演进诉求并存"

→ **A → B 渐进路径**（推荐）：
- 阶段 1：A 落地（4-6 周），同时把 B 的 7 阶段路线挂入 backlog
- 阶段 2：每个 sprint 拆 1-2 项 B 的能力（生命周期、灰度、RBAC ...）增量交付
- 阶段 1 字段命名按 §5.2 提前对齐，降低阶段 2 重构成本

### 6.4 通用建议（无论选哪个）

1. **先校准基础数据**：当前 XML 实测为 9 模型 / 27 路由，与 A 中的 17/42 不符；在动手前统一以实测为准
2. **设计 ADR**：把 §1.1 的"方案 A vs B 实体决策"写成 Architecture Decision Record，提交团队评审
3. **路径冲突测试集**：为 productClass 路由准备一份"已知冲突测试用例"（如 `FAP/MLN/SC` 与兜底 `FAP` 的优先级），自动化跑通
4. **类型一致性校验前置**：无论选 A 还是 B，发布前的"私有 path 类型 == 标准 path 类型"校验都是必备防呆，建议优先实现
5. **观测先行**：哪怕选 A，至少先注册"翻译失败计数 + 路由匹配分布"两个指标，否则上线后无法发现路由错配
