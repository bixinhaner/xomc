# 产品模型 — 业务流程与表结构关系

> 提取自 `omcgo/docs/param-model-delivery/参数模型重新设计方案.md`（v 2026-04-29）
> 范围：聚焦业务流程 + 表结构关系；实施阶段 / REST API / 前端设计参见原文 §3-§7

---

## 0. 一句话定位

**TR-069 标准路径 ↔ 厂商私有路径双向映射系统**：一个产品（参数模型）有多个软件版本，不同版本可能有不同私有路径；OMC 统一面向标准路径操作，由 Translator 运行时翻译。

---

## 1. 业务流程

### 1.1 总览（4 个独立流程）

```
A. 启动加载       — 17 个 XML → 5 张表（一次性，进程启动时）
B. 设备首次连接   — productClass 字符串 → 路由解析 → 加载默认参数模型
C. 基站参数交集   — CPE 上传完整模型 → 与默认模型取交集 → 按软件版本存储
D. 参数操作翻译   — standardPath ↔ privatePath O(1) 翻译（每次 RPC 触发）
```

依赖关系：A 是基础（无 A 后续全失败）；B / C 在设备生命周期触发各一次；D 在每次 SetParameterValues / GetParameterValues 触发。

---

### 1.2 流程 A — 启动加载（loader.go）

```
配置目录 ParamModelConfig.XMLDirectory
   │
   ▼
扫描 *.xml → 解析四种格式
   ├── 产品映射 XML (17 份，对应 17 个 paramModel)
   ├── product-name-routing.xml  (42 条规则)
   ├── param-model-routing.xml   (42 条规则)
   └── standard-model.xml        (~2555 条标准路径)
   │
   ▼
事务内 Upsert（每 XML 一个事务，保证单文件原子性）
   ├── 删除该 paramModel 旧映射
   └── 批量插入新映射 + 路由规则按 XML 元素位置赋 sort_order = 1, 2, 3 ...
   │
   ▼
预热 L1 缓存（sync.Map）→ 等待运行时查询
```

**预期落库行数**：17 模型 × ~800 = 约 13,600 条 `param_mappings` + 42 条 `product_name_routing` + 42 条 `param_model_routing` + ~2555 条 `standard_params`。

---

### 1.3 流程 B — 设备首次连接（registry.go）

替代旧 carrier/tech/oui/product_class 三级回退，直接走两步路由 + 加载：

```
基站 Inform 报文 → productClass 字符串（如 "FAP/pBS7430/DC"）
   │
   ▼
Step 1: productName 路由
   ├── ORDER BY sort_order ASC 遍历 product_name_routing
   ├── 首个 regexp.MatchString 命中 → productName（如 "QRTB-DC"）
   └── 用途：UI 设备列表显示名
   │
   ▼
Step 2: paramModel 路由
   ├── ORDER BY sort_order ASC 遍历 param_model_routing
   ├── 首个 regexp.MatchString 命中 → param_model_id（如 "QRTB"）
   ├── 多条同时命中 → 报错（提示调正则精确度）
   └── 用途：加载映射集
   │
   ▼
Step 3: 加载参数模型（三级缓存）
   ├── L1 sync.Map → L2 Redis (parammodel:mapping:{id}:{ver}) → L3 PostgreSQL
   └── 返回 standardToPrivate + privateToStandard 双向 map
```

**关键设计 — sort_order 决定匹配优先级**

`regexp.MatchString` 是**子串匹配**（非全匹配），因此匹配顺序必须确保**具体规则在前、宽泛兜底在后**。机制：

1. `generate_routing.py` 按正则特异性（锚点 `^$` > 通配符 `\w+` > 纯字符串）排序后输出 XML
2. 加载器按 XML 元素位置依次赋 `sort_order = 1, 2, 3, ...`
3. 运行时 `ORDER BY sort_order ASC` 逐条遍历，首次命中即返回

**反例**：兜底规则 `FAP` 能匹配所有含 "FAP" 的字符串。如果它排在前面，所有 Baicells 产品（FAP/MLN/SC、FAP/pBS7430/DC 等）都会被错误识别为 RTS。**正解**：兜底规则 sort_order 排到最大，仅在前面具体规则全部 miss 时生效。

**匹配示例**（productClass = `"FAP/pBS7430/DC"`）：

| 步骤 | 遍历到的正则 | 是否命中 | 说明 |
|------|-------------|---------|------|
| productName #1 | `FAP/\w*BSC\w+` | ✗ | 无 BSC |
| productName #N | `FAP/\w+(BS31)\w+/DC` | ✓ | 命中，返回 "QRTB-DC" |
| paramModel #N | `FAP/\w+(BS31)\w+/DC` | ✓ | 命中，加载 QRTB 参数模型 |

兜底规则 `FAP` 排在最后，仅在前面具体规则全部 miss 时才被命中（→ RTS）。

### 1.4 流程 C — 基站参数交集（intersect.go）

设备首次连接后会上传自身完整参数模型 XML。系统需与 OMC 预定义的默认模型取交集，得到该基站实际支持的参数子集：

```
CPE 上传参数模型 XML
   │
   ▼
解析得到 privatePath 集合（设备真实支持的私有路径）
   │
   ▼
通过流程 B 拿到默认 paramModel
   ├── param_mappings WHERE param_model_id = ? AND software_version IS NULL
   └── 即启动时从 XML 导入的全量映射
   │
   ▼
遍历 默认模型 的 privateToStandard 反向索引
   │
   ▼
交集 = 默认 paramModel 中 privatePath 存在于 CPE 集合的条目
   │
   ▼
按 (param_model_id, software_version) 写回 param_mappings
   └── software_version 非 NULL，标记为该设备特定版本的覆盖映射
```

**意义**：默认模型是产品线全集；交集结果是设备实际能力子集，避免下发设备不支持的路径。

---

### 1.5 流程 D — 参数操作翻译（translator.go）

每次 ACS 与 CPE 交互时双向翻译路径：

```
配置下发（SetParameterValues）
   ├── 模板 / 规则使用 standardPath 定义
   ├── TranslateToPrivate(ctx, paramModelId, softwareVersion, standardPath)
   ├── O(1) map 查找 → privatePath
   └── TR-069 SOAP 报文使用 privatePath 下发

参数响应（GetParameterValues / Inform）
   ├── CPE 返回 privatePath
   ├── TranslateToStandard(ctx, paramModelId, softwareVersion, privatePath)
   ├── O(1) map 查找 → standardPath
   └── 应用层按 standardPath 存储 / 联动配置基线 / KPI 等
```

**软件版本回退语义**：先用 `software_version` 精确匹配；未命中则回退到 `software_version IS NULL` 的默认映射。

## 2. 表结构关系

### 2.1 ER 关系总览

```
                           ┌─────────────────────┐
                           │   param_models      │
                           │  (17 行：参数模型)    │
                           │  - id (PK, UUID)    │
                           │  - name (UNIQUE)    │
                           └────┬────────────────┘
                                │ 1:N (CASCADE)
                                │
              ┌─────────────────┼──────────────────┐
              │                                     │
              ▼ N                                   ▼ N
      ┌──────────────────┐               ┌──────────────────────┐
      │ param_mappings   │               │ param_model_routing  │
      │ (~13,600 默认行) │               │ (42 条规则)            │
      │ 双向映射核心      │               │ productClass→model   │
      └──────────────────┘               └──────────────────────┘

      ┌─────────────────────┐                 ┌────────────────────┐
      │ product_name_routing│                 │  standard_params   │
      │ (42 条规则)          │                 │  (~2555 条)         │
      │ productClass→显示名  │                 │  OMC 标准路径全集    │
      │ 1:1 映射             │                 │  独立于厂商私有实现  │
      └─────────────────────┘                 └────────────────────┘
            │                                          │
            └────── 由 productClass 路由（双查询）─────┘
                       两表查询互不依赖
```

**关系特征**：

- `param_models` ⇄ `param_mappings`：**1:N 强耦合**（CASCADE 删除）。一个参数模型有多组（standardPath, privatePath）映射；不同 software_version 可同时存在
- `param_models` ⇄ `param_model_routing`：**1:N 强耦合**（CASCADE）。同一参数模型可被多个 productClass 正则指向（如 QRTB-CA/DC/SC 三个 productClass 都路由到 QRTB 参数模型）
- `product_name_routing` 与 `param_model_routing`：**形式同构、语义独立**。两表各 42 条规则，前者解析显示名（1:1），后者解析参数集（N:1）。运行时分别查询，结果互不影响
- `standard_params`：**独立全局表**。OMC 跨产品的标准路径定义，不与任何厂商私有路径直接关联；通过 `param_mappings.standard_path` 间接关联

**关键 N:1 案例**：QRTB-CA / QRTB-DC / QRTB-SC 三个不同子型号 → `param_model_routing` 三条规则 → 都指向同一 `QRTB` `param_models` 行 → 共用一组 `param_mappings` 默认映射；但 UI 上通过 `product_name_routing` 显示三个独立产品名。

**唯一约束**（两个 partial unique index 处理 NULL 语义）：

```sql
CREATE UNIQUE INDEX idx_pm_default ON param_mappings (param_model_id, standard_path)
  WHERE software_version IS NULL;
CREATE UNIQUE INDEX idx_pm_versioned ON param_mappings (param_model_id, software_version, standard_path)
  WHERE software_version IS NOT NULL;
```

**查询索引**（流程 D 双向翻译热路径）：

```sql
CREATE INDEX idx_pm_lookup_std  ON param_mappings (param_model_id, software_version, standard_path) WHERE is_active;
CREATE INDEX idx_pm_lookup_priv ON param_mappings (param_model_id, software_version, private_path)  WHERE is_active;
```

**预估行数**：17 模型 × ~800 默认映射 ≈ 13,600 行 + 设备特定覆盖（按上线设备数 × 软件版本累积）。

### 2.7 正则匹配三类形态（路由表共用）

`product_class` 列存正则表达式，运行时 `regexp.MatchString` 子串匹配：

| 形态 | 占比 | 示例 | 场景 |
|------|------|------|------|
| **A. 精确匹配**（无通配符） | ~20 条 | `CHINA_TELECOM`、`fBS3251-B01`、`HM-TCELL-*-2100` | 第三方厂商固定 productClass（京信、大唐、CICT、华为）|
| **B. 锚定路径**（`^...$`） | ~10 条 | `^FAP/MLN/SC$`、`^FAP/MLQ/SC$` | Baicells 自有产品已知子型号 |
| **C. 通配符模式**（`\w+` / `\w*`） | ~12 条 | `FAP/\w+(BS31)\w+/SC`、`FAP/\w*BSC\w+` | 通过芯片型号 + 射频模式组合识别 |

**兜底规则** `FAP`（精确字符串匹配，无锚定）必须 sort_order 最大 — 任何含 "FAP" 的字符串都会命中，作为终兜底防漏匹配。

## 3. 索引读写视图汇总

| 操作场景 | 命中索引 | 表 | 流程 |

## 5. Redis 缓存键（运行时性能）

```
parammodel:mapping:{paramModelId}:{softwareVersion}  — paramModel 映射 JSON (TTL 24h)
parammodel:mapping:{paramModelId}:default            — 默认 paramModel 映射 (TTL 24h)
parammodel:name_routing:{productClass}               — 产品名路由结果 (TTL 1h)
parammodel:model_routing:{productClass}              — 参数模型路由结果 (TTL 1h)
parammodel:cache_version                             — 跨实例失效计数器
```

三级缓存：L1 sync.Map（进程内）→ L2 Redis → L3 PostgreSQL。

## 6. 告警定义（alarm-definitions/ XML → 数据库）

> 数据源：`omcgo/docs/param-model-delivery/xml/alarm-definitions/*.xml`（7 份，按 neType 一文件）

### 6.1 XML 结构与抽取摘要

```xml
<alarmModel neType="ENB" deviceType="0,1" totalCount="217">
    <alarms>
        <alarm identifier="100671499"
               cnName="SCTP断链告警" enName=""
               severity="Critical" eventType="30000"
               cnProbableCause="传输异常或者配置错误" enProbableCause="Connection Establishment Error"
               cnSuggestion="检查sctp对端地址是否可达" enSuggestion=""
               isShow="N" />
        ...
    </alarms>
</alarmModel>
```

**根属性**：

| 属性 | 取值 | 含义 |
|------|------|------|
| `neType` | CPE / EGW / ENB / EPC / GNB / OMC / UPS | 网元类型（一文件一类型） |
| `deviceType` | 单值或逗号串：`0`、`1`、`3`、`4`、`5`、`6`、`7`、`0,1` | 设备类型数值（与 OMC `devices.device_type` 字段对齐）；逗号串表示该告警族适用于多种 deviceType |
| `totalCount` | INT | 该 neType 下告警总数（用于加载时校验） |

**告警实体属性**：

| 属性 | 类型 | 枚举 / 说明 |
|------|------|------|
| `identifier` | INT | 厂商定义的告警码（小到 8、大到 100675599）|
| `cnName` / `enName` | TEXT | 告警中文 / 英文名（enName 可为空） |
| `severity` | ENUM | `Critical` / `Major` / `Minor` / `Warning` |
| `eventType` | ENUM | `30000` / `30001` / `30002` / `30003` / `30004` / `30007` / `None` |
| `cnProbableCause` / `enProbableCause` | TEXT | 中英文可能原因 |
| `cnSuggestion` / `enSuggestion` | TEXT | 中英文处理建议 |
| `isShow` | CHAR(1) | `Y` / `N`，是否在 UI 默认显示 |

**当前数据规模**（按文件实测）：

| 文件 | neType | deviceType | 告警条数 |
|------|--------|-----------|----------|
| CPE.xml | CPE | 6 | 2 |
| EGW.xml | EGW | 4 | 16 |
| ENB.xml | ENB | 0,1 | 217 |
| EPC.xml | EPC | 3 | 52 |
| GNB.xml | GNB | 7 | 108 |
| OMC.xml | OMC | 0 | 28 |
| UPS.xml | UPS | 5 | 19 |
| **合计** | — | — | **442** |

**唯一性确认**：`identifier` 在跨 neType 范围内不冲突（实测 442 行 identifier 均唯一）。但因告警码本身按 neType 命名空间分配（如 ENB 用 1xxxxxxxx 段、OMC 用 1xx 段），**自然主键应使用 `(ne_type, identifier)` 复合键**，避免未来新增网元时编号空间撞车。

**约束与索引**：

```sql
-- 自然主键：跨 neType 命名空间
CREATE UNIQUE INDEX uk_alarm_def_ne_id
  ON alarm_definitions (ne_type, identifier)
  WHERE is_active;
```

### 6.3 加载流程 E（启动 / 热更新）

```
配置目录 alarm-definitions/*.xml
   │
   ▼
扫描 7 份 XML，按文件解析（neType 由根元素决定）
   │
   ▼
事务内 Upsert（每文件一事务）

   ├── isShow Y/N → BOOLEAN

   │

```

**幂等与回滚**：每文件独立事务；任一文件解析失败不影响其余。`totalCount` 与解析行数比对，不一致则回滚该文件的事务并报警。

## 7. KPI 指标（kpi-indicators/ XML → 数据库）

> 数据源：`omcgo/docs/param-model-delivery/xml/kpi-indicators/`
> - 顶层：`GNB.xml`（NR）、`GSM.xml`（GSM/BSC）
> - `enb/`：LTE 平台目录，`ALL.xml` + 8 个产品平台文件（BAIBLQ / BLQ / BLX / BM / ENB_DEFAULT_098 / ENB_DEFAULT_181 / MLN / MLQ）

### 7.1 XML 结构与抽取摘要

```xml
<indicatorModel platform="MLN" indicatorCount="1163">
    <indicators>
        <!-- 原始计数器（isCounter=1，arithmetic = 自身 ID） -->
        <indicator id="C000000001" enName="RRC.SetupTimeMean" reportKey="RRC.SetupTimeMean"
                   cnName="RRC连接平均建立时长" isBuildIn="1" isCounter="1"
                   dataType="整数" unitId="ms" statisType="avg"
                   arithmetic="C000000001" indicatorLevel="device"
                   formula="RRC.SetupTimeMean" />
        <!-- 派生 KPI（isCounter=0，arithmetic 引用其他 Counter） -->
        <indicator id="K900010002" enName="RRC setup success rate" reportKey="RRC setup success rate"
                   cnName="RRC连接建立成功率" isBuildIn="1" isCounter="0"
                   unitId="%" statisType="pct"
                   arithmetic="C000000012/C000000005*100"
                   indicatorLevel="device"
                   formula="RRC.SuccConnEstab/RRC.AttConnEstab*100" />
    </indicators>
</indicatorModel>
```

**根属性**：

| 属性 | 取值 | 含义 |
|------|------|------|
| `platform` | `BaiBNX` / `BSC` / `ALL` / `BAIBLQ` / `BLQ` / `BLX` / `BM` / `ENB_DEFAULT_098` / `ENB_DEFAULT_181` / `MLN` / `MLQ` | KPI 所属平台名（与 `param_models.name` 在 LTE 范围有部分重叠：BLQ/BM/MLN/MLQ/ENB_DEFAULT_*） |
| `deviceType` | `GNB` / `GSM`（LTE 文件不带此属性） | 网络制式 |
| `indicatorCount` | INT | 平台下指标总数（用于加载校验） |

**指标实体属性**：

| 属性 | 类型 | 枚举 / 说明 |
|------|------|------|
| `id` | TEXT | 指标编码：`C` 开头 = 原始计数器，`K` 开头 = 派生 KPI |
| `enName` / `reportKey` / `cnName` | TEXT | 英文名 / 上报字段名 / 中文名（多数情况下 enName == reportKey） |
| `isBuildIn` | `0` / `1` | 是否系统内置（用户自定义指标可能为 0） |
| `isCounter` | `0` / `1` | `1` = 原始计数器；`0` = 派生 KPI |
| `dataType` | `整数` / `浮点数` / `实数` / `Integer` / `number` / `整数n` | 历史多源命名，加载时归一为 `INT` / `FLOAT` |
| `unitId` | TEXT | `%` / `number` / `time` / `ms` / `s` / `KByte` / `Mbps` / `dBm` / `Erl` / `ppm` / ... |
| `statisType` | ENUM | `sum` / `avg` / `max` / `min` / `pct` |
| `arithmetic` | TEXT | 基于编码的公式（如 `C000090019/C000090018*100`）；原始计数器 = 自身 ID |
| `formula` | TEXT | 基于名称的公式（同 arithmetic 但用 reportKey 替代编码） |
| `indicatorLevel` | ENUM 可空 | `device` / `plmn` / `both`（顶层 GNB.xml 可能不带） |

**当前数据规模**（按文件实测）：

| 文件 | platform | isCounter=1 | isCounter=0（KPI） | 合计 |
|------|----------|-------------|-------------------|-----|
| GNB.xml | BaiBNX (NR) | 217 | 65 | 282 |
| GSM.xml | BSC (GSM) | 45 | 28 | 73 |
| enb/ALL.xml | ALL (LTE 通用) | 59 | 9 | 68 |
| enb/BAIBLQ.xml | BAIBLQ | 1003 | 63 | 1066 |
| enb/BLQ.xml | BLQ | 641 | 35 | 676 |
| enb/BLX.xml | BLX | 720 | 37 | 757 |
| enb/BM.xml | BM | 973 | 63 | 1036 |
| enb/ENB_DEFAULT_098.xml | ENB_DEFAULT_098 | 383 | 23 | 406 |
| enb/ENB_DEFAULT_181.xml | ENB_DEFAULT_181 | 383 | 23 | 406 |
| enb/MLN.xml | MLN | 1100 | 63 | 1163 |
| enb/MLQ.xml | MLQ | 907 | 61 | 968 |
| **合计** | — | **6431** | **470** | **6901** |

**重复性确认**：`id` 在跨 platform 范围**会重复**（如 `K900010037` 在 8 个 LTE 平台文件中出现，定义完全一致）。建模选择 **per (platform, code) 反范式存储**，理由：
1. 加载源（XML 文件）天然按 platform 组织，反范式 = 与源对齐，加载逻辑简单
2. 运行时查询都是"该设备所属 platform 的 KPI 集"，按 platform 分区天然命中
3. 每平台数据规模 < 1200 行，重复存储成本可忽略
4. KPI 公式依赖关系也在同 platform 内闭合（`arithmetic` 引用的 C 编码必为同平台），不存在跨平台 join

### 7.2 `kpi_indicators` 表

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | UUID PK | |
| `platform` | VARCHAR(32) NOT NULL | XML `platform` 属性 |
| `code` | VARCHAR(32) NOT NULL | XML `id` 属性（C 开头 / K 开头） |
| `kind` | VARCHAR(8) NOT NULL | `counter`（isCounter=1）/ `kpi`（isCounter=0） |
| `device_type` | VARCHAR(8) | `NR` / `GSM` / `LTE`（LTE 文件无此属性，加载时由路径 `enb/` 注入） |
| `en_name` | VARCHAR(256) NOT NULL | |
| `cn_name` | VARCHAR(256) | |
| `report_key` | VARCHAR(256) NOT NULL | CPE/网元上报时使用的 key（与 enName 通常相同） |
| `is_built_in` | BOOLEAN NOT NULL DEFAULT TRUE | 由 isBuildIn 转换 |
| `data_type` | VARCHAR(16) NOT NULL | 归一后：`INT` / `FLOAT`（原始 `整数/Integer/number/整数n` → INT；`浮点数/实数` → FLOAT） |
| `unit_id` | VARCHAR(16) NOT NULL | 单位枚举 |
| `statis_type` | VARCHAR(8) NOT NULL | CHECK IN ('sum','avg','max','min','pct') |
| `arithmetic` | TEXT NOT NULL | 基于编码的公式 |
| `formula` | TEXT | 基于名称的公式（可空） |
| `indicator_level` | VARCHAR(8) | CHECK IN ('device','plmn','both') 或 NULL |
| `is_active` | BOOLEAN NOT NULL DEFAULT TRUE | |
| `loaded_from` | VARCHAR(64) NOT NULL | 来源 XML 文件名 |
| `created_at` / `updated_at` | TIMESTAMPTZ NOT NULL | |

**约束与索引**：

```sql
-- 自然主键：(platform, code)
CREATE UNIQUE INDEX uk_kpi_platform_code
  ON kpi_indicators (platform, code) WHERE is_active;

-- 按 platform 全集查询（设备首次接入后加载该平台 KPI 集）
CREATE INDEX idx_kpi_platform
  ON kpi_indicators (platform) WHERE is_active;

-- 按 reportKey 反查（CPE 上报数据时映射回 KPI 定义）
CREATE INDEX idx_kpi_platform_reportkey
  ON kpi_indicators (platform, report_key) WHERE is_active;

-- 按 kind 区分（计算引擎只关心 kpi，存储引擎关心 counter）
CREATE INDEX idx_kpi_platform_kind
  ON kpi_indicators (platform, kind) WHERE is_active;
```

**职责**：F03 性能管理（PM/KPI）域的"指标字典"。
- **counter**（原始计数器）：CPE 直接上报，按 `report_key` 落 TimescaleDB 时序表
- **kpi**（派生指标）：worker 进程按周期调度，解析 `arithmetic` 公式 → 拉取依赖 counter 时序数据 → 计算 → 写回时序表

### 7.3 `kpi_dependencies` 表（KPI 公式依赖 DAG）

> 由加载器在解析 `arithmetic` 字段时同步抽取，提供 KPI 计算引擎所需的依赖图。

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | UUID PK | |
| `kpi_id` | UUID NOT NULL FK → `kpi_indicators.id` | CASCADE 删除 |
| `depends_on_kpi_id` | UUID NOT NULL FK → `kpi_indicators.id` | CASCADE 删除 |
| `depends_on_code` | VARCHAR(32) NOT NULL | 冗余存储被依赖方的 code，便于跨 platform 排查时不查 join |
| `created_at` | TIMESTAMPTZ NOT NULL DEFAULT NOW() | |

**约束**：

```sql
CREATE UNIQUE INDEX uk_kpi_dep
  ON kpi_dependencies (kpi_id, depends_on_kpi_id);

-- 反查：某 counter 被哪些 KPI 引用（影响面分析）
CREATE INDEX idx_kpi_dep_reverse
  ON kpi_dependencies (depends_on_kpi_id);
```

**抽取规则**：用正则 `[CK]\d{6,}` 在 `arithmetic` 字段中匹配所有编码引用，再按 `(platform, code)` 解析为 `kpi_id`。
- 例：`K900010002` 的 arithmetic = `C000000012/C000000005*100` → 抽出 `C000000012`、`C000000005` 两条依赖
- 原始计数器（kind = counter）的 arithmetic = 自身 ID，依赖记录可省略（不入表）

**用途**：
- 计算引擎拓扑排序，确定 KPI 计算顺序
- UI 展示某 KPI 的"依赖树"
- 删除 / 禁用某 counter 前的影响面校验

### 7.4 加载流程 F（启动 / 热更新）

```
配置目录 kpi-indicators/*.xml + kpi-indicators/enb/*.xml
   │
   ▼
按 platform 解析（11 份 XML）
   │
   ▼
事务内 Upsert（每文件一事务）
   ├── dataType 归一：整数/Integer/number/整数n → INT；浮点数/实数 → FLOAT
   ├── isBuildIn / isCounter "0/1" → BOOLEAN / kind 枚举
   ├── enb/ 目录下文件强制注入 device_type = 'LTE'
   ├── 用 (platform, code) 做 ON CONFLICT DO UPDATE
   ├── 同步重建 kpi_dependencies：DELETE WHERE kpi_id IN (...) → INSERT 新依赖
   └── 标记本批次未出现的同 platform 旧记录 is_active = FALSE
   │
   ▼
预热 L1（sync.Map[platform] → []KpiIndicator）+ Redis L2 hash
   │
   ▼
等待 F03 PM 采集 / KPI 计算引擎查询
```

**校验**：解析行数 == XML `indicatorCount`；每个 KPI 的 `arithmetic` 引用的所有编码必须在同 platform 中存在（**例外**：跨 platform 的"通用"指标在 ALL.xml 中独立存在，不与产品平台 join）。

## 8. 跨域 ER 总览

### 8.1 三域整合 ER 图

```
┌─────────────────────────────────────────────────────────────────────┐
│                  参数模型域（§1-§5，已有）                              │
│                                                                       │
│   product_name_routing ──┐                                            │
│   param_model_routing ───┴─→ param_models ──── param_mappings        │
│                                  │                                    │
│                                  └─ standard_params (全局标准路径)    │
└─────────────────────────────────────────────────────────────────────┘
                            ↕ 弱关联（platform name 命名空间共享）
┌─────────────────────────────────────────────────────────────────────┐
│                   KPI 指标域（§7）                                     │
│                                                                       │
│   kpi_indicators (per platform) ── kpi_dependencies (公式 DAG)        │
└─────────────────────────────────────────────────────────────────────┘
                            ↕ 独立（按 ne_type 维度）
┌─────────────────────────────────────────────────────────────────────┐
│                   告警定义域（§6）                                     │
│                                                                       │
│   alarm_definitions (per ne_type)                                    │
└─────────────────────────────────────────────────────────────────────┘
```

**跨域关系**：

| 关系 | 强度 | 说明 |
|------|------|------|
| `param_models.name` ↔ `kpi_indicators.platform` | **弱关联**（命名空间共享，非外键） | 共有：BLQ / BM / MLN / MLQ / ENB_DEFAULT_098 / ENB_DEFAULT_181（6 个 LTE 平台）。KPI 域额外有 `BAIBLQ` / `BLX` / `BSC` / `BaiBNX` / `ALL` 不在参数模型域；参数模型域额外有 `BSC` / `BTS` / `BaiBNQ` 不在 KPI 域。**不建立外键**，避免一域增删牵动另一域 |
| `alarm_definitions.applicable_device_types[]` ↔ `devices.device_type` | **强关联**（数值码） | 设备详情页基于此关联展示该设备类型的所有可能告警；运行时只读，不级联 |
| `alarm_definitions.ne_type` ↔ `kpi_indicators.device_type` | **无关联** | 不同维度（neType vs network technology），不需要 join |

**为什么不跨域建外键**：参数模型 / KPI / 告警三个域来自三套独立的厂商规范，演进节奏不同。强外键会让任一域的"删旧加新"操作（如删除 `BLQ` 参数模型）级联到其它域，带来运维风险。改用 **TEXT 字段 + 应用层校验** 维持松耦合。

### 8.2 加载顺序与启动时序

```
进程启动
   │
   ├─→ 流程 A 参数模型加载（§1.2）  ──┐
   ├─→ 流程 E 告警加载（§6.3）       ├─ 三者并行（独立目录、独立事务）
   └─→ 流程 F KPI 加载（§7.4）        ─┘
```
