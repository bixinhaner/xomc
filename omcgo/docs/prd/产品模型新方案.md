# 核心功能描述
1、首先定义关于设备的参数模型，一个模型是同类产品的高度抽象，比如厂家的模型系统设备都满足这个模型定义
2、一个模型绑定的标准参数，比如 tr069协议中定义的标准 path
3、产品管理，一个产品是 OMC 中对同类产品的统一抽象，一个产品必须关联一个模型，与模型的绑定关系1:1，多个产品可以绑定同一个模型
4、产品有多版本管理，每个版本可以独立管理私有 path 和模型标准 path 的映射关系
5、产品可以配置匹配规则，用于 inform 报文的 productClass 字段匹配，匹配当前设备属于哪个产品：设备 > 产品 > 模型 > 设备参数
6、设备参数计算方式：a、先找到设备属于哪个模型，确定所有的标准 path；b、再根据设备当前的软件版本找到私有 path;c、通过私有 path 去报文中提取对应的值，再转换成标准的 path;d、再根据模型定义的标准 path 去报文中提取所有的标准 path 数据；e、合并 c、d,存在重复 path 时以 c 为准
7、私有path 和标准 path 的转换：a、设备请求报文中的私有 path转换成标准 path 存储在 omc 系统中；b、omc 下发报文时需要把系统中存储的标准 path 转换成私有 path，全系统使用统一转换方法
8、以上需满足 tr069协议的定义

## 9. 核心实体关系细化

### 9.1 五个一等实体

| 实体 | 唯一标识 | 职责 | 与其他实体关系 |
|------|---------|------|--------------|
| **Model** | `name`（如 `LTE_FAP_MODEL_v1`） | 定义某类设备的标准 path 全集 + 类型 / 取值约束（来自 TR-069 / TR-181）。**与厂商无关、与具体型号无关** | 1:N → Product（一个模型可被多个产品复用） |
| **Product** | `code`（如 `MLN`、`QRTB`） | OMC 中对一类商用产品的统一抽象。绑定一个 Model，承载匹配规则与版本族 | N:1 → Model；1:N → ProductVersion；1:N → ProductMatchingRule |
| **ProductVersion** | `(product_id, version)`（如 `MLN/v1.2.0`） | 同一产品的特定版本。携带 **(私有 path → 标准 path)** 映射表 | N:1 → Product；1:N → SoftwareVersionRange |
| **ProductMatchingRule** | `(product_id, sort_order)` | 一条 productClass 正则匹配规则。同一产品可有多条 | N:1 → Product |
| **Device** | `serial_number` | 实际接入的 CPE。运行时被绑定到某 Product + 某 ProductVersion | N:1 → Product；N:1 → ProductVersion（按 software_version 反查） |

### 9.2 实体关系图

```
                    Model (1)
                      │
                      │ 1:N
                      ▼
          ┌──── Product (N) ──────────┐
          │       │                    │
          │ 1:N   │ 1:N                │
          ▼       ▼                    │
    ProductMatchingRule  ProductVersion (N)
                            │
                            │ 1:N
                            ▼
              SoftwareVersionRange (N)  ←──── Device.software_version
                                                      │
                                                      │ 路由
                                                      ▼
                                            (Product, ProductVersion) → 取映射表
```

### 9.3 与 TR-069 / TR-181 概念对齐

| TR-069/TR-181 概念 | 本方案对应 |
|------|---------|
| Data Model（如 Device:2.16） | **Model** 定义的标准 path 集 |
| OUI + ProductClass | Device 的 Inform 中的 `DeviceId` 字段，被 ProductMatchingRule 的正则捕获 |
| SoftwareVersion | Device.software_version，反查到 ProductVersion |
| Vendor-specific extension（X_VENDOR.* / X_BAICELLS.*） | ProductVersion 映射表中"私有 path"那一列 |
| Standard parameter | ProductVersion 映射表中"标准 path"那一列 |

## 10. 实体生命周期与状态机

### 10.1 三套生命周期

```
Model:           draft → published → deprecated → archived
ProductVersion:  draft → published → deprecated → archived
Product:         active → suspended → archived
```

| 状态 | 含义 | 允许操作 |
|------|------|---------|
| `draft` | 初稿，可任意编辑 | 编辑、删除、提交评审 |
| `published` | 已发布，对运行时可见 | 不可改字段，仅可标记 deprecated |
| `deprecated` | 已被新版替代，但仍服务存量设备 | 仅查询，不再分配给新设备 |
| `archived` | 归档，从运行时缓存移除（DB 保留） | 只读历史记录 |

### 10.2 状态转换与运行时约束

- **同一 Product 下，同一时刻最多一个 ProductVersion 处于 `published` 状态**——这是"当前主推版本"，新设备首次接入时优先尝试匹配。
- **`deprecated` 不立即下线**：保证存量设备继续可服务，避免大规模回滚风险。
- **`draft` 对运行时不可见**：只在 OMC 管理 UI 中可见，便于运营人员组装新版本。
- **状态转换必须可审计**：记录 actor、时间、原因（参见 §14）。

### 10.3 版本号约定（建议 SemVer）

`MAJOR.MINOR.PATCH`：
- MAJOR：标准 path 集发生不向后兼容变更（依赖 Model 升级）
- MINOR：私有 path 映射调整、新增可选标准 path
- PATCH：修复映射错误、补充原本遗漏的私有 path

## 11. 设备接入与匹配的完整流程

补充第 5、6 点的细节，覆盖边界场景。

### 11.1 完整流程（CPE Inform → 加载映射）

```
CPE Inform 到达
   │
   ▼
解析 DeviceId.ProductClass
   │
   ▼ Step 1: Product 匹配（productClass → Product）
ORDER BY product_matching_rule.sort_order ASC
   ├─ 命中 0 条 → fallback 到 default Product（参见 11.4）
   ├─ 命中 1 条 → 取对应 Product
   └─ 命中 ≥ 2 条 → 报错并告警（参见 11.5），落到 default Product
   │
   ▼ Step 2: ProductVersion 匹配（device.software_version → ProductVersion）
精确版本号匹配 → SoftwareVersionRange 区间匹配 → 取 Product 的 published 版本兜底
   ├─ 命中 → 取对应 ProductVersion
   └─ 未命中 → 用该 Product 当前 published 版本，告警"未识别软件版本"
   │
   ▼ Step 3: 加载映射 + 缓存预热
按 (product_id, product_version_id) 加载映射表到 L1/L2 缓存
   │
   ▼
进入正常服务流程（Get/Set 时调用统一 Translator）
```

### 11.2 ProductVersion 与 SoftwareVersion 的映射

软件版本（device 上报）和产品版本（OMC 定义）不一定 1:1：

| 关系 | 示例 | 处理 |
|------|------|------|
| 1 ProductVersion ↔ 1 SoftwareVersion | `MLN/v1.2.0` ↔ `MLN_R1.2.0` | 精确匹配 |
| 1 ProductVersion ↔ 多 SoftwareVersion | `MLN/v1.2.x` ↔ `MLN_R1.2.0..MLN_R1.2.9` | `software_version_ranges` 表存区间 |
| N ProductVersion ↔ 1 SoftwareVersion | 同一软件版本支持新旧两套 path 集 | **不建议**，强制运营在变更时确定唯一映射 |

**`software_version_ranges` 表**：

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | UUID PK | |
| `product_version_id` | UUID FK | |
| `version_pattern` | TEXT | 正则或 SemVer 通配（如 `1.2.*` / `^MLN_R1\.2\..*$`） |
| `priority` | INT | 多区间命中时取 priority 最大者 |

### 11.3 多匹配规则的优先级

完全沿用既有 `param_model_routing` 的设计哲学（参见 [产品模型.md §1.3](./产品模型.md)）：
- `sort_order` 决定遍历顺序
- 具体规则在前（`^FAP/MLN/SC$`）、宽泛兜底在后（`FAP`）
- **首次命中即返回**

### 11.4 Default Product（兜底）

为防止未知设备无法接入：
- 系统预置一个 `__DEFAULT__` Product，绑定到一个最小 Model（仅含 TR-181 必备 path）
- 任何未匹配到具体 Product 的设备，临时挂到 `__DEFAULT__` 下，能完成 Inform 注册但只支持有限管控
- 运维人员在 OMC UI 看到"未识别设备"列表，手工分配或新增匹配规则

借鉴 ThingsBoard 的 **Default Device Profile** 模式，避免接入失败。

### 11.5 多规则同时命中的冲突处理

| 场景 | 处理 |
|------|------|
| 跨 Product 同时命中（如 productClass 同时被 ProductA 和 ProductB 的规则匹配）| **报错**：写入"参数模型路由冲突"告警表，记录涉及的所有 Product；设备临时挂到 `__DEFAULT__`，等待运维收紧正则 |
| 同 Product 内多规则命中 | **允许**（同一产品可以有多条等价规则），按 sort_order 取首条 |

## 12. 参数计算与路径转换的细化

补充第 6、7 点的工程实现细节。

### 12.1 第 6 点 a-e 的细化

第 6 点描述了"合并以私有 path 为准"的合并规则。补充三类边界：

| 场景 | 处理 |
|------|------|
| 标准 path 在 Model 定义、ProductVersion 提供了私有 path、报文中两个 path 都有值 | **以私有 path 的值为准**（点 6e）；用 OTel 标注 `value.source=private` |
| 标准 path 在 Model 定义、但 ProductVersion 未提供私有 path、报文中标准 path 也存在 | **使用标准 path 值**；记录"私有 path 缺失"日志，便于补全映射 |
| 报文中出现既不在 Model、也不在 ProductVersion 映射的 path | **写入"参数发现日志"** `parameter_discovery_log`（已有表，仅追加 product_version_id 维度），不入主参数表，供运维评估是否纳入 Model |
| 私有 path 与标准 path 类型不一致（如 STRING vs INT） | **校验失败**：丢弃该值并告警；强制 ProductVersion 发布前必须通过类型一致性校验 |

### 12.2 统一 Translator 抽象（点 7"全系统使用统一转换方法"的落地）

```go
// 单一接口，全系统调用入口
type Translator interface {
    // ACS 接收：私有 path → 标准 path
    PrivateToStandard(ctx, productID, productVersionID, privatePath) (standardPath string, err error)
    // ACS 下发：标准 path → 私有 path
    StandardToPrivate(ctx, productID, productVersionID, standardPath) (privatePath string, err error)
    // 批量优化版本（避免循环调用）
    BatchPrivateToStandard(ctx, ..., privatePaths []string) (map[string]string, err error)
    BatchStandardToPrivate(ctx, ..., standardPaths []string) (map[string]string, err error)
}
```

**调用方约束**：
- ACS 接收 SOAP 响应、Inform → 调用 `PrivateToStandard`
- ACS 下发 SetParameterValues、模板引擎、自动开站 → 调用 `StandardToPrivate`
- KPI 引擎、北向 OSS 导出 → **不直接接触私有 path**，全部消费标准 path
- 配置基线 / 配置模板 → **存储标准 path**，下发瞬时翻译

**实现要求**：
- O(1) map 查找，单次翻译延迟 < 10μs
- 缓存 miss 时回源 PostgreSQL，并异步写回 L1/L2
- 找不到映射不 panic：返回 `ErrNoMapping`，由调用方决定降级策略（点 12.1 边界处理）

## 13. 一致性、缓存与热加载

### 13.1 三级缓存与失效协议

| 层级 | 介质 | 主键 | TTL | 失效机制 |
|------|------|------|-----|---------|
| L1 | `sync.Map` 进程内 | `(product_id, product_version_id)` | 无（全量驻留） | 监听 L2 cache_version 变化 |
| L2 | Redis | `mapping:{product_id}:{version_id}` | 24h | 写时主动 DEL + 自增 `mapping:cache_version` |
| L3 | PostgreSQL | 表行 | — | 持久层 |

### 13.2 多 ACS 实例同步

- 任何写操作（发布新版本、废弃旧版本、修改匹配规则）：
  1. 先写 PostgreSQL（事务）
  2. DEL 涉及的 Redis key
  3. 自增 `mapping:cache_version`
- 各 ACS 实例后台 goroutine 每 30s 检查一次 cache_version，发现变化则清空 L1，按需懒加载

借鉴 **etcd / Consul 的 watch 模式**：未来可改为 Redis Pub/Sub 主动推送，实现秒级失效。

### 13.3 ProductVersion 灰度发布（借鉴 Eclipse Hawkbit）

新版本发布不一刀切，按设备分组逐批切换：

| 字段 | 说明 |
|------|------|
| `rollout_strategy` | `immediate` / `percent` / `device_group` / `scheduled` |
| `rollout_percent` | 0-100，按 `device.serial_number` 哈希分配 |
| `rollout_groups` | 设备组 UUID 数组（与 F06 拓扑分组联动） |
| `rollout_started_at` / `rollout_completed_at` | 时间戳 |

回滚机制：标记新版本 `published → deprecated`，自动让运行时回退到上一 `deprecated` 版本（仍服务），1 小时观察期后再决定是否 `archived`。

## 14. 权限、审计与变更管理

### 14.1 RBAC 角色矩阵

| 角色 | Model | Product | ProductVersion | MatchingRule |
|------|-------|---------|---------------|--------------|
| 协议工程师（model_admin） | CRUD + 发布 | — | — | — |
| 产品经理（product_admin） | 只读 | CRUD | 创建 draft + 提交发布 | CRUD |
| 运维（ops） | 只读 | 只读 | 审批发布 + 灰度策略 | 只读 |
| 普通用户（viewer） | 只读 | 只读 | 只读 | 只读 |

### 14.2 变更审计

每次变更写 `param_model_audit_log`：

| 列 | 说明 |
|----|------|
| `entity_type` | `Model` / `Product` / `ProductVersion` / `MatchingRule` |
| `entity_id` | UUID |
| `action` | `create` / `update` / `publish` / `deprecate` / `archive` |
| `actor_id` | 操作人 |
| `diff` | JSONB（变更前后字段差异） |
| `reason` | TEXT，发布 / 废弃必填 |
| `created_at` | TIMESTAMPTZ |

### 14.3 评审流程

- ProductVersion `draft → published` 必须经过：
  1. 类型一致性自动校验（参见 §12.1）
  2. 至少一名 `ops` 角色审批
  3. 灰度策略明确（默认 `percent=10`）

## 15. 可观测性

### 15.1 关键指标（Prometheus）

| 指标 | 类型 | 标签 | 含义 |
|------|------|------|------|
| `omc_translator_calls_total` | Counter | `direction=p2s/s2p`, `product_id`, `result=ok/no_mapping/type_err` | 翻译调用次数 |
| `omc_translator_latency_seconds` | Histogram | `direction` | 翻译延迟（p99 < 1ms） |
| `omc_product_match_total` | Counter | `result=hit/conflict/miss/default` | 设备接入匹配结果分布 |
| `omc_product_version_active_devices` | Gauge | `product_id`, `version_id` | 各版本承载设备数（灰度看板） |
| `omc_mapping_cache_hit_ratio` | Gauge | `layer=l1/l2` | 缓存命中率 |

### 15.2 关键日志

- 翻译失败（`ErrNoMapping` / 类型不一致）：WARN 级别 + 设备 SN + path
- 多规则冲突：ERROR 级别 + 涉及的所有 Product
- ProductVersion 发布 / 废弃 / 灰度推进：INFO 级别 + actor + diff

### 15.3 关键告警

| 告警 | 触发条件 | 严重 |
|------|---------|------|
| 路由冲突 | 单 productClass 命中 ≥ 2 个 Product 的规则 | Major |
| 翻译失败激增 | `no_mapping` 速率 > 100/min | Minor |
| 默认 Product 兜底设备过多 | 挂在 `__DEFAULT__` 的设备 > 总数 1% | Warning |
| 类型校验失败 | ProductVersion 发布前校验报错 | Critical（阻塞发布）|

## 16. 借鉴的开源 IoT 平台设计

### 16.1 Eclipse Vorto（最相关，强烈推荐借鉴）

**项目定位**：开源的设备模型与跨平台映射框架（Bosch 主导，Eclipse Foundation 托管）。

**核心概念**：
- **Information Model**：抽象描述某类设备的能力（property / event / operation），与本方案的 Model 几乎一一对应
- **Function Block**：可复用的能力片段（如"温湿度传感器"），多个 Function Block 组合成 Information Model — **可借鉴用于 Model 的模块化拆分**
- **Mapping Specification**：把抽象 Information Model 映射到具体协议（LWM2M / AWS IoT / Bosch IoT Things），与本方案的 ProductVersion 映射表对应
- **Mapping Engine**：运行时执行 Mapping Specification，与本方案的 Translator 对应
- **Vorto Repository**：模型仓库，支持 SemVer 版本化与依赖

**可直接借鉴**：
1. **Function Block 组合模式**：把"LTE 基站"、"GNSS 模块"、"SAS 接口"拆为独立 Function Block，Model 由组合得到，便于复用
2. **Mapping DSL**：Vorto Mapping Spec 是声明式 DSL，比"两列表格"表达力强（支持 stereotype / xpath / 内嵌函数），适合复杂厂商私有协议
3. **Repository + 依赖管理**：Model 之间可声明依赖，避免重复定义

参考：https://github.com/eclipse-vorto/vorto

### 16.2 阿里云物联网平台 TSL（Thing Specification Language）

**核心概念**：
- 物模型 = 产品模型，包含三要素：**属性（property）/ 服务（service）/ 事件（event）**
- 标准物模型库（联盟标准）+ 自定义扩展模块
- 产品 → 设备两层抽象（与本方案 Product → Device 一致）

**可直接借鉴**：
1. **三要素扩展**：当前 Model 仅描述属性（path），未来扩展到服务（RPC 方法，如 Reboot / FactoryReset）和事件（自主上报，如告警 / 状态变化），可统一管理
2. **标准物模型库**：参考阿里云"标准品类"思路，OMC 维护一套"标准基站物模型"（LTE / NR），新厂商接入时基于标准扩展，减少重复设计
3. **物模型版本管理**：阿里云物模型支持版本，新版本不影响存量设备 — 与本方案 §10 的生命周期一致

参考：https://help.aliyun.com/document_detail/73727.html

### 16.3 ThingsBoard Device Profile

**核心概念**：
- Device Profile 是一组配置（transport / alarm rule / queue routing / provisioning rule）
- 每个 Device 引用一个 Profile，Profile 变更自动应用到所有引用设备
- 提供 **Default Profile** 兜底未识别设备

**可直接借鉴**：
1. **Default Product 兜底**（§11.4）—— 已采纳
2. **Profile 内嵌 alarm rule** —— 后续可考虑把 §6 章节的告警字典与 ProductVersion 关联（不同产品版本可能告警含义不同）
3. **Profile API 风格**：ThingsBoard 的 Profile REST API 设计清晰（CRUD + assign），可借鉴 OMC 管理 API

参考：https://github.com/thingsboard/thingsboard

### 16.4 Eclipse Ditto（Digital Twin）

**核心概念**：
- Thing = 数字孪生（reported state + desired state）
- **Connection + Mapping function**：协议层与 Thing 模型的双向映射，支持自定义 JS 映射函数
- **Policy**：基于 thing/feature/path 的细粒度 ACL

**可直接借鉴**：
1. **Mapping function** 思路：当前 Translator 仅做 path 转换；未来若出现"私有协议中需要值变换"（如位运算解码、单位换算），可参考 Ditto 在 Mapping 中嵌入 JS 函数的模式
2. **细粒度 Policy**：ProductVersion 的访问控制可下钻到 path 级（某些敏感 path 仅 ops 可下发）

参考：https://github.com/eclipse-ditto/ditto

### 16.5 Eclipse Hawkbit（IoT 软件更新）

**核心概念**：
- **Distribution Set**：版本化的软件包集合
- **Rollout**：灰度发布策略（percent-based / device-group / scheduled）
- **Action history**：完整审计

**可直接借鉴**：
1. **Rollout 灰度模型**（§13.3）—— 已采纳
2. **Action history**：每次 ProductVersion 切换、灰度推进、回退都记入历史表，便于事后追溯
3. **回滚自动化**：Hawkbit 在新版本失败率超阈值时自动回退，可借鉴用于 ProductVersion

参考：https://github.com/eclipse-hawkbit/hawkbit

### 16.6 AWS IoT Device Shadow

**核心概念**：
- `reported`（设备实际状态）vs `desired`（云端期望状态）
- `delta` = desired - reported，云端通知设备同步

**可直接借鉴**：
1. **配置基线 vs 实际状态的差分**：OMC 配置模板下发的"期望参数值" vs CPE 上报的"实际参数值"，可建立 delta 视图，运维一眼看到偏差
2. **冲突合并策略**：Device Shadow 在 reported / desired 同时变更时的版本号机制（version + clientToken）值得参考

参考：https://docs.aws.amazon.com/iot/latest/developerguide/iot-device-shadows.html
