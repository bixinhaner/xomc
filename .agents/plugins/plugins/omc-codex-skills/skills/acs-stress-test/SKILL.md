# ACS 全链路压力测试

使用项目的 `omcgo/scripts/loadtest` 和 `omcgo/configs/acs-stress.yaml` 验证 ACS 到 Worker、NATS、MinIO、PM/MR Collector 的完整数据管线。

## 1. 先确定测试级别

先说明目标环境、模式（`acs`、`kpi`、`mr`、`all`）、设备数、并发、持续时间和通过标准。

- 冒烟：确认链路可用，低并发、短时。
- 基线：记录正常吞吐、延迟和资源占用。
- 压力：递增负载，寻找吞吐或成功率拐点。
- 极限：高并发或长时运行，只能在用户明确批准了具体负载和环境后执行。

默认从冒烟或基线开始；不要直接运行旧流程中的 5 万设备或 5 千并发档位。

## 2. 前置检查

- 以 `deployments/docker/README.md` 和实际 compose 状态确认运行方式、端口和健康检查；不要凭旧命令假设裸进程环境。
- 确认 ACS、Worker、NATS JetStream、Redis、MinIO、PostgreSQL 均可用；Worker 日志中不得已有 panic 或订阅失败。
- 构建压测工具并确认使用压测专用 `acs-stress.yaml`，不得误用默认限流配置。
- 记录压测前 ACS、Worker、NATS、MinIO 的 CPU、内存、进程/容器状态和队列深度。

## 3. 执行与观察

- 使用递增轮次；每轮完成后等待管线排空，再决定是否升档。
- 每轮记录请求/会话成功率、吞吐量、p50/p95/p99 延迟、上传速率和错误分类。
- 同时观察 Worker 存活、panic/FATAL、NATS 积压和压测结束后的资源回落。
- 压测后 CPU 持续高、日志持续增长、队列未清空或进程崩溃均判为失败，不得只看 HTTP 成功率。

## 4. 环境保护

- 不得默认执行 `pkill`、`kill -9`、清空 JetStream、重启共享基础设施或删除压测数据。
- 如必须停止或清理，先列出精确目标、影响和可恢复性，取得用户确认；只处理本次测试启动的进程。
- 保留日志和结果；清理只在用户要求或测试计划约定时执行。

## 5. 报告

输出各轮负载与结果、性能拐点、资源回落情况、失败证据、环境差异和下一步建议。没有达到预先约定的成功率、延迟或恢复标准时，结论必须为未通过。
