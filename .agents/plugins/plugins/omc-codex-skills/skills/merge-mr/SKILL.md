# 合并 MR

只在用户当前回合明确指定要合并 MR 后执行。

- 用户给出 MR 编号时，合并该 MR。
- 用户未给出 MR 编号，但本会话中只创建/推进过一个明确的 MR，且最近交付结果里已把该 MR 作为当前交付对象报告给用户时，可直接使用这个会话 MR，不要再次询问编号。
- 用户未给出 MR 编号，且本会话有多个候选 MR、候选不清楚，或没有可追溯的会话 MR 时，先询问。
- 不要仅根据当前分支、最近仓库 MR 或“继续”推断合并授权。

## 合并前检查

1. 使用 `glab mr view <MR编号>` 确认 MR 为 open、目标分支为 `main` 或用户指定的目标分支，并记录源分支。
2. 确认当前工作区状态已知；不得通过 `git push` 或直接向 `main` / `master` 推送来替代 MR 合并。
3. 若 MR 已关闭、已合并、目标分支不符合用户要求，或检查失败，停止并报告原因。

## 合并规则

使用 GitLab CLI 合并指定 MR，并启用删除源分支选项：

```bash
glab mr merge <MR编号> --remove-source-branch
```

- 按仓库既有策略选择 merge/squash/rebase；用户未指定时，不擅自改变该项目或 MR 的合并策略。
- 不使用 `--force`，不直接执行 `git merge` 到 `main` / `master`。
- 合并命令如需交互确认，向用户展示 GitLab 的实际合并策略和提示，不要猜测或绕过保护规则。

## 合并后验证

1. 再次读取 MR，确认状态为 merged。
2. 确认源分支已删除；若受保护或 GitLab 策略导致无法删除，明确报告而不要手动删除其他分支。
3. 向用户报告 MR 链接、合并结果、源分支删除结果，以及当前在用的是哪个模型。
