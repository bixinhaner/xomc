# OMC 项目整改路线图（2026Q2）

> 本方案配套 `docs/methodology/从0到生产可发布完整方法论.md`，把方法论应用到当前 OMC 工程的真实现状上，给出**带刀的、有时间盒的、有 Owner 的**整改计划。
>
> **核心结论**：当前是 **74% 完成度的僵尸状态**——表面繁荣（37 任务、159 测试文件、4459 行 E2E 脚本），实质堵在五个生产级阻塞点。如果不整改，再往下做新功能 = 在沼泽里盖楼。
>
> **整改原则**：先收尾、再硬化、最后 GA。**14 周**完成 Wave 1-3，达到可商用 Beta 状态。

## 第 3 章 · 流程刚性升级

整改后**永久生效**的工作纪律。**这是防止再陷僵尸状态的关键**，比任何技术改动重要。

### 3.1 Backlog 三铁

1. **In-progress ≤ 3**：超过 3 立刻暂停新立项，强制 finishing day
2. **新立项必须有 Owner + DoD + 验收人**：缺一项不进 backlog
3. **每周五是 finishing day**：禁止开新功能，只能收尾

### 3.2 PR 五铁

PR 合入门槛（`.github/pull_request_template.md` 强制）：

```markdown
## What / Why / How / Verify
（必填，缺一项关闭 PR）

## DoD（缺一项不合入）
- [ ] go build & npm typecheck 通过
- [ ] 单元测试覆盖（成功 + 失败路径）
- [ ] E2E 用例（用户可见功能）
- [ ] staging 自测 + 截图/curl 输出
- [ ] 日志 + 指标已加
- [ ] 回滚方案明确
- [ ] 文档已更新
- [ ] 影响 frontend-core 已评估三皮肤兼容
```

CI 检查：未勾完的 PR 阻塞合入。

### 3.3 测试覆盖率单调不降

`go test -coverprofile` 进 CI；新 PR 若使**覆盖率下降则阻塞**。当前基线 28% → Wave 2 末提到 60% → Wave 3 末提到 70%。

### 3.4 E2E 用例数单调不降

每个新切片必须**至少新增 1 个 E2E 用例**；删除用例需在 PR 描述写明理由 + 替代方案。

### 3.5 依赖识别强制

新立项必须填**依赖清单**：上游模块 + 下游消费方 + 阻塞项。CLAUDE.md §6 列出的跨域基础设施（task / notification / transfer / events）改动必须激活架构专家审查。

### 3.6 三个开关

写死在 CI / dev-pipeline 不可绕过：
- ❌ 不合并红 CI（`go test` / `golangci-lint` 任一失败）
- ❌ 不合并 DoD 不全的 PR
- ❌ 不合并使 E2E/单测覆盖率下降的 PR

## 第 7 章 · 整改 Anti-Pattern（永远不做）

以下行为整改期间出现 = 立刻打回：

1. ❌ "Wave 1 太慢了，我们边整改边做新功能" → 不行，14 周要纪律
2. ❌ "这个 E2E 用例先放着，下个 PR 补" → 不行，**当 PR 必须含**
3. ❌ "DoD 模板我先勾上，CI 跑过再说" → 不行，CI 自动检查模板内容
4. ❌ "测试覆盖率短期降一点没关系" → 不行，单调不降是红线
5. ❌ "F08 SNMP 还是塞进 Wave 3 吧反正都得做" → 不行，外部依赖不可控不能阻塞 GA
6. ❌ "整改完了我们松松螺丝" → 不行，三铁 + 五铁是永久制度
7. ❌ "AI 帮我写了，跑过本地就直接合入" → 不行，必须 staging + review
8. ❌ "这个模块只有我懂，让我自己 review 自己的 PR" → 不行，**所有 PR 必须他人 review**
