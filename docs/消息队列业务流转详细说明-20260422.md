## 2. 整体架构

OMC 采用**分层多实现**的消息基础设施，不同机制各自解决一类耦合：

| 层 | 机制 | 库 / 协议 | 跨进程 | 持久化 | 典型场景 |
|----|------|----------|:------:|:------:|---------|
| L1 | **NATS JetStream** | `nats-io/nats.go` | ✅ | ✅ 文件 | 主事件总线（app ↔ acs ↔ worker）|
| L1 | **Channel EventBus** | 纯 Go channel | ❌ | ❌ | 单进程测试 / 无 NATS 部署兜底 |
| L2 | **Redis 任务队列** (`acs:taskq:*`) | `redis/go-redis` | ✅ | ✅ Redis + PG 双写 | 每设备 RPC 命令下发 + 响应匹配 |
| L3 | **Redis Pub/Sub** | `redis/go-redis` | ✅ | ❌ | Casbin 策略热更新广播 |
| L3 | **Redis 滑动窗口 ZSET** (`reboot:abnormal:*`) | `redis/go-redis` | ✅ | ✅ Redis | 异常重启频次判定 |
| L4 | **SSE MessageHub** | 纯 Go channel + 可选存储 | ❌ | 可选 | 浏览器实时推送（MML / 通知）|

## 3. NATS JetStream 流

[nats.go DefaultStreams](omcgo/internal/core/components/nats/nats.go) 注册 **14 条** JetStream 流。每条流以一个点分前缀吸纳一类事件，保留策略统一为 `WorkQueuePolicy`（消费完删除），存储为 `FileStorage`，最大存活 72h。

| Stream | Subject 模式 | 业务定位 |
|--------|-------------|---------|
| `DEVICE` | `device.>` | 设备入网 / 心跳 / 参数变更 / 告警 / 传输 / 重启事件 |
| `COMMAND` | `command.>` | TR-069 RPC 响应事件（按 RPC 方法分主题） |
| `TASK` | `task.>` | 设备任务终态（completed / failed），跨进程驱动业务聚合 |
| `PM` | `pm.>` | 性能管理文件（received / parsed） |
| `MR` | `mr.>` | 测量报告文件（received / parsed） |
| `ALARM` | `alarm.>` | 告警生命周期（raised / cleared / acknowledged） |
| `OSS` | `oss.>` | 北向推送（告警 / PM / 配置快照） |
| `PROVISION` | `provision.>` | 自动开站任务状态 |
| `DATAMODEL` | `datamodel.>` | 数据模型 XML 上传 / 接收 |
| `SOFTWARE` | `firmware.>` `upgrade.>` | 固件库与升级生命周期 |
| `BACKUP` | `backup.>` | 配置备份任务 |
| `REPORT` | `report.>` | 报表生成任务 |
| `NEDIRECT` | `nedirect.>` | 网元直连会话事件（审计/诊断） |
| `SYS` | `sys.>` | 系统级控制广播（Casbin 策略热更新等） |

> **2026-04-22 变更**：新增 `TASK` / `SOFTWARE` / `BACKUP` / `REPORT` / `NEDIRECT` 五条流。此前这些主题没有对应 Stream，意味着发布者的消息不会持久化、订阅者掉线即丢消息。补齐后全部事件都能被 JetStream 持久化并重放。
> **2026-04-22 Phase 4 变更**：新增 `SYS` 流承载 `sys.>` 系统级控制事件，首批主题为 `sys.casbin.policy.reload`。Casbin 策略广播从 Redis Pub/Sub 迁到该流，获得持久化 + 断线重连回放。

## 5. Redis 队列与缓存

### 5.1 设备任务队列 `acs:taskq:*` + `acs:task:*` + `acs:cwmp2task:*`

**唯一的 RPC 下发通道**。统一化任务系统，由 Redis 承载运行时队列，PostgreSQL `device_tasks` 表提供持久化与审计。所有业务层写入都通过 [task/service.go](omcgo/internal/task/service.go) 协调双写。

| Key 前缀 | 结构 | TTL | 用途 |
|----------|------|-----|------|
| `acs:taskq:{device_sn}` | Sorted Set，member=taskID | 无（ZSET 空则自动消失） | 每设备命令队列，Score = `priority × 1e13 + created_at 纳秒` |
| `acs:task:{taskID}` | Hash，字段 `data`（JSON） | 24h | 任务详情，供 ACS 取用 + 状态变更 |
| `acs:cwmp2task:{cwmp_id_hash}` | String，值为 taskID | 24h | RPC 响应按 CWMP ID 反查任务 O(1) |

**接口**（[task/queue.go](omcgo/internal/task/queue.go)）：

```go
type TaskQueue interface {
    Push(ctx, task) error            // ZADD + HSET（pipeline）
    Pop(ctx, deviceSN) (*Task, error) // ZRANGE + ZREM（pipeline）
    Peek(ctx, deviceSN) (*Task, error)
    Exists(ctx, deviceSN, taskID) (bool, error) // ZScore 判存，用于启动加载去重
    GetByID(ctx, taskID) (*Task, error)
    GetByCWMPID(ctx, cwmpID) (*Task, error)
    MarkTaskSent / MarkTaskCompleted / MarkTaskFailed(...)
    GetStaleSentTasks(ctx, sn, stale) ([]*Task, error) // 恢复僵死任务
    Delete / Update / Len(...)
}
```

**任务状态机**：

```
pending ──Pop──▶ sent ──Response──▶ completed
   │                │
   │                └──Fault───▶ failed
   │
   ├──Cancel──▶ cancelled
   └──Expire──▶ expired
```

**双写协议**：[TaskService.CreateTask](omcgo/internal/task/service.go) 先 `repo.Create`（PG）再 `queue.Push`（Redis），Redis 失败时回滚 PG 记录。终态更新在 `MarkTaskCompleted/Failed` 里先写 Redis 再 `repo.Update` PG。

**启动加载**（2026-04-22 新增）：Worker 进程启动时调用 [TaskService.RestorePendingQueues](omcgo/internal/task/service.go)，遍历 `device_tasks status='pending'`，用 `ZScore` 检查对应设备队列成员是否存在——不存在才 `Push`。多次重启 / 多实例启动均幂等，不会重复入队。仅恢复 `pending`，`sent` 状态交由设备重连时的 `RecoverPendingTasks` 按 `sent_at` 陈旧阈值处理。

### 5.2 旧接口兼容层 `acs:cmdq:*` —— 已完全下线（2026-04-23）

**现状**：`cmdqueue` 包（`internal/acs/cmdqueue/`）、`cmdqueue.CommandQueue` 接口、`task.BridgeQueue` 适配器 **均已删除**。所有业务模块（provision / software / backup / config / interop / filemanager / device）直接依赖 `task.Enqueuer` 窄接口（`CreateTask + GetQueueLength`），由 `task.TaskService` 提供实现。

Redis 上 `acs:cmdq:*` 键前缀不再有任何代码写入；`acs:taskq:*` / `acs:task:*` / `acs:cwmp2task:*` 是唯一的命令队列存储。Dispatcher 所需的"SOAP 渲染入参"已从 `cmdqueue.Command` 搬家到 [internal/acs/rpc/command.go](omcgo/internal/acs/rpc/command.go)（`rpc.Command`），ACS handler 从 `TaskService.PopTask` 取出 `*task.Task`，拷贝最小字段到 `rpc.Command` 喂给 12 个 RPC Handler 渲染 SOAP。

> 剩余运维动作：生产 Redis 清理历史 `acs:cmdq:*` 残留 key，见 §11.2。

### 5.3 Casbin 策略广播 `sys.casbin.policy.reload` (NATS JetStream)

**2026-04-22 Phase 4 变更**：从 Redis Pub/Sub `casbin:policy:reload` 迁到 NATS 主题 `sys.casbin.policy.reload`（属于新增的 `SYS` 流），Redis 上彻底消除广播语义。

**实现**: [admin/casbin_nats.go](omcgo/internal/admin/casbin_nats.go) 的 `natsCasbinWatcher` 实现 `persist.Watcher` 接口：
- `Update` → `bus.Publish(SubjectSysCasbinPolicyReload, ...)`
- `StartListener` → `bus.Subscribe(...)`（普通 Subscribe 而非 QueueSubscribe，保留广播语义：每个副本都要各自 `LoadPolicy`）

**语义**: 管理员改动 RBAC 权限后，本地 `Enforcer.LoadPolicy()` 完成后通过 `CasbinAuthorizer.NotifyPolicyChange` 调用 `Watcher.Update`，在集群范围广播；所有订阅者收到后各自从 PG 全量重载策略。

**交付保证**: At-Least-Once（JetStream Durable Consumer + Ack），订阅者断线重连可回放 72h 内消息——比原 Redis Pub/Sub fire-and-forget 更可靠。

**降级路径**: `EventBus` 为 nil（单测 / 无 NATS 部署）时 `natsCasbinWatcher` 退化为 no-op，`CasbinAuthorizer.StartPeriodicRefresh`（默认 5 min）作为周期性兜底，最终一致仍有保障。

**历史兼容**：[admin/casbin.go](omcgo/internal/admin/casbin.go) 的 `redisWatcher` 类型保留供单测与历史回退（未在生产链路装配）。

### 5.4 异常重启滑动窗口 `reboot:abnormal:{device_sn}` (ZSET)

[alarm/reboot_monitor.go](omcgo/internal/alarm/reboot_monitor.go) 订阅 `device.reboot.abnormal`，在对应设备 ZSET 上一次性完成 `ZADD` + `ZREMRANGEBYSCORE`（剔除窗口外）+ `ZCARD` + `EXPIRE` 四步管线操作。窗口内计数达阈值则抬升 `FREQUENT_ABNORMAL_REBOOT` 告警。默认窗口 5 分钟 / 阈值 3 次。

## 6. 业务流端到端图

### 6.1 设备 Inform 处理

```
 ┌─────┐  SOAP Inform
 │ CPE │ ────────────────┐
 └─────┘                 ▼
        ┌────────────────────────────────────────────────┐
        │ [ACS] acs/handler.go publishInformEvents        │
        │  按 EventCode 分支 Publish 到 DEVICE Stream：     │
        │   ├─ 0 BOOTSTRAP       → device.inform.bootstrap       │
        │   ├─ 1 BOOT / M Reboot → device.inform.reboot_complete │
        │   ├─ 2 PERIODIC        → device.inform.periodic        │
        │   ├─ 4 VALUE_CHG       → device.inform.value_change    │
        │   ├─ M AlarmInfo       → device.inform.alarm  (见 §6.2)│
        │   ├─ TransferCompl     → device.inform.transfer_complete (见 §6.5)
        │   └─ AutoXferCompl     → device.inform.autonomous_xfer (见 §6.3)
        └────────────────┬───────────────────────────────┘
                         │ NATS JetStream (DEVICE)
                         ▼
        ┌────────────────────────────────────────────────┐
        │ [APP] device/inform_handler.go                  │
        │  QueueSubscribe：                                │
        │   - device-mgr-bootstrap → 设备注册 + provisioning
        │   - device-mgr-periodic  → 心跳 / 在线状态       │
        │   - device-mgr-valuechange → 参数变更落库        │
        │   - device-mgr-reboot    → 重启状态同步（见 §6.9）│
        └────────────────────────────────────────────────┘
```

**关键语义边界**：
- `0 BOOTSTRAP`（可同时携带 `1 BOOT`）→ bootstrap，走设备注册 + 自动开站。

- 两种语义**不混流**，避免设备重启意外触发开站。

### 6.8 MML 任务聚合（2026-04-22 新打通）

**场景**：MML 任务扇出成多个 `device_tasks`，每个子任务在 ACS 完成后需要回传给 APP 的 `mml_tasks` 做统计聚合（success_count / failed_count / 最终状态），并经 SSE Hub 推送到浏览器。

**背景**：ACS / APP / Worker 是三个独立进程，ACS 直接调用 APP 注册的 callback 不可能。原实现用同进程回调 `TaskService.AddCompletionCallback(aggregator)`，但 APP 的 TaskService 从未被调用 `MarkTaskCompleted`（那只发生在 ACS 进程），导致 MML 聚合链路**断链**。2026-04-22 修正：ACS 通过 NATS 广播终态，APP 以 `CompletionEventBridge` 订阅后驱动聚合器。

```
 [APP] mml/service.go
  SubmitMMLTask(...)
   ├─ INSERT mml_tasks (PG)
   └─ Fanouter.Fanout (mml/fanout.go)
       └─ N × TaskService.CreateTask
                ├─ INSERT device_tasks (source='mml', source_id=<mml_task.id>)
                └─ Redis taskq Push
                            │
                            ▼
                 ACS 会话 Pop → SOAP RPC → CPE 执行 → SOAP Response
                            │
                            ▼
         [ACS] handler.go: MarkTaskCompleted / MarkTaskFailed
                            │
                            ▼
         [ACS] task/service.go notifyCompletion
          ├─ 如挂了 EventBus：Publish task.completed / task.failed (NATS)
          └─ 否则（单测/无 NATS）：本地 callback
                            │ NATS (TASK)
                            ▼
         [APP] task/event_bridge.go (task-completion-bridge)
          DecodePayload(Task) → aggregator.OnTaskCompleted
                            │
                            ▼
         [APP] mml/result_aggregator.go
          ├─ IncrementStats(mml_task_id, success_delta, failed_delta)
          ├─ 当 done >= total 时置最终状态
          └─ messageHub.Publish(executor_userID, "mml_task_completed")
                            │
                            ▼
                   [APP] events/hub.go → SSE → Browser
```

**关键保证**：
- **消费去重**：`CompletionEventBridge` 使用 `QueueSubscribe("task-completion-bridge")`，多 APP 副本下每条事件只被处理一次。
- **避免双重计数**：[task/service.go `notifyCompletion`](omcgo/internal/task/service.go) 做二选一——注入 EventBus 则**只**发事件，不再调用本地 callback，防止同进程的发布者同时触发回调和订阅者。
- **过滤范围**：仅对 `source='mml'` 且带 `source_id` 的任务发射，避免普通 API 任务占用广播带宽。
- **字段语义**：`device_tasks.source_id` 是统一的"任务来源外键"，`source='mml'` 时指向 `mml_tasks.id`；后续扩展其它 source（如 `provision` / `backup`）也复用此字段。

**数据库字段**：[migration 000028](omcgo/migrations/000028_device_tasks_rename_source_id.sql) 将 `parent_task_id` 重命名为 `source_id`，索引同步改名。

### 6.9 设备重启流

**三种重启语义**（按 Inform 事件码判定）：

| 情形 | 事件码组合 | 处理 |
|------|-----------|------|
| 首次入网 / 出厂复位 | `0 BOOTSTRAP` (+ `1 BOOT` 可选) | 走 `device.inform.bootstrap`（§6.1），不进入本流 |
| ACS 命令重启 | `1 BOOT` + `M Reboot` | 正常重启回访，**不抬告警**，兜底关闭 `device_tasks` 里的 Reboot/FactoryReset 任务 |
| 自主 / 异常重启 | `1 BOOT`（无 `M Reboot` 无 `0 BOOTSTRAP`） | 看门狗/崩溃/断电，抬 `device.reboot.abnormal`，滑动窗口累计告警 |

**流转**：

```

                                        │ Publish device.inform.reboot_complete
                                        ▼
     ┌──────────────────┬──────────────────┬────────────────────────┐
     ▼                  ▼                  ▼                        ▼
 [APP]                [WORKER]           [WORKER]               (OSS 目标)
 inform_handler.go    task/reboot_       northbound/push
 (device-mgr-reboot)   closer.go          Engine
                       (task-reboot-     DataTypes⊇"device_event"
                        closer)
 ① UpdateFromInform                      ⑤ 透传订阅该
 ② RecordBootFromInform                     类型 OSS 目标
    (原子 ++ boot_count,
     写 last_boot_at)
 ③ 不含 M Reboot →
    Publish device.reboot.abnormal
                      ③ 含 M Reboot →
                      扫 PG 找 method IN
                      (Reboot, FactoryReset)
                      status IN (pending, sent)
                      → MarkTaskCompleted
           │
           ▼
 [WORKER] alarm/reboot_monitor.go (alarm-reboot-monitor)
  Redis ZSET reboot:abnormal:{sn} 管线操作：
   ZADD + ZREMRANGEBYSCORE + ZCARD + EXPIRE

```

| 职责 | 文件 |

## 8. 交付保证与可靠性

### 8.1 NATS JetStream

- **交付语义**：At-Least-Once（Durable Consumer + Explicit Ack）。
- **重试策略**：指数退避（1s / 2s / 4s / 8s），最多 5 次（[nats_bus.go](omcgo/internal/core/event/nats_bus.go)）。
- **超限处理**：`msg.Term()` 终止消息，避免死循环。
- **保留策略**：`WorkQueuePolicy`（消费完删除）+ MaxAge 72h。
- **部署选择**：`cfg.NATS.URL == ""` 时自动降级到 `ChannelEventBus`（单进程内存实现，支持 NATS 风格通配符）。

### 8.2 Redis 任务队列

- **原子 Pop**：`ZRANGEBYSCORE + ZREM` pipeline 保证并发安全。
- **过期跳过**：`ExpiresAt` 到期任务在 Pop 时跳过并标记 `expired`。
- **优先级 + FIFO**：Score = `priority × 1e13 + timestamp_ns`，优先级越小越优先；同优先级 FIFO。
- **持久化**：Redis AOF/RDB + PG `device_tasks` 双写；Redis 失败回滚 PG 记录。
- **启动恢复**：Worker 启动时 `RestorePendingQueues` 扫 PG + ZScore 去重补灌。
- **僵死恢复**：`GetStaleSentTasks(sn, 5m)` 找 `sent` 超时任务，`CanRetry` 通过则重置为 pending 重新入队，否则标记 failed。

### 8.3 任务完成事件（NATS `task.>`）

- 与 §8.1 共享 JetStream 保证。
- 订阅端采用 QueueSubscribe，APP 多副本下每条终态仅处理一次。
- 发布端内部过滤：仅对 `source=mml` 且有 `source_id` 的任务发布，普通 API 任务不占广播。

### 8.4 Redis Pub/Sub（Casbin）

- Fire-and-forget，订阅者掉线丢通知。
- 通过 Casbin 自身的周期性 `LoadPolicy` 兜底，实现最终一致。

### 8.5 SSE Hub

- 每用户独立 channel，channel 满时丢弃最旧消息。
- [events/store.go](omcgo/internal/events/store.go) 提供可选持久化，支持 EventSource 重连 `Last-Event-ID` 回放。

# 方式 A：生产 Redis（支持 SCAN，推荐）
redis-cli --scan --pattern 'acs:cmdq:*' | xargs -r -n 100 redis-cli DEL

# 方式 B：Redis Cluster
for node in $(redis-cli cluster nodes | awk '/master/ {print $2}' | cut -d@ -f1); do
  redis-cli -h "${node%:*}" -p "${node##*:}" --scan --pattern 'acs:cmdq:*' \
    | xargs -r -n 100 redis-cli -h "${node%:*}" -p "${node##*:}" DEL

### 11.3 任务恢复路径

- **Worker 启动加载**：启动日志 `"restore pending task queues done"` + `scanned/pushed/skipped/failed` 指标。

- **重启兜底关闭**：CPE 上报 `M Reboot` 时 `RebootCloser` 关闭未 ACK 的 Reboot / FactoryReset 任务。
