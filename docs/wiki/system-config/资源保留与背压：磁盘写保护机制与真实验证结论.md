# 资源保留与背压：磁盘写保护机制与真实验证结论

> 记录日期：2026-08-10  
> 测试环境：172.24.224.197:8081  
> 页面入口：系统管理 → 系统配置 → 资源保留与背压  
> 记录性质：功能说明 + 真实测试记录  
> 测试结论：磁盘写保护真实生效，本次测试通过

## 1. 这个功能解决什么问题

“资源保留与背压”的目标是防止系统被磁盘空间压垮。

当系统磁盘空间越来越紧张时，如果还继续放行上传、备份、报表、PM/MR 文件写入等动作，磁盘可能被写满。磁盘写满后，系统可能出现上传失败、服务异常、日志无法落盘、数据库异常等问题。

这个页面就是用来提前设定保护规则：

- 空间接近危险线时，系统先提示风险。
- 空间达到阻断线时，系统拒绝新的写入类操作。
- 空间恢复到安全线以下后，系统再恢复正常写入。

## 2. 页面上主要看什么

页面主要分为两块：

1. **容量总览**：告诉我们当前哪些分区被系统保护，以及这些分区用了多少空间。
2. **存储保护**：告诉我们空间达到什么水位时提示、阻断、恢复，以及当前是否已经阻断。

### 2.1 容量总览

容量总览可能显示多个分区。例如本次测试环境显示：

- `/`
- `/home`
- `/var`

这里的“分区”，可以理解为系统实际写文件时落到的存储位置。

这些分区不是页面写死的。系统会先找出需要保护的目录，例如业务文件、数据库数据、OMC 日志、Docker 数据等，再判断这些目录实际落在哪些分区上。多个目录如果落在同一个分区，会合并显示，避免重复计算。

本次页面上的对应关系大致是：

| 分区 | 主要关联内容 |
|---|---|
| `/` | OMC 自身数据和日志，例如 `/opt/omc/data`、`/opt/omc/run/logs` |
| `/home` | 业务文件和中间数据，例如 MinIO、NATS、Postgres 等 |
| `/var` | Docker 数据，例如 `/var/lib/docker` |

### 2.2 存储保护

“存储保护”是一套全局保护规则。它不是给每个分区分别配置一套规则，而是用一套规则保护整个系统的关键写入行为。

页面上的配置含义如下：

| 配置项 | 业务含义 |
|---|---|
| 提示线 | 达到后开始提示空间风险 |
| 恢复线 | 已经阻断后，低于这条线并连续确认后才恢复 |
| 阻断线 | 达到后开始拒绝新的写入类操作 |
| 检查周期 | 系统多久检查一次容量 |
| 容量未知时 | 如果暂时拿不到容量信息，是允许写入并记录提示，还是直接阻断 |

## 3. 多个分区时怎么判断

当容量总览显示多个分区时，存储保护不会把多个分区加起来算平均值，也不会等所有分区都快满了才处理。

系统会看所有受保护分区里**最紧张的那个分区**：

- 哪个分区使用率最高，就按哪个分区判断风险。
- 只要最紧张的分区达到提示线，系统就进入提示状态。
- 只要最紧张的分区达到阻断线，系统就进入阻断状态。
- 恢复时，也要等最紧张的分区降到恢复线以下，并连续确认后才恢复正常。

这样做的原因是不能用平均值掩盖风险。

例如 `/home` 快满时，即使 `/var` 还有很多空间，业务文件继续写入 `/home` 仍然可能把系统压垮，所以系统应该按 `/home` 的风险来保护。

## 4. 本次真实测试目标

本次测试要证明：

- 页面配置不是只显示成功，而是真的能影响系统行为。
- 当存储保护进入阻断后，PM 文件写入会被拒绝。
- 恢复原配置后，系统能够解除阻断并恢复正常。

本次没有采用“写满磁盘”的方式测试，因为这种方式风险高、清理成本高。测试采用临时调低保护线的方式，让当前真实磁盘使用率超过阻断线，从而触发保护。

## 5. 测试前基线

测试前先确认 PM 上传链路本身是正常的，避免把“本来就没有上传”误判成“写保护生效”。

检查对象：上一个 PM 上传周期，也就是 `11:15 UTC` 附近。

检查窗口：`2026-08-10 11:14:00` 到 `11:20:00`。

检查目录：`/home/omc-data/minio/pm-files/2026/08/10`。

检查结果：

| 时间 | PM 文件元数据记录数 |
|---|---:|
| `11:15` | 8088 |
| `11:16` | 7996 |
| `11:17` | 3916 |
| 合计 | 20000 |

基线结论：开启写保护前，PM 上传链路正常，有大量 PM 文件进入系统。

## 6. 写保护触发测试

经人工确认后，临时把存储保护阈值调整为：

| 配置项 | 原值 | 临时测试值 |
|---|---:|---:|
| 提示线 | 80% | 60% |
| 恢复线 | 85% | 65% |
| 阻断线 | 90% | 70% |
| 检查周期 | 30 秒 | 30 秒 |

当时页面显示的最高占用率约为 `71.5%`。临时阻断线设为 `70%` 后，系统应该进入阻断。

页面实际结果：

- 配置保存成功。
- 容量总览中 `/` 和 `/home` 显示为已阻断。
- 存储保护当前状态显示为已阻断。
- 页面状态记录显示系统先从正常进入提示，再从提示进入已阻断。

## 7. 写保护后的 PM 上传验证

开启写保护后，等待下一个 PM 上传周期。

检查窗口：`2026-08-10 11:44:00` 到 `11:50:00`。

检查目录：`/home/omc-data/minio/pm-files/2026/08/10`。

检查结果：

| 对比项 | 结果 |
|---|---:|
| 开启写保护前 `11:14` 到 `11:20` | 20000 个 PM 文件元数据记录 |
| 开启写保护后 `11:44` 到 `11:50` | 0 个 PM 文件元数据记录 |

同时，ACS 上传日志中出现了 PM 上传被拒绝的记录，拒绝原因包含 `resource_pressure`。这说明系统不是只在页面上显示“已阻断”，而是真的拒绝了 PM 文件写入。

本轮判断：写保护真实生效。

## 8. 测试后恢复

测试完成后，立即恢复原配置：

| 配置项 | 恢复值 |
|---|---:|
| 提示线 | 80% |
| 恢复线 | 85% |
| 阻断线 | 90% |
| 检查周期 | 30 秒 |

恢复后刷新页面确认：

- 当前状态：正常
- 当前阻断：未阻断
- 状态记录显示：系统已从已阻断恢复为正常，并提示“连续两次低于恢复线，已恢复写入”

## 9. 最终结论

本次测试通过。

结论如下：

- PM 上传在测试前是正常的。
- 临时调低阻断线后，系统能进入已阻断状态。
- 已阻断状态下，下一轮 PM 文件没有继续写入。
- 日志中能看到 PM 上传被资源压力拒绝的记录。
- 恢复原阈值后，系统能解除阻断并恢复正常。

因此可以确认：**系统管理 → 系统配置 → 资源保留与背压中的磁盘写保护功能真实有效。**

## 10. 使用和测试注意事项

- 不建议通过真实写满磁盘来测试该功能。
- 推荐通过临时调低保护线来模拟磁盘空间紧张。
- 修改测试环境配置前必须人工确认。
- 测试完成后必须恢复原配置，并确认页面显示“当前状态正常、当前阻断未阻断”。
- 判断写保护是否生效时，不能只看页面状态；还要结合真实业务写入结果，例如 PM 文件是否继续落盘。
