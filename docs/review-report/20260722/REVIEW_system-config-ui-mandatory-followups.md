# 系统配置界面后续必修问题

> 记录日期：2026-07-22（Asia/Shanghai）
> 审查基线：`8197cb2eb1850da0334a54a2c703a33907d49887`
> 范围：只记录当前系统配置界面仍需后续修复的存量问题；本轮不修改这些业务逻辑。
> 关联审查：`docs/review-report/20260720/REVIEW_cccbb2b3_system-config-code-review.md`

## 1. 业务前提

系统配置是 OMC 的运行控制面，不是普通表单。后续修复必须遵守以下约束：

1. 查询失败、配置缺失和配置值为零是三种不同状态，不能互相替代。
2. 页面展示值必须是后端实际生效值，前端不得独立定义会改变业务语义的默认值。
3. “数据库已保存”“事件已投递”“目标运行态已应用”必须明确区分。
4. 基站在线状态是告警、任务执行和设备运维的基础状态，不能提供没有后端语义的开关。
5. 安全策略、保留策略等共享配置必须由后端执行最终校验，不能只依赖前端控件范围。

## 2. 必修问题

### P0：加载失败或配置稀疏时，保存会写入前端默认值

**现状**

- 系统配置主页面在查询未返回配置时使用各页签的 `initialValues`。
- 保存按钮没有以查询成功为前置条件。
- 保存时会序列化整张表单，而不只是用户实际修改的字段。
- 当前环境的 `security` 分类只有少量已落库字段，因此风险不是理论场景。
- 安全页和后端的缺省策略不一致，例如密码长度前端为 `10–23`，后端为 `8–32`；账号锁定和并发登录策略也存在差异。

**业务影响**

管理员只修改一个设置，也可能静默改变整套登录和密码安全策略；查询失败时点击保存，还可能把“未知状态”覆盖为前端默认值。

**最小修复方案**

1. 当前分类加载中或加载失败时禁止保存，并展示明确错误。
2. 后端返回持久化值与运行默认值合并后的 effective config；前端只展示该结果。
3. 前端只提交用户实际修改的字段，或由后端基于版本执行差异更新。
4. 删除前端独立维护的业务默认值，默认值只保留一个后端来源。

**验收标准**

- 配置查询失败时无法提交。
- 空库或稀疏配置加载后，不做修改直接保存不会改变任何 effective policy。
- 修改单个安全字段不会新增或改变其他安全字段。

### P1：`enbTimeoutEnable` 是无效控制

**现状**

- 设备配置页展示 `enbTimeoutEnable` 开关。
- 后端离线判定始终读取并执行 `enbTimeout`，没有消费该开关。
- 当前环境为 `enbInformPeriod=60`、`enbTimeout=100`；代码缺省值为 600 秒，两者不能在未确认设备 Inform 抖动和运营商要求时擅自互换。

**业务影响**

用户关闭开关后，基站仍会被判离线，页面承诺与实际设备状态不一致，进而误导告警和任务判断。

**建议业务语义**

- OMC 正常运行时在线/离线判定不可关闭：移除无效开关，只配置超时阈值。
- 如运营商确有暂停判定需求，应设计明确的“设备维护模式”，并同步定义告警抑制、任务调度和恢复行为，不能继续复用无效开关。
- `enbTimeout` 的最终值必须根据实际 Inform 周期、允许抖动和离线发现 SLA 确认。

**验收标准**

- 页面不存在后端不消费的控制项。
- 阈值说明与实际离线扫描算法一致。
- 维护模式如被采用，需覆盖设备状态、告警和任务三条业务链。

### P1：保留策略页面把“保存成功”当作“应用成功”

**现状**

- 资源保留/背压和日志保留卡片在批量保存返回后直接提示成功。
- 部分页面没有继续观察配置应用批次，异常处理也可能不向用户展示。
- `minio.retention` 会触发 MinIO 生命周期规则应用，外部应用可能失败。

**业务影响**

数据库已保存但 MinIO 生命周期规则没有生效时，页面仍可能显示成功，影响 PM/MR/KPI 原始文件容量治理和保留预期。

**最小修复方案**

1. 对存在持久化应用目标的分类复用 PM 保留页的批次状态跟踪。
2. 明确展示“配置已保存”“正在应用”“应用失败并重试”“已应用”。
3. 仅依赖缓存或下次读取生效的分类，成功文案只能表述为“配置已保存”。
4. 网络和后端错误必须显式提示，禁止空 `catch`。

**验收标准**

- MinIO 应用失败时页面不能显示“已生效”。
- 自动重试后状态可恢复，不需要重新保存配置。
- 查询或保存失败都有可见错误信息。

### P1：安全配置缺少跨字段后端校验

**现状**

- 当前后端主要执行单字段校验，没有基于批次最终状态执行分类级组合校验。
- 页面可组合出 `pwdMinLength > pwdMaxLength`、`promptBeforeDays > validPeriod` 等无效策略。
- 前端 `InputNumber` 的范围不能替代服务端约束，也不能保护 API 直调。

**业务影响**

密码最小长度大于最大长度时，可能导致用户创建、密码修改和密码重置全部无法通过；过期提醒配置矛盾也会造成错误提示。

**最小修复方案**

1. 为 `security` 分类建立 typed schema 和批次最终状态校验。
2. 至少校验 `pwdMinLength <= pwdMaxLength`、`promptBeforeDays <= validPeriod`。
3. 同批修改默认密码和密码规则时，必须使用修改后的最终规则校验默认密码。
4. 后端返回可定位到字段的错误，前端再做同规则的即时提示。

**验收标准**

- UI 和 API 直调都不能写入矛盾的安全策略。
- 同批修改多个相关字段时，校验基于最终候选配置，而不是保存前旧配置。

## 3. 归因与提交边界

上述问题均可追溯到更早的系统配置实现，不是 2026-07-21 两个系统配置 MR 新引入的问题。本轮回归修复不应夹带这些修改，后续应单独建立范围明确的 MR。

建议后续顺序：

1. 加载成功前禁止保存，并统一 effective config 默认值来源。
2. 删除 `enbTimeoutEnable` 假开关，确认超时阈值业务口径。
3. 补齐各独立卡片的应用状态和错误反馈。
4. 增加安全配置分类级后端校验。

## 4. 本文明确不要求的改动

- 不重构整个系统配置页面。
- 不调整与上述问题无关的 UI 布局和文案。
- 不把部署期 MinIO 参数全部开放成运行期配置。
- 不在缺少设备 Inform、网络抖动和运营商 SLA 证据时擅自修改离线阈值。
- 不把 ACS 事件投递升级为完整集群确认协议；该能力应作为独立架构需求评审。
