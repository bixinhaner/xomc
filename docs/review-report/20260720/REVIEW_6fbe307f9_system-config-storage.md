## 1. 结论摘要

系统配置页当前实际有 9 个页签，功能主链路基本完整；PM、告警、MinIO 原始件、站点日志和数据库日志的保留任务在当前环境都已启动，2026-07-20 最近一次任务均成功。当前样本数据量很小，尚未触发任何保留边界，不能用“本次删除 0 条”代替大数据量场景的容量验证。

需要优先关注以下问题：

| 优先级 | 问题 | 影响 |
|---|---|---|
| P1 | 系统仪表盘磁盘占用固定回退为 `58%`，后端 `/system/info` 不返回磁盘字段 | 页面展示可能与真实磁盘完全不一致，不能用于运维判断 |
| P1 | 通用配置接口先提交 `sys_configs`，再以无返回值 hook 应用 Timescale/MinIO 等运行时策略 | 页面“保存成功”只代表 KV 已落库，不代表外部策略已生效 |
| P1 | PM 和告警保留策略采用 `remove_retention_policy` 后再 `add_retention_policy`，不在同一事务内 | 第二步失败时会留下“无保留策略”的窗口，可能导致数据持续增长 |
| P1 | ACS 传输页默认 `127.0.0.1`，并强制归一化为 `http://{host}:8080` | 生产设备不可访问回环地址；保存旧的 HTTPS/自定义端口配置时可能被静默改写 |
| P2 | PM、日志、背压等大部分 KV 仅有前端范围校验，通用后端接口未逐项注册 validator | 直接调用 API 可写入非法值，运行时又回退默认值，造成“库中值”和“生效值”不一致 |
| P2 | 文件日志只有按文件大小、时间和归档年龄控制，没有目录总容量硬上限 | 高频日志可持续消耗磁盘；当前 `app` 日志目录已约 241 MB |
| P2 | 背压后端支持 IO PSI 和最大在途数，但页面没有展示这 3 个关键参数 | 运维人员无法从页面确认或调优完整的保护策略 |
| P2 | 代码已更新到最新 `origin/main`，但正在运行的 app/acs/worker 容器启动时间早于最新提交 | 本报告的页面来自最新前端源码，后端运行态仍是旧镜像，部署后还需复验 |

| P3 | 浏览器走查出现 4 类 Ant Design 废弃 API 告警 | 暂不影响功能，但升级组件库时存在兼容风险 |

## 4. PM 数据存储全链路

```text
设备 PM/MR 文件
  -> ACS 上传入口
     -> 最大在途数门闸
     -> MinIO 磁盘 / IO PSI 背压
  -> MinIO pm-files / mr-files
     -> 60 天 ILM
     -> 解析成功后 best-effort gzip
  -> worker 解析
  -> TimescaleDB
     -> pm_metrics：30 天保留，7 天压缩
     -> 小时聚合：180 天保留，14 天压缩
  -> PostgreSQL 普通聚合表
     -> 日/周：730 天
     -> 月：1825 天
     -> 每日异步分批删除
```

这套策略的关键特点是：

1. “原始文件保留 60 天”和“15 分钟指标保留 30 天”是两条独立策略，不要求相同。
2. 原始文件 gzip 不等于删除；真正删除由 MinIO ILM 完成。
3. 日/周/月表不是 Timescale hypertable，依赖 worker 定时任务。
4. 配置保存、策略应用、异步清理是三种不同状态，当前页面没有把它们区分展示。

### P1-2 “保存成功”与“策略已应用”没有一致性保证

证据：

- `SysConfigService.BatchUpsert` 先提交数据库。
- 提交后再调用 SavedHook。
- hook 没有 error 返回值；panic 被 recover，PM/告警/MinIO 应用失败只写 warning 日志。

建议：

- 短期：保存响应返回 `persisted/applied/pending/failed`，页面明确提示“已保存但应用失败”。
- 中期：把外部策略应用放入可重试 outbox/异步任务，记录最后成功时间和错误。
- 提供统一“配置生效状态”接口，核对 KV、Timescale job、MinIO ILM 和服务缓存版本。

### P1-3 Timescale 保留策略替换不原子

证据：

- PM 和告警策略都执行 `remove_retention_policy`，再执行 `add_retention_policy`。
- 两条 SQL 没有显式事务包裹，失败后旧策略不会恢复。

建议：

- 优先使用 Timescale 支持的 job 修改能力；必须 remove/add 时应放入事务并做 post-check。
- 应保存旧策略，失败时自动补偿恢复。
- 增加“期望保留期 vs 实际 job config”周期巡检。

### P1-4 ACS 地址有生产误配风险

证据：

- 页面默认回环地址。
- 页面强制 HTTP、8080 和固定路径。
- 读取存量值时会归一化旧协议、端口和路径。

建议：

- 生产模式禁止 `127.0.0.1`、`localhost` 和不可路由地址。
- 提供设备视角的可达性检查。
- 如果产品确实只支持 HTTP:8080，应在部署前置检查中强约束；否则不要在前端静默重写后端存量值。

### P2-1 服务端 KV 校验不完整

当前仅安全默认密码、MinIO 公网端点等少量 key 注册了专用 validator。PM、日志、背压等配置主要依赖前端校验和运行时回退。

建议：

- 为所有可编辑 key 定义统一 schema：类型、范围、单位、默认值、是否敏感、热加载方式。
- 批量保存时做跨字段校验，例如 `low <= high`、最小长度不大于最大长度。
- 非法值应拒绝落库，不要静默回退后继续显示“保存成功”。

### P2-2 日志和磁盘缺少总量控制

建议：

- 增加日志目录总大小上限和紧急清理水位。
- 增加 Docker build cache 运维策略，但避免自动清理正在使用的构建层。
- 增加磁盘容量预测：按 7/30 天增长率给出预计写满时间。

### P2-3 背压的关键控制项未在页面暴露

建议：

- 展示 IO PSI 高/低水位、最大在途数、当前采样值和背压状态。
- 展示最近一次进入/解除背压的原因和时间。
- 按设备厂家统计 503 后重传成功率，验证“拒收但不丢失”的前提。

### P3-1 默认值与显式配置混淆

建议：

- 每个字段显示来源：`显式配置`、`系统默认`、`环境变量`、`运行时回退`。
- 点击保存时只写用户实际确认的值，避免浏览页面后保存就把整套默认值固化。
- 为 `storage.alarmHisMaxHoldTime=365` 补 seed/migration，或明确允许缺省并在页面标识。

### P3-2 文档与组件库兼容债务

建议：

- 重写 `omcgo/docs/prd/system/config.md`，以当前 9 页签和实际 API 为准。
- 已隐藏的通知、网管磁盘告警、北向空壳继续保持隐藏，直到后端能力和验收标准完整。
- 清理浏览器检测到的 4 类 Ant Design 废弃 API。

## 7. 建议实施顺序

### 第一阶段：避免运维误判

1. 删除磁盘固定 `58%` 回退，接入真实指标。
2. 页面增加“配置来源”和“最后生效状态”。
3. 生产部署检查拒绝 ACS 回环地址。
4. 为 PM、日志、背压补齐服务端 validator。

### 第二阶段：加强数据保留可靠性

1. 把 Timescale retention 重设改为原子操作或带补偿的任务。
2. 增加期望策略与实际策略巡检。
3. 增加普通表清理 backlog、耗时和失败告警。
4. 增加未压缩原始件补偿工具和离线巡检，不建议恢复常驻全桶扫描。

### 第三阶段：容量治理

1. 建立按设备规模的 PM/MinIO/Timescale 容量模型。
2. 增加日志目录硬上限和磁盘预计写满时间。
3. 建立 Docker build cache 定期维护流程。
4. 用至少一个跨过保留边界的加速环境验证 30/60/180/730/1825 天删除行为。
