## 1. 总体评估

OMC 系统整体呈现"架构骨架扎实、安全与运营就绪度不足"的典型特征。后端采用模块化单体 + 独立 ACS 引擎，认证框架（JWT + API Key + Casbin RBAC）、运营商抽象（Carrier 接口隔离 cmcc/ctcc/cucc）、参数字典三级缓存、NATS At-Least-Once 交付、备份信封加密（AES-256-GCM/HMAC 常量时间校验）、SQL 全量参数化（Squirrel + pgx，无 ORM 拼接）等核心设计经得起审查。前端 frontend-core 业务层与三皮肤 UI 壳分离干净，无越权 axios 调用，Route 懒加载 / React Query / vite 分片到位。这是一个有真实工程纪律的代码库，不是脚手架。

但在面向运营商商用交付的标准下，存在一批可立即利用、会造成断网或数据泄露的硬伤。最严重的是凭证管理全面失守：PostgreSQL（omcgo123）、MinIO（minioadmin）、JWT、TR-069 共享密钥（dps）在 config.prod.yaml 与 docker-compose 中硬编码并入 git 历史（已核实 cmd/acs/etc/config.prod.yaml、cmd/app/etc/config.prod.yaml 等多处），任何能读仓库或容器镜像层的人即可完全接管数据库、对象存储与 TR-069 信道。其次是南向攻击面：ACS handler.go:222 直接 io.ReadAll(r.Body) 无 MaxBytesReader（全仓库零处使用），恶意 CPE 一个超大 POST 即可 OOM 拖垮服务影响全网 10 万站；SOAP XML 解析未禁用外部实体（XXE）；会话无 IP/设备绑定，cookie 泄露即可冒充任意设备下发 Reboot/SPV。前端把 accessToken/refreshToken 与"记住我"明文密码直接写 localStorage（已核实 login/index.tsx:37），XSS 即可窃取管理员全权。

可扩展性方面，当前 10 万规模可运行，但向 100 万演进存在确定性瓶颈，多处已被代码坐实而非推测：alarm Statistics() 接收 filter 参数却完全忽略（pg_store.go:261-291 硬编码全表 COUNT/GROUP BY，已核实），统计页面在百万告警下周期性卡死；device_parameters 缺 (parameter_path, parameter_value) 复合索引导致 SoftwareVersion 过滤全表扫描；task.wakeDevice 每次 CreateTask 派生无界 goroutine、Worker cron 与 PM 聚合无并发上限、PM metrics 逐行 VALUES 拼接 O(n²)、文件解析器整文件入内存无流式、TimescaleDB 压缩 chunk >7d 补传硬错无降级。这些在 inform 风暴下会级联放大为连接池耗尽与 OOM。

可观测性与测试是第二梯队风险。OTel 核心设施健全，但业务关键路径（PM 计数器丢弃、告警 raise/clear、Worker 健康探针、事件总线 terminated 投递）几乎无指标，运营商无法实时定位静默丢数。测试方面 458 个后端测试文件掩盖了 10 个零测试模块、迁移脚本 0 幂等性测试、前端 60 个 API 钩子与 30 个类型文件全 0 覆盖、463 处只查 isLoading 仅 7 处查 isError——网络故障对操作员"不可见"。

结论：当前状态可作为 10 万规模 POC / 受控内网试点交付，但尚未达到面向运营商的商用生产就绪。在凭证轮换 + 注入运行时校验、ACS 请求体限流 + XXE 加固、前端令牌存储改造、北向/NE Direct 鉴权这四类 critical/high 修复落地前，不应暴露于不可信网络或正式商用环境。所幸绝大多数硬伤是"配置与边界缺口"而非"架构错误"，多数 quick win 在数小时内可消除，整改路径清晰。

## 2. 贯穿性主题（根因聚类）

1. Secrets 管理是贯穿全栈的系统性失败：后端 config.prod.yaml/docker-compose 硬编码 PG/MinIO/JWT/TR069(dps)、备份 KEK 经 env 可被 /proc 读取、trace 明文存 CPE 凭证、前端 localStorage 明文存令牌与密码。同一根因——缺乏'秘密不入代码/不入日志/不入浏览器持久存储'的强制 guardrail，且无启动期校验拒绝默认值。
2. '框架建好但边界未强制'反复出现：认证中间件覆盖 85% 但 device 详情 IDOR、北向无 carrier 过滤、NE Direct 零鉴权绕过；Carrier 接口设计优雅但 InformHandler 与 MRE parser 硬编码绕过；InsecureSkipVerify、明文密码登录均靠'配置正确'兜底而非代码强制。设计意图对，enforcement 漏。
3. 无界资源派生模式在多处复制：task.wakeDevice 每次 CreateTask 派生无界 goroutine、Worker cron 无并发上限、ACS body 无 MaxBytesReader、PM metrics Query 无强制 LIMIT、ListPendingAllDevices 无界加载、文件解析整文件入内存。10 万可撑、100 万 inform 风暴下集体转化为 OOM 与连接池耗尽。
4. 故障对操作员'不可见'是可观测性与前端共有主题：后端 PM 丢弃/告警/事件 terminated 无指标、Worker 无健康探针静默丢事件；前端 463 处查 isLoading 仅 7 处查 isError、错误状态几乎不渲染。两端叠加——百万规模下数据丢失与 API 故障无人察觉，只能事后 grep 日志。
5. 失败路径测试系统性缺失：后端 10 模块零测试 + 迁移 0 幂等性测试 + Device 缓存/Admin RBAC/Provision 状态机缺失败路径；前端 60 API 钩子 + 30 类型文件全 0 覆盖。成功路径有保障，但网络超时/401/429/500/畸形响应/并发冲突等真实生产故障无任何回归网。
6. 查询忽略过滤参数 / 缺索引导致全表扫描在数据访问层重复：alarm Statistics 收 filter 却全表 COUNT（已核实）、device_parameters 缺 (path,value) 复合索引、PM 设备组维度 JOIN 后 GROUP BY 无索引、PM Query 无默认 LIMIT。在百万行时序/告警表上一致地退化为秒级延迟与 DB CPU 热点。

## 3. 最高优先级风险（按影响排序）

1. 硬编码生产凭证入 git 历史（PG omcgo123 / MinIO minioadmin / JWT / TR069 dps，已核实多个 config.prod.yaml 与 docker-compose）——任何能读仓库、CI 日志或镜像层的人即可完全接管数据库、对象存储、API 认证与 TR-069 信道，是 critical 级、对全网 10万-100万 站的合规与可用性灾难。必须立即轮换全部凭证 + 加启动期拒绝默认值校验。
2. ACS SOAP handler 无请求体大小限制（handler.go:222 裸 io.ReadAll，全仓库零 MaxBytesReader）+ SOAP XML 未禁用外部实体（XXE）——互联网可达的南向攻击面，恶意/故障 CPE 一个超大 POST 或恶意实体即可 OOM 拖垮 ACS，造成全网 10 万站断管理面，立即可利用无需认证。
3. 前端令牌与密码明文存 localStorage（login/index.tsx:37 存明文密码、store 存 accessToken/refreshToken 未加密）+ 8 个高危 npm 依赖（axios 原型污染/lodash 注入/xlsx ReDoS）——任意低级 XSS 即可窃取管理员全权，进而对全网设备恶意配置/关停，是前端最高风险。
4. 外部 API 鉴权与多租户隔离缺口：北向 sync/export 无 carrier 过滤致跨运营商数据外泄（一个被盗 ctcc 账号可导出全部 10万 设备）、北向 config 导出不校验设备归属、NE Direct（虽默认 enabled:false）一旦启用即零鉴权后门。100 万多租户部署的合规与数据泄露主风险。
5. 向 100 万扩展的级联失效组合：alarm Statistics 全表扫（已核实）+ device_parameters 缺索引全表扫 + wakeDevice/Worker 无界 goroutine + 连接池 50/30 偏小 + 文件解析无流式 OOM——inform 风暴下连接池耗尽、统计页卡死、Worker OOM 相互放大，是从 10万 迁 100万 前必须解决的扩展性硬障碍。
6. 运营盲区致故障不可见：Worker 无健康探针（静默丢 PM/告警事件数小时）+ 事件总线 terminated 无指标 + PM 丢弃无指标 + 前端 463:7 的 isLoading:isError 比 + 0 迁移幂等性测试——百万规模下数据丢失、队列饱和、迁移失败均无实时告警，SRE 只能事后 grep，违背运营商 SLA。

#### CRITICAL-1　No request body size limits on ACS SOAP message handler
- **维度 / 区域**：security · `omcgo/internal/acs` · lens:`sec-tr069` · 工作量:small · 置信:high
- **位置**：`omcgo/internal/acs/handler.go:222`、`omcgo/cmd/acs/etc/config.prod.yaml:9-11`
- **问题**：The ACS handler reads entire request bodies into memory via io.ReadAll(r.Body) without enforcing per-request size limits. CPE devices can exhaust memory by sending arbitrarily large SOAP messages. No MaxBodySize enforcement is applied at HTTP layer (no http.MaxBytesReader wrapper).
- **证据**：handler.go line 222: `body, err := io.ReadAll(r.Body)` is called unconditionally on incoming HTTP requests without prior size validation. config.prod.yaml lines 9-11 define read/write/idle timeouts but not MaxRequestBodySize. The http.Server struct (server.go line 137-143) does not set MaxHeaderBytes. Compare with upload/handler.go which uses io.LimitedReader for file uploads.
- **影响**：Unprotected memory DoS: malicious or misbehaving CPE device sends multi-GB POST body → ACS process OOM → service degradation affecting all 10万 connected stations. At 10万 scale, this is a network-wide outage vector.
- **建议**：Wrap r.Body with http.MaxBytesReader BEFORE calling io.ReadAll. TR-069 spec defines SOAP message maximum as ~1MB typical case; set limit to 50MB as safe upper bound (covers large Inform with extensive parameter list + future extensibility). Concrete fix at handler.go line 222: `body, err := io.ReadAll(http.MaxBytesReader(w, r.Body, 50*1024*1024))`. Alternatively, set http.Server.MaxHeaderBytes to 1MB minimum (protects headers but not body). Also audit upload/download handlers to ensure they enforce max file size limits at request body read time (currently they do via config.Upload.MaxFileSize at line 155 in main.go, but verify application in ServeHTTP).
