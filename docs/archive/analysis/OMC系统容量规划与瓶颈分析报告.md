## 一、分析背景与假设

### 1.1 业务场景

| 业务 | 频率 | 说明 |
|------|------|------|
| 心跳（Periodic Inform） | 每 1~3 分钟一次 | TR-069 SOAP/HTTP，ACS 处理 |
| KPI 文件上传（PM） | 每 15 分钟一次 | AutonomousTransferComplete → 下载 → MinIO → 解析 → TimescaleDB |
| MR 文件上传 | 每 15 分钟一次 | 同 PM 路径，文件更大 |
| 固件升级任务 | 按需触发（突发） | ConnectionRequest → Download RPC → TransferComplete |

### 1.2 基站规模

| 规模 | 1,000 | 5,000 | 10,000 | 30,000 | 60,000 |
|------|-------|-------|--------|--------|--------|
| 定位 | 试点 | 区域 | 省级小 | 省级大 | 全网 |

### 1.3 关键参数假设

| 参数 | 值 | 来源 |
|------|-----|------|
| PM 文件大小 | 30~200 KB（均值 100KB） | 小基站典型值 |
| PM 文件计数器数 | 200~800（均值 500） | 3GPP 32.435 |
| MR 文件大小 | 50~500 KB（均值 200KB） | MRO/MRS/MRE |
| MR 文件记录数 | 100~500（均值 300） | 含邻区测量 |
| 单次 Inform 会话时长 | 500ms~1.5s（均值 1s） | 3~5 HTTP 往返 |
| 单次 Inform 会话内存 | ~50 KB | goroutine 栈 + 缓冲 |
| COPY 吞吐 (pgx) | 100K~1M 行/秒 | PostgreSQL COPY 协议 |
| Redis 单实例 QPS | 100,000+ ops/s | 标准配置 |
| NATS 单实例吞吐 | 1,000,000+ msg/s | JetStream 模式 |
| Worker 单实例处理速度 | ~20 PM 文件/秒，~25 MR 文件/秒 | XML 解析 + COPY |

## 二、各规模负载量化分析

### 2.1 ACS 引擎负载（omcgo-acs，端口 7547）

ACS 引擎承载所有基站的 TR-069 会话：心跳、PM/MR 上报通知、升级回调。

#### 心跳负载（1 分钟间隔 / 3 分钟间隔）

| 规模 | 1min: 会话/秒 | 1min: 并发 | 3min: 会话/秒 | 3min: 并发 |
|------|:------------:|:----------:|:------------:|:----------:|
| 1,000 | 16.7 | ~17 | 5.6 | ~6 |
| 5,000 | 83.3 | ~83 | 27.8 | ~28 |
| 10,000 | 166.7 | ~167 | 55.6 | ~56 |
| 30,000 | 500.0 | ~500 | 166.7 | ~167 |
| 60,000 | 1,000.0 | ~1,000 | 333.3 | ~333 |

#### PM/MR 上报通知（每 15 分钟，共 2 个 ATC 事件/设备）

| 规模 | PM ATC/秒 | MR ATC/秒 | 合计 ATC/秒 |
|------|:---------:|:---------:|:-----------:|
| 1,000 | 1.1 | 1.1 | 2.2 |
| 5,000 | 5.6 | 5.6 | 11.2 |
| 10,000 | 11.1 | 11.1 | 22.2 |
| 30,000 | 33.3 | 33.3 | 66.6 |
| 60,000 | 66.7 | 66.7 | 133.4 |

#### ACS 综合负载（心跳 1min 间隔 + PM/MR + 升级并发 5%）

| 规模 | 总会话/秒 | 峰值并发会话 | ACS 实例需求 | 内存估算 |
|------|:---------:|:-----------:|:------------:|:--------:|
| 1,000 | ~20 | ~25 | 1 | ~1.2 MB |
| 5,000 | ~100 | ~120 | 1 | ~6 MB |
| 10,000 | ~200 | ~240 | 1 | ~12 MB |
| 30,000 | ~600 | ~700 | 1 | ~35 MB |
| 60,000 | ~1,200 | ~1,400 | 1~2 | ~70 MB |

> **结论**：ACS 引擎单实例最大支持 10,000 并发会话，60,000 基站在 1 分钟心跳下稳态仅 ~1,400 并发，**ACS 不是瓶颈**。但需考虑掉电恢复等突发场景（全量重连），建议 ≥30,000 时部署 2 个 ACS 实例。

### 2.2 Worker 处理负载（omcgo-worker）

Worker 是异步事件消费者，处理 PM/MR 文件解析和入库。这是**最关键的吞吐瓶颈**。

#### PM 文件处理管线

```
TransferBridge: HTTP GET 下载 → MinIO PUT → publish pm.file.received
PMCollector:    MinIO GET → XML 流式解析 → COPY pm_counters → KPI 计算 → COPY kpi_values
```

| 规模 | 文件/15min | 文件/秒 | 计数器行/秒 | KPI 行/秒 | Worker 需求 |
|------|:---------:|:-------:|:-----------:|:---------:|:-----------:|
| 1,000 | 1,000 | 1.1 | 556 | ~11 | 1 |
| 5,000 | 5,000 | 5.6 | 2,778 | ~56 | 1 |
| 10,000 | 10,000 | 11.1 | 5,556 | ~111 | 1 |
| 30,000 | 30,000 | 33.3 | 16,667 | ~333 | 2 |
| 60,000 | 60,000 | 66.7 | 33,333 | ~667 | 4 |

#### MR 文件处理管线

```
TransferBridge: HTTP GET 下载 → MinIO PUT → publish mr.file.received
MRCollector:    MinIO GET → 类型检测(MRO/MRS/MRE) → XML 解析 → COPY mr_records
```

| 规模 | 文件/15min | 文件/秒 | MR 记录行/秒 | Worker 需求 |
|------|:---------:|:-------:|:----------:|:-----------:|
| 1,000 | 1,000 | 1.1 | 333 | 1 |
| 5,000 | 5,000 | 5.6 | 1,667 | 1 |
| 10,000 | 10,000 | 11.1 | 3,333 | 1 |
| 30,000 | 30,000 | 33.3 | 10,000 | 2 |
| 60,000 | 60,000 | 66.7 | 20,000 | 3 |

#### TransferBridge 文件下载

TransferBridge 需从基站下载 PM/MR 文件再上传到 MinIO，是 Worker 管线的前置步骤。

| 规模 | 下载任务/秒 | 网络带宽需求 | TransferBridge 实例 |
|------|:---------:|:----------:|:------------------:|
| 1,000 | 2.2 | ~0.7 MB/s | 1 |
| 5,000 | 11.2 | ~3.4 MB/s | 1 |
| 10,000 | 22.2 | ~6.7 MB/s | 1 |
| 30,000 | 66.7 | ~20 MB/s | 2 |
| 60,000 | 133.3 | ~40 MB/s | 3 |

#### Worker 总需求汇总

| 规模 | PM Worker | MR Worker | TransferBridge | **总 Worker 实例** |
|------|:---------:|:---------:|:--------------:|:-----------------:|
| 1,000 | 1 | 1 | 1 | **2** |
| 5,000 | 1 | 1 | 1 | **2** |
| 10,000 | 1 | 1 | 1 | **2** |
| 30,000 | 2 | 2 | 2 | **3~4** |
| 60,000 | 4 | 3 | 3 | **5~6** |

### 2.3 数据库负载

#### PostgreSQL（主库，结构化数据）

| 操作 | 来源 | 频率 |
|------|------|------|
| UPDATE devices | 心跳更新 last_inform_at | 每次 Inform |
| UPSERT device_parameters | 参数变更 | 部分 Inform |
| INSERT/UPDATE upgrade_tasks | 升级状态变更 | 升级期间 |
| INSERT provisioning_tasks | 新设备注册 | Bootstrap |
| SELECT 各种查询 | App REST API | 前端轮询 |

| 规模 | 心跳写/秒 (1min) | 心跳写/秒 (3min) | 连接池需求 | 瓶颈风险 |
|------|:----------------:|:----------------:|:---------:|:--------:|
| 1,000 | 17 | 6 | 10 | 无 |
| 5,000 | 83 | 28 | 15 | 无 |
| 10,000 | 167 | 56 | 20 | 低 |
| 30,000 | 500 | 167 | 30 | **中** |
| 60,000 | 1,000 | 333 | 50 | **高** |

> **60,000 基站 + 1 分钟心跳 = 1000 UPDATE/秒**。PostgreSQL 单实例可以处理，但需要 SSD + 充足连接池 + 适当索引。设备表已按运营商分区（`PARTITION BY LIST (carrier)`），有助于减轻写放大。

#### TimescaleDB（时序数据 — 核心瓶颈）

| 规模 | pm_counters 行/秒 | kpi_values 行/秒 | mr_records 行/秒 | **总行写入/秒** |
|------|:-----------------:|:----------------:|:----------------:|:--------------:|
| 1,000 | 556 | 11 | 333 | **900** |
| 5,000 | 2,778 | 56 | 1,667 | **4,501** |
| 10,000 | 5,556 | 111 | 3,333 | **9,000** |
| 30,000 | 16,667 | 333 | 10,000 | **27,000** |
| 60,000 | 33,333 | 667 | 20,000 | **54,000** |

> **关键发现**：60,000 基站下 TimescaleDB 持续写入 **54,000 行/秒**。使用 COPY 协议批量写入，单 TSDB 实例可以处理（PostgreSQL COPY 吞吐可达 100K~1M 行/秒），但：
> - 需要 **NVMe SSD** 磁盘
> - 需要充足的 **shared_buffers**（推荐 8~16GB）
> - **work_mem** 和 **max_wal_size** 需调大
> - 连续聚合（pm_counters_hourly）会增加额外负载

### 3.2 瓶颈排序（60,000 基站）

```
🔴 瓶颈 1：TimescaleDB 写入吞吐
   - 54,000 行/秒持续写入
   - pm_counters + kpi_values + mr_records 三表并行 COPY
   - 连续聚合 (pm_counters_hourly) 实时化物化增加额外 I/O
   - WAL 写放大、压缩策略 CPU 开销

🔴 瓶颈 2：Worker 处理能力
   - 133 文件/秒（PM 67 + MR 67）需要 5~6 Worker 实例
   - XML 解析是 CPU 密集型操作
   - 文件下载→MinIO→再下载→解析→入库 的多阶段链路

🟠 瓶颈 3：PostgreSQL 主库写入
   - 1000 UPDATE/秒（心跳）+ 升级/告警/参数变更写入
   - 设备表分区有帮助但仍需关注 WAL 和 autovacuum

🟠 瓶颈 4：MinIO I/O
   - 133 PUT/秒 + 133 GET/秒
   - 单日存储增长：PM ~830GB + MR ~1.66TB = ~2.5TB/天（原始文件）

🟡 瓶颈 5：网络带宽
   - ACS 入站 + Worker 文件传输 + DB 写入 ≈ 230 MB/s
```

## 四、固件升级场景专项分析

### 4.1 升级任务触发流程

```
前端 POST /upgrade-tasks/batch
  → 创建 N 个 upgrade_tasks 记录 (PostgreSQL)
  → 批量 Enqueue Download RPC (Redis CmdQueue)
  → 并发发送 ConnectionRequest (HTTP Digest, sem=5)
  → 设备收到 ConnReq → 发送 Inform → ACS Dequeue Download RPC
  → 设备下载固件 (MinIO) → 安装 → Inform(TransferComplete)
  → Worker 更新 upgrade_task 状态
```

### 4.2 升级场景负载叠加

假设同时升级 10% 的设备（仅在 Inform 时执行，不会同时全量）：

| 规模 | 升级设备数 | 额外 ACS 会话/秒 | MinIO 固件下载/秒 | 固件带宽 |
|------|:---------:|:----------------:|:----------------:|:--------:|
| 1,000 | 100 | +1.7 | 1.7 | ~85 MB/s |
| 5,000 | 500 | +8.3 | 8.3 | ~415 MB/s |
| 10,000 | 1,000 | +16.7 | 16.7 | ~835 MB/s |
| 30,000 | 3,000 | +50 | 50 | **~2.5 GB/s** |
| 60,000 | 6,000 | +100 | 100 | **~5 GB/s** |

> 固件包大小假设 50MB，设备通过 MinIO URL 直接下载。

### 4.3 升级期间的关键风险

1. **MinIO 带宽爆满**：60K 规模升级 10%，固件下载需 5GB/s，远超单实例能力
2. **ACS 会话叠加**：升级 Inform 比普通心跳会话更长（含 Download RPC 往返）
3. **PostgreSQL 写放大**：upgrade_tasks 状态频繁 UPDATE
4. **NATS 消息积压**：transfer_complete 事件突增

### 4.4 升级优化建议

- **分批升级**：限制同时升级比例 ≤5%，使用 `BatchUpgradeRequest.Concurrency` 控制
- **固件 CDN**：≥10K 规模在 MinIO 前加 CDN/Nginx 缓存层
- **夜间窗口**：将升级安排在 PM/MR 低峰期（避开 15 分钟边界）
- **连接请求限流**：ConnReq 并发已限制为 5（代码中 sem channel），≥30K 可调到 10~20

## 六、部署架构建议

### 6.1 规模：1,000 基站（试点）

```
┌────────────────────────────────────────────────┐
│               单服务器部署 (8C16G)                │
├────────────────────────────────────────────────┤
│  omcgo-app ×1    (REST API)                     │
│  omcgo-acs ×1    (TR-069 ACS)                   │
│  omcgo-worker ×2 (PM/MR 处理)                   │
│  PostgreSQL ×1   (主库 + TimescaleDB 扩展)       │
│  Redis ×1        (Standalone)                   │
│  NATS ×1         (JetStream)                    │
│  MinIO ×1        (单节点, 500GB SSD)             │
│  Nginx ×1        (反向代理 + TLS)                │
├────────────────────────────────────────────────┤
│  磁盘: 1TB SSD                                  │
│  网络: 千兆                                      │
│  CPU: 8 核足够                                   │
│  内存: 16GB (PG 8GB + 应用 4GB + Redis 2GB)      │
```

## 七、高可用设计

### 7.1 各组件 HA 方案总结

| 组件 | HA 方案 | RTO | RPO | 适用规模 |
|------|---------|:---:|:---:|:--------:|
| **omcgo-app** | 多实例无状态 + LB 健康检查 | 0s | 0 | 全部 |
| **omcgo-acs** | 多实例无状态 + LB 一致性哈希 | ~5s (CPE 重连) | 0 | ≥10K |
| **omcgo-worker** | 多实例 + NATS Queue Subscribe | 0s (自动接管) | 0 | 全部 |
| **PostgreSQL** | Patroni + 流复制 | ~30s | 0 (同步) | ≥10K |
| **TimescaleDB** | 同 PostgreSQL | ~30s | 0 | ≥10K |
| **Redis** | Cluster 6 节点 (3M+3S) | ~5s | 极少量丢失 | ≥10K |
| **NATS** | 3 节点 JetStream Cluster | ~5s | 0 (R=3) | ≥10K |
| **MinIO** | 纠删码 4+ 节点 | 0s | 0 | ≥30K |

### 7.2 故障场景分析

| 故障 | 影响 | 恢复 | 数据丢失 |
|------|------|------|---------|
| ACS 实例宕机 | 进行中 TR069 会话中断 | LB 自动摘除；设备超时后重连（30~120s）；命令在 Redis 不丢失 | 无 |
| Worker 实例宕机 | 正在处理的 PM/MR 文件暂停 | NATS 未 ACK 消息自动重投给其他 Worker（AckWait 超时） | 无 |
| App 实例宕机 | 前端 API 部分失败 | LB 自动切换；无状态，即时恢复 | 无 |
| PostgreSQL 主宕 | 所有写操作暂停 | Patroni 30s 内提升备库；连接池自动重连 | 0 (同步复制) |
| TimescaleDB 主宕 | PM/MR/KPI 写入暂停 | 同上；Worker NATS 消息不 ACK，等恢复后重新消费 | 0 |
| Redis 节点故障 | 部分会话/心跳键失效 | Cluster 自动提升副本（~5s）；设备下次 Inform 重建会话 | 极少 |
| NATS 节点故障 | 消息投递短暂延迟 | JetStream 跨节点复制；消费者自动重连从上次 ACK 恢复 | 0 |
| MinIO 节点故障 | 文件读写短暂延迟 | 纠删码自动修复；降级模式继续服务 | 0 |
| **全机房断电** | 全部中断 | 基站本地缓存 PM/MR 文件；恢复后突发重连（需准入控制） | PM/MR 可能丢 1 个周期 |

### 7.3 突发重连保护（掉电恢复）

当大规模断电恢复时，可能出现全量基站同时发送 Bootstrap/Periodic Inform：

| 规模 | 瞬时 Inform 数 | ACS 准入控制 | 恢复时间 |
|------|:-------------:|:------------:|:--------:|
| 1,000 | 1,000 | max=10,000，无影响 | <30s |
| 5,000 | 5,000 | 无影响 | <30s |
| 10,000 | 10,000 | 达到上限，需排队 | ~1min |
| 30,000 | 30,000 | 超出上限 3x | ~3min |
| 60,000 | 60,000 | 超出上限 6x | ~6min |

> **建议**：≥30K 规模需将 ACS `max_concurrent` 提升到 30,000~50,000，并增加 ACS 实例数。同时 ACS 前 LB 配置连接排队（而非拒绝）。

## 九、关键优化建议

### 9.1 必须实施的优化（≥30K）

| 优化项 | 说明 | 影响 |
|--------|------|------|
| **TSDB 独立部署** | TimescaleDB 从 PostgreSQL 主实例分离到独立服务器 | 避免 PM/MR 写入影响设备管理/告警等 OLTP 操作 |
| **TSDB 参数调优** | shared_buffers=32GB, max_wal_size=16GB, wal_compression | 写入吞吐提升 3~5x |
| **Worker COPY 攒批** | 多个 PM 文件的 counter 攒够 5000 行后一次 COPY | 减少 COPY 次数，提升 TSDB 写入效率 |
| **MinIO 生命周期** | PM/MR 原始 XML 文件 30 天自动清理 | 防止存储无限增长 |
| **万兆网络** | 应用层和数据层间万兆互联 | 消除文件传输瓶颈 |

### 9.2 建议实施的优化（≥10K）

| 优化项 | 说明 |
|--------|------|
| **ACS 一致性哈希 LB** | 同一设备始终路由到同一 ACS 实例，减少 Redis session 交互 |
| **心跳 DB 写入批量化** | 累积 100~500 个设备心跳后批量 UPDATE，减少 PG 事务数 |
| **连续聚合延迟刷新** | pm_counters_hourly 改为每小时定时刷新而非实时 |
| **Prometheus 指标完善** | 监控 ACS 并发会话数、Worker 处理延迟、NATS consumer lag、TSDB 写入速率 |

### 9.3 长期演进建议（≥60K 或 100K+）

| 优化项 | 说明 |
|--------|------|
| **MR 数据迁移到 ClickHouse** | mr_records JSONB 查询在 100K+ 规模下 ClickHouse 更优 |
| **NATS → Kafka** | 若 NATS JetStream 出现分区问题或需要严格有序消费 |
| **TimescaleDB 分布式超表** | 多节点 TimescaleDB，按 device_id 分片 |
| **读写分离** | PostgreSQL 只读副本承担 App API 读查询 |
| **Worker 按职责拆分** | PM Worker / MR Worker / Alarm Worker 独立部署，独立扩缩 |

## 十、总结

### 10.1 核心结论

1. **主瓶颈是 TimescaleDB 写入**：60K 基站下持续 54,000 行/秒，是系统第一瓶颈。需独立部署 + 深度调优。

2. **第二瓶颈是 Worker 处理能力**：133 文件/秒的 XML 解析 + COPY 是 CPU 密集型操作，需 5~6 Worker 实例。

3. **ACS 引擎不是瓶颈**：Go goroutine 模型下，60K 基站仅产生 ~1,400 并发会话，单实例可承受。但需 2~3 实例保障 HA 和突发恢复。

4. **Redis/NATS 完全不是瓶颈**：两者均有 100x 以上的余量。

5. **存储增长是运维挑战**：60K 规模日增 ~286GB（TSDB）+ ~1.73TB（MinIO），90 天 TSDB ~5.4TB + MinIO ~156TB（无清理策略时）。

### 10.2 成本效益分析

| 规模 | 月度基础设施成本估算（云） | 每基站成本 |
|------|:-----------------------:|:---------:|
| 1,000 | ~¥2,000 | ¥2.0 |
| 5,000 | ~¥8,000 | ¥1.6 |
| 10,000 | ~¥20,000 | ¥2.0 |
| 30,000 | ~¥80,000 | ¥2.7 |
| 60,000 | ~¥180,000 | ¥3.0 |

> 成本随规模非线性增长，主要因存储和 TimescaleDB 高配需求。30K 是成本效率拐点。

### 10.3 一句话建议

- **≤10K**：单体部署 + PostgreSQL/TimescaleDB 共享实例，简单可靠
- **10K~30K**：Kubernetes 化 + TSDB 独立 + Redis Cluster，标准 HA
- **≥30K**：全组件集群化 + TSDB 深度调优 + MinIO 分布式 + 万兆网络，精细化运维
