# 设备升级与回退流程设计文档

> **定位**：面向 Go 重构的权威参考文档，描述升级/回退的**公共流程**与**平台差异点**。
>
> **核心设计原则**：升级流程 80% 以上逻辑是公共的，平台差异通过适配器隔离。

---

## 一、文档范围

**本文档覆盖**：
- 标准 4G/5G 基站（eNB/gNB）的 IMG 软件主镜像升级
- 软件版本回退（Rollback）

**不在本文档范围**：
- NXP 分布式基站（EU/RU/BU 分体升级）
- AP 升级（taskType=7，独立路径）
- PATCH/BIOS/FPGA 等类型（共用状态机框架，差异仅在权限码和 FileType，按需补充）

## 二、升级文件管理

### 2.1 文件类型

| file_type | 含义 | 存储目录 |
|-----------|------|----------|
| 0 | IMG 软件主镜像（本文重点） | `software_path/upgrade/` |
| 1 | PATCH 补丁包 | `software_path/ca/` |
| 6 | FPGA | `software_path/fpga/` |

### 2.2 文件入库流程（公共）

所有类型的升级文件共用同一套入库流程：

```
上传请求
  → ① 磁盘空间检查（达到告警阈值则拒绝）
  → ② 版本唯一性校验（file_type + version 唯一）
  → ③ 确定物理存储目录（按 file_type 分目录）
  → ④ 保存文件（本地文件系统或 MinIO）
  → ⑤ 计算 MD5
  → ⑥ 写入 update_file_info 表
  → ⑦ 若开放给运营商 → 写入版本通知表
  → ⑧ 记录操作日志，返回 MD5
```

### 2.3 文件列表查询过滤

| 过滤维度 | 说明 |
|----------|------|
| `is_gnb` | 4G（0）/ 5G（1）|
| `file_type` | 升级文件类型 |
| `product` | 产品名称匹配 |
| `operator_code` | 运营商（权限过滤）|
| `user_type` | admin / beta / 普通（可见范围不同）|

## 三、升级状态机（公共）

### 3.1 状态定义

升级流程采用**步骤驱动的状态机**，任务调度器循环推进 `nextStep`。

**公共步骤链（4G 和 5G 共享前 5 步）**：

```
checkDevicePermission → verifyDeviceOnline → sendDownloadCmd
  → waitDownloadComplete → waitTransferComplete → [5G: waitUpgradeFinish]
```

### 3.2 主任务状态

| 状态 | 含义 |
|------|------|
| `IN_PROGRESS` | 升级进行中 |
| `END` | 升级已结束 |
| `SUSPEND` | 任务被手动挂起 |

### 3.3 子任务状态

| 状态 | 含义 |
|------|------|
| `IN_PROGRESS` | 设备升级进行中 |
| `WAITTING` | 等待设备上线或文件续传 |
| `END` | 升级结束 |

### 3.4 子任务结果

| 结果 | 含义 |
|------|------|
| `SUCCESS` | 成功 |
| `FAILURE` | 失败 |
| `DEFAULT` | 默认（等待中）|

### 3.5 内存控制标志

| 标志 | 含义 |
|------|------|
| `TerminateFlag` | 任务被终止 |
| `SuspendFlag` | 任务被挂起 |
| `WaittingFlag` | 等待设备重连 |

## 四、升级公共流程

以下流程 **4G 和 5G 完全共享**，是重构的核心公共代码。

### 4.1 任务关键参数

| 字段 | 说明 |
|------|------|
| `taskId` | 任务唯一标识 |
| `taskType` | 任务类型（见第八章） |
| `productType` | 设备产品类型（用于区分平台） |
| `filename` | 升级文件名 |
| `filesize` | 文件大小（字节） |
| `md5` | 文件 MD5 |
| `rawMode` | 保留配置标志：`"false"` = 保留，`"true"` = 不保留 |
| `commandKey` | Download 命令唯一键（同时用于 TransferComplete 匹配） |
| `isGnb` | 是否 5G：`"1"` = 5G，`"0"` = 4G |
| `userCode` | 操作用户 |

### 4.2 Step 0：权限检查（公共）

```
校验用户对设备的升级权限（featureCode）
  IMG 升级：CODE_ENB_UPGRADE_IMAGE（4G）/ CODE_GNB_UPGRADE_IMAGE（5G）
  PATCH：CODE_ENB_UPGRADE_PATCH
  FPGA：CODE_ENB_UPGRADE_FPGA
  回滚：CODE_ENB_ROLLBACK（4G）/ CODE_GNB_ROLLBACK（5G）

  无权限 → 子任务 FAILURE，结束
```

> **平台差异点**：仅权限码因 4G/5G 不同，校验逻辑完全相同。

### 4.3 Step 1：设备在线检查（公共）

```
① 冲突检查：是否有其他任务正在升级此设备（查 upgrading_info）
   已有任务 → 子任务失败，结束

② 标记设备正在升级（写入 upgrading_info）

③ 检查设备在线状态
   在线 → 进入 Step 2
   离线 → 记录等待时间，子任务状态 WAITTING
          轮询等待设备上线：
            上线 → 进入 Step 2
            超过 waitEnbReconnectTime（默认 1 小时）→ 超时失败
```

### 4.4 Step 2：下发 Download 命令（公共）

```
① 更新主任务/子任务状态 → IN_PROGRESS

② 构造 commandKey
   格式："Download Upgrade," + UUID
   DXDF 平台特殊：UUID 截取前 12 位

③ 确定 TR069 FileType
   FIRMWARE      → "1 Firmware Upgrade Image"（主镜像，本文核心场景）
   BIOS_UPGRADE  → "0 Firmware Upgrade Bios"
   PATCH         → "X {OUI} Software Upgrade Patch"
   FPGA          → "Firmware Upgrade Fpga"

④ 构造 Download URL
   基础：{downloadRootUrl}/downloadFileServlet?filename={filename}
   附加：&task_id={taskId}&taskType={taskTypeStr}&smallCellCode={cellCode}
   注意：eNB/gNB 使用转义 \& 拼接，NB-IOT/DXDF 使用普通 & 拼接

⑤ 构造 TR069 Download 报文
   ┌──────────────┬─────────────────────────────────┐
   │ CommandKey    │ commandKey                       │
   │ FileType      │ TR069 FileType 字符串            │
   │ URL           │ 构造的下载地址                    ���
   │ Username      │ 配置文件中的下载认证用户名         │
   │ Password      │ 配置文件中的下载认证密码           │
   │ FileSize      │ filesize（字节）                  │
   │ TargetFileName│ filename                         │
   │ Md5           │ md5                              │
   │ RawMode       │ rawMode（保留配置标志）            │
   └──────────────┴─────────────────────────────────┘

⑥ 通过命令队列下发 Download，设置 Redis TransferComplete 等待标识
   uuid = "TransferCompleteReq_" + commandKey.split(",")[1]
   Redis: hmset(uuid, {"complete": "0"})

⑦ 等待 DownloadResponse
   超时 → 子任务失败，清理任务
   FaultCode → 子任务失败
   成功 → 进入 Step 3
```

**保留配置（rawMode）说明**：
- 由前端 `isKeepConfig` 字段决定：`"1"` → rawMode=`"false"`（保留），`"0"` → rawMode=`"true"`（不保留）
- 写入 Download SOAP 报文的扩展字段 `<RawMode>`

### 4.5 Step 3：等待文件下载完成（公共）

通过 Redis Key `DownloadingFlag[taskId_cellCode]` 监控下载进度：

| Redis 值 | 含义 | 处理 |
|-----------|------|------|
| null | 设备尚未请求下载 | 等待，超时（默认 10 分钟）→ 失败 |
| `"0"` | 正在下载中 | 继续等待 |
| `"2"` | 下载中断（断点续传） | 等待恢复，超时（默认 10 分钟）→ 失败 |
| `"3"` | 升级文件不存在 | 立即失败 |
| 其他 | 下载完成 | 进入 Step 4 |

同时检查：
- 是否提前收到了 TransferComplete（含 faultCode → 失败）
- 任务是否被终止（TerminateFlag）

### 4.6 Step 4：等待 TransferComplete（公共）

```
从 jobParam 中取出 commandKey，构造 Redis 匹配键：
  uuid = "TransferCompleteReq_" + commandKey.split(",")[1]
  订阅该 Redis key 等待 TR069 进程写入结果

WAIT → 继续等待

TIMEOUT →
  容错机制：向设备查询当前运行版本，与目标版本比对
    版本一致 → 视为升级成功（TransferComplete 可能因网络丢失）
    版本不一致 → 升级失败
  无论结果：清理任务

FINISHED →
  FaultCode → 子任务失败，清理任务
  成功 →
    【4G】子任务结束，SUCCESS，清理任务   ← 4G 终态
    【5G】进入 Step 5（waitUpgradeFinish）← 5G 继续
```

> **这是 4G 与 5G 的唯一分叉点**：4G 在此结束，5G 继续等待升级完成事件。

## 五、5G 专有步骤

### 5.1 sendDownloadCmd 后的额外操作

5G 在 Step 2（sendDownloadCmd）DownloadResponse 成功后，额外执行：

```
预删除 Redis 标识：del({cellCode}_upgrade_finish)
→ 防止上次升级残留的 102 事件标识干扰本次判断
```

### 5.2 waitDownloadComplete 的差异

5G 下载完成时**不删除** TransferComplete Redis 标识（4G 会删除），因为 5G 的 TransferComplete 仅表示文件下载完成，还需后续步骤。

### 5.3 Step 5：等待升级完成事件（5G 专有）

```
初始化：构造 TR069OperParam
  deviceCode = cellCode
  operType = UPGRADE_FINISH
  向 TR069 进程发起订阅，监听 102 UPGRADE FINISH 事件

WAIT → 继续轮询

TIMEOUT →
  此阶段超时不做版本比对，直接失败
  → 失败：ShengJiChaoShiWeiShouDaoShengJiWanChengBiaoShi

FINISHED →
  upgradeStatus == "2" 或 "3" → 升级失败
    failureReason 非空 → 记录具体原因
    failureReason 为空 → 记录 "Fail"
  其他值（含 "1"） → 升级成功
  清理任务
  【5G 升级至此完成】
```

## 六、4G 与 5G 差异精确对比

| 环节 | 公共/差异 | 4G | 5G |
|------|-----------|----|----|
| 权限码 | 差异 | `CODE_ENB_*` | `CODE_GNB_*` |
| checkDevicePermission | **公共** | 相同 | 相同 |
| verifyDeviceOnline | **公共** | 相同 | 相同 |
| sendDownloadCmd | **公共** + 5G 附加 | 相同 | 额外预删除 `{cellCode}_upgrade_finish` |
| URL 拼接 | **公共** | 相同 | 相同 |
| RawMode（保留配置） | **公共** | 相同 | 相同 |
| commandKey 生成 | **公共** | 相同 | 相同 |
| waitDownloadComplete | **公共** + 差异 | 完成时删除 TC 标识 | 完成时**不删除** TC 标识 |
| waitTransferComplete 初始化 | **公共** | 相同 | 相同 |
| waitTransferComplete 超时容错 | **公共** | 版本比对 | 版本比对 |
| waitTransferComplete 成功 | **分叉点** | 子任务结束 | 进入 waitUpgradeFinish |
| waitUpgradeFinish | 5G 专有 | 无此步骤 | 等待 `102 UPGRADE FINISH` |
| 升级完成判定 | 差异 | TC 无错误即成功 | 102 事件 upgradeStatus 为成功 |

> **重构建议**：公共流程提取为 `BaseUpgradeExecutor`，4G/5G 通过策略模式或钩子方法覆盖差异点。

## 七、软件版本回退（Rollback）

回退是**独立于升级的流程**，不走 Download 路径，通过 TR069 SetParameterValues 触发设备侧回退。

### 7.1 回退公共流程

```
创建回退任务（taskType=2）
  │
  ├─ 检查任务是否已终止/挂起
  ├─ 权限检查：4G → CODE_ENB_ROLLBACK，5G → CODE_GNB_ROLLBACK
  ├─ 冲突检查：有其他任务正在执行 → 失败
  ├─ 标记设备正在回退（upgrading_info）
  │
  ├─ [条件] 查询回退可用性（仅 4G 普通���台需要）
  │   GetParameterValues（ROLLBACK_ENABLE）
  │   enable=false → 失败（设备不支持回退）
  │
  ├─ SetParameterValues（触发回退）
  │   超时 → 入等待队列，等待重连后恢复
  │   FaultCode → 失败
  │   成功 → 等待重启
  │
  ├─ 等待 RebootComplete
  │   成功 → 子任务 SUCCESS
  │   超时 → 子任务 FAILURE
  │
  └─ finally：清除 upgrading_info 标记
```

### 7.2 平台差异点

| 差异维度 | 4G 普通（Intel/高通） | 5G / DXDF / NB-IOT |
|----------|----------------------|---------------------|
| 是否需要先查询回退可用性 | **需要**（GetValues 查 ROLLBACK_ENABLE） | **不需要**（直接下发） |
| SetValues 参数路径 | `ROLLBACK_CONTROL`（私有路径，平台映射） | 5G: `Device.SoftwareCtrl.ActivateEnable`（固定）；DXDF: `Device.DeviceInfo.ACTIVATE_ENABLE`；NB-IOT: `ROLLBACK_CONTROL` |
| SetValues 参数值 | 高通=`"true"`，Intel=`"1"` | `"1"` |

> **参数路径说明**：上述路径为逻辑抽象路径，实际私有路径通过平台参数映射表动态获取。

### 7.3 断线等待恢复机制（公共）

当 GetValues 或 SetValues 阶段设备无响应时，不立即失败：

```
超时 → 写入等待重连队列（upgradeWaitDeviceMap）
        JSON：{ taskId, upgradeType:"2", waitTimeBegin }
        保留 upgrading_info 标记

设备重新上线 → 调度器触发重连恢复：
    取出等待队列中的 taskId
    按原流程重试 GetValues / SetValues / RebootComplete
    finally：清除 upgrading_info
```

## 十二、重构架构建议

### 12.1 公共/差异分层

```
┌─────────────────────────────────────────────────┐
│  升级任务管理层（公共）                            │
│  创建任务 / 查询进度 / 终止任务 / 挂起恢复          │
└──────────────────┬──────────────────────────────┘
                   │
┌──────────────────▼──────────────────────────────┐
│  升级执行引擎（公共状态机）                         │
│  Step 0-4：权限→在线→Download→等待下载→等待TC      │
│  ↓ 通过钩子方法注入平台差异                        │
│    onDownloadResponseSuccess()  → 5G: 删除旧标识  │
│    onDownloadComplete()         → 5G: 不删TC标识   │
│    onTransferCompleteSuccess()  → 5G: 继续Step5    │
│                                 → 4G: 结束         │
└──────────────────┬──────────────────────────────┘
                   │ 仅 5G 进入
┌──────────────────▼──────────────────────────────┐
│  5G 专有步骤                                      │
│  Step 5: waitUpgradeFinish（102 事件）            │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│  回退执行引擎（独立流程）                          │
│  权限→冲突→[查询可回退性]→SetValues→等待重启       │
│  ↓ 平台适配器                                     │
│    needCheckRollbackEnable()  → 4G普通: true       │
│    getRollbackParamPath()     → 按平台映射          │
│    getRollbackParamValue()    → 高通:"true"/其他:"1"│
└─────────────────────────────────────────────────┘
```

### 12.2 对齐现有代码模式

| 设计要素 | 对齐的现有模式 | 参考位置 |
|----------|---------------|---------|
| 状态机 | software/state_machine.go 的 validTransitions 模式 | internal/software/ |
