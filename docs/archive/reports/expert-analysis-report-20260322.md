## 三、各专家核心发现详述

### 3.1 架构专家 — 评分 8.0/10

**核心优势**：
- 严格的 DAG 依赖结构，完全无循环依赖
- 87% 模块遵循标准三层分层（handler → service → repository）
- EventBus 41 个主题全部遵循 `domain.action.detail` 层级命名
- ACS 引擎高度独立，仅依赖 3 个模块，可水平扩展

**核心问题**：
- 4 个模块缺 service 层：northbound、filemanager、interop、nedirect
- bootstrap 位于 internal/core/（应用级代码不应在库级位置）
- app 部署单元集成 30 个模块，无模块初始化失败降级机制

### 3.2 Go 工程专家 — 评分 4.2/5

**核心优势**：
- SQL 安全满分 — Squirrel 全覆盖，零注入风险

- 命名规范 100% 符合 Go 习惯用语
- defer Close() 覆盖所有资源（51 处 rows.Close）

**核心问题**：

- 后台 goroutine 使用 `context.Background()` 无法 graceful shutdown

## 五、关键结论

### 项目优势（值得保持的）

1. **架构设计严谨** — 无循环依赖、严格分层、EventBus 解耦
2. **SQL 安全零风险** — Squirrel 全覆盖，禁止 ORM 的决策正确
3. **运营商抽象层完美** — Carrier 接口 10 方法完整，零 hardcode
4. **TR-069 协议合规** — SOAP/XML 编解码完全合规，会话状态机完整
5. **日志与关闭机制** — Zap 结构化日志 + request_id 贯穿 + 优雅关闭

### 项目短板（需要改进的）

1. **多运营商支持** — CTCC/CUCC 仅骨架，是最大业务风险
2. **测试覆盖** — 33% 覆盖率，task/core 模块高风险
3. **安全细节** — 文件上传认证禁用、RBAC 不完整、Digest Auth 弱
4. **数据规模准备** — PM 数据未分层、Redis 缓存无 TTL、JSONB 无索引
5. **可观测性** — 健康检查虚假、业务指标缺失、OTEL 未启用

### 一句话总结

> **OMC 项目工程基础扎实（架构 8.0、Go 工程 4.2/5、SQL 安全满分），但在多运营商业务覆盖（62%）、测试深度（72.4/100）和安全细节（7.5/10）上存在明显短板，需要按 P0→P1→P2 优先级在 4 周内完成关键修复，Phase 3 补齐 CTCC/CUCC 适配和北向接口可靠性。**
