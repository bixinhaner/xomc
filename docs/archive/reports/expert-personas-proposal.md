# OMC 项目 CLAUDE.md 专家角色体系建议报告

> 编写日期：2026-03-22
> 目标：为 CLAUDE.md 新增专家角色（Expert Personas），使 AI 在不同场景下以对应领域专家的视角审视代码、提供建议，从而提升代码质量与业务看护能力。

---

## 1. 为什么需要专家角色

当前 CLAUDE.md 提供了**通用开发规范**，但缺乏**领域深度指导**。实际开发中，不同类型的变更需要不同维度的审视：

| 场景 | 当前问题 | 期望效果 |
|------|---------|---------|
| 修改 ACS 会话状态机 | AI 不了解 TR-069 协议约束，可能破坏会话时序 | 协议专家视角：检查状态转换完整性、SOAP 信封合规性 |
| 新增数据库迁移 | AI 不考虑 10 万级基站的查询性能 | 数据专家视角：索引策略、分区方案、TimescaleDB 特性 |
| 修改告警去重逻辑 | AI 不理解运营商对告警 SLA 的要求 | 业务专家视角：告警生命周期、关联规则、升级策略 |
| 添加新 API 端点 | AI 只关注功能正确性 | 安全专家视角：RBAC 权限检查、输入验证、审计日志 |

**核心理念**：每个专家角色不是独立的 Agent，而是一组**领域知识 + 审查清单 + 决策原则**，嵌入 CLAUDE.md 后，AI 在相关场景下自动激活对应视角。

---

## 2. 推荐专家角色总览

基于项目实际业务复杂度，推荐 **9 个专家角色**（比原始提议增加了数据管道专家和前端专家，合并了部分角色）：

| # | 角色 | 覆盖范围 | 激活场景（触发条件） |
|---|------|---------|-------------------|
| 1 | 架构专家 | 系统设计、模块边界、部署拓扑、扩展性 | 新增模块、跨模块依赖、部署变更 |
| 2 | Go 工程专家 | Go 语言最佳实践、并发安全、性能优化 | 所有 Go 代码变更 |
| 3 | TR-069 协议栈专家 | CWMP 协议、SOAP/XML、RPC 方法、会话管理 | `internal/acs/` 及 `pkg/tr069/` `pkg/soap/` 变更 |
| 4 | 电信业务专家 | 3GPP 标准、运营商规范、功能域业务规则 | F01-F10 业务逻辑变更 |
| 5 | 数据与存储专家 | PostgreSQL/TimescaleDB/Redis/NATS/MinIO | 数据库迁移、查询优化、缓存策略、消息流 |
| 6 | 前端专家 | React/TypeScript/Ant Design/状态管理 | `omcmb/webcode/` 代码变更 |
| 7 | 测试专家 | 单元测试、E2E、压测、CPE 模拟 | 测试代码编写与审查 |
| 8 | 安全合规专家 | 认证鉴权、RBAC、输入验证、运营商安全规范 | 认证/权限/API 安全相关变更 |
| 9 | 运维与可观测性专家 | 部署、监控、日志、链路追踪、容量规划 | 部署配置、监控指标、日志策略变更 |

## 3. 各专家角色详细设计

### 3.1 架构专家（Architecture Expert）

**职责**：守护系统整体架构的一致性和演进方向。

**核心知识**：
- 模块化单体架构 — 当前阶段不拆微服务，按功能域内聚
- 三个部署单元：app（:8080）、acs（:7547）、worker（后台）
- 模块间通信：同进程直接调用 + EventBus（NATS JetStream）
- 扩展路线：10 万 → 100 万基站时按功能域渐进拆分

**审查清单**：
- [ ] 新模块是否遵循 handler → service → repository 分层
- [ ] 跨模块依赖是否通过接口而非直接引用
- [ ] 是否引入了循环依赖
- [ ] EventBus 事件主题是否遵循层级命名（`domain.action.detail`）
- [ ] 是否不必要地耦合了 app/acs/worker 三个部署单元
- [ ] 新的公共组件放置位置是否合理（`internal/core/` vs `pkg/`）

**决策原则**：
- 优先内聚（一个模块完成一个业务域），而非方便（跨模块共享代码）
- 模块间耦合通过 EventBus 事件解耦，不通过直接依赖
- `internal/core/` 放业务无关的基础设施，`pkg/` 放可独立复用的库

---

### 3.2 Go 工程专家（Go Engineering Expert）

**职责**：确保 Go 代码质量、并发安全性和性能。

**核心知识**：
- Go 1.25 特性与最佳实践
- 并发模型：goroutine + channel + sync 原语
- 内存管理：避免大对象逃逸、合理使用 sync.Pool
- 接口设计：小接口、消费者定义接口

**审查清单**：
- [ ] 错误处理：`fmt.Errorf("context: %w", err)`，不裸 panic
- [ ] 并发安全：共享状态是否有 mutex/channel 保护
- [ ] Context 传递：是否正确传播 ctx，长操作是否响应取消
- [ ] 资源释放：defer Close()、连接池归还、goroutine 泄漏检查
- [ ] 接口设计：是否符合「接受接口，返回具体类型」原则
- [ ] 命名规范：导出 PascalCase，未导出 camelCase，包名小写单数
- [ ] SQL 构建：Squirrel 构建，禁止字符串拼接，禁止 ORM

**性能关注点**：
- ACS 处理路径（热路径）：避免反射、减少内存分配、使用预编译模板
- 批量操作：使用 Squirrel 的批量 INSERT/UPDATE
- 连接池：pgxpool 配置合理的 MaxConns/MinConns

---

### 3.3 TR-069 协议栈专家（TR-069 Protocol Stack Expert）

**职责**：保障 TR-069/CWMP 协议实现的正确性和合规性。

**核心知识**：
- **TR-069 Amendment 6**（核心协议规范）
- **TR-098/TR-181**（数据模型标准 — InternetGatewayDevice / Device:2）
- **SOAP 1.1 + CWMP 命名空间**
- **会话状态机**：Inform → (事务循环) → Empty Response → 结束
- **12 种 RPC 方法**：GetParameterValues / SetParameterValues / GetParameterNames / AddObject / DeleteObject / Download / Upload / Reboot / FactoryReset / GetRPCMethods / Inform / TransferComplete

**审查清单**：
- [ ] SOAP 信封：命名空间声明是否完整（`cwmp:`, `soap:`, `xsd:`, `xsi:`）
- [ ] cwmpID：请求/响应的 `<cwmp:ID>` 必须匹配
- [ ] 会话状态转换：是否覆盖所有合法转换路径，异常路径是否安全降级
- [ ] Inform 事件码：是否正确处理 0-BOOTSTRAP / 1-BOOT / 2-PERIODIC / 6-CONNECTION REQUEST 等
- [ ] 参数路径格式：`Device.X_VENDOR.` vs `InternetGatewayDevice.` 适配
- [ ] 文件传输：Download/Upload 的 URL 生成、认证、超时设置
- [ ] 会话超时：Redis TTL 设置是否合理（默认 5 分钟）
- [ ] 速率限制：per-device 限流 + 全局准入控制的协同
- [ ] Empty HTTP Response（204/空 body）：用于释放 CPE 会话

**协议陷阱**（基于项目经验）：
- CPE 可能在 Inform 中携带多个事件码，必须全部处理
- 某些 CPE 不支持 Connection Request 主动连接，需降级为轮询模式
- SOAP Fault 响应必须保持正确的 XML 结构，否则 CPE 可能进入异常循环
- 不同厂商 CPE 的参数路径可能有私有扩展（`X_VENDOR_`前缀）

### 3.4 电信业务专家（Telecom Domain Expert）

**职责**：确保功能实现符合运营商业务需求和行业标准。

**核心知识**：
- **运营商差异**：CMCC/CTCC/CUCC 在参数映射、告警规范、性能指标上的差异
- **3GPP 标准**：32.435（PM XML）、32.422（MR）、32.111（告警）
- **功能域 F01-F10**：各域业务规则、数据流向、运营商定制点

**各功能域关键业务规则**：

| 功能域 | 核心业务规则 |
|--------|------------|
| F01 南向接口 | ACS 必须支持多厂商 CPE 同时在线；会话并发数受限于 Redis 和 goroutine 池 |
| F02 配置管理 | 三级回退（产品→OUI→运营商默认）；配置模板支持批量下发和回滚 |
| F03 性能管理 | PM 文件格式遵循 3GPP 32.435；KPI 计算支持多级聚合（设备→站点→区域→网络）|
| F04 告警管理 | 告警去重窗口、关联规则、升级策略必须可配置；活动告警必须持久化 |
| F05 测量报告 | MRO/MRS/MRE 三种类型；RSRP/RSRQ/SINR 测量值解析 |
| F06 核心管理 | 设备生命周期（发现→注册→激活→运行→退服）；固件升级需灰度策略 |
| F09 自动开站 | 零接触部署流程：CPE 首次 Inform → 模板匹配 → 参数下发 → 激活确认 |

**运营商适配原则**：
- 所有运营商差异通过 `Carrier` 接口适配器实现
- 禁止 `if carrier == "cmcc"` 硬编码
- 新增运营商只需实现 Carrier 接口，不修改核心逻辑

---

### 3.5 数据与存储专家（Data & Storage Expert）

**职责**：保障数据层的正确性、性能和可扩展性。

**核心知识**：
- **PostgreSQL 16**：业务数据主存储，UUID 主键，JSONB 扩展字段
- **TimescaleDB**：PM 计数器、KPI 时序数据、告警历史的超表（hypertable）
- **Redis 7**：会话存储（Hash+TTL）、命令队列（Sorted Set）、缓存（三级缓存 L1→L2→L3）
- **NATS JetStream**：事件流、异步任务分发
- **MinIO**：PM/MR 文件、固件包、备份文件的对象存储

**审查清单**：
- [ ] 迁移文件：编号连续、有 up/down 配对、幂等性
- [ ] 索引策略：高频查询字段是否有索引，复合索引顺序是否正确
- [ ] 分区/超表：时序数据是否使用 TimescaleDB hypertable
- [ ] 连接池：pgxpool 配置是否合理（MaxConns = CPU 核数 × 2 + 磁盘数）
- [ ] Redis 键命名：遵循 `domain:entity:{id}` 层级格式
- [ ] Redis TTL：所有缓存键必须设置 TTL，避免内存泄漏
- [ ] 事务边界：写操作是否在事务内完成，是否正确处理回滚
- [ ] N+1 查询：列表接口是否避免循环查询，使用 JOIN 或批量查询
- [ ] 大批量操作：是否分批处理（BATCH_SIZE），避免长事务锁表

**容量规划基线**（10 万基站）：
- PM 计数器写入：~50,000 rows/min（高峰期）
- 活动告警：~100,000 条常驻 Redis
- 会话并发：~5,000 同时在线 CPE（ACS）
- 文件存储：~500 GB/月（PM + MR 文件）

### 3.6 前端专家（Frontend Expert）

**职责**：确保前端代码质量、用户体验和前后端一致性。

**核心知识**：
- React 19 + TypeScript 严格模式
- Ant Design 5 组件库规范
- Zustand 状态管理（userStore / deviceStore / uiStore）
- React Query 数据请求与缓存策略
- Axios 拦截器：自动 camelCase ↔ snake_case 转换、Bearer Token 注入

**审查清单**：
- [ ] 类型安全：禁止 `any`，后端响应必须定义 `BackendXxx` 接口并映射
- [ ] API 服务模式：一模块一文件（`xxxApi.ts`），导出服务对象
- [ ] Hook 模式：`useMock ? mockService : realApi` 切换
- [ ] 查询键层级：`['domain', 'action', params]`，确保缓存失效正确
- [ ] 国际化：所有用户可见文本通过 `react-intl` 处理
- [ ] 组件复用：使用 `src/components/` 现有组件，不重复造轮子
- [ ] 错误处理：API 错误通过 Axios 拦截器统一处理，页面级 ErrorBoundary
- [ ] 前后端字段映射：snake_case（后端）→ camelCase（前端）自动转换是否覆盖

---

### 3.7 测试专家（Testing Expert）

**职责**：保障测试覆盖率、测试质量和测试基础设施的可靠性。

**核心知识**：
- **单元测试**：Go table-driven tests + testify，Mock 接口实现
- **E2E 测试**：452 个 curl 用例（`e2e_verify.sh`），覆盖 10 个 Sprint
- **CPE 模拟器**：Python 实现的完整 TR-069 会话模拟（`cpe_simulator.py`）
- **压力测试**：递进式加压（200→500→1K→2K→5K 设备）

**审查清单**：
- [ ] 测试覆盖：新功能必须包含成功和失败两条路径的测试
- [ ] 测试确定性：不依赖时间、随机数、外部服务状态
- [ ] Mock 隔离：单元测试使用 in-memory Mock，不依赖真实数据库/Redis
- [ ] E2E 数据：新端点是否添加对应的 seed 数据和 E2E 用例
- [ ] 测试命名：`Test_<Function>_<Scenario>`，清晰表达意图
- [ ] 绝不禁用失败测试 — 修复它们
- [ ] 压测基线：性能变更是否需要更新压测基线数据

**测试金字塔**：
```
         /  E2E (452 cases)  \         ← 端到端：验证完整业务流
        / Integration Tests   \        ← 集成：验证模块组合
       /   Unit Tests (84 files) \     ← 单元：验证函数/方法逻辑
      ─────────────────────────────
```

### 3.8 安全合规专家（Security & Compliance Expert）

**职责**：确保系统满足运营商级安全要求。

**核心知识**：
- **认证**：CPE 认证（HTTP Basic/Digest）、管理面 JWT Token
- **授权**：RBAC 角色权限矩阵，操作级权限控制
- **运营商安全规范**：三大运营商各自的网管安全要求
- **通信安全**：HTTPS/TLS 配置、证书管理

**审查清单**：
- [ ] API 鉴权：所有管理面端点必须经过 JWT 验证中间件
- [ ] RBAC 检查：敏感操作（设备重启、固件升级、配置下发）必须校验角色权限
- [ ] 输入验证：所有外部输入（HTTP 请求参数、SOAP XML）必须验证和清洗
- [ ] SQL 注入：Squirrel 参数化查询，禁止字符串拼接
- [ ] XSS 防护：前端渲染用户输入时必须转义
- [ ] 密码安全：bcrypt 哈希存储，禁止明文日志中打印密码/Token
- [ ] 审计日志：关键操作（用户登录、设备配置变更、固件升级）必须记录审计日志
- [ ] 敏感信息：禁止在日志/错误消息中泄露设备密钥、ACS 认证信息
- [ ] 文件上传：验证文件类型和大小，防止路径遍历攻击

---

### 3.9 运维与可观测性专家（Operations & Observability Expert）

**职责**：保障系统可运维性、可观测性和故障恢复能力。

**核心知识**：
- **三个部署单元**的启停、健康检查、资源监控
- **Prometheus 指标**：ACS 会话数、RPC 延迟、队列深度、错误率
- **Zap 结构化日志**：日志级别、字段规范、日志轮转
- **OpenTelemetry 链路追踪**：请求链路、跨服务追踪
- **部署方式**：Docker Compose（开发）、Kubernetes（生产）

**审查清单**：
- [ ] 健康检查：新服务/组件是否暴露 `/health` 端点
- [ ] 指标暴露：关键操作是否注册 Prometheus 指标（计数器、直方图、仪表盘）
- [ ] 日志规范：使用 `zap.String/Int/Error` 结构化字段，禁止 `fmt.Sprintf` 拼接日志
- [ ] 错误追踪：错误是否携带 `request_id`，是否可关联到链路追踪
- [ ] 优雅关闭：新增的 goroutine/监听器是否响应 SIGTERM 信号
- [ ] 配置外置：环境相关配置（端口、DB 地址、Redis 地址）不硬编码
- [ ] 容量告警：是否设置关键资源的告警阈值（连接池使用率、队列积压、磁盘空间）
- [ ] 故障恢复：服务重启后是否能自动恢复状态（Redis 会话、NATS 消费位点）

## 4. 专家角色激活机制

建议在 CLAUDE.md 中采用**场景触发**方式，而非让 AI 同时扮演所有角色：

```
当修改的文件/模块命中以下路径时，自动激活对应专家视角：

internal/acs/**          → TR-069 协议栈专家 + Go 工程专家
internal/config/**       → 电信业务专家 + 数据与存储专家
internal/pm/**           → 电信业务专家 + 数据与存储专家
internal/alarm/**        → 电信业务专家 + 安全合规专家
internal/admin/**        → 安全合规专家 + Go 工程专家
migrations/**            → 数据与存储专家
deployments/**           → 运维与可观测性专家
omcmb/webcode/**         → 前端专家
scripts/e2e*             → 测试专家
scripts/loadtest*        → 测试专家 + 运维专家
cmd/**/main.go           → 架构专家 + 运维专家
新增模块目录             → 架构专家 + Go 工程专家
```

## 6. 总结

推荐的 9 个专家角色完整覆盖了 OMC 项目的技术栈和业务域：

