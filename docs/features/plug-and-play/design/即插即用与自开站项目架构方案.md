# 即插即用与自开站项目架构方案

## 1. 编写目的

本文基于《即插即用功能页面处理说明》和《自开站方案说明》，结合当前 `xomc` 项目架构，给出即插即用（Plug and Play，PnP）与自开站功能的落地方案。

方案目标不是复刻旧 OMC 的 JSP + Java 实现，而是把旧系统里的站型分流、策略配置、参数下发、任务状态这些能力，映射到当前项目的 React 前端、Go 后端、ACS 任务队列和参数模型体系中。

## 2. 当前项目架构认知

当前项目里和本方案直接相关的模块如下：

| 层级 | 当前实现位置 | 职责 |
|---|---|---|
| 新前端页面 | `omcmb/webcode/src/pages/device/PlugAndPlay` | 即插即用策略列表、执行状态、策略配置页 |
| 前端 API 封装 | `omcmb/frontend-core/src/services/api/provisionApi.ts` | 对接 `/api/v1/provisioning/tasks` |
| 后端自开站编排 | `omcgo/internal/provision` | 设备注册后的 provisioning 编排、模板匹配、任务状态流转 |
| 配置模板 | `omcgo/internal/config/template` | `config_templates` 增删改查、显式 dispatch |
| ACS 任务队列 | `omcgo/internal/task`、`omcgo/internal/acs` | 统一设备任务、TR069 RPC 出队与结果回写 |
| 文件传输配置 | `omcgo/internal/acs/transfercfg`、`omcgo/internal/acs/download` | Download/Upload 地址、下载服务、文件传输 |
| 设备生命周期 | `omcgo/internal/device` | `first_online_time`、`device.registered`、`device.online` 事件 |
| 老 OMC 对照 | `omcmb/original-omc` | 旧 JSP、Java action/service、TR069 path 参考 |

当前 `PlugAndPlay` 主页面已经接入真实的 `provisioning_tasks` 执行状态接口，但策略列表仍是前端 mock。页面源码中也明确标注：当前后端只暴露任务资源，没有 PnP policies 资源。因此，本方案的核心后端增量是补齐“策略聚合层”，并把策略和现有 `config_templates`、`provisioning_tasks`、`device_tasks` 串起来。

## 3. 总体设计原则

1. 站型在入口层分流，不在一个大表单里靠站型下拉硬切。
2. 产品类型或产品型号是站型内部的能力分支，用于控制字段、默认值、可选模块和模板匹配。
3. 页面策略是业务聚合对象，参数 XML 文件是执行对象，不能把所有 PnP 策略字段都塞进 TR069 SPV 模板。
4. 后端执行统一走现有 `provision` + `task` + `acs` 架构，不新建一套 MethodTaskMgr 风格的任务系统。
5. 参数自开站统一走 `auto_start` XML 文件生成与 ACS `Download` 下发路径，不走 `SetParameterValues` 模板下发。
6. 软件升级、License、自开站参数配置是三个模块，但共享一个策略、一个执行记录、多个子任务。

## 4. 页面方案

### 4.1 路由与站型分流

旧 OMC 页面按 JSP 拆为：

| 站型 | 旧主页面 | 旧配置页 |
|---|---|---|
| eNB | `plug_and_play.jsp` | `add_config.jsp` |
| CPE | `plug_and_play.jsp` | `add_config_cpe.jsp` |
| gNB | `gnb_plug_and_play.jsp` | `gnb_add_config.jsp` |
| GSM | `gsm_plug_and_play.jsp` | `gsm_add_config.jsp` |

新前端建议保持“页面能力分流”的思想，但不要按旧 JSP 文件一比一迁移。当前已有：

1. `/device/plug-and-play`：主列表页。
2. `/device/plug-and-play/add`：新增策略。
3. `/device/plug-and-play/edit/:id`：编辑策略。
4. `/device/plug-and-play/view/:id`：查看策略。

建议在新增/编辑页内部引入 `stationType` 路由参数或查询参数，例如：

1. `/device/plug-and-play/add?stationType=enb`
2. `/device/plug-and-play/add?stationType=cpe`
3. `/device/plug-and-play/add?stationType=gnb`
4. `/device/plug-and-play/add?stationType=gsm`

主列表页可以用页签或分段控件筛选站型，但配置页不要把 eNB、CPE、gNB、GSM 的完整字段混成一个无边界大表单。当前 `AddPolicyPage.tsx` 已经把 eNB/gNB/GSM 字段集中在一个文件中，后续建议按站型拆分为：

1. `AddPolicyPage.tsx`：路由壳、策略基础信息、提交编排。
2. `sections/EnbPolicyForm.tsx`：eNB 参数配置。
3. `sections/CpePolicyForm.tsx`：CPE 参数配置。
4. `sections/GnbPolicyForm.tsx`：gNB 参数配置。
5. `sections/GsmPolicyForm.tsx`：GSM 参数配置。
6. `sections/UpgradeConfig.tsx`：软件升级通用块。
7. `sections/LicenseConfig.tsx`：License 通用块。

### 4.2 主列表页

主列表页保持上下双表结构：

1. 上半区：策略列表。
2. 下半区：执行状态列表。

策略列表字段建议为：

| 字段 | 说明 |
|---|---|
| 启用状态 | 对应策略 `policy_switch` |
| 站型 | eNB/CPE/gNB/GSM |
| 产品类型/型号 | 站型内部匹配条件 |
| 策略名称 | 用户可识别名称 |
| 执行方式 | 自动/手动 |
| 软件升级 | 是否启用升级模块，展示目标版本摘要 |
| License | 是否启用 License 模块 |
| 参数配置 | 是否启用自开站参数模块 |
| 操作 | 编辑、检测、复制、删除、查看详情 |

执行状态列表当前已对接 `provisioning_tasks`，但字段较少。建议后端扩展聚合查询，返回策略和设备摘要，避免前端只能显示 `device_id`：

| 字段 | 来源 |
|---|---|
| 设备编码 | `device.serial_number` |
| 站型 | PnP 策略或产品中心 |
| 产品类型/型号 | PnP 策略或产品中心 |
| 策略名称 | `pnp_policies.name` |
| 执行方式 | `pnp_policies.execute_type` |
| 开始/结束时间 | `provisioning_tasks.started_at/completed_at` |
| 进度 | `current_step/total_steps` |
| 状态 | `provisioning_tasks.status` 映射 |
| 失败原因 | `error_message`，必要时聚合 `device_tasks.result` |

### 4.3 配置页模块

配置页统一为“基础信息 + 模块选择 + 模块配置 + 参数配置”的结构。

基础信息：

1. 策略开关。
2. 策略名称。
3. 站型。
4. 产品类型或产品型号。
5. 执行方式。
6. 优先级。

模块选择：

1. 软件升级。
2. License。
3. 参数配置。

CPE 不展示 License 模块；eNB、gNB、GSM 展示三类模块。

参数配置按站型分组：

1. eNB：基础 LTE 参数、核心网、WAN、IPsec、功控、DNS、NTP、自定义参数。
2. CPE：WLAN、WiFi5、DMZ、LAN、LTE 锁频和扫描策略。
3. gNB：GNB 基本信息、CELL、PLMN/Slice、AMF、WAN/LAN、IPsec、静态路由、HaloB、Management、NTP、自定义参数。
4. GSM：基础参数、WAN、静态路由、DNS/时区、高级设置、自定义参数。

## 5. 后端领域模型方案

### 5.1 策略聚合表

新增 `pnp_policies`，作为页面策略和执行编排的聚合根。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键 |
| name | varchar | 策略名称 |
| station_type | varchar | enb/cpe/gnb/gsm |
| product_class | varchar | 产品类型或产品型号匹配条件 |
| carrier | varchar | 运营商 |
| technology | varchar | LTE/NR/GSM/CPE 等 |
| execute_type | varchar | auto/manual |
| policy_switch | boolean | 策略开关 |
| priority | int | 多策略命中时排序 |
| upgrade_enabled | boolean | 软件升级模块开关 |
| license_enabled | boolean | License 模块开关 |
| config_enabled | boolean | 参数配置模块开关 |
| template_id | uuid | 可选关联 `config_templates.id`，仅用于匹配元数据或兼容现有模板能力 |
| xml_file_id | uuid | 最近一次生成的参数 XML 文件引用 |
| upgrade_config | jsonb | 初始版本、目标版本、保留配置等 |
| license_config | jsonb | License 文件匹配、导入记录引用等 |
| config_payload | jsonb | 页面原始参数配置快照 |
| active | boolean | 软启用 |
| created_at/updated_at | timestamptz | 审计字段 |

`config_payload` 保存业务结构化表单，参数自开站执行前编译为 `auto_start` XML 文件。XML 文件引用写入策略或执行任务，设备侧通过 ACS `Download` 获取文件并完成参数开站。

### 5.2 策略和 XML 文件的关系

当前 `config_templates` 已经支持：

1. `template_type = provisioning`。
2. `carrier`、`technology`、`product_class`。
3. `parameters` JSON。
4. `priority`、`active`。
5. `auto_dispatch`。

参数自开站不再使用 `config_templates.parameters` 执行下发。`config_templates` 可以保留为现有 provisioning 架构的匹配元数据或兼容入口，但 PnP 参数配置的执行产物必须是 XML 文件。

建议 PnP 策略保存时采用以下关系：

1. 用户保存策略时，后端校验 `config_payload`。
2. 后端根据站型和产品类型，把业务字段转换为 XML 内部参数模型。
3. 保存策略时可只保存 `config_payload`，不立即生成 XML。
4. 执行前按策略、设备、站型生成本次 `auto_start` XML 文件。
5. `pnp_policies.xml_file_id` 可记录最近一次生成文件；执行任务需要记录本次文件引用，保证审计可追溯。
6. 自动执行策略由 `pnp_policies.policy_switch + execute_type = auto` 控制；手动策略通过页面检测或指定设备触发 dispatch。

这样可以复用当前 `provisioning_tasks` 的总任务状态和 `device_tasks` 的 ACS RPC 队列，但参数下发步骤必须由 PnP 编排层生成 `Download` 子任务，而不是复用 `BuildProvisioningSteps()` 的 GPV/SPV 步骤。

### 5.3 执行任务

继续使用现有两级任务：

1. `provisioning_tasks`：一次自开站执行的总任务，记录 discovered、identifying、matching、configuring、verifying、completed、failed 等状态。
2. `device_tasks`：实际下发到设备的 ACS RPC 子任务。参数自开站固定生成 `Download` 子任务；软件升级、License 也走文件类 Download；必要时追加 `Reboot` 或状态查询任务。

当前 `ProvisioningEngine` 已经具备任务状态、事件订阅、超时清理、任务回调等基础能力，但其 Path A 默认生成 GPV/SPV/Reboot，不符合“参数均走 XML 文件下发”的约束。

PnP 策略接入后，应在 `provision` 引擎或其外侧增加 PnP 编排分支：

1. 设备注册事件进入 `HandleBootstrap()`。
2. 创建 `provisioning_tasks`。
3. 匹配启用的 PnP 策略。
4. 根据策略生成 XML 文件。
5. 创建 `Download` 子任务写入 `device_tasks`。
6. ACS 出队执行 Download。
7. RPC 结果回调推进 `provisioning_tasks` 状态。

这意味着 PnP 参数自开站不能直接调用现有 `BuildProvisioningSteps()`，需要新增面向 XML 文件下发的 step builder。

## 6. 执行链路设计

### 6.1 自动执行链路

自动执行用于“设备首次上线后命中策略即执行”。

流程：

1. 设备通过 TR069 Inform 上线。
2. `device` 模块写入或保持 `first_online_time`，发布 `device.registered` 或相关首次发现事件。
3. `ProvisioningEngine` 订阅事件并进入 `HandleBootstrap()`。
4. 根据设备 `carrier`、`technology`、`product_class` 查询启用的 PnP 策略。
5. 选择 `policy_switch = true`、`execute_type = auto`、优先级最高的策略。
6. 读取策略配置、文件生成规则和文件传输配置。
7. 根据策略生成本次 `auto_start` XML 文件，并构建 Download/Reboot 或验证子任务。
8. 子任务进入 `device_tasks`，由 ACS 会话下发。
9. 子任务完成后推进 `provisioning_tasks`，页面执行状态刷新。

### 6.2 手动执行链路

手动执行用于页面“检测/指定设备计划/批量导入设备编码”。

流程：

1. 用户在策略列表点击“检测”。
2. 前端选择设备或批量输入设备编码。
3. 后端按策略 ID 和设备 ID 调用显式 dispatch。
4. 后端创建 `provisioning_tasks`，记录 `policy_id/template_id`。
5. 复用 `ProvisioningEngine.DispatchTemplate()` 构建并入队子任务。
6. 页面展示执行详情和失败重试。

当前已有 `POST /api/v1/templates/:id/dispatch`，但它以模板为入口。建议新增 PnP 语义接口：

1. `POST /api/v1/pnp/policies/:id/dispatch`
2. 请求体包含 `device_ids` 或 `serial_numbers`。
3. 后端内部查策略，生成本次 XML 文件，并创建 Download 子任务。

### 6.3 软件升级与 License 链路

旧文档里软件升级和 License 都走文件类下发，本质是 ACS `Download`。

建议第一阶段不要把升级和 License 强塞进 `ProvisioningEngine.BuildProvisioningSteps()`，而是在 PnP 编排层生成模块化步骤：

1. upgrade_enabled：创建软件升级任务，复用 `internal/software` 现有能力或生成 `Download` 子任务。
2. license_enabled：生成 License 文件下载任务，文件来源走统一文件服务。
3. config_enabled：生成参数 XML 文件，并创建 `Download` 子任务。

任务顺序建议：

1. 软件升级。
2. License。
3. 参数配置。
4. Reboot 或激活验证。

如果产品要求参数先下发再升级，可以在 `pnp_policies` 增加 `module_order` JSONB，但默认不暴露给普通用户。

### 6.4 参数 XML 文件下发链路

参数自开站统一走 XML 文件下发，因此必须新增“参数文件生成器”：

1. 输入：`pnp_policies.config_payload`、设备信息、站型和产品类型。
2. 输出：`auto_start` XML 文件。
3. 文件落地：接入 `filemanager` 或 ACS 下载服务目录。
4. 子任务：创建 `device_tasks.method = Download`，参数包含文件类型、URL、用户名、密码、文件大小、md5、command_key。
5. 结果：ACS 收到 DownloadResponse 或 TransferComplete 后更新任务。

XML 文件生成需要记录输入摘要、文件名、md5、大小、生成时间和策略/任务 ID。失败定位从“单字段 SPV fault”转为“XML 生成校验 + Download 传输结果 + 设备解析结果”三段定位。

## 7. 参数映射方案

### 7.1 业务字段与 XML 节点

当前 `ProvisioningEngine` 支持标准路径到私有路径的翻译，但参数自开站不走 SPV，下发口径应从“标准 path-value”调整为“业务字段到 XML 节点/属性”的映射：

1. 页面字段只表达业务语义，例如 `gnb_name`、`pci`、`tac`。
2. 后端按站型把业务字段转换为 XML 结构。
3. 多实例对象如 PLMN、Slice、AMF、WAN、Route 需要明确 XML 中的列表顺序和实例号。
4. 自定义参数仍保留 `cust_path/cust_value`，但写入 XML 的自定义参数区域。
5. 保存和执行前均应提供 XML 预览或字段校验摘要，避免到设备侧才发现格式问题。

### 7.2 字段转换器

建议新增 `omcgo/internal/pnp` 或 `omcgo/internal/provision/pnp` 包，承载策略领域逻辑，避免污染 `provision` 引擎。

包内核心接口：

```go
type PolicyCompiler interface {
    Compile(ctx context.Context, policy *PnPPolicy) (*CompiledPolicy, error)
}

type StationParamMapper interface {
    StationType() string
    BuildXML(ctx context.Context, payload json.RawMessage, device DeviceContext) (*GeneratedXML, error)
}
```

站型实现：

1. `EnbParamMapper`
2. `CpeParamMapper`
3. `GnbParamMapper`
4. `GsmParamMapper`

字段来源以两份说明文档中的参数清单为初始输入，并优先对齐当前 `data/param-mappings`、产品中心、参数模型库中已有映射。

### 7.3 gNB 优先字段

gNB 首期建议优先覆盖以下字段，因为文档中路径较完整：

1. `gnb_name`
2. `gnb_id`
3. `gnb_length`
4. `plmn_id`
5. `tac`
6. `pci`
7. `nrarfcndl`
8. `nrarfcnul`
9. `dlbandwidth`
10. `ulbandwidth`
11. `nrbandwidth`
12. `freq_band_indicator`
13. `ssb_frequency`
14. `ssb_block_power`
15. `prach_root_sequence_index`
16. `prach_root_sequence_value`
17. `amf`
18. `amf_plmn_id`
19. `default_route`
20. WAN/LAN/IPsec/DNS/NTP 基础项

未确认的现场字段保留在 `customParams`，用户可填写 `cust_path/cust_value`，但要在 UI 上标记为自定义参数，不混入标准字段。

## 8. API 方案

### 8.1 PnP 策略接口

新增接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/pnp/policies` | 策略分页列表 |
| POST | `/api/v1/pnp/policies` | 新增策略 |
| GET | `/api/v1/pnp/policies/:id` | 策略详情 |
| PUT | `/api/v1/pnp/policies/:id` | 更新策略 |
| DELETE | `/api/v1/pnp/policies/:id` | 删除策略 |
| PATCH | `/api/v1/pnp/policies/:id/switch` | 启停策略 |
| POST | `/api/v1/pnp/policies/:id/dispatch` | 指定设备执行 |
| POST | `/api/v1/pnp/policies/:id/xml/preview` | 参数 XML 预览 |

### 8.2 执行状态接口

保留当前：

1. `GET /api/v1/provisioning/tasks`
2. `GET /api/v1/provisioning/tasks/:id`
3. `POST /api/v1/provisioning/tasks`
4. `POST /api/v1/provisioning/tasks/:id/retry`

建议增强：

1. 列表支持 `policy_id`、`station_type`、`serial_number`、`product_class` 过滤。
2. 返回设备编码、策略名称、站型、产品类型摘要。
3. 详情返回子任务列表，聚合 `device_tasks` 的 method、status、params 摘要、result、fault。

### 8.3 导入导出接口

新增：

1. `GET /api/v1/pnp/templates/:stationType/download`
2. `POST /api/v1/pnp/templates/:stationType/import`
3. `GET /api/v1/pnp/policies/:id/export`

导入后不要直接下发，应生成 `config_payload` 预览和 XML 校验结果，用户确认保存后在执行阶段生成 XML 文件。

## 9. 数据流

### 9.1 保存策略

1. 前端提交策略基础信息和模块配置。
2. 后端校验站型、产品类型、模块开关。
3. 后端校验 `config_payload` 能否生成合法 XML。
4. 后端按需创建或更新匹配元数据；参数内容不写入 SPV 模板。
5. 后端创建或更新 `pnp_policies`。
6. 返回策略详情和 XML 校验摘要。

### 9.2 首次上线自动开站

1. ACS 收到 Inform。
2. 设备信息写库，触发设备注册或上线事件。
3. `provision` 引擎接收事件。
4. PnP 策略匹配命中。
5. 生成 `provisioning_tasks`。
6. 生成 `device_tasks`。
7. ACS 下发 Download/Reboot 或后续验证任务。
8. 回调推进任务状态。
9. 前端 10 秒轮询刷新。

### 9.3 重试

重试不应复用已失败的 `device_tasks`。建议沿用当前 `provisioning_tasks/:id/retry` 语义：

1. 原任务必须是 failed。
2. 新建一条 `provisioning_tasks`。
3. 继承原任务的 `policy_id/device_id`，重新生成本次 XML 文件。
4. 重新生成子任务。
5. 原任务保留失败详情，便于审计。

## 12. 风险与处理

| 风险 | 影响 | 处理 |
|---|---|---|
| 老字段和 XML 节点映射不一致 | XML 生成失败或设备解析失败 | 保存时提供 XML preview；执行时记录生成校验、文件 md5 和设备解析结果 |
| 所有站型塞在一个 React 文件 | 后续维护困难 | 按站型拆 sections，通用模块抽组件 |
| 策略和文件边界不清 | 页面回显困难、执行数据污染 | `pnp_policies.config_payload` 与每次执行生成的 XML 文件分离 |
| 文件生成与 Download 状态断裂 | 任务状态难聚合 | 总任务统一在 PnP 编排层，XML 文件生成和 Download 子任务都绑定 `provisioning_task_id` |
| 首次上线重复触发 | 重复下发 | 使用现有 provision stale task 处理和 Redis 节流；策略层增加幂等命中记录 |
| gNB 多实例 path 不确定 | PLMN/Slice/AMF 写错实例 | 首期限制数量并提供预览；结合设备模型发现结果确认实例 |

## 13. 推荐结论

即插即用和自开站在当前项目中应作为“策略聚合 + provisioning 编排”的能力建设，而不是作为一组独立页面和独立任务系统迁移。

前端继续使用现有 `/device/plug-and-play` 入口，但把策略 mock 替换为真实 `pnp_policies`。后端新增 PnP 策略领域，保存业务表单快照；执行时由 PnP 编排层生成本次 `auto_start` XML 文件，并通过 `device_tasks` 和 ACS `Download` 完成下发。软件升级、License、参数自开站均作为文件类下发模块接入统一 PnP 总任务，不使用 `SetParameterValues` 模板下发参数。

这样做可以最大化复用当前 Go 架构中的模板、任务、ACS、参数翻译和任务状态能力，同时保留旧 OMC 文档中已经沉淀的站型字段、页面组织方式和 TR069 path 清单。
