# 即插即用当前实现与目标状态差异梳理

更新时间：2026-07-30

## 1. 结论摘要

本文第 2 章保留实施前的现状基线；第 1.1 节记录 2026-07-30 本次实施后的代码状态。

- 已有页面：`omcmb/webcode/src/pages/device/PlugAndPlay/index.tsx`
- 已有路由：
  - `/device/plug-and-play`
  - `/device/plug-and-play/add`
  - `/device/plug-and-play/edit/:id`
  - `/device/plug-and-play/view/:id`
- 已显示菜单：通过 seed 迁移将 `device:plug-and-play` 主菜单改为 `show`
- 已落地部分：策略持久化、手动选择设备、快速设置参数编译、规范 XML、ACS Download 下发及 105/106 事件闭环
- 仍待后续：AOS 北向兼容接口、设备注册自动触发、真实设备/厂商私有模板联调

特别约束：参数自开站目标态必须统一走 XML 文件下发路径，不走 `SetParameterValues` 模板下发。

### 1.1 本次实施状态

本次已完成手动执行 XML 自开站的后端与前端主链路：

- 页面配置和导入参数统一编译：quicksettings 优先，缺失项从设备产品对应的 `ParamRegistry` 参数映射补齐；两处均未注册的路径、未解析 `{i}`、只读参数、非法枚举/范围和重复冲突路径会在生成前拒绝。
- XML 使用规范 `autoConfigFile/dataModelSpecific/config/vendorSpecific` 结构；`vendor` 取设备 Manufacturer，生成 UTC 毫秒时间、规范文件名和 SHA-256 快照校验值。
- ACS Download 使用 `103 Base Station Startup File`，同时保留设备下载校验需要的 MD5；`CommandKey` 使用 `PNPXML_<taskId>`。生成的 XML 快照同步写入 Firmware MinIO bucket，设备任务只保存 `bucket/object` 内部引用，由 ACS 与文件管理升级、License 下发统一应用运行时 `acs_transfer.downloadBaseURL + downloadPath`。专用 `/api/v1/provisioning/xml-downloads/:id` 及 token 仅保留给 OMC 页面预览/人工下载。
- `TransferComplete` 成功不再直接完成任务：NR 进入设备开站阶段上报流程；LTE/GSM 创建 `Reboot` 子任务并等待设备重新上线。
- NR：ACS 将 `105 STARTUP STAGE REPORT` 和 `106 STARTUP RESULT REPORT` 路由为独立事件；阶段 1/2/3 分别推进参数校验、参数配置和小区激活，结果状态 1 完成任务，状态 2 持久化 `FailureCause`。
- LTE/GSM：设备重新上线后才启动 5 分钟观察窗口；到期主动发起新的全量参数同步，同步完成并刷新 `device_info` 后检查小区状态。未激活时按 5 分钟间隔继续检查，最多 3 次。
- Inform 事件保留原始 `EventStruct/CommandKey`，优先精确关联任务；缺少 CommandKey 时按设备回退查找活动任务。
- 执行详情统一展示 12 个步骤；一次手动执行最多 50 台设备，并拒绝停用策略和重复设备。
- 软件升级和 License 不再维护即插即用专用文件流程：版本包导入复用固件库接口，License 列表/导入/删除复用 `device-licenses` 接口；策略执行通过 UFTE 分别创建制式对应的镜像升级任务和 `LICENSE_UPGRADE` 任务。固件、License 的 MinIO、URL 拼装、ACS Download 和任务跟踪规则均由文件管理既有服务负责。
- 软件升级、License、参数自配置的开关相互独立，可按策略需要同时启用多项；页面只互斥展示配置面板，不互斥开关值。策略保存保留全部已选模块。执行时按软件升级、License、参数配置严格串行：每个站只提交首个已选模块，复用现有升级/License 状态机的成功或失败终态；成功后才提交下一模块，未选择的模块直接跳过，失败则停止推进。
- 软件升级或 License 任务成功提交到 UFTE 后，同时为每台设备写入一条即插即用执行记录并关联统一文件任务 ID，确保本页“执行状态”列表可见；软件升级在 UFTE 受理后保持执行中，按统一升级流程发布的设备级 `upgrade.completed` / `upgrade.failed` 结果收口，失败保留原始原因，不把“提交成功”误判为“升级成功”。详细设备执行过程继续由统一任务中心跟踪。
- 策略不再保存 License 文件快照；执行时由 `LICENSE_UPGRADE` 按选中设备 SN 获取 License 库中各设备最新文件。未启用参数自配置时，不生成或下发 XML。
- 新增 `000005_plug_and_play_xml_autostart.sql`，为已存在数据库补齐策略、XML 快照和任务关联字段。

本次没有实现 AOS Token/jobId/回调等北向接口，也没有把自动策略挂到设备注册事件；这两部分仍按后续阶段实施。

参数口径补充：

- 页面手工配置和导入文件必须进入同一份“业务字段 -> 快速设置参数 -> TR path”映射，不允许各自维护一套下发字段名。
- 最终 XML 中的 `config.name` 必须是已解析实例号的具体 TR path；页面字段名、Excel 表头、内部 JSON key 都不能直接作为下发参数名。
- NR XML 内容结构可使用 `references/nr/17219396.xml(NR)` 做 golden sample；当样例与技术要求不一致时，以可读版《中国移动一体化皮基站扩展型皮基站自动开通技术要求》中的 Schema、字段语义和协议时序为准。
- 可读版技术要求位于 `omcgo/规范/移动/南向接口/中国移动一体化皮基站扩展型皮基站自动开通技术要求.docx`。文档封面版本为 `1.0.0`，修订历史仍标注 `2021-05-18` 初稿，实施时需要把“规范明确项”和“项目补充策略”分开管理。

## 3. 目标状态

目标态应将 `即插即用` 建成一个真实的策略驱动开站页面，而不是前端 mock 配置页。

### 3.1 页面目标

页面应支持：

- 策略真实增删改查
- 策略启停落库
- 按 Product Class / 设备型号 / 软件版本 / 设备分组匹配策略
- 策略详情查看
- 策略检测真实设备
- 一键或自动触发执行
- 执行状态实时刷新
- 查看 XML 生成结果和下发记录
- 失败原因定位和重试

### 3.2 策略模型目标

策略需要从 mock state 转为后端持久化资源。

建议核心字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 策略 ID |
| `name` | 策略名称 |
| `enabled` | 是否启用 |
| `product_class` | 匹配产品类型 |
| `execute_type` | 自动执行 / 手动执行 |
| `priority` | 多策略命中时优先级 |
| `upgrade_enabled` | 是否包含软件升级 |
| `target_version` | 目标版本 |
| `license_enabled` | 是否包含 License |
| `self_config_enabled` | 是否包含参数自配置 |
| `xml_template_id` | XML 模板或生成规则 |
| `config_source` | `page` / `import` / `mixed` |
| `mapping_version` | 本次策略绑定的参数映射版本 |
| `parameter_values` | 以快速设置参数稳定标识为 key 的配置快照 |
| `created_at` / `updated_at` | 审计字段 |

### 3.3 参数自开站目标路径

参数自开站统一走 XML 文件下发路径。

#### 3.3.1 分层参数映射源

页面配置和文件导入共用同一条分层映射链：

1. 根据设备 `product -> paramModel` 找到 `data/quicksettings/<ParamModel>.xml`
2. quicksettings 命中的参数优先使用其 `standardPath` 或 `group.objectPath + param.leaf`
3. quicksettings 未覆盖的参数，通过 `ParamRegistry.GetByProduct(productId, firmwareVersion)` 获取；设备发现映射优先，未命中时回退产品参数模型的 `param_mappings`
4. 参数表只接纳活动、设备支持且 `entry_type=parameter` 的记录，并复用其读写属性、类型、范围和枚举约束
5. 页面字段和导入模板列只保存“参数标识/映射标识”，不能另外保存一条脱离 quicksettings/产品参数表的 TR path
6. XML 生成时按上述优先级解析权威 TR path 模板

NR 的现有快速设置文件 `data/quicksettings/BaiBNQ.xml` 已覆盖样例中的主要参数，例如：

| 页面/导入参数 | 快速设置权威 TR path 模板 | NR 样例中的具体 TR path |
| --- | --- | --- |
| gNB Name | `Device.Services.FAPService.1.FAPControl.NR.RAN.Common.gNBName` | `Device.Services.FAPService.1.FAPControl.NR.RAN.Common.gNBName` |
| gNB ID | `Device.Services.FAPService.{i}.FAPControl.NR.RAN.Common.gNBId` | `Device.Services.FAPService.1.FAPControl.NR.RAN.Common.gNBId` |
| PCI | `Device.Services.FAPService.{i}.CellConfig.{i}.NR.RAN.RF.PhyCellID` | `Device.Services.FAPService.1.CellConfig.1.NR.RAN.RF.PhyCellID` |
| NR 下行频点 | `Device.Services.FAPService.{i}.CellConfig.{i}.NR.RAN.RF.NRARFCNDL` | `Device.Services.FAPService.1.CellConfig.1.NR.RAN.RF.NRARFCNDL` |
| NR 上行频点 | `Device.Services.FAPService.{i}.CellConfig.{i}.NR.RAN.RF.NRARFCNUL` | `Device.Services.FAPService.1.CellConfig.1.NR.RAN.RF.NRARFCNUL` |
| TAC | `Device.Services.FAPService.{i}.CellConfig.{i}.NR.CN.TA.{i}.TAC` | `Device.Services.FAPService.1.CellConfig.1.NR.CN.TA.1.TAC` |
| AMF IP | `Device.Services.FAPService.{i}.FAPControl.NR.AMFPoolConfigParam.{i}.AmfIP1` | `Device.Services.FAPService.1.FAPControl.NR.AMFPoolConfigParam.1.AmfIP1` |

`references/nr/自开站Trpath（NR）` 可用于补充需求覆盖范围和别名，但不能绕过 quicksettings 或产品参数表直接成为第三套运行时映射。该文件中部分路径缺少 `Device.` 前缀或存在空路径，必须通过映射审查后再纳入，不能在生成阶段盲目补前缀。

#### 3.3.2 统一中间模型

无论值来自页面还是导入文件，后端都先转换为同一中间模型，再生成 XML：

```text
ResolvedParameter
  parameter_id       quicksettings 或产品参数表中的参数稳定标识
  trpath_template     quicksettings 路径；缺失时为产品参数表 standardPath
  trpath              已解析实例号的具体 TR path
  value               已转换为设备线值的字符串
  source              page / import
  source_location     页面字段，或 sheet/row/column
  mapping_version     映射版本
```

内部可以保存额外的显示名和导入来源用于审计，但 XML 只消费 `trpath + value`。

#### 3.3.3 页面配置转换

快速设置页面与即插即用配置页应复用同一份参数定义和取值转换逻辑：

1. 页面提交参数稳定标识、实例上下文和原始值
2. 后端按设备产品和 `paramModel` 查 quicksettings，并由 ParamRegistry 补齐缺失参数
3. 使用所命中参数源的类型、枚举、必填、范围和只读校验
4. 枚举显示值必须转换成快速设置定义的设备线值，例如页面 label 不能直接下发
5. 解析实例号，得到具体 TR path
6. 形成 `ResolvedParameter[]`

禁止由前端拼接最终 TR path；前端可展示解析结果，但后端必须独立校验并生成。

#### 3.3.4 导入文件转换

导入模板每一列必须通过有版本的映射定义关联到快速设置参数稳定标识。推荐映射键：

```text
technology + template_version + sheet_name + normalized_header
    -> paramModel 参数标识 + 实例角色 + value_converter
```

导入处理顺序：

1. 解析工作表、表头、设备 SN 和行号，保留原始来源位置
2. 依据模板版本将表头映射到参数标识
3. 用设备 SN 查询真实设备、产品和 `paramModel`
4. quicksettings 优先、产品参数表兜底，并按命中元数据校验类型、枚举、范围、必填项
5. 按行内小区、TA、AMF、载波等实例信息解析所有 `{i}`
6. 输出与页面配置完全相同的 `ResolvedParameter[]`
7. 保存导入报告：成功、未知表头、无映射参数、实例不明确、值非法、重复 TR path 冲突

不允许把 Excel 表头（如 `gNB Name`、`NRARFCNDL`）或当前 `sheetParameters` 中的原始 key 直接写入 XML。

同一设备同时存在页面配置和导入配置时，建议显式记录 `config_source=mixed`，按“设备级导入值覆盖页面默认值”合并；相同具体 TR path 出现多个不同导入值时必须报冲突，不能依赖工作表顺序静默取最后一条。

#### 3.3.5 `{i}` 实例解析

TR path 模板中的每一个 `{i}` 都必须按其对象层级独立解析，不能统一替换为 `1`。

实例来源按优先级为：

1. 导入行或页面显式选择的实例
2. 设备当前参数树/对象实例
3. 策略中明确配置的单实例默认规则

若某层存在多个候选实例且没有足够上下文，生成必须失败并指出具体参数和占位层级。XML 中不得残留 `{i}`，也不得出现空 `name`。

#### 3.3.6 NR XML 生成契约

NR 输出结构必须与 `17219396.xml(NR)` 保持一致：

```xml
<?xml version="1.0" encoding="UTF-8" standalone="no"?>
<autoConfigFile
    generateTime="2021-04-26T08:00:00.000"
    networkType="NR"
    serialNumber="设备序列号"
    vendor="设备 Manufacturer">
    <dataModelSpecific version="v1.7">
        <config name="具体 TR path" value="设备线值"/>
    </dataModelSpecific>
    <vendorSpecific>厂家私有参数的 Base64 文本，可为空字符串</vendorSpecific>
</autoConfigFile>
```

生成规则：

- `generateTime` 使用 UTC 时间字符串；技术要求样例格式为 `yyyy-MM-dd'T'HH:mm:ss.SSS`。文件名中的时间才使用 `yyyyMMddHHmmss`，两者不能混用
- `networkType` 对 NR 固定为 `NR`
- `serialNumber` 来自目标设备，不信任导入文件中的覆盖值
- `vendor` 来自设备 TR-069 `Inform.DeviceId.Manufacturer`，不是 OUI；值应与设备上报内容一致
- `dataModelSpecific.version` 不能硬编码在通用生成器中，应由制式/厂商 XML profile 决定；当前 NR 样例为 `v1.7`
- 每个有效参数生成一个同时带 `name`、`value` 属性的 `<config name="..." value="..."/>`
- `name` 使用已解析实例号的具体 TR path，`value` 统一转为字符串并进行 XML 转义
- `value=""` 仅在快速设置参数定义和技术要求明确允许空值时保留
- `vendorSpecific` 按技术要求的 Schema 为必选节点；没有私有参数时保留空节点，有私有参数时写入厂家 XML 文件内容的 Base64 编码文本
- 不生成样例中无 `name/value` 的空 `<config/>`；将其视为样例残留数据
- 输出顺序按映射定义顺序或具体 TR path 稳定排序，保证同一输入生成内容可重现
- 生成后必须执行 XML 语法、Schema、根节点属性、`vendorSpecific`、重复路径、空路径、未解析 `{i}` 和必填参数校验
- 南向文件名固定遵循 `<serialNumber>_<Manufacturer>_<dataModelVersion>_<yyyyMMddHHmmss>.xml`

当前 `<AutoStartConfiguration>/<Parameters>/<Parameter>` 格式必须整体替换，不能与目标格式并存。

#### 3.3.7 XML 快照和下发

目标链路：

1. 设备注册或人工检测触发
2. 匹配启用中的即插即用策略
3. 读取设备、站点、License、软件版本、页面配置或导入配置
4. 解析设备 `paramModel` 和映射版本
5. 转换并校验 `ResolvedParameter[]`
6. 按制式/厂商 XML profile 生成 NR 自开站 XML
7. 保存不可变 XML 快照、SHA-256、映射版本、输入来源和生成报告
8. 生成受控下载 URL，通过 ACS `Download` RPC 下发
9. `DownloadResponse` 只表示 RPC 已受理，任务进入 `wait_transfer_complete`
10. 以同一 `CommandKey` 关联 `TransferComplete`
11. 处理设备 `Inform` 中的 `M Download`、`7 TRANSFER COMPLETE` 事件以及 `TransferComplete`
12. `FaultCode=0` 后等待设备依次上报参数校验、参数配置、小区激活阶段
13. 处理 `105 STARTUP STAGE REPORT`，读取 `ParameterList.Stage`：`1=参数校验`、`2=参数配置`、`3=小区激活`
14. 处理 `106 STARTUP RESULT REPORT`，读取 `Status` 和失败时必选的 `FailureCause`
15. 仅当目标基站涉及的全部小区均激活后，将单站任务标记为成功
16. 更新 provisioning task 步骤与最终状态，并形成任务级结果

重试必须复用原 XML 快照，或明确生成新版本并建立 `retry_of` 关系；不能在不留痕的情况下用最新策略覆盖原失败任务。下载 URL token 在每次重试时轮换。

`Download.FileType` 固定使用技术要求规定的 `103 Base Station Startup File`。生成 XML 在数据库保留不可变审计快照，同时以 `plug-and-play/<xmlFileId>.xml` 写入 Firmware bucket；设备任务中的 URL 使用 `bucket/object` 内部引用，最终地址由 ACS 通用 Download dispatcher 根据 `acs_transfer.downloadBaseURL` 和 `acs_transfer.downloadPath` 统一生成。因此主机、端口、反向代理前缀和服务路径均与文件管理升级、License 下发同源。`CommandKey` 格式、下载凭据和超时时间属于项目补充策略，应进入制式/厂商传输 profile。

#### 3.3.8 明确不走的路径

明确不走：

- 不使用 `SetParameterValues` 作为参数自开站模板下发路径
- 不将策略参数直接转成 SPV 任务执行
- 不把页面字段名、Excel 表头或任意 JSON key 直接写成 XML 参数名
- 不在前端生成最终 XML
- 不在 XML 中输出未解析的 `{i}` 或空 `<config/>`

### 3.4 执行任务目标

当前已有 `provisioning_tasks`，但需要扩展任务语义，让页面能准确表达 XML 文件下发过程。

建议任务步骤：

| 步骤 | 说明 |
| --- | --- |
| `match_policy` | 匹配策略 |
| `prepare_context` | 准备设备和站点上下文 |
| `generate_xml` | 生成 XML |
| `upload_file` | 保存 XML 文件并生成下载 URL |
| `download_xml` | ACS `Download` 下发，`FileType=103 Base Station Startup File` |
| `wait_transfer_complete` | 等待设备传输完成 |
| `parameter_validation` | 等待 `Stage=1` 参数校验完成 |
| `parameter_configuration` | 等待 `Stage=2` 参数配置完成 |
| `cell_activation` | 等待 `Stage=3` 小区激活完成 |
| `wait_startup_result` | 等待 `106 STARTUP RESULT REPORT` 单站结果 |
| `verify_online` | 验证设备及全部小区最终状态 |
| `completed` / `failed` | 结束状态 |

页面进度需要同时表达规范中的五个节点：`0=与 OMC 建链`、`1=开站文件下载`、`2=参数校验`、`3=参数配置`、`4=小区激活`。其中节点 0、1 由 OMC 根据连接和文件传输事件计算，节点 2～4 由设备阶段上报驱动。

### 3.5 AOS 北向兼容目标

技术要求定义了 AOS 与 OMC 之间的标准北向接口。项目内部前端 API 可以继续使用 `/api/v1/...`，但不能与下面的运营商兼容接口混为一套契约：

| 功能 | 方法 | URI |
| --- | --- | --- |
| 登录 | `POST` | `/api/rest/autoConfig/v1/oauth/token` |
| 退出 | `DELETE` | `/api/rest/autoConfig/v1/oauth/token` |
| Token 保活 | `POST` | `/api/rest/autoConfig/v1/oauth/handshake` |
| 创建开站任务 | `POST` | `/api/rest/autoConfig/v1/setupJob` |
| 下发规划文件 | `POST` | `/api/rest/autoConfig/v1/planFile/{jobId}` |
| 查询任务进度 | `GET` | `/api/rest/autoConfig/v1/progress/{jobId}` |
| 上报任务结果 | `POST` | `/api/rest/autoConfig/v1/resultReport` |

兼容要求：

- 登录返回 `accessToken`，规范固定有效期为 1800 秒；业务请求通过请求头携带 Token
- 北向规划文件命名为 `AOS_planFile_<yyyyMMddHHmmss>_<jobId>.xls`
- 单个规划文件最多包含 50 个网元
- 同一 `jobId` 允许多次下发规划文件；OMC必须执行参数合并和更新，以支持失败站点再次开站
- 进度响应同时返回任务总进度和每个设备的 `serialNumber + progress`
- 任务结果通知失败时最多重试 3 次；重复失败后记录告警和审计日志
- 任务级成功要求全部目标基站完成开站；失败响应需包含可读原因和失败设备列表
- 外部 AOS 接口使用独立认证、限流、幂等和审计边界，不能直接暴露前端会话接口

是否在当前最小版本开放 AOS 北向接口可由产品范围决定，但数据库模型、任务 `jobId`、规划文件批次和结果聚合不应设计成只能服务单一前端页面。

### 3.6 OMC 管理与审计目标

除执行闭环外，技术要求明确要求 OMC 提供以下管理能力：

- 生成开站文件前，对规划值、必填项、范围、枚举、IP/VLAN和实例关系进行规范性检查
- 按 `jobId` 查询任务总进度、设备进度、创建时间和当前阶段，并支持 Excel/XML/CSV 等格式导出
- 按 `jobId` 查询开站结果、失败原因和完成时间，并支持导出
- 支持厂家私有 XML 模板导入、修改、保存和版本管理
- 保存 AOS 北向操作日志：AOS IP、访问用户名、URI、HTTP 方法、时间和返回码
- 保存设备南向操作日志：设备 IP、RPC/HTTP 操作内容、事件时间、返回码、`CommandKey` 和关联任务
- 日志、XML 快照、导入报告、阶段事件和重试记录使用同一 `jobId/taskId/deviceId` 关联，保证可追溯

## 6. 风险点

### 6.1 与现有 Path A 的边界

当前后端 Path A 会基于配置模板构造 `SetParameterValues` 步骤。参数自开站目标态不能复用这条路径直接下发参数。

建议新增独立路径，例如：

- `Path XML Auto Start`
- 或在 provisioning engine 中新增明确分支 `handleXmlAutoStart`

该路径只生成 XML 并走 ACS Download。

### 6.2 菜单权限与隐藏路由

当前 `device:plug-and-play:edit` 同时被按钮权限和隐藏编辑菜单使用，存在 permission_key 复用问题。

已通过 seed 迁移保持：

- 按钮 `device:plug-and-play:edit`：`show`
- 隐藏编辑路由 `device:plug-and-play:edit`：`hide`

后续建议拆分权限 key，避免同名权限造成维护风险：

- `device:plug-and-play:edit`：按钮权限
- `device:plug-and-play:editor-route`：隐藏路由权限

### 6.3 任务模型字段不足

当前 `provisioning_tasks` 返回字段较少，页面只能显示设备 ID、状态、进度、时间、失败原因。

目标态可能需要补充：

- 策略 ID
- 策略名称
- 设备 SN
- Product Class
- XML 文件 ID
- Download 任务 ID
- 当前步骤名称
- 每步开始/结束时间
- 每步错误码和错误消息

### 6.4 本地迁移历史不一致

热重启过程中发现本地数据库卷存在“goose 版本与实际表结构不完全一致”的情况：

- 主库缺少 `pm_aggregation_tasks`
- TSDB 缺少部分 PM 聚合表
- 部分后续迁移原本未做表存在性保护，导致启动阻塞

已临时将相关后续迁移改为表存在才执行，保证本地环境能启动。后续若要合入主干，需要结合团队迁移策略确认是否保留这种兼容处理。

### 6.5 快速设置与导入映射漂移

如果导入映射直接保存 TR path 字符串，而快速设置 XML 后续调整了路径，两条链路会再次分叉。

建议：

- 参数使用稳定 `parameter_id`，TR path 由快速设置映射版本解析
- 策略发布或执行前做映射版本兼容检查
- 映射变更提供 diff，明确新增、删除、改名和实例层级变化
- 已生成 XML 保留原映射版本，不随配置热加载发生变化

### 6.6 技术要求版本成熟度

仓库内已找到可读 OOXML 版本：

- `omcgo/规范/移动/南向接口/中国移动一体化皮基站扩展型皮基站自动开通技术要求.docx`

已从原文核验并可直接固化的内容包括：

- 南向 `Download.FileType=103 Base Station Startup File`
- 南向文件命名规则
- `M Download`、`7 TRANSFER COMPLETE`、`105 STARTUP STAGE REPORT`、`106 STARTUP RESULT REPORT`
- Stage/Status/FailureCause 语义
- AOS 北向 URI、Token 有效期、单文件 50 网元限制和结果通知 3 次重试
- XML Schema、`Manufacturer`/`SerialNumber` 来源和 `vendorSpecific` 语义

仍需作为项目或厂商 profile 补充确认的内容包括：

- `CommandKey` 格式、下载 URL token、超时和重试间隔
- NR 设备执行 XML 后是否重启、何时重新 Inform、关键参数抽查集合；LTE/GSM 已固定为 OMC 下发 Reboot、BOOT 上线后等待 5 分钟再查询小区状态
- 不同厂商对 `vendorSpecific` 空节点、Base64内容和数据模型版本的兼容性
- 规范封面仍有标准号和发布日期占位符，修订历史仅为 2021 年初稿；若获得更新版本，应执行契约 diff 后再升级 profile

| `17219396.xml(NR)` | 作为 NR XML 结构 golden sample |
| 可读版自动开通技术要求 | 作为接口时序、FileType、文件命名、XML Schema、阶段和状态语义依据 |

## 8. 最小可交付版本建议

建议最小可交付版本不要一次做全自动闭环，可以先做“手动执行 XML 自开站”：

1. 策略 CRUD 落库
2. 手动选择设备
3. 页面配置和 NR 导入模板统一映射到快速设置 TR path
4. 解析全部实例号并展示“来源字段 -> 具体 TR path -> 值”的预览
5. 按 NR 样例生成 XML 并可预览
6. 点击执行后 ACS Download 下发
7. 执行状态列表展示任务进度
8. 失败可查看原因并重试

等手动链路稳定后，再接设备注册/上线事件做自动触发。

## 9. 验收标准

### 9.1 参数映射

- 同一参数分别通过页面填写和文件导入，生成的具体 TR path 和设备线值完全一致
- 未在 quicksettings 或产品参数表中注册的导入列不能进入待下发集合
- 映射结果可追溯到 `paramModel`、`parameter_id`、`mapping_version` 和原始位置
- XML 生成前不存在空路径、重复冲突路径或未解析 `{i}`

### 9.2 XML 内容

- 根节点、属性名和子节点结构与 `17219396.xml(NR)` 一致
- `serialNumber`、`vendor` 与目标设备一致
- `vendor` 与设备 `Inform.DeviceId.Manufacturer` 一致，不能写 OUI
- `generateTime` 使用 UTC 时间字符串，文件名时间使用 `yyyyMMddHHmmss`
- `dataModelSpecific.version` 来自 NR XML profile
- XML 存在 `vendorSpecific`；有私有模板时内容为可解码的 Base64 文本
- 所有 `<config>` 都具有 `name` 和 `value` 属性，`name` 非空；空 `value` 仅在参数定义明确允许时通过
- XML 中不存在 `<AutoStartConfiguration>`、`<Parameter>` 或业务字段名
- 特殊字符可正确转义，生成文件为 UTF-8
- 相同输入和映射版本生成的参数集合及排序一致
- 文件名符合 `<serialNumber>_<Manufacturer>_<dataModelVersion>_<yyyyMMddHHmmss>.xml`

### 9.3 下发闭环

- 每次执行都可关联策略、设备、XML 快照、checksum、device task 和 `CommandKey`
- `Download.FileType` 等于 `103 Base Station Startup File`
- `DownloadResponse` 后任务不能直接标成功
- `TransferComplete` fault 能回写错误码和错误信息
- `105 STARTUP STAGE REPORT` 可依次驱动参数校验、参数配置和小区激活进度
- `106 STARTUP RESULT REPORT` 可回写单站成功或失败及 `FailureCause`
- 成功路径经过 `TransferComplete`、阶段上报、单站结果和全部小区激活校验后才完成
- 重试保留历史 XML 和执行记录，并轮换下载 token

### 9.4 AOS 北向兼容

- Token 登录返回 1800 秒有效期，退出后 Token 立即失效，握手可在过期前保活
- 创建任务返回唯一 `jobId`
- 单个规划文件超过 50 个网元时拒绝并返回明确错误
- 同一 `jobId` 多次上传时按规则合并更新，不创建不可追溯的独立任务
- 进度接口返回任务总进度和每个设备进度
- 结果通知失败时最多重试 3 次，每次调用均保留日志

### 9.5 审计与导出

- 可按 `jobId` 导出任务进度和最终结果
- 可通过 `jobId/taskId/deviceId/CommandKey` 串联规划文件、XML快照、Download、TransferComplete、阶段事件、单站结果和重试
- 北向日志包含 AOS IP、用户名、URI、方法、时间和返回码
- 南向日志包含设备 IP、RPC/HTTP 操作、事件时间、返回码和关联任务

### 9.6 最小测试集

- 页面配置与导入配置同值生成 XML 的等价性测试
- NR golden sample 结构测试
- 技术要求 Schema 和 `vendorSpecific` 测试
- 多层 `{i}` 实例解析测试
- 未知表头、非法枚举、越界值、重复路径冲突测试
- XML 转义和 UTF-8 测试
- Download 的 FileType、受理、TransferComplete 成功/fault、超时和重试测试
- 105 阶段事件、106 单站结果、失败原因和全小区激活判定测试
- AOS Token、50 网元限制、多批次合并、进度查询和结果通知 3 次重试测试
