# 即插即用功能页面处理说明

## 1. 设计目标

这份说明聚焦即插即用功能的前端页面设计，目标是把“站型如何选择”“进入后展示哪些配置块”“每个站型到底有哪些字段”说清楚，便于产品、前端和测试统一口径。

## 2. 页面分流与站型选择

### 2.1 页面分流方式

即插即用不是单页动态拼装，而是按站型拆成多套页面：

| 站型 | 主页面 | 配置页 |
|---|---|---|
| eNB | plug_and_play.jsp | add_config.jsp |
| CPE | plug_and_play.jsp | add_config_cpe.jsp |
| gNB | gnb_plug_and_play.jsp | gnb_add_config.jsp |
| GSM | gsm_plug_and_play.jsp | gsm_add_config.jsp |

### 2.2 站型如何选择

站型不建议放在同一个配置表单里做下拉选择，而是按入口页面直接分流：

1. 进入 eNB / CPE 共享主页面后，通过页签或路由决定当前站型。
2. gNB 和 GSM 直接进入独立页面，不和 eNB / CPE 混在同一个 Vue 实例里。
3. 进入配置页后，用户再选择的是“产品类型”或“产品型号”，不是站型本身。

这样做的好处是站型相关的字段、校验和保存结构都能稳定收敛，不会在单页里靠大量条件渲染硬拼。

### 2.3 站型与产品类型的区别

需要明确两层概念：

1. 站型：eNB、CPE、gNB、GSM，是页面级分流维度。
2. 产品类型 / 产品型号：站型内部的能力分支维度，用来控制显示哪些字段、哪些默认值、哪些列表可见。

例如 eNB 里不同产品类型会影响频点、带宽、子帧、核心网和高级设置的显示规则；CPE 则按产品型号决定无线、LAN、WAN 和 LTE 侧能力是否出现。

## 3. 通用页面骨架

### 3.1 主列表页通用结构

主列表页统一由两部分组成：

1. 上半区策略列表。
2. 下半区执行状态列表。

共同能力包括：

1. 新增策略按钮。
2. 搜索过滤。
3. 行内更多操作菜单。
4. 启用 / 停用开关。
5. 任务状态筛选、重试、删除、查看详情。

### 3.2 配置页通用结构

配置页统一采用“左侧主表单 + 右侧辅助面板”的布局：

1. 左侧是核心配置内容。
2. 右侧通常承载版本选择、版本列表、导入列表或增删编辑弹层。
3. 底部是确定 / 取消按钮。

通用分组顺序通常是：

1. 基本信息。
2. 模块选择。
3. 软件升级。
4. License。
5. 参数配置。

### 3.3 参数配置与升级的边界

即插即用里要明确区分两条不同的链路：

1. 软件升级 / 文件类下发：走 DownloadRequest，对应的是文件名、文件大小、md5、任务ID、文件类型等信息。
2. 自开站的参数配置文件生成后，会被整理成 `auto_start` XML，再走文件类下发。

也就是说，DownloadRequest 解决的是“把一个文件送到设备并触发升级或启动文件下发”，自开站参数最终解决的是“把配置对象转成 XML 文件再下发”。

### 3.4 参数配置流程总览

自开站配置建议按“页面导入 -> 策略落库 -> XML 生成 -> 文件下发”四段来理解：

1. 用户在配置页录入参数，或者下载模板后填写 xlsx 再导入。
2. 后端把 xlsx 解析成多个 Vo 对象，再合并成统一的参数配置对象。
3. 参数配置对象先保存到策略库，成为可复用的配置快照。
4. 后端再把配置对象生成 `auto_start` XML 文件，供后续文件类下发使用。

如果进一步拆到 CPE 场景，可以再细化为：

1. xlsx 导入阶段：`importBatchConfigurationInfos()` 解析模板中的各个 sheet。
2. 导出阶段：`exportBatchConfigurationInfos()` 把 `CPEParamConfigVo` 回填到模板。
3. 保存阶段：导入得到的配置对象进入策略数据。
4. 文件生成阶段：自开站相关配置按需要生成 XML 或导出模板。

## 4. eNB 页面设计

### 4.1 eNB 主列表页

eNB 主页面使用 [plug_and_play.jsp](../src/main/webapp/WEB-INF/content/cell/son/selfConfiguration/plug_and_play.jsp)，表现为上下双表结构：

1. 上方策略列表：显示启用状态、产品类型、策略名称、执行方式、升级、License、参数配置开关。
2. 下方执行状态列表：显示设备编码、产品类型、策略名称、执行方式、开始 / 结束时间、进度、状态和失败原因。

### 4.2 eNB 配置页总览

eNB 配置页使用 [add_config.jsp](../src/main/webapp/WEB-INF/content/cell/son/selfConfiguration/add_config.jsp)，页面以“基础信息 + 模块选择 + 分组参数”组织。

#### 4.2.1 基本信息区

基础信息区固定展示以下字段：

1. 设置开关。
2. 策略名称。
3. 产品类型。
4. 执行方式。

其中产品类型会影响后续参数区的显示规则，属于 eNB 页面最重要的联动入口。

#### 4.2.2 模块选择区

eNB 支持 3 个模块入口：

1. 软件升级。
2. License。
3. 参数配置。

页面一次只展开一个模块，模块切换时其余模块保持收起，避免表单状态交叉污染。

#### 4.2.3 软件升级区

软件升级区包含：

1. 升级开关。
2. 初始版本选择方式。
3. 初始版本列表。
4. 目标版本选择。
5. 保留配置开关。

展示规则如下：

1. 初始版本支持手工新增，也支持从列表中多选。
2. 当“初始版本类型”切到“所有”时，不允许继续手工新增单个版本。
3. 目标版本通过下拉列表选择。
4. 保留配置独立作为一个布尔选项展示。

#### 4.2.4 License 区

License 区采用表格管理：

1. 许可证开关。
2. 按设备编码搜索。
3. 导入按钮。
4. 删除按钮。
5. 表格字段包括设备编码、License 文件、上传时间、状态。

#### 4.2.5 参数配置区

参数配置区是 eNB 最复杂的部分，采用“参数数据池 + 树形分组 + 高级设置”组织。

##### A. 参数数据池基础字段

先展示一个总开关，打开后才允许继续配置子项。基础分组里默认包含：

1. 模块类型列表。
2. 支持频段。
3. 带宽。
4. 频点。
5. 子帧配比。
6. 特殊子帧配比。
7. TAC。
8. 小区标识 / ECI。
9. PCI。
10. 生成序列索引。
11. 载波类型。
12. PLMN ID。
13. 发射功率。

##### B. 不同产品类型的显示差异

eNB 不同产品类型会影响字段显隐，设计上建议按以下方式理解：

1. QAFA：额外显示模块类型列表，可新增、编辑、删除模块项。
2. DXDF：使用独立的频点、带宽和 PLMN 展示方式，部分 LTE 通用字段隐藏。
3. NBIOT：显示 DL Frequency 等专用字段，部分 LTE 常规字段不展示。
4. RTS / RTD / QRTB / BAIBLQ / MLQ / CR-B4860 / MLN：保留通用 LTE 配置，同时按能力开放子帧、特殊子帧和载波类型选项。

##### C. 核心网分组

核心网分组对非 DXDF 产品展示，主要包括：

1. HaloB 开关。
2. PLMN。
3. MME 列表。

MME 支持多值维护，右侧以可删除的列表形式展示。

##### D. 高级设置分组

高级设置不是固定必显，而是按能力字段动态出现。当前页面至少覆盖以下子组：

1. WAN 配置。
2. IPsec 配置。
3. 功率控制。
4. DNS。
5. NTP。

高级设置采用右侧参数树选择后再在左侧展开的方式，适合大量可选项场景；每个子组内部都支持按需添加、删除和回填。

### 4.3 eNB 页面设计结论

eNB 的设计重点是“产品类型驱动字段显隐”。基础信息固定，模块入口固定，真正复杂的是参数配置区，所以 eNB 页面应该优先保证字段显隐规则稳定、版本选择逻辑清晰、列表型字段可批量维护。

## 5. CPE 页面设计

### 5.1 CPE 主列表页

CPE 仍然复用 [plug_and_play.jsp](../src/main/webapp/WEB-INF/content/cell/son/selfConfiguration/plug_and_play.jsp) 的主框架，但配置页进入 [add_config_cpe.jsp](../src/main/webapp/WEB-INF/content/cell/son/selfConfiguration/add_config_cpe.jsp)。

### 5.2 CPE 配置页总览

CPE 配置页的组织方式是“产品型号 + 网络模板 + 批量配置”。

#### 5.2.1 基本信息区

基础信息区展示：

1. 策略名称。
2. 产品型号多选。

产品型号选择后会影响后续网络配置块和批量项是否可用，是 CPE 页面最关键的联动入口。

#### 5.2.2 模块选择区

CPE 只保留 2 个模块：

1. 软件升级。
2. 参数配置。

没有独立 License 模块，这是和 eNB / gNB / GSM 最直观的差异。

#### 5.2.3 软件升级区

升级区包含：

1. 升级开关。
2. 目标版本。
3. 初始版本类型。
4. 初始版本列表。

初始版本支持搜索、添加、删除，右侧列表以卡片 / 表格形式维护。

#### 5.2.4 参数配置区

CPE 的参数配置页按“网络设置”组织，并进一步拆成多个业务块：

1. WLAN。
2. WiFi5。
3. DMZ。
4. LAN。
5. LTE。

##### A. WLAN 区

WLAN 区展示：

1. WiFi 开关。
2. 2.4G 频点。
3. 信道带宽。
4. MBSSID 列表。

MBSSID 表格至少展示：

1. SSID。
2. 安全模式。
3. 状态。

##### B. WiFi5 区

WiFi5 区展示：

1. WiFi5 开关。
2. 网络模式。
3. 信道。
4. 信道带宽。
5. 支持信道。
6. MBSSID 列表。

MBSSID 表格至少展示：

1. SSID。
2. 安全模式。
3. 状态。

##### C. DMZ 区

DMZ 区展示：

1. DMZ 启用开关。
2. DMZ 地址。

##### D. LAN 区

LAN 区展示：

1. LAN 接口开关。
2. DHCP Server。
3. DNS 选项。
4. DNS1。
5. DNS2。

当 DNS 选项切为手动时，才展示 DNS1 和 DNS2。

##### E. LTE 区

LTE 区主要展示：

1. PCI lock / 扫描方式。
2. Full Band。
3. Band / Frequency Preferred。
4. PCI lock。

这一区域主要服务于 CPE 的 LTE 锁频和扫描策略配置。

### 5.3 CPE 页面设计结论

CPE 的核心是“网络型模板”。相比 eNB，它不强调无线小区级细粒度参数，而是强调 WLAN、LAN、DMZ、LTE 的组合配置和批量维护。

## 6. gNB 页面设计

### 6.1 gNB 主列表页

gNB 使用独立页面 [gnb_plug_and_play.jsp](../src/main/webapp/WEB-INF/content/cell/son/selfConfiguration/gnb_plug_and_play.jsp)，与 eNB / CPE 的主列表结构类似，但入口独立，避免混用状态和表单模型。

### 6.2 gNB 配置页总览

gNB 配置页使用 [gnb_add_config.jsp](../src/main/webapp/WEB-INF/content/cell/son/selfConfiguration/gnb_add_config.jsp)，页面风格与 eNB 接近，但参数结构更深。

#### 6.2.1 基本信息区

基本信息区展示：

1. 设置开关。
2. 策略名称。
3. 产品类型。
4. 执行方式。

#### 6.2.2 模块选择区

gNB 支持 3 个模块：

1. 软件升级。
2. License。
3. 参数配置。

#### 6.2.3 软件升级区

升级区和 eNB 的交互模型一致：

1. 升级开关。
2. 初始版本类型。
3. 初始版本列表。
4. 目标版本。
5. 保留配置。

#### 6.2.4 License 区

License 区采用表格维护：

1. 许可证开关。
2. 设备编码搜索。
3. 导入。
4. 删除。
5. 表格字段包括设备编码、文件名、上传时间、状态。

#### 6.2.5 参数配置区

gNB 的参数配置采用“分组折叠 + 树形嵌套”的设计，核心分组如下：

##### A. GNB 基本信息分组

展示字段：

1. GNB 名称。
2. GNB 标识长度。
3. GNB 标识。

##### B. CELL 分组

展示字段分为两层：

1. 基础层：PCI。
2. 高级层：频点、带宽、双工方式、子载波间隔、天线数、时隙 / 符号配置、PRACH 相关参数。

具体包括：

1. 频带指示。
2. 下行 NRARFCN。
3. 下行带宽。
4. SSB 频点。
5. 上行 NRARFCN。
6. 上行带宽。
7. 基站制式。
8. 下行 / 上行子载波间隔。
9. 发射 / 接收天线数。
10. 模式 1 和模式 2 的连续时隙、符号、周期参数。
11. PRACH 根序列索引和值。

页面支持“更多”展开收起，默认只显示基础项，展开后才显示完整无线参数。

##### C. PLMN 分组

PLMN 区域采用三级嵌套表格：

1. PLMN 列表。
2. 每个 PLMN 下挂 PLMN Config 列表。
3. 每个 PLMN Config 下挂 Slice 列表。

约束规则：

1. PLMN 数量不超过 6。
2. 每层子项数量也不超过 6。
3. 表格支持新增、编辑、删除。

Slice 列表至少展示：

1. ID。
2. SD。
3. SNSSAI。

##### D. 网络类分组

gNB 的网络配置按树节点独立展开，典型包括：

1. AMF。
2. WAN / LAN。
3. IPSEC。
4. 静态路由。
5. HaloB。
6. Management。
7. NTP。

这类分组通常在右侧树中勾选后，左侧才出现对应配置块。

##### E. 导入与详情面板

gNB 还会伴随以下辅助面板：

1. IPsec 配置新增 / 编辑弹窗。
2. 设备检测列表弹窗。
3. 批量输入设备编码弹窗。
4. 执行详情抽屉。

### 6.3 gNB 页面设计结论

gNB 的设计重点不是字段数量本身，而是“嵌套层级”。它比 eNB 更适合做成树形、分组、级联展开的编辑体验，避免把所有字段压成一个超长表单。

## 8. 关键交互规则

### 8.1 模块切换规则

软件升级、License、参数配置三个模块之间互斥展开，切换模块时要保留当前表单状态，但不在 DOM 中同时渲染全部配置块。

### 8.2 只读与编辑规则

1. 查看态只展示数据，不显示新增 / 删除 / 导入按钮。
2. 修改态保留字段值，但产品类型或站型相关字段通常不可再改。
3. 需要动态显隐的字段必须和产品类型联动，不能只靠样式隐藏。

### 8.3 列表型字段规则

以下字段都应该按列表 / 卡片 / 表格处理，不建议做成单行输入：

1. 初始版本列表。
2. License 记录。
3. MME 列表。
4. PLMN / Slice 嵌套列表。
5. 自定义参数。
6. 静态路由。
7. WAN 条目。

### 8.4 默认展开策略

页面打开后，默认只展开最常用的一层内容：

1. 基本信息始终展开。
2. 模块只默认选中一个。
3. 参数区默认打开“参数数据池”页签。
4. 复杂子项如高级设置、PLMN 树、Slice 列表、WAN / IPsec 详情默认折叠。

## 9. 设计结论

当前即插即用页面最合理的设计方式是：站型入口分离、页面结构统一、配置内容按站型收敛。

1. eNB 重点在无线能力和高级参数联动。
2. CPE 重点在网络模板和 WiFi / LAN / DMZ / LTE 配置。
3. gNB 重点在树形嵌套和多层配置对象。
4. GSM 重点在批量网络配置和自定义参数维护。

如果后续还要继续细化，建议下一步把这份文档补成页面原型说明，再把每个站型的字段级布局画成逐块清单，直接能给前端开发照着实现。

## 10. 任务编排方案

这一部分把即插即用从“页面配置”推进到“任务执行”的编排关系说明清楚。页面负责生成配置，任务编排负责把配置变成可执行的设备动作。

### 10.1 编排目标

任务编排需要同时满足四个目标：

1. 把策略配置和设备执行解耦，页面只负责定义策略，执行链路负责分发任务。
2. 支持按站型、按模块、按设备的差异化编排。
3. 支持手动触发、自动触发、批量触发和重试。
4. 保证任务状态、失败原因、执行进度能够回显到主列表页。

### 10.2 总体链路

即插即用的任务不是从前端直接下发，而是由设备上报触发后再进入编排链路。当前已知的核心链路是：

1. 设备首次上线或相关条件满足后上报 Inform。
2. 后端进入即插即用任务创建入口。
3. 任务管理器生成策略任务并分发到对应站型处理逻辑。
4. 站型处理逻辑根据模块开关拆出软件升级、License、参数配置等子任务。
5. 子任务进入执行队列，逐个或并行下发给设备。
6. 执行结果回写到任务状态表和执行明细表。

### 10.3 触发方式

任务编排支持三类触发方式：

1. 自动触发：设备满足首次上线或条件更新后自动创建任务。
2. 手动触发：用户在主列表页或详情页点击执行。
3. 批量触发：用户选中多个设备后统一重试或执行。

自动触发和手动触发的区别不在于执行内容，而在于任务来源和初始状态。

### 10.4 任务生命周期

建议把任务生命周期拆成以下阶段：

1. 待创建：页面配置已保存，但任务尚未生成。
2. 待执行：任务已创建，等待设备条件满足或用户点击启动。
3. 执行中：任务已下发，正在等待设备反馈。
4. 成功：全部或关键子任务成功完成。
5. 失败：任务执行中断或关键步骤失败。
6. 跳过：部分模块未启用或条件不满足，编排层主动跳过。

建议界面层只展示“成功、失败、进行中、未执行、跳过”这五类状态，避免状态过细导致用户难以理解。

### 10.5 编排层拆分

任务编排建议按三层拆分：

#### A. 策略层

策略层负责保存页面配置，不直接执行设备动作。它包含：

1. 站型。
2. 产品类型或产品型号。
3. 启用开关。
4. 执行方式。
5. 模块开关。
6. 参数快照。

#### B. 任务层

任务层负责把策略展开成一次具体执行，核心内容包括：

1. 目标设备。
2. 模块拆分结果。
3. 执行顺序。
4. 重试次数。
5. 执行开始与结束时间。
6. 失败原因。

#### C. 子任务层

子任务层负责真正落到设备动作上，例如：

1. 软件升级子任务。
2. License 导入子任务。
3. 参数下发子任务。
4. 批量导入设备计划子任务。

### 10.6 模块编排规则

模块编排建议按以下规则执行：

1. 如果策略未启用，则不创建执行任务。
2. 如果某个模块开关关闭，则该模块在编排阶段直接跳过。
3. 如果某个模块配置不完整，则只影响该模块子任务，不应阻断其他模块。
4. 如果软件升级与参数配置同时开启，建议先升级，再参数下发。
5. 如果 License 作为独立模块开启，建议在升级前或升级后固定一个顺序，避免版本与授权状态不一致。

### 10.7 站型编排差异

不同站型的编排差异不在“是否有任务”，而在“任务拆分方式”和“默认执行顺序”。

#### A. eNB 编排

eNB 的编排重点是：

1. 设备上线后识别策略。
2. 判断是否需要升级。
3. 判断是否需要下发 License。
4. 判断是否需要下发无线和高级参数。
5. 按模块顺序执行并回写结果。

eNB 的参数配置子任务通常是最大头，应该支持失败重试和局部回滚提示。

#### B. CPE 编排

CPE 的编排重点是：

1. 先判断产品型号匹配关系。
2. 再判断 WiFi、LAN、DMZ、LTE 配置是否都可用。
3. 把网络配置拆成可独立执行的子块。
4. 批量导入场景下优先保证设备维度隔离，避免一台失败影响整批。

#### C. gNB 编排

gNB 的编排重点是：

1. 先生成基础信息和无线侧参数。
2. 再展开 PLMN / Slice / AMF / 网络类配置。
3. 任务下发顺序要严格，建议按“基础信息 -> CELL -> PLMN -> 网络类”展开。
4. 任一层级失败时，子任务状态要能定位到具体层级，不要只给笼统失败。

#### D. GSM 编排

GSM 的编排重点是：

1. 先完成基础参数和网络参数编排。
2. 再处理静态路由、WAN、自定义参数。
3. 批量导入页签对应的任务应作为独立编排批次处理。
4. 支持按设备计划执行，不把“计划配置”和“即时配置”混成一个执行单元。

### 10.8 状态回写与页面联动

任务编排完成后，状态需要回写到列表页，页面上至少要反映四类信息：

1. 执行状态：成功、失败、进行中、未执行、跳过。
2. 执行进度：显示当前模块或当前步骤。
3. 失败原因：尽量返回可定位信息。
4. 时间信息：开始时间和结束时间。

当用户在主列表页点击“信息”或进入详情抽屉时，应能看到每个模块的子任务明细，而不是只看到总任务结果。

### 10.9 重试、删除和启动规则

建议编排层对以下动作作统一约束：

1. 重试只针对成功、失败、跳过等已结束状态。
2. 启动只针对未执行状态。
3. 删除只针对未执行、失败、成功、跳过等已结束或可取消状态。
4. 进行中任务原则上不允许删除，除非有明确取消机制。

### 10.10 任务编排建议的数据切面

为了让页面和任务编排之间的耦合更低，建议至少保留以下数据切面：

1. 策略主表：保存站型、产品类型、模块开关和启停状态。
2. 任务主表：保存一次执行的整体状态。
3. 任务明细表：保存模块级或步骤级执行结果。
4. 设备关联表：保存任务与设备的对应关系。
5. 失败原因表或字段：保存最后一次失败定位信息。

### 10.11 方案结论

即插即用的任务编排，推荐采用“策略配置和任务执行分离、模块拆分和子任务回写、站型差异化编排”的方式实现。

这样可以保证：

1. 页面设计清晰。
2. 任务执行可追踪。
3. 失败后可重试。
4. 不同站型可以各自演进，不互相影响。

### 10.12 即插即用专用下发入口

即插即用功能本身不是“页面保存后直接发一个 TR-069 请求”，而是先把策略转成任务，再由任务入口按设备和站型分发。

从代码看，真正的 PnP 执行入口是 `executePolicyTask(policyId, operatorCode, codeList)`：

1. 页面保存后的策略先落到 Mongo 中。
2. 用户点击执行，或者设备满足触发条件后，服务层调用 `executePolicyTask()`。
3. 该方法先根据 `policyId` 查出当前策略对应的站型和产品类型。
4. 再按设备编码逐个组装 `paramMap`，内容至少包含 `deviceCode`、`softwareVersion`、`deviceType`、`productType`，CPE 还会带 `modelName`。
5. 随后调用 `MethodClient.addPlugAndPlayTask(paramMap)` 把任务推给 MethodExecuteHandler。
6. 真正的下发动作由 MethodExecuteHandler 再拆成升级、参数配置等子任务执行。

也就是说，PnP 的“下发”在系统里先表现为“任务投递”，不是立即表现为某个文件或者某个报文。

### 10.13 即插即用的两条子链路

PnP 进入任务执行后，通常会分成两条不同的子链路：

1. 软件升级链路：走 `DownloadRequest`，本质是文件类下发，携带文件名、文件大小、md5、task_id、filetype、commandKey 等信息。
2. 参数配置链路：走参数对象到 `SetValuesRequest` 的转换，最终生成 TR-069 参数报文，不走 `DownloadRequest`。

因此，`DownloadRequest` 只覆盖 PnP 里的升级类动作，不覆盖参数配置本身。PnP 的整体实现是“任务入口 + 子任务分流”，不是单一请求对象。

## 11. 下发文件格式与消息格式

这一部分把“页面保存的数据如何变成下发文件、下发消息长什么样、每个站型支持什么文件类型”单独说明清楚。实际实现里，页面提交和批量导入都以表单提交或 multipart/form-data 为主，文件本体统一采用 Excel。

### 11.1 文件类型总览

即插即用相关的文件类型主要有四类：

1. 策略配置模板文件：用于用户下载模板后填写再导入。
2. 批量导入文件：用户在页面上选中文件后上传，格式为 .xlsx 或 .xls。
3. 导入失败文件：上传校验失败时返回，文件内容会被标红，便于用户修正后重传。
4. 参数导出文件：页面按当前策略内容导出一份可回填的 Excel，用于备份或复制策略。

当前代码里，导入入口都明确校验了 .xlsx 和 .xls，其他后缀直接返回“File format is wrong”。

### 11.2 各站型模板文件名

| 站型 | 模板下载接口 | 模板文件名 | 失败文件名 |
|---|---|---|---|
| CPE | /cpe/batchconfig/downloadTemplate.action | CPE_Batch_Configuration.xlsx | 未在当前文档对应接口中固定输出 |
| gNB | /gnb/pnp/downloadSelfConfigTemp.action | 5G_Autonomous_Self-Deployment_Template.xlsx | 5G_Autonomous_Self-Deployment_failure.xlsx |
| GSM | /gsm/pnp/downloadSelfConfigTemp.action | GSM_Autonomous_Self-Deployment_Template.xlsx | GSM_Autonomous_Self-Deployment_failure.xlsx |
| eNB | 当前页面更偏向策略录入和页面维护，批量模板逻辑和具体站型参数页分离 | 以页面保存和参数页导出为主 | 视具体参数模块而定 |

说明：

1. CPE 的模板下载接口返回文件名 CPE_Param_Configuration.xlsx，但其资源模板文件名是 CPE_Batch_Configuration.xlsx，实际页面下载时会以返回名作为用户看到的下载名。
2. gNB 和 GSM 的模板文件名在代码中是明确固定的，导入失败时也各自返回对应的 failure.xlsx。

### 11.3 文件下发消息格式

页面往后端提交时，消息格式分两种：

1. 普通表单消息：用于新增、编辑、启停、删除等操作，参数直接来自页面表单。
2. 文件上传消息：用于模板导入，Content-Type 为 multipart/form-data，文件字段名统一是 uploadFile。

常见的表单字段包括：

1. policyId：策略主键。
2. policyName：策略名称。
3. productType 或 productModule：产品类型 / 产品型号。
4. pushType：推送类型。
5. targetVersion：目标版本。
6. isKeepConfig：是否保留配置。
7. triggerEvent：触发事件。
8. specifyVersionType：初始版本类型。
9. upgradeEnable：升级开关。
10. configEnable 或 selfConfigEnable：参数配置开关。
11. licenseEnable：License 开关。
12. operType：导入模式，通常用于覆盖或新增。
13. serialNumber：设备编码，批量导入时按设备维度保存。

### 11.4 页面下发的典型消息样式

#### A. eNB 策略保存消息

eNB 保存时，页面把表单参数直接提交给后端，核心字段包括：

1. policyName。
2. productType。
3. pushType。
4. targetVersion。
5. isKeepConfig。
6. triggerEvent。
7. specifyVersionType。
8. originalVersion。
9. frequencyBand。
10. earfcn。
11. bandWidth。
12. plmn。
13. tac。
14. pci。
15. eci。
16. subframeAssignment。
17. specialSubframePatterns。
18. halobEnable。
19. mmeIp。
20. ipsecEnable。
21. ikeDestinationPort。
22. leftInterface。
23. ipsecList。

这类消息是典型的页面表单消息，不是文件上传消息。

#### B. CPE 参数导出消息

CPE 导出时，页面会把当前表单组装成一个 paramConfig JSON 字符串，再随普通表单一起提交。其结构可以理解为：

1. wifi：WLAN 配置块。
2. wifi5：WiFi5 配置块。
3. dmz：DMZ 配置块。
4. lan：LAN 配置块。
5. pciLock：扫描 / 锁频配置块。
6. wanAcc：WEB 访问控制配置块。
7. watchDog：看门狗配置块。

页面提交时，paramConfig 是一个 JSON 字符串，后端解析后再拆成各个 Vo 结构保存。

#### C. gNB / GSM 批量导入消息

gNB 和 GSM 的批量导入统一采用 multipart/form-data，常见字段如下：

1. uploadFile：Excel 文件流。
2. policyId：策略 ID。
3. operType：导入模式。
4. serialNumber：部分编辑动作会补充设备编码。

页面导入时通常不会把整份配置直接拼成长 JSON，而是先把 Excel 模板下发给用户，再让用户填完后重新上传。

### 11.5 详细示例一：CPE 模板导入

CPE 的导入流程最适合做示例，因为它既有模板下载，又有导出和导入回填。

1. 用户进入 CPE 配置页，点击“下载模板”。
2. 页面请求 /cpe/batchconfig/downloadTemplate.action。
3. 后端返回模板文件 CPE_Batch_Configuration.xlsx，浏览器保存为 CPE_Param_Configuration.xlsx。
4. 用户在 Excel 里填写 7 个 sheet 或对应页签中的字段。
5. 用户重新选择文件并上传。
6. 页面以 multipart/form-data 提交 uploadFile 给 /cpe/batchconfig/importBatchConfigurationInfos.action。
7. 后端校验后缀必须是 .xlsx 或 .xls。
8. 后端使用 POI 读取各 sheet，解析出 WifiVo、DmzVo、LanVo、PciLockVo、WanAccVo、WatchdogVo、Wifi5Vo。
9. 解析成功后，后端把这些对象合并成 CPEParamConfigVo，保存到策略下。
10. 若存在格式错误，错误单元格会被标红，前端返回失败提示。

#### CPE 导入文件结构示例

sheet 0：WLAN 基础信息

1. 第 1 行通常是标题或说明。
2. 第 2 行开始写入数据。
3. 字段顺序为：WLAN 开关、信道、带宽、SSID、加密方式、密码、WLAN1 开关、WLAN1 SSID、WLAN1 加密、WLAN1 密码、WLAN2 开关……一直到 WLAN3。

sheet 1：DMZ

1. DMZ 开关。
2. DMZ Host Address。

sheet 2：LAN

1. LAN 开关。
2. DHCP 开关。
3. DNS1。
4. DNS2。
5. LAN 选项。

sheet 3：PCI Lock

1. 扫描模式。
2. PCI 或 EARFCN 字段，按扫描模式不同采用不同填法。

sheet 4：WEB Access Control

1. UI 密码。
2. HTTPS 开关。
3. HTTPS WAN 开关。
4. WAN 访问开关。
5. 地址段。

sheet 5：Watchdog

1. Watchdog 开关。
2. Ping IP。
3. 超时时间。
4. Ping 次数。
5. 失败后是否重启。

sheet 6：WiFi5

1. WiFi5 开关。
2. 模式。
3. 信道。
4. 带宽。
5. 支持信道。
6. SSID。
7. 加密方式。
8. 密码。
9. 1、2、3 组附加 SSID 与密码。

### 11.6 详细示例二：gNB 模板导入

gNB 的导入流程强调多层配置和失败回退。

1. 用户点击“下载模板”，系统返回 5G_Autonomous_Self-Deployment_Template.xlsx。
2. 用户按模板填写基础信息、CELL、PLMN、Slice、AMF、WAN、IPSEC、静态路由等内容。
3. 用户选择文件后，页面通过 multipart/form-data 提交到 /gnb/pnp/importBatchConfigInfos.action。
4. 请求体中除了 uploadFile 之外，还会带 operType 和 policyId。
5. 后端按 sheet 依次解析。
6. 如果导入模式为覆盖，先删除原有配置，再写入新的配置。
7. 解析失败时，系统生成 5G_Autonomous_Self-Deployment_failure.xlsx，用户下载后可以看到被标红的错误单元格。

gNB 的导入更适合按“基础信息 -> CELL -> PLMN -> 网络类配置”的顺序理解，因为页面和模板都围绕这个层级展开。

### 11.7 详细示例三：GSM 模板导入

GSM 的模板导入结构和 gNB 类似，但偏向设备计划与批量网络配置。

1. 用户点击“下载模板”，系统返回 GSM_Autonomous_Self-Deployment_Template.xlsx。
2. 用户填写基础信息、路由、WAN 等字段。
3. 页面以 multipart/form-data 上传到 /gsm/pnp/importBatchConfigInfos.action。
4. 后端按 sheet 解析基础配置、静态路由、WAN 配置。
5. 如果导入模式为覆盖，则先清理原数据再写入。
6. 失败时返回 GSM_Autonomous_Self-Deployment_failure.xlsx。

GSM 批量导入的关键点是“设备维度”和“配置维度”同时存在，所以 policyId + serialNumber 是最重要的定位组合。

### 11.8 统一的下发流程说明

完整的下发流程建议按下面的顺序理解：

1. 用户在页面录入策略，或者下载模板后填写 Excel。
2. 页面把表单数据或 Excel 文件提交到对应站型接口。
3. 后端校验文件后缀、必填字段、范围值和关联关系。
4. 校验通过后，配置数据先进入策略表或批量配置表。
5. 设备上线后触发 Inform 或用户点击执行按钮，任务编排层生成执行任务。
6. 任务编排层把策略拆成模块级子任务。
7. 子任务按站型和模块顺序逐步下发。
8. 执行结果回写任务主表、任务明细表和失败原因。
9. 页面列表刷新，用户可以看到成功、失败、进行中或跳过状态。

### 11.9 需要特别注意的约束

1. 文件名可以不同，但文件类型必须是 Excel。
2. uploadFile 是当前批量导入的统一字段名。
3. 导入时不要把 JSON 和 Excel 混用成一套接口，页面上本质是“参数表单”和“模板文件”两条通路。
4. 如果某个站型没有模板导入能力，就不要强行套用统一模板，应该保留站型自己的页面录入方式。

### 11.10 本章结论

如果把即插即用看成一个完整链路，可以把数据流概括成两类：

1. 页面表单流：策略名称、产品类型、模块开关、参数 JSON。
2. Excel 文件流：模板下载、批量导入、错误回传、导出备份。

这两类数据流最终都会落到同一套策略和任务体系里，只是入口不同、验证方式不同、回显形式也不同。

### 11.11 自开站 XML 文件格式示例

自开站 / 启动文件 / 自配置文件在真正下发前，会先由参数对象生成一个 XML 文件。源码里生成的根节点是 `auto_start`，其下每个参数都以 `<param>` 节点表达，子节点固定包含 `name` 和 `value` 两个字段。

这个 XML 文件的用途不是给人直接看，而是给设备侧在 `DownloadRequest` 后作为配置载体使用。文件名通常是 `auto_start_<sn>.xml`，再被写入本地存储和 FTP 目录，最后按文件类下发。

一个典型的 XML 结构可以写成下面这样：

```xml
<auto_start>
	<param>
		<name>LTE_DL_BANDWIDTH</name>
		<value>20</value>
	</param>
	<param>
		<name>LTE_DL_EARFCN</name>
		<value>38950</value>
	</param>
	<param>
		<name>LTE_OAM_PLMNID</name>
		<value>46011</value>
	</param>
	<param>
		<name>LTE_TAC</name>
		<value>12345</value>
	</param>
	<param>
		<name>LTE_CELL_IDENTITY</name>
		<value>10001</value>
	</param>
	<param>
		<name>LTE_PHY_CELLID_LIST</name>
		<value>101</value>
	</param>
	<param>
		<name>LTE_TDD_SUBFRAME_ASSIGNMENT</name>
		<value>2</value>
	</param>
	<param>
		<name>LTE_TDD_SPECIAL_SUB_FRAME_PATTERNS</name>
		<value>7</value>
	</param>
	<param>
		<name>LTE_SON_PRACH_ROOT_SEQUENCE_INDEX_LIST</name>
		<value>22</value>
	</param>
	<param>
		<name>Device.Time.NTPServer1</name>
		<value>10.10.10.10</value>
	</param>
	<param>
		<name>LTE_SIGLINK_SERVER_LIST</name>
		<value>10.20.30.40</value>
	</param>
</auto_start>
```

这个格式可以按下面几层来理解：

1. 根节点 `auto_start` 表示这是一个自启动配置文件，而不是普通业务参数文件。
2. 每个 `<param>` 是一个“参数项”，对应设备侧一个可下发的配置点。
3. `<name>` 存的是设备侧参数路径或参数名，可能是标准路径，也可能是平台私有路径。
4. `<value>` 存的是实际配置值，例如频点、带宽、PLMN、TAC、ECI、NTP 地址等。
5. 同一个文件里可以同时存在基础参数、无线参数、网络参数和高级参数。

结合代码里的实际生成规则，还要注意几种变化：

1. `LTE_DL_BANDWIDTH` 会根据平台把 `n25 / n50 / n75 / n100` 归一成 `5 / 10 / 15 / 20` 或 `25 / 50 / 75 / 100`，不同平台转换规则不完全相同。
2. `LTE_OAM_PLMNID` 可能会展开成多个 `<param>`，当 PLMN 有多个值时，后续会按索引追加私有路径节点。
3. `LTE_TDD_SUBFRAME_ASSIGNMENT` 和 `LTE_TDD_SPECIAL_SUB_FRAME_PATTERNS` 只在支持 TDD 的场景下输出，FDD 可能不生成。
4. `Device.Time.NTPServer1`、`LTE_SON_TX_POWER`、`LTE_SON_TIME_ZONE` 等节点是否出现，取决于平台类型和高级配置开关。
5. `LTE_SIGLINK_SERVER_LIST` 与 `LTE_HALOB_ENABLE_STATE` 二选一或按条件出现，具体由 HaloB 开关控制。

如果从文件格式角度再压缩一下，这类 XML 的本质就是：

1. 一个根节点。
2. 一组有序的参数项。
3. 每个参数项由“参数名 + 参数值”组成。
4. 文件被 `DownloadRequest` 作为一个整体下发到设备侧，设备收到后按参数项逐条应用。
