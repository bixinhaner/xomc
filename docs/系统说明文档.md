# OMC 系统说明文档 — 服务模块与数据流

> 本文档说明 goomc（OMC，小基站无线操作维护中心）的**部署单元 / 服务模块职责 / 模块间数据流**。
> 生成于 2026-06-16，基于代码实地勘察（`omcgo/internal/`、`cmd/`、`deployments/docker/`）。
> 配套文档：架构概览 `CLAUDE.md §5`、术语表 `CONTEXT.md`、可观测性 `docs/operations/`、消息队列 `docs/消息队列全流程流转说明书.md`。

## 1. 总览：三进程 + 共享中间件

OMC 是**模块化单体 + 独立 ACS 引擎**：不拆微服务，按功能域分模块，运行态是 docker compose 编排的容器栈。后端只有 **3 个业务进程**，外加一组共享中间件。

| 部署单元 | 进程 | 职责 | 入口 | 横扩 |
|----------|------|------|------|------|
| `omcgo-acs` | ACS 引擎 | TR069/CWMP 南向协议，纯 net/http，与 CPE 直接对话 | `cmd/acs` | 无状态，多实例 |
| `omcgo-app` | 主应用 | F02–F10 管理面 REST(Gin) + gRPC，前端的后端 | `cmd/app` | 单/多实例（定时任务用锁） |
| `omcgo-worker` | 后台工作进程 | PM/MR 文件解析、KPI 聚合、告警接收、备份执行、报文采集 | `cmd/worker` | 群组消费（NATS QueueSubscribe） |

辅助入口：`cmd/migrate`（goose 迁移）、`cmd/omcctl`（运维 CLI）、`cmd/tools`、`cmd/backup-reencrypt`（备份密钥轮换）。

### 共享中间件（docker compose 实拍）

| 中间件 | 用途 |
|--------|------|
| **PostgreSQL** (`postgres`) | 业务主库：设备、任务、配置、告警活动表 |
| **TimescaleDB** (`postgres-tsdb`) | 时序库（物理分离）：PM 指标/KPI、MR 测量、告警历史、报文 |
| **Redis** (`redis`) | 任务队列、CWMP↔Task 映射、会话状态、字典 L2 缓存、分布式锁 |
| **NATS JetStream** (`nats`) | 进程间事件总线（ACS↔App↔Worker 解耦的核心） |
| **MinIO** (`minio`) | 对象存储：PM/MR/固件/备份/导出文件 |
| 可观测性 | OTel Collector → Tempo(trace) / Loki(log) / Prometheus(metric) + Grafana + Alertmanager |
| 接入层 | nginx（前端 SPA + `/api` 反代到 app） |

> **关键架构选择**：ACS 与 App **不直接 RPC 调用**，而是通过「共享 Redis/PG + NATS 事件」松耦合。这让 ACS 能无状态横向扩展（10 万→100 万基站），同时 App/Worker 独立演进。

## 4. 核心数据流

### 4.1 设备上报（南向上行）

```
CPE → ACS (HTTP POST /acs, SOAP/XML)
  → 会话状态机：IDLE → INFORM_RECEIVED → PROCESSING → RPC_PENDING → COMPLETE
  → 解析 Inform（参数值 / Events / 告警 / 文件上传通知）
  → 按内容发布 NATS 事件 device.inform.*
       ├─ periodic  → device 更新最后在线
       ├─ alarm     → alarm.Receiver
       └─ transfer  → transfer.Bridge / software / backup
```
证据：`internal/acs/handler.go`（ServeHTTP / publishInformEvents）、`cmd/acs/main.go`。

### 4.2 任务下发（北向下行 + 队列）

```
App REST API (创建任务) → task.CreateTask
  → PG: device_tasks (status=pending)  +  Redis: acs:taskq:{sn} (Sorted Set)  ← 双写
  → [设备下次 Inform 或 Connection Request 唤醒]
  → ACS 会话 Pop Redis 队列 → 组装 RPC (SetParameterValues / Download / Reboot ...)
  → HTTP Response (SOAP) → 设备执行
  → 设备回包携带 CommandKey → ACS 用 Redis acs:cwmp2task:{hash} 反查 taskID
  → task.MarkTaskCompleted/Failed → 更新 PG + 发布 task.completed
  → notification / mml.ResultAggregator 消费聚合
```
**双写语义**：Redis 是运行态真相源（低延迟出队），PG 是持久化权威源；worker 周期 `reconciler` 扫 PG 中 pending/sent 任务与 Redis 对账，TTL 24h 自愈。
证据：`internal/task/service.go`、`internal/task/cwmp_id.go`、`internal/acs/task_service.go`。

### 4.3 PM 性能数据流

```
设备自主上传 PM 文件 → ACS (AutonomousTransferComplete)
  ├─ 路径A: transfer.Bridge 下载 TransferURL → MinIO，发 pm.file.received（含设备元数据）
  └─ 路径B: ACS upload.Handler 直接落 MinIO，发 pm.file.received（瘦载荷，仅路径+sn）
  → pm.Collector (worker) 消费：
       下载 XML → 解析 Counter → 白名单过滤孤儿计数器
       → KPIEngine 按「设备→产品→平台→公式」计算 KPI
       → 单事务原子写时序库 pm_files + pm_metrics + pm_kpi
       → 原始 XML 压缩归档（rawArchive 省盘）
  → worker cron（时/日/周/月）自然桶聚合 → pm_natural_bucket
  → 报表/北向按 KPI Router 查询导出
```
存储：MinIO `pm-files/` `pm-files-raw/`；时序库 `pm_files`/`pm_metrics`/`pm_kpi`/`pm_natural_bucket`（hypertable）。
证据：`internal/pm/collector/collector.go`、`internal/pm/kpi/router/`、`cmd/worker/main.go`。

### 4.4 MR 测量报告数据流

```
设备上传 MR → ACS（自主上传 或 F05 MR 任务触发）→ MinIO mr-files/
  → 发 mr.file.received / mr.file.uploaded
  → mr.Collector (worker)：按 FileType 选 MRO/MRS/MRE 解析器
       → Carrier 适配判定是否采集 MRE → 写时序库 mr_files / mr_measurements
  → F05 MR 任务侧（app）：mrtask.Dispatcher 用 Translator 翻译路径，
       SPV 下发 Device.MeasurementControl.* 开关，Scheduler @30s 巡检（Redis 锁），
       Cleaner @daily 清超期文件；HeartbeatSubscriber 写心跳
```
证据：`internal/mr/collector/`、`internal/mr/parser/`、`internal/mr/task/`、`cmd/app/provider/modules.go`。

### 4.5 告警数据流

```
设备告警 → ACS Inform (AlarmInfo / FaultMgmt.ExpeditedEvent) → 发 device.inform.alarm
  → alarm.Receiver (worker)：
       查 alarm_definitions 定义库
         ├─ 已知 → engine.Process
         └─ 未知 → 看设备 enable_unknown_alarm：开则 Warning 入库(is_unknown)，关则丢弃+计数
  → alarm.Engine：按 (device_id + alarm_identifier) 去重/更新/关联
       → 写 alarms_active（活动）+ alarms_history（时序）
       → filterEngine 过滤规则：forward / suppress / auto_clear，触发 Webhook/邮件
       → 发 alarm.raised
  → northbound.push：白名单过滤 → Outbox 模式 HTTP POST 转推 OSS（可靠投递+重试）

告警清除：periodic Inform 无该告警 → AlarmSyncProcessor 比对 → auto_clear → 转 history
告警确认：App DELETE /alarms/{id} → 标记 acknowledged → 转 history
实时推送：ExpeditedEvent（NewAlarm/ChangedAlarm/ClearedAlarm）低延迟直入库
```
表：`alarms_active`（去重唯一键）、`alarms_history`（hypertable）、`alarm_filter_rules`、`alarm_definitions`。
证据：`internal/alarm/receiver.go`、`internal/alarm/engine.go`、`internal/alarm/sync_processor.go`、`internal/alarm/definition/`。

### 4.6 北向 OSS 数据流

```
告警/PM/配置事件 → northbound.push.Engine
  → 读 northbound_servers 主备配置
  → 白名单过滤
  → Outbox 模式：先写 PG outbox 表（事务内）→ 后台 Poller 批量 HTTP POST → 成功删/失败指数退避重试
  主备切换：App PUT /northbound/servers/{id}/active → 健康检查 → 切 primary → 刷新推送目标
```
开放数据：告警转推（JSON/XML 批量）、PM 聚合导出、配置快照同步。协议：HTTP(S) POST。
证据：`internal/northbound/push/engine.go`、`internal/northbound/server_service.go`。

## 5. 字典与配置热更新

`product`/`config` 的参数字典（标准↔私有路径翻译、产品路由、指标公式）启动期由 `core/dictloader` 从 `data/` 加载 XML/JSON 到 PG，运行期走 Redis L2 缓存。配置变更发 `sys.config.saved` 事件，各实例 `ensureFresh` 刷新版本，无需重启。这是 ACS 端把设备私有参数路径翻译为标准路径的基础。

## 6. 可靠性与扩展性要点

| 机制 | 说明 |
|------|------|
| ACS 无状态横扩 | 会话副作用状态（准入计数/会话指针/ConnReq URL/Digest nonce）外移到共享 Redis，多实例无亲和 |
| 任务双写+对账 | Redis 快出队 + PG 持久化 + reconciler 周期对账 + TTL 自愈，任务不丢 |
| Outbox 模式 | 北向推送先落库再异步投递，指数退避重试，保证最终送达 |
| 原始文件归档 | PM/MR 原始 XML 压缩回写（rawArchive），节省时序盘，rawSweeper 补漏 |
| Worker 群组消费 | NATS QueueSubscribe 负载均衡，worker 可水平扩展 |
| 运营商适配 | 全部差异封装在 `core/carrier`，禁止 `if carrier == "cmcc"` 硬编码 |
| 时序物理分离 | PM/MR/告警历史走独立 TimescaleDB 实例，与业务主库隔离 |

- **告警**：设备 → ACS → alarm.Engine(去重/关联) → 活动表+历史表 → 北向 Outbox 推送
```
