# OMC 资源、队列与存储保护监控说明

> **文档版本**：v1.0
> **更新日期**：2026-07-28
> **适用版本**：资源监控、队列治理与磁盘写入保护 MR !360
> **当前提交**：`2c49ced97`
> **文档性质**：已实现功能说明与使用入口

## 1. 功能概览

本次改动围绕“资源是否接近上限、业务队列是否积压、磁盘满后是否继续接受业务写入”补齐了监控和治理能力，分为四类：

1. 修复已有主机、容器、OMC 进程的 CPU、内存和磁盘监控查询，使其适配 Docker Compose 环境实际使用的标签。
2. 新增存储目标、MinIO、NATS JetStream、Redis 任务队列、PostgreSQL 持久化队列的业务指标。
3. 新增 Grafana“存储与队列治理”统一仪表盘和 Prometheus 告警规则。
4. 新增 OMC“资源与存储保护”页面，按统一物理文件系统配置容量阈值；写入类型仅用于业务优先级、降级顺序和审计，并将准入结果接入部分业务写入入口。

应用进程内部 Go Channel、Worker 内存队列、SSE 缓存和 Trace 本地内存队列不纳入本期队列监控。

## 3. 已有监控内容的修改和优化

### 3.1 CPU、内存和容器资源

原有 Docker Compose 环境的部分查询使用了 Kubernetes `namespace="omcgo"` 或 cAdvisor 不稳定的 `name` 标签，现场可能出现面板无数据。本次统一调整为 `service`、`container_id`、`job`、`instance` 等实际标签。

调整内容：

- OMC app、acs、worker 按服务展示 CPU 使用率和内存使用率。
- 依赖服务 PostgreSQL、TimescaleDB、Redis、NATS、MinIO、Web 按服务展示 CPU/内存饱和度。
- 监控服务 Prometheus、Grafana、Loki、Tempo、OTel Collector、Alertmanager、cAdvisor 按服务展示内存。
- 容器 CPU 限额、内存限额、CFS 限流、网络收发和块 IO 使用稳定的 `service` 维度。
- 增加或补齐容器重启次数、OOM 事件、块 IO 读写等运行状态面板。
- 保留 Go 协程数、GC 暂停、GOMEMLIMIT、连接池和文件描述符监控。

主要页面：

- **OMC - 服务资源与运行时**：查看 OMC 三进程的实时资源和运行时状态。
- **OMC - 依赖服务端与监控栈**：查看依赖组件和监控组件的资源占用。
- **OMCGo - Operations Dashboard**：查看 OMC 服务整体 CPU/内存趋势。

### 3.2 主机磁盘和文件系统

在原有磁盘使用率基础上补充：

- 按挂载点查看文件系统使用率。
- inode 使用率。
- 可用空间减少速度。
- 基于历史趋势的预计耗尽时间。
- 排除 `tmpfs`、`overlay`、`squashfs` 等不代表实际可写主机容量的伪文件系统。
- 使用 `$mountpoint` 和 `device` 变量进行挂载点筛选。

主要页面：

- **OMCGo - Nginx 流量 / 主机 / 容器资源**：主机磁盘、inode、增长速度和耗尽预测。
- **OMC - 依赖服务端与监控栈**：主机及数据盘容量、inode 和 4 小时耗尽预测。
- **OMC - 存储与队列治理**：按逻辑存储目标查看使用率。

### 3.3 OMC 服务在线和 Operations 查询口径

`OMCGo - Operations Dashboard` 做了 Docker Compose 适配：

- “Pod Count” 改为 OMC 服务在线数量。
- 去除 `namespace="omcgo"` 查询。
- 服务 CPU、内存和 HTTP 请求按 OMC 实际 `service`/`component` 标签查询。
- 保留已有 PM 队列、备份清理、请求延迟和服务健康面板。

## 4. 新增监控内容

### 4.1 统一物理存储目标和逻辑观测

当前部署不涉及外部存储，所有 OMC 数据共用宿主机根文件系统。容量保护只配置一个物理目标；业务组件仍保留逻辑分类，用于观测、清理和写入优先级：

| 目标层级 | 目标 ID | 监控内容 |
|---|---|---|
| physical | `filesystem/root` | 宿主机 `/` 的真实物理容量，作为唯一告警、阻断和恢复判断依据 |
| logical observation | `application`、`minio`、`database`、`monitoring` | 业务分类、MinIO/数据库逻辑大小和监控组件保留量；不单独配置磁盘阈值 |

说明：同一物理设备上的应用根盘、Docker volume、MinIO、PostgreSQL/TSDB 和监控目录不会重复计入容量策略。当前已能直接采集主机根文件系统，MinIO 集群和 PostgreSQL/TSDB 逻辑大小仅用于定位占用来源；只有未来挂载独立磁盘或接入外部存储时，才新增物理目标。

新增或统一使用的指标包括：

- `omc_storage_capacity_bytes`：目标容量。
- `omc_storage_used_bytes`：目标已用空间。
- `omc_storage_used_ratio`：目标使用率。
- `omc_minio_bucket_usage_bytes`：固定业务分类的 MinIO 桶容量。
- `minio_cluster_capacity_usable_total_bytes`、`minio_cluster_capacity_usable_free_bytes`：MinIO 集群总量和可用量。
- `minio_node_ilm_expiry_pending_tasks`：MinIO ILM 待处理清理任务。

MinIO 桶使用固定业务分类，不把对象路径、设备号等高基数内容作为 Prometheus 标签。当前配置契约包括 PM、MR、固件、配置备份、日志、报表、交换文件、UI 资源、Trace、文件包、配置快照和设备许可；本次 Recording Rule 已实际接入配置备份分类，其他分类作为后续桶容量采集的固定允许列表。

### 4.2 NATS JetStream 队列

新增 OMC JetStream observer，使用已有 NATS JetStream 连接周期采样已注册的 Stream/Consumer，不依赖现场无数据的旧 exporter 查询。

当前注册的业务队列包括：

- PM：`PM/pm-workers`
- MR：`MR/mr-workers`
- Trace 捕获：`TRACE_MSG/trace-capture`
- Trace 导出：`TRACE_EXPORT/trace-export`
- 备份：`BACKUP/backup-executors`
- 报表：`REPORT/report-generators`

指标包括：

- Stream 消息数、已占字节数、最大字节数。
- Consumer pending 数量、Ack pending 数量。
- 重投递次数。
- 最老待处理消息年龄。
- 投递速率和 Ack 速率。
- 最近采样时间、数据新鲜度、观测是否可用和观测失败次数。

主要页面：

- **OMC - 存储与队列治理**：NATS JetStream 积压面板。
- **OMC - 依赖服务端与监控栈**：NATS 依赖状态和队列面板。
- 原 **OMCGo - Operations Dashboard**：保留原有 NATS 概览面板。

### 4.3 Redis cmdq/taskq 队列

新增 Redis 队列观测，覆盖两类设备队列：

- `cmdq`：旧命令队列，匹配 `acs:cmdq:{device}`。
- `taskq`：新版设备任务队列，匹配 `acs:taskq:{device}`。

观测使用 Redis `SCAN`，不使用会阻塞生产环境的 `KEYS`。指标按队列族聚合，不把设备号作为 Prometheus 标签：

- `omc_redis_task_queue_length_total`：队列总长度。
- `omc_redis_task_queue_active_devices`：非空设备队列数。
- `omc_redis_task_queue_max_length`：单设备最大队列长度。
- `omc_redis_task_queue_oldest_age_seconds`：最老任务年龄。
- `omc_redis_task_queue_scan_duration_seconds`：扫描耗时。
- `omc_redis_task_queue_scan_failures_total`：扫描失败次数。
- `omc_redis_task_queue_up`、`omc_redis_task_queue_sample_timestamp_seconds`：观测状态和采样时间。

同时保留和补充 Redis 与 PostgreSQL 对账指标：

- `omc_task_queue_redis_pg_diff`：Redis/PG 状态差异。
- `omc_task_queue_recovery_action_total`：恢复动作次数。
- `omc_task_queue_write_failures_total`：队列写入失败次数。

主要页面：**OMC - 存储与队列治理**中的“Redis cmdq/taskq 积压”和“Redis 最老任务年龄”。

### 4.4 PostgreSQL 持久化队列

新增统一持久化队列 observer，以固定队列名称和状态采样 PostgreSQL 中的可恢复业务任务：

- `device_tasks`
- `async_jobs`
- `parameter_sync_outbox`
- `northbound_outbox`
- `pm_kpi_export`
- `trace_export`
- `backup_tasks`
- `dead_letters`

统一指标包括：

- `omc_persistent_queue_pending{queue,status}`：各队列、各状态的待处理数量。
- `omc_persistent_queue_oldest_age_seconds{queue,status}`：最老任务年龄。
- `omc_persistent_queue_overdue_oldest_age_seconds{queue,status}`：按任务自身 `expires_at` 计算的最大逾期时长；未逾期为 0。
- `omc_persistent_queue_failed_total{queue}`：失败数量。
- `omc_persistent_queue_dead_letter_total{queue}`：死信数量。
- `omc_persistent_queue_processed_total{queue,result}`：终态处理数量。
- `omc_persistent_queue_observer_failures_total{queue}`：观测失败次数。
- `omc_persistent_queue_up{queue}`、`omc_persistent_queue_sample_timestamp_seconds{queue}`：观测状态和采样时间。

主要页面：**OMC - 存储与队列治理**中的“PostgreSQL 持久化队列”和“持久化队列最老任务”。

空队列会输出 0；数据库查询失败时保留业务指标上一次值，并通过 `up` 和 failure 指标表示不可用，避免把“采集失败”误判为空队列。

### 4.5 写入保护监控

新增写入准入指标：

- `omc_storage_admission_state`：`normal=0`、`warning=0`、`blocked=1`、`unknown=2`。
- `omc_storage_write_rejected_total`：写入被拒绝次数。
- `omc_storage_write_degraded_total`：告警或未知状态下的降级写入次数。
- `omc_storage_check_failures_total`：容量/准入检查失败次数。
- `omc_storage_policy_info`：当前策略信息。

主要页面：

- **OMC - 存储与队列治理**：查看写入保护状态和最近 5 分钟拒绝次数。
- OMC → 系统管理 → **资源与存储保护**：查看容量、策略、当前状态和审计。

## 5. OMC“资源与存储保护”页面说明

### 5.1 页面展示内容

页面路由：`/system/storage-protection`。

页面包含：

1. **容量总览**：统一物理根文件系统的容量、已用空间、使用率和状态；逻辑分类只作参考。
2. **保护策略列表**：统一物理目标的告警/阻断/恢复阈值、当前状态和是否启用。
3. **新增/编辑保护策略**：表单不再提供目标类型、写入范围、目标标识输入；系统固定使用 `filesystem/root`，用户只配置阈值、检查周期和容量未知时的处理方式。
4. **状态变更审计**：记录从正常、告警、阻断、未知之间切换的原因和观测比例。

### 5.2 可配置项

| 配置项 | 说明 |
|---|---|
| 物理存储目标 | 固定为 `filesystem/root`，对应宿主机 `/` |
| 写入范围 | 策略固定为 `all`；upload、log、backup、report、trace、pm、mr 仅作为业务优先级/审计分类 |
| 告警阈值 | 使用率达到该比例进入 warning |
| 阻断阈值 | 使用率达到该比例后阻断受控业务写入 |
| 恢复阈值 | 使用率下降到该比例后恢复写入，形成迟滞，避免反复切换 |
| 检查周期 | 周期性重新采集容量和评估策略 |
| 容量未知时 | `allow_with_alarm`：允许但告警；`block_new_uploads`：阻断新写入 |

页面当前提示“有效期与清理策略属于后续容量治理阶段”。本次已完成容量观测、阈值策略和写入准入，统一 retention 配置和清理编排不属于本次已落地页面功能。

### 5.3 已接入的业务写入入口和 OMC 服务日志阻断

当前写入保护服务已接入：

- ACS 文件上报：普通文件、PM 文件、MR 文件、配置备份按写入类型判断。
- 文件管理服务的 MinIO 上传。
- 报表生成后的 MinIO 写入。
- Trace 导出到 MinIO 的写入。

OMC 应用服务日志已接入同一物理容量准入状态：

- `app`、`acs`、`worker` 的 zap 日志同时写 stdout 和挂载日志文件；状态进入 `blocked` 时，logger core 在编码前丢弃日志，两个输出都不会产生新日志行。
- ACS 独立 `protocol.log` 使用同一门禁；日志轮转、压缩和过期归档任务在门禁关闭时也停止，避免维护任务继续产生日志写入。
- 状态为 `unknown` 时日志门禁按 fail-closed 处理；恢复到 `normal` 或 `warning` 后重新放行。无启用策略时保持放行。

这里的“OMC 服务日志”特指上述三个 Go 应用服务。Nginx、PostgreSQL、Redis、NATS、MinIO、Prometheus、Loki、Tempo 和 Docker daemon 日志暂不由该门禁控制，继续使用各自的日志/保留策略和主机磁盘告警治理。

## 6. Prometheus 告警

本次新增 `deployments/monitoring/alerts/storage-queue-alerts.yml`，主要告警如下：

| 告警 | 默认条件 |
|---|---|
| `RedisTaskQueueBacklogHigh` | Redis 队列积压超过 1000，持续 10 分钟 |
| `RedisTaskQueueOldestAgeHigh` | Redis 最老任务超过最长业务 TTL 60 分钟及 5 分钟清理宽限，持续 10 分钟 |
| `RedisTaskQueueObserverUnavailable` | Redis 队列观测不可用，持续 5 分钟 |
| `PersistentQueueBacklogHigh` | PostgreSQL 持久化队列 pending/running 待处理任务超过 1000，持续 10 分钟 |
| `PersistentQueueInFlightStale` | `device_tasks` sent 任务超过自身 `expires_at` 5 分钟，且持续 10 分钟未清理 |
| `PersistentQueueObserverUnavailable` | PostgreSQL 队列观测不可用，持续 5 分钟 |
| `NATSConsumerBacklogHigh` | NATS Consumer pending 超过 1000，持续 10 分钟 |
| `NATSConsumerObserverUnavailable` | NATS 队列观测不可用，持续 5 分钟 |
| `StorageCapacityWarning` | 存储使用率超过 80%，持续 10 分钟 |
| `StorageCapacityCritical` | 存储使用率超过 90%，持续 5 分钟 |
| `StorageWriteAdmissionBlocked` | 写入准入状态为 blocked，持续 2 分钟 |
| `StorageWriteRejected` | 最近 5 分钟出现被拒绝写入，持续 2 分钟 |

主机 CPU、内存、磁盘、容器 OOM、PM 队列等原有告警继续保留，并在现有规则文件中按 Docker Compose 标签口径修正。

## 8. 自测环境验证结果

在 113 自测环境中已验证：

- Grafana“OMC - 存储与队列治理”可以正常打开并显示 8 个治理面板。
- Prometheus 监控目标全部为 `up`。
- 统一根文件系统使用率约 84.18%；MinIO/数据库数值仅作为逻辑占用观测，不作为独立物理阈值。
- PostgreSQL 持久化队列 `device_tasks` 有积压数据，Prometheus 可查询到当前数量。
- OMC“资源与存储保护”页面可以展示统一物理根文件系统容量、策略配置和审计区域。
- 当前环境未创建保护策略，因此没有产生策略状态和拒绝写入数据；配置策略后相关状态指标才会出现业务时间序列。
