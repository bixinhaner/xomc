# OMC 资源、队列与存储保护监控自测验证报告

> **验证日期**：2026-07-28
> **验证环境**：113 自测环境（实际连接 `172.21.158.113`）
> **验证版本**：MR !360，提交 `2c49ced97`
> **验证方式**：可见 Chrome 实际页面 + Prometheus 实时查询 + OMC/ Grafana 健康检查

## 1. 验证结论

本次改动的核心链路已经部署并可访问：OMC 存储保护页面、Grafana 新增治理仪表盘、Prometheus 新增指标和告警规则均能加载。

但当前不能判定为“全部通过”，发现以下需要回修的问题：

1. PostgreSQL 持久化队列 Grafana 查询对 app 和 worker 两份相同观测值执行 `sum`，会造成数量翻倍。
2. cAdvisor 实际暴露的容器标识为 `/system.slice/docker-<id>.scope`，现有 Grafana 查询按 `service` 或 `/docker/.+` 过滤后无数据，容器 CPU/内存面板显示 `No data`。
3. 写入保护当前没有配置策略，`omc_storage_admission_state` 和拒绝计数没有序列，Grafana 显示 `No data`。这是无策略场景的空态，但页面没有显示“未配置策略”的明确监控状态。
4. MinIO 业务分类当前只实际采集 `config-backup`，且 app、acs、worker 暴露了重复的分类序列，日志、报表、Trace 等分类尚未形成有效业务容量统计。

## 4. 发现的问题

### 4.1 cAdvisor 容器 CPU/内存面板无数据

Grafana 页面实测：

- `OMC - 服务资源与运行时` 的最高 CPU/内存饱和度、容器 CPU/内存、CFS 限流、网络等面板显示 `No data`。
- `OMCGo - Nginx 流量 / 主机 / 容器资源` 的“容器 CPU（按容器 ID）”“容器内存（按容器 ID）”显示 `No data`。

Prometheus 对照：

- `count(container_cpu_usage_seconds_total)=54`，说明 cAdvisor 有原始数据。
- `count(container_cpu_usage_seconds_total{container_id=~"/docker/.+"})=0`。
- `count(container_cpu_usage_seconds_total{service=~"app|acs|worker"})=0`。
- 实际容器标识为 `/system.slice/docker-<id>.scope`，同时存在 `id` 和 `container_id`，但没有当前查询所依赖的 `service` 标签。

结论：不是 cAdvisor target down，而是指标 relabel/面板过滤条件与 113 环境实际标签不一致。需要先补齐 Prometheus metric relabel 的 Compose service 映射，或统一按 Docker cgroup scope 过滤并用映射规则恢复服务名，再重新验证 CPU、内存、网络、IO、重启和 OOM 面板。

### 4.2 写入保护当前没有可展示的策略状态

OMC 页面当前显示：

- 保护策略：暂无保护策略；
- 当前阻断：当前没有被阻断的写入；
- 审计记录：暂无状态变更记录。

Prometheus 查询结果：

- `omc_storage_policy_info`：无序列；
- `omc_storage_admission_state`：无序列；
- `omc_storage_write_rejected_total`：无序列。

因此 Grafana“写入保护状态”显示 `No data`。这符合当前没有配置策略的事实，但监控层面无法区分“未配置策略”和“指标采集失败”。建议增加无策略的明确状态或策略信息序列，并在面板中显示“未配置保护策略”。

本次未保存临时保护策略，也未人为制造磁盘满和写入拒绝场景，原因是该操作会改变 113 自测环境的写入准入行为；所以“阻断新写入、拒绝计数递增、恢复阈值回切”仍需在可回滚的专用测试环境完成。

### 4.3 MinIO 业务分类采集范围不完整

当前 `omc_minio_bucket_usage_bytes` 实际只返回 `config-backup` 分类，并分别从 app、acs、worker 暴露为 0 值序列。新仪表盘能够加载分类面板，但当前不能据此统计日志、报表、Trace、文件包等分类的独立容量。

MinIO 集群总使用率 `78.58%` 可用且准确；业务分类容量属于采集范围不完整和重复序列问题，需要后续补齐固定分类 observer，并在 Grafana 端按分类去重/聚合。

## 6. 建议回修顺序

1. P0：修正 PostgreSQL 队列 Grafana 查询去重，避免积压和终态数量翻倍。
2. P0：修正 cAdvisor 标签映射，恢复服务级 CPU、内存、网络、IO、重启和 OOM 面板数据。
3. P1：统一 app/worker 的 NATS、Redis、PostgreSQL、MinIO 观测源展示口径，并补充观测源健康状态。
4. P1：补齐 MinIO 日志、报表、Trace、文件包等固定业务分类采集。
5. P1：为无保护策略场景增加明确的“未配置”状态，并在可回滚环境验证阻断、拒绝、恢复和审计链路。
6. P1：处理 113 环境 Redis worker observer=0 和 PM sample stale 告警，避免误判为业务队列正常。
