# OMC 容器栈内存分配与设备承载量规划

> 编写日期：2026-06-11 ｜ 适用：单机 docker compose 部署（dev / 一体化小规模商用）
> 数据来源：2026-06-11 KPI 上传压测实测（`omcgo/test/pmperf/`）+ 代码事实接地（迁移/配置/指标库）。
> 本文只覆盖 **OMC 容器栈** 的内存切分；不含同机 boss/cgrates/temporal 等外部栈。

---

## 1. 背景与现状问题

本机 Docker Desktop VM 由 6GB 上调到 **12GB**（物理 Mac 24GB，富余充足）。借此机会重排 OMC 各服务内存。当前（6GB 时代）配置存在三处明显问题：

| 问题 | 现状 | 影响 |
|------|------|------|
| **Redis 严重过配** | cap 3GB，实测仅用 5MB | 3GB 上限给了最不吃内存的服务，是纯浪费（历史 OOM 事故后加的保险，但 OMC 实际量级用不到）|
| **PG 自调参数对不上容器** | TimescaleDB 镜像 `timescaledb-tune` 按 **VM 总量**（6GB）调，不是按 **容器 cap**（2GB）：`shared_buffers=1.45GB`（占容器 74%）、`effective_cache_size=4.34GB`（**超过容器 cap**）| PG 长期贴在 87-92%，`shared_buffers`+`maintenance_work_mem(740MB)` 在压缩/建索引时可能 >2GB → **潜在 OOM-kill**；规划器被 4.34GB 的假缓存误导 |
| **work_mem 过低** | 1.23MB（被 max_connections=300 摊薄） | KPI 在线聚合（GROUP BY/排序）一超就落盘，直接拖慢 PG-bound 的入库 |

**结论先行**：OMC 是**重 PG 型**负载（已实测 ingest 为 PG-bound：worker CPU ~20%、PG CPU 55-220%/内存 92%）。内存应**向 PG 倾斜**，把 Redis 的浪费回收，并**显式钉 PG 内部参数**（不靠镜像自调），使容器 cap 真正被用上且安全。

---

## 2. 设计原则

1. **容器 `limits.memory` 是“安全上限/熔断”，不是预留**。非 swarm 的 compose 下 limits 走 cgroup 硬限，reservations 基本是软提示。各服务 cap 之和**可以超过 VM**——因为除 PG 外的服务实测都只用几十 MB，不会同时顶到天花板。**真正会吃满 cap 的只有 PG**，所以 PG 的 cap + 内部参数是唯一关键旋钮。
2. **所有业务必须正常**：核心数据面（postgres/redis/nats/minio）+ 应用（acs/app/worker/web）在任何档都常驻可用。observability（prometheus/grafana/loki/tempo/otel/exporters，limits 合计 ~4.2GB）按档开关：6GB 档整组关闭，12GB 起逐步开。
3. **PG 内部参数随档显式设置**（compose `command` 加 `-c` 覆盖镜像自调）：
   - `shared_buffers` ≈ 容器 cap 的 25%
   - `effective_cache_size` ≈ 容器 cap 的 60-70%（反映 shared_buffers + 该容器可用页缓存，**不得超过容器 cap**）
   - `maintenance_work_mem` 适度（压缩/建索引）；**硬约束：容器 cap ≥ shared_buffers + maintenance_work_mem + 连接 backend 余量**
   - `work_mem` 随档抬高（KPI 聚合的关键），但注意 `work_mem × 活跃连接` 的上界
4. **Redis 回收**：`maxmemory` 与容器 cap 同步压到与实际负载匹配（队列/会话丢失可从 PG 双写或重报恢复）。

## 3. 四档内存分配方案

> 单位 GB。observability 一列为整组合计预算（多个容器）。“OS/Docker 余量”是留给 VM 内核+引擎+页缓存的部分。
> caps 之和允许 > VM（见原则 1）；表末“实测峰值占用”才是真实需要量。

### 3.1 容器内存上限（limits.memory）

| 服务 | 6GB 档 | **12GB 档（本机采用）** | 26GB 档 | 32GB+ 档 | 说明 |
|------|:---:|:---:|:---:|:---:|------|
| **postgres** | 2.5 | **4** | 12 | 16 | 唯一会吃满 cap 的服务；高档需同步抬 CPU |
| redis | 0.5 | **0.75** | 1.5 | 2 | maxmemory 同步：384m/512m/1g/1.5g |
| nats | 0.5 | **0.75** | 1.5 | 2 | PM 突发 in-flight 堆积留量 |
| minio | 0.75 | **1** | 2 | 4 | 随对象数/分片缓冲 |
| acs | 0.5 | **0.75** | 1.5 | 1.5×N副本 | 会话内存随设备线性，>1万设备需多副本 |
| app | 0.75 | **1** | 2 | 2×N副本 | 近似常量，余量给突发 |
| worker | 0.75 | **1** | 2 | 2×N副本 | PM/KPI 解析；高档建议多副本横扩 |
| web(nginx) | 0.25 | **0.25** | 0.4 | 0.5 | 静态壳，常量 |
| observability（整组）| 关闭 | ~2.5（可选）| ~4 | ~6 | prometheus 随 series（=设备×指标）增长 |
| **OS/Docker 余量** | ~1 | ~1.5 | ~2 | ~3 | VM 内核/引擎/页缓存 |
| 核心 caps 合计 | ~6.5 | ~9.5 | ~22 | ~30 | （含 obs，未含 OS 余量）|
| **实测峰值占用** | ~3.5 | ~6 | 视设备数 | 视设备数 | 远低于 caps（除 PG）|

> 本机 12GB 档实际只起 8 个核心容器（observability 不在本地起栈清单内），峰值占用 ~5-6GB，留 6GB 给 PG 增长 + boss 栈共存。

### 3.2 PostgreSQL 内部参数（compose `command -c`）

| 参数 | 6GB(PG 2.5g) | **12GB(PG 4g)** | 26GB(PG 12g) | 32GB+(PG 16g) |
|------|:---:|:---:|:---:|:---:|
| `shared_buffers` | 640MB | **1GB** | 3GB | 4GB |
| `effective_cache_size` | 1.5GB | **2.5GB** | 8GB | 11GB |
| `work_mem` | 6MB | **12MB** | 24MB | 32MB |
| `maintenance_work_mem` | 256MB | **512MB** | 1GB | 2GB |
| `max_wal_size` | 1GB | **2GB** | 4GB | 8GB |
| `max_connections` | 300 | **300** | 300（+pgbouncer）| pgbouncer 必备 |
| PG `cpus`（compose）| 2 | 2 | 4-6 | 6-8 |

校验（12GB 档）：`shared_buffers 1G + maintenance_work_mem 512M + work_mem 12M×~80活跃 ≈ 0.96G + 页缓存` ≈ 2.5-3G < **4G cap** ✓ 安全。`effective_cache_size 2.5G < 4G cap` ✓ 不再撒谎。

## 4. 设备承载量估算

> 本节经一轮对抗校验（adversarial review）修正：承载量必须以**实测的 files/s 硬锚**为准、与 rows/s 取小，不能单用 rows/s 外推（否则低行数制式 NR/GSM 会被夸大 2-5 倍）。

### 4.1 换算模型（两条约束取小）

承载量 = **min（① files/s 能跟上、② rows/s 能跟上）**，再被 ③ 存储、④ 会话/连接 封顶。内存主要抬高 ① 和 ②。

```
每设备产文件率 = 1 文件 / 900s（15min 周期，1 文件/周期，96 文件/天/设备）
N_max ≈ min(  文件处理率(文件/s) × 900 ,  行入库率(行/s) × 900 ÷ 每设备每周期行数 )
```

- **唯一硬实测锚**：大表（3.2M 行）200 并发 = **20 文件/s**（单文件 45ms）；空表 30 文件/s。生产表恒大 → 取稳态 ~20 文件/s 为 6GB 基准。
- **per-file 成本 ≈ 固定开销(NATS/MinIO/解析/事务 ~20-25ms) + 行数×~0.02ms**：故 LTE(1180行)单文件 ~49ms、GSM(60行)~26ms → **files/s 随 RAT 变**（LTE 慢、GSM 快），不是常数；但 GSM 也被“固定开销”封顶，不会无限高。
- **每文件行数**（counter+派生 KPI）：LTE/BLQ ≈ 1180、NR/GNB ≈ 286、GSM/BSC ≈ 75；混合 ≈ 480。
- **内存↔吞吐**：shared_buffers 增大→活跃 chunk 的唯一索引页常驻→减少 UPSERT 冲突探测的随机 IO（实测大表 45ms vs 空表 28ms 的退化来源）；work_mem 放宽→KPI 聚合不溢盘。随内存档**亚线性**提升 files/s（6G→26G 约 3 倍），26G 后受单机磁盘随机写 IO 封顶。

### 4.2 承载量结果（每档 files/s 估值 → 设备数；区间含 RAT 差异）

| 档 | 估 files/s(混合) | LTE 为主 | **混合** | GSM 为主 | 主瓶颈 |
|---|:---:|:---:|:---:|:---:|------|
| **6GB** | ~20（实测） | ~7k | **~15k–18k** | ~25k | PG 2.5g 缓存 + 2 CPU；observability 必须关 |
| **12GB** | ~30–40 | ~12k | **~25k–35k** | ~45k | PG 写入/CPU；舒适 dev/试点档 |
| **26GB** | ~50–70 | ~24k | **~50k–60k** | ~65k（撞 ACS/连接顶）| PG 单机写入 + CPU（PG cpus→4-6）；>1万并发需 ACS 多副本 |
| **32GB+** | ~70–90（单机顶）| ~30k | **~65k–80k** | ~80k | **单机天花板 ~8万（混合）**；10万+ 必须横扩，RAM 不再是主杠杆 |

> 与初版相比，**GSM/NR 档已从 ~10万 下修到 files/s 顶以内**——低行数制式仍受 per-file 固定开销限制，不能用 rows/s 推到天上。

### 4.3 为什么是这些数（四个必须说清的前提）

1. **上传周期是最大杠杆**：上表按 15min/96 文件/天。放宽到 1h（`periodic_upload_interval=3600`）承载量 **×4**，日级再 ×24。运营商不需要 15min 粒度时，这是最廉价的扩容手段。
2. **RAT 构成决定单文件成本**：LTE 单文件 ~1180 行 ≈ GSM 的 ~16×，但因有固定 per-file 开销，files/s 只差 ~2× 不是 16×。故 LTE-为主取低端、GSM-为主取高端，但都被 files/s 封顶。
3. **磁盘×保留期是独立、往往更紧的约束**（与内存无关）：
   - 压缩/保留（已核实）：pm_metrics 7 天后 columnstore 压缩(~10-15×)、**30 天后丢弃**；小时/天聚合表保留 180 天（体积小）。
   - 每设备每天原始量：混合 ~17MB（96×480×375B）、LTE ~42MB；30 天（7天原始+23天压缩）≈ 混合 **~150MB/设备**、LTE **~380MB/设备**。
   - **本机磁盘 256GB** → 混合约 **~1,500-1,700 设备**即写满 30 天历史，**远早于内存吞吐上限**。
   - 即：**12GB 内存能“实时跟上” ~30k 混合设备的上报，但本机磁盘只能“留存” ~1.6k 设备的 30 天数据**。生产 10万-100万必须配大容量独立存储 + 保留期/降采样。
4. **ACS 会话/连接**：ACS 周期性短连接，`max_concurrent=10000`/实例。Inform 周期 300s + 会话处理仅数秒 → 稳态并发 ≈ N×(处理时长/300)，加抖动后单实例可远超 1 万设备；但**开站/同步风暴**（设备齐发 Inform）撞 10000 准入上限，需 Inform 间隔抖动。连接池实测 **dev 140 / prod 180，上限 300**；单副本余量充足，**多副本（N≥3）累加逼近 300 时必上 pgbouncer**。
5. **observability 内存与设备数解耦**（已核实）：业务指标标签为 status/carrier 等**有界维度**，无 per-device 标签，prometheus 活跃 series 不随设备数爆炸 → obs 内存按档固定即可，无需随规模上调。

## 5. 横向扩展（32GB+ / 10万-100万级）

单机 PG 内存到 16GB 后再加 RAM 收益递减，瓶颈转为**单机 PG 写入吞吐 + 连接数 + 磁盘**。百万级目标（项目既定）需架构演进，非调内存：

1. **pgbouncer**：连接池逼近 `max_connections=300` 前置 transaction pooling 复用（既定演进项）。
2. **worker / acs 多副本**：worker 解析 CPU 可线性横扩；acs 每实例 ~1万并发会话准入，多实例分担。
3. **独立 PG / TimescaleDB 节点**：把时序（pm_metrics 等）从业务库剥离到专用 TimescaleDB（可多节点/分布式 hypertable），业务 PG 单独。
4. **保留期降采样**：原始 15min 仅保留短期（如 7-30天），长期看小时/天聚合表（已 180天保留），大幅削减存储与写放大。
5. **PM 文件率分片**：按设备分片到多 ACS/MinIO/NATS consumer，避免单点 NATS/worker 成为漏斗。

## 6. 本机落地（12GB 档）

- VM：Docker Desktop 已置 `MemoryMiB=12288`，重启后生效（实测 `docker info` Total Memory ≈ 11.67GiB）✓。
- compose：`deployments/docker/docker-compose.yml` 已按 §3 的 **12GB 档** 调整 postgres/redis/nats/minio/acs/app/worker/web 的 `limits.memory` + postgres `-c` 参数 + redis `maxmemory`。
- 起栈（本机端口偏移见 [[omc-local-stack-bringup]]）：
  ```bash
  docker compose -p omc -f deployments/docker/docker-compose.yml -f /tmp/omc-ports-override.yml \
    up -d --no-build postgres redis nats minio migrate-schema migrate-seed app worker acs web
  ```
- 验证：`docker stats` 看各 cap 已更新、PG `shared_buffers/work_mem` 经 `SHOW` 确认生效。

> 其它档（6/26/32GB+）参数见 §3，切换时同步改 compose `limits.memory` 与 PG `-c` 参数；observability 按 §3 开关。
