当前 Issue 只重建**邮件通知**业务闭环。旧项目短信链路仅作为边界依据，不在本 MR 中实现或验收：

```text
旧短信：告警产生/清除
  → Redis alarmInvokeKafkaQueue
  → 消费者
  → Kafka topic
  → 外部短信/北向系统

当前邮件：SMTP 通道配置
  → 告警订阅或 KPI 定期报表
  → 数据库异步任务
```

旧短信链路中 Kafka 接收成功不代表手机收到短信。若后续需要短信，应另建需求，明确短信服务商、回执、重试、限流和审计，不能塞入本次邮件 MR。

### 4.1 系统级 SMTP 通道

路径：`System → Settings → Notification Setting`

189 当前页面可见：

### 4.2 告警邮件订阅

路径：`Alarm → Notification Setting`

189 当前页面可见：

- 全局 `Email Notification` 开关和默认收件人；
- 多收件人使用分号分隔；
- 告警模板可独立启停；
- 模板支持实时、10 分钟等发送周期；
- 模板可配置容忍/聚合时间；
- 模板可填写自己的收件人；
- 可决定是否合并全局默认收件人。

实际只读打开一个模板并取消退出，确认编辑框包含 `Enable`、`Interval`、`Tolerance Duration`、模板收件人和 `Notify the Default recipients`。这说明老 OMC 业务语义是：

```text
系统 SMTP 通道
  + 全局默认收件人
  + 告警模板收件人
  + 是否合并默认收件人
  + 实时/周期及容忍时间
  → 告警邮件
```

新项目用“SMTP 设置 + 告警邮件订阅”承接同一业务分层，不把发件账号与业务收件人混为一谈。为避免误发，受控验收订阅必须关闭默认收件人合并，并只填写 `hezhenguo@baicells.com`。

### 6.5 告警实时链路并存演练

复用本地持久化 NATS 启动新 Worker 时，发现 ALARM stream 使用 `WorkQueuePolicy`，邮件和北向消费者不能同时过滤相同的 `alarm.raised` / `alarm.cleared`。这会导致先创建的消费者正常、后创建的消费者启动失败，不是简单更换 durable 名称可以解决的问题。

修复保持业务语义不变：AlarmEngine 在原有北向生命周期事件之外，同步发布 `alarm.email.raised` / `alarm.email.cleared` 专用事件；邮件 Worker 只消费专用主题。实际容器验证结果：

- 北向消费者继续使用 `alarm.raised`、`alarm.cleared`；
- 邮件消费者使用 `alarm.email.raised`、`alarm.email.cleared`；
- 两类消费者同时存在，过滤主题不重叠；
- 邮件消费者启动成功，pending/ack pending 均为 `0`；
- App、Worker、PostgreSQL、TimescaleDB、Redis、NATS、MinIO 健康检查通过。

此调整只隔离消息传输主题，不改变默认收件人、订阅筛选、实时/周期、容忍时间、告警正文、投递重试或发送记录。
