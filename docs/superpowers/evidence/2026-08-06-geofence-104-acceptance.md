## 1. 验收目标与判定边界

本次验收证明新项目是否覆盖老 OMC 的以下业务闭环：

```text
系统总开关
  → 运营商开关
  → 创建并发布围栏
  → 查询、定位和编辑
  → 候选预览与设备绑定/改绑
  → TR-069 或第三方位置上报
  → 连续位置判定
  → 越界告警与 IPSec/RF 去激活
  → 回区后的安全恢复
  → 禁用、归档、审计和现场恢复
```

### #105820 业务约束

1. 同一设备同一时刻只能有一个 active 的 `polygon_allow_zone` 绑定；加入新围栏必须经过
   `move` 预览并原子替换原绑定，不能叠加。
2. 围栏名称修改保持 `fence_id` 不变，不创建几何版本、不改变绑定、不生成设备控制动作。
3. 几何和策略版本不可变；编辑先创建草稿，发布后才切换当前版本。
4. 位置来源按设备配置在 `tr069/external` 中唯一选取；无效、过期、乱序位置为 `unknown`，
   不能猜测为安全或越界。
5. `off/observe` 不创建设备控制任务；`enforce` 仍以授权真机的 SPV、GPV 和最终参数值为
   验收门禁。
6. 禁用、解绑和归档不得隐式激活设备；回区只能恢复本系统此前已验证去激活且实际修改的参数。
7. 修复完成后先执行自动化回归，再重新部署 104，按本文件原用例顺序补齐证据；系统和运营商
   开关在真机控制验收完成前保持 `off`。

验收遵循以下原则：

1. 页面提示成功只证明请求被受理，不能替代数据库事实、异步任务终态和设备回读。
2. `off/observe` 不得创建设备控制任务；`enforce` 必须取得真实设备 SPV、GPV 和最终参数值证据。

6. 所有危险操作必须记录测试关联 ID、操作原因和恢复动作。
7. 未取得真实回执的项目只能标记为“代码具备/待真机验收”，不能标记为通过。

## 5. 页面与配置验收

### GF-01 默认关闭与入口隐藏

前置：P0 全部通过，系统模式为 `off`。

步骤：

1. 使用超级管理员登录 104。
2. 打开 `系统管理 → 系统配置 → 电子围栏`。
3. 记录“电子围栏总开关”的状态和说明。
4. 打开 `拓扑管理 → GIS 地图`。
5. 刷新页面并重新登录一次。

预期：

- 总开关为关闭；
- GIS 顶部不显示“电子围栏”入口；
- 普通用户无法通过按钮或直接写接口绕过系统开关；
- 数据库 `sys_configs(category='geofence',key='mode')` 为 `off`。

证据：系统配置截图、GIS 截图、availability 响应、数据库查询结果。

### GF-02 开启系统总开关并验证持久化

步骤：

1. 超级管理员打开电子围栏配置页。
2. 点击系统总开关。
3. 核对影响预览：已启用围栏数、活动绑定数、新增观察设备数。
4. 确认开启；记录请求和响应。
5. 刷新配置页，确认开关仍开启。
6. 打开 GIS，确认“电子围栏”入口出现。
7. 重启 `app/worker/web`，重新登录并再次检查。

预期：

- 系统模式变为 `enforce`；
- 只有超级管理员可以修改系统模式；
- GIS 入口由服务端 availability 控制并在刷新、重启后保持；
- 此时运营商仍为 `off`，不得开始位置判定或设备控制。

### GF-03 运营商级开关

步骤：

1. 在 GIS 点击“电子围栏”。
2. 核对当前运营商标识。
3. 打开运营商开关，阅读影响提示并确认。
4. 刷新 GIS，确认开关保持开启。
5. 切换到无权限或另一运营商视图，检查隔离。
6. 关闭运营商开关并确认围栏图层隐藏，然后重新开启以继续后续测试。

预期：

- 运营商开关只影响当前运营商；
- 系统 `enforce` + 运营商 `enforce` 时有效模式才是 `enforce`；
- 关闭运营商开关不会自动激活或恢复设备；
- 请求失败时 UI 恢复服务端权威状态。

### GF-07 编辑名称与重绘区域

1. 编辑测试围栏，只修改名称为约定的修改名称并保存。
2. 确认 `fence_id`、当前版本和绑定均未改变。
3. 再次编辑，选择重绘区域。
4. 调整至少一个顶点并形成草稿版本。
5. 发布新版本。
6. 回查版本列表、当前版本、地图图形和候选设备预览。

预期：

- 改名不创建几何版本、不触发设备控制；
- 重绘和设备绑定是两个独立动作；
- 草稿不影响当前有效区域，发布后才切换当前版本；
- 区域变化后必须重新核对候选和绑定，不自动静默改绑。

### GF-08 启用、禁用与归档

步骤：

1. 对测试围栏执行启用预览，填写原因后确认。
2. 回查列表、地图和数据库状态。
3. 执行禁用预览，核对受影响绑定、设备和活动任务数量。
4. 填写原因后确认禁用。
5. 尝试直接归档仍启用的围栏，确认被拒绝。
6. 在禁用状态执行归档预览并确认。

预期：

- 每次危险操作均先预览并要求原因；
- 归档只允许从 `disabled` 进入；
- 活动批量作业会阻止归档；
- 归档后默认列表和地图不再返回，但历史版本、绑定和控制记录仍保留；
- 禁用/归档不会自动激活设备。

与老系统差异：老页面物理删除并提示设备自动去激活；新系统以可审计归档替代物理删除，
但对活动绑定、最后确认在围栏内且策略明确为 `deactivate` 的设备，仍应生成幂等去激活动作。

## 7. 设备候选、绑定与改绑验收

### GF-09 区域候选预览

步骤：

1. 打开测试围栏的“区域设备预览”。
2. 记录区域内、区域外和无位置设备数量。
3. 核对候选设备运营商、设备组权限和当前位置。

预期：候选由服务端按当前发布几何计算；前端不自行猜测；无权限设备不泄漏；预览不改变绑定。

### GF-10 批量 SN 预览与逐项结果

准备四类输入：有效未绑定 SN、有效但属于其他围栏的 SN、不存在 SN、重复 SN。

步骤：

1. 使用空格、逗号、分号和换行混合输入。
2. 点击绑定预览。
3. 核对 `eligible/move/skipped` 分类和稳定原因码。
4. 未填写原因时尝试提交。
5. 填写测试关联 ID 作为原因并创建绑定任务。
6. 轮询任务总览和逐项结果直到终态。
7. 刷新页面，重新查询绑定列表。

预期：

- 最多接受 1000 个原始输入并去重；
- 不存在或无权访问的 SN 不泄漏设备信息；
- `move` 明确显示原围栏和目标围栏；
- 一项失败不回滚其他成功项；
- 作业总览与逐项结果终态一致，不残留“汇总成功、明细待处理”；
- 保存后从服务端回查，不依赖本地缓存。

### GF-11 单一归属与原子改绑

步骤：

1. 记录设备在原围栏的活动绑定。
2. 在目标围栏预览该 SN，确认显示 `move`。
3. 确认改绑。
4. 同时回查原围栏和目标围栏的绑定列表。
5. 在预览后、任务执行前模拟原归属变化，验证任务跳过而非静默移动新归属。

预期：原 active 绑定标记为 `removed/reassigned`，目标围栏产生唯一 active 绑定；不存在两个活动多边形归属。

### GF-12 绑定管理与导出

步骤：

1. 查看已绑定设备的名称、SN、状态、位置判定、位置版本和时间。
2. 暂停绑定并填写原因。
3. 恢复绑定并填写原因。
4. 导出绑定 CSV，核对只包含当前用户可见设备且不包含原始经纬度。
5. 移除绑定并填写原因。
6. 刷新页面确认状态为 removed 或不再出现在活动清单。

预期：暂停/恢复/移除均可审计；移除只停止该规则后续检查，不自动恢复或激活设备。

回归：设备在线/离线状态必须来自真实读模型，覆盖老项目问题 #107428。

### GF-14 位置来源隔离

步骤：

1. 对默认 `tr069` 设备调用第三方位置接口。
2. 将专用船载测试设备明确切换为 `external`，记录审计。
3. 提交第三方位置并回查。
4. 让该设备再上报 TR-069 GPS，回查位置事实。
5. 恢复原 `location_source_mode`。

预期：

- `tr069` 设备接受 TR069 GPS 和第三方位置，按观测时间防乱序；
- `external` 设备接受第三方位置；
- `external` 模式下 TR-069 GPS 不覆盖权威位置，但其他参数同步不受影响；
- 第三方接口不隐式切换设备模式，相同观测时间幂等。

### GF-15 Observe 判定与告警

前置：系统/运营商有效模式为 `observe`，围栏已启用且设备有 active 绑定。

步骤：

1. 上报围栏内位置，满足连续回区次数。
2. 上报围栏外位置，未满足连续越界次数时检查候选状态。
3. 继续上报围栏外位置直至确认 outside。
4. 重复提交同一位置版本。
5. 上报无效、过期或异常位置。
6. 再上报围栏内位置直至确认 inside。

预期：

- 每次判定关联 binding、围栏版本和 observation version；
- 连续采样达到阈值后才切换 confirmed state；
- outside 产生一条 `GEOFENCE_LOCATION_OUTSIDE` 活动告警；inside 清除对应告警；
- 重复事件不重复生成 evaluation、告警或控制动作；
- 无效位置结果为 `unknown`；
- observe 全程不创建设备 SPV/GPV 控制任务。

## 9. 真实设备控制与恢复验收

本节是能否宣称完整替代老系统的最终门禁，只能对已授权测试设备执行。

### GF-16 越界去激活

前置：

- 测试设备在线；
- 已记录 IPSec、RF、可写 Admin/AdminRF 和所有目标小区只读 OpState 原值；
- 已记录 `InUse`、`NumOfCells`、产品 `radioModes`、ParamModel `NumOfCells.enumValues` 最大能力及
  最终目标实例集合；无法确认有效小区时记录回退到产品/模型最大能力的原因；若最大集合缺少任一
  必要快照证据，记录动作失败而不是缩小目标集；
- 产品模型解析到实际存在、可写的控制参数及只读运行终态；缺任一角色时 fail closed；
- 系统与运营商均为 `enforce`；
- 围栏策略为 `deactivate`。

步骤：

1. 先让设备稳定处于围栏内。
2. 上报连续越界位置直至 outside 边沿。
3. 记录 effective state version、事件 ID 和 control action ID。
4. 检查 SPV 请求参数和值，并确认未向已明确 `InUse=false` 或超过合法 `NumOfCells` 的实例下发。
5. 等待 SPV 终态，再检查 RF、IPSec、Admin/AdminRF 的关联 GPV。
6. 轮询每个目标小区 OpState，直到全部 inactive 或超过产品终态窗口。
7. 核对设备参数树、设备列表独立 RF/激活列、告警和控制动作详情。
8. 重复上报相同越界状态。

预期：

- 动作键为同一设备、状态版本和动作类型的稳定幂等键；
- IPSec、RF、Admin/AdminRF 按已确认产品映射写入关闭值；
- SPV 后控制参数必须 GPV 精确回读一致，并且所有目标小区 OpState=inactive，才标记 `verified`；
- 控制值一致但 OpState 尚未 inactive 时保持 `verifying`；终态超时为 `partial_failed/failed`；
- 缺值、不可写、能力歧义、超时、部分失败或回读不一致不能标记成功；
- 重复越界不创建第二个逻辑去激活动作。

### GF-17 回区安全恢复与失败场景

步骤：

1. 对 GF-16 已 verified 的设备上报连续回区位置。
2. 检查恢复动作只引用最近一条尚未恢复的 verified 去激活动作。
3. 检查恢复参数只包含本系统实际修改且 GPV 已验证的项，并与回区时当前有效小区求交集；无法
   确认时最多恢复原动作拥有的最大实例集合。
4. 验证 IPSec → RF → Admin/AdminRF 的恢复顺序和关联 GPV 回读。
5. 若控制前 OpState=active，轮询并验证恢复后 OpState=active。
6. 分别验证：旧契约 verified、无 verified 所有权、设备离线、SPV 超时、部分参数失败、GPV 不一致、OpState 超时。
7. 完成后恢复所有设备原值并再次回读。

预期：

- 无本系统 verified 去激活记录时不自动激活；
- 前置失败不得恢复 Admin/AdminRF；
- 成功恢复后控制参数与测试前记录一致；原来 active 的小区最终 OpState=active，动作有父子关联；
- 失败、超时和部分成功保留真实状态，可重试或转人工，不产生影子成功。

### 20.2 Web 入口原始日志与 request ID

- 老接口路径通过 104 统一 Web 入口 `8081` 请求时由 Nginx 返回 HTTP `405`；当前只有直连 App 映射端口

  错误体 `request_id` 均原样返回该值。因此 **HTTP 入口的 request ID 生成/透传已证明**。
- 代码核对确认 App 全局 `RequestLogger` 会以结构化字段记录 `request_id、method、path、status、duration_ms、
  client_ip、user_agent`，不记录认证头、完整请求体、SN、船名和精确坐标；这一设计满足脱敏方向。

  与上述 401 请求对应的原始日志行，也尚未补一组授权成功请求的入口原始日志。
- **全链路关联当前不仅是证据缺口，也是实现缺口：**`third_party_location_batches` 只保存
  `idempotency_key/request_hash/status/result`；位置 Outbox `Record`、`DeviceLocationObservedPayload` 和后续
  围栏判定事件没有承载 HTTP request ID。现有 request ID 只在同一 HTTP `context` 的同步日志与 SQL tracer
  中有效，跨 Outbox/NATS 到 Worker、告警和 RF/IPSec 控制后无法继续用同一个 request ID 检索。因此原单
  第 7 项可以判定“入口 request ID 已存在、脱敏字段设计正确”，但“成功请求的原始日志归档及 request ID
  全链路关联”仍未通过。

老项目对此的呈现不是可查询的北向日志：第三方位置请求后 `North Interface Logs` 仍为 0；Redmine 附件

### 20.4 第二角色、重投与不重复控制的含义

- “第二角色权限”指除当前 `System Admin` 外，再用只读或普通运营商角色验证：页面按钮不可见/不可用、
  直接调用写接口返回 403、不能跨运营商或设备组操作，并留下拒绝审计。它用于证明 RBAC 不是只在前端隐藏
  按钮。若 #105820 原单没有权限矩阵要求，本项属于安全扩展验收，不阻塞本次核心签署。
- “重投”指同一第三方位置请求、Outbox 事件或 NATS 消息因超时、进程重启或消息重送而再次到达；
  “不重复控制”指同一业务边沿只产生一次有效告警和一次 RF/IPSec 控制，不因重送重复下发 SPV。
- 当前已通过 API 层幂等：相同 `Idempotency-Key` 同内容返回原结果、同 key 不同内容返回 409、早于当前
  位置的样本被拒绝。尚未执行的是故意重启 App/Worker、重复投递 Outbox/NATS 后的恢复测试；若原单没有
  明确要求故障注入，本项按可靠性扩展验收管理，不阻塞本次核心签署。

### 20.6 设备控制结果展开区 UI 优化记录

本轮在“绑定设备 → 设备控制结果”展开区确认功能数据能够展示，但选中/展开后的可读性较差，后续应作为
前端体验优化项处理，不影响本轮已经取得的控制事实证据。

当前问题：

- 两台设备的结果连续堆叠在同一大块文本中，设备边界和操作批次层级不明显；SN、动作和“已确认”状态与
  参数明细的视觉关联较弱。
- “请求值”“设备回读值”逐条重复，无法快速横向比较期望值与实际值；正常、缺失和不一致参数没有直观
  区分。
- TR069 完整路径很长，当前按普通正文自动换行，出现 `R` / `FTxStatus` 等生硬断行，扫描困难且容易误读。
- 原始路径、实例号和数值使用相同字号与颜色，信息层级不足；深色背景下正文对比度偏低。
- “设备控制结果”标题选中后出现类似输入框焦点的整圈蓝色描边，和折叠面板的视觉语义不一致；右侧数量
  徽标与标题区域也显得拥挤。
- 详情区域纵向占用过大，必须长距离滚动才能看完两个设备，不利于快速判断整批控制是否全部成功。

建议收敛样式：

1. 每台设备使用独立卡片或折叠行，头部固定展示 `SN / 动作 / 最终状态 / 完成时间`，批次总状态与单设备

2. 参数使用表格或紧凑键值行，至少提供“参数、请求值、回读值、结果”四列；请求值和回读值相等时显示
   绿色确认，不一致、缺失或超时时使用明确告警样式。
3. 默认展示友好名称，如“LTE 小区 1 RF”“IPSec 隧道 2”；完整 TR069 path 放在可展开详情或 tooltip，
   使用等宽字体并提供复制按钮，避免在任意字符处断行。
4. RF 与 IPSec 分组展示，并按实例号稳定排序；支持“一键展开全部/收起全部”，减少纵向滚动。
5. 折叠标题使用常规 hover/active 背景和清晰展开箭头，移除输入框式焦点描边；保留键盘焦点时采用符合
   无障碍要求但不干扰内容阅读的 focus-visible 样式。
6. 调整深色模式文字对比度、行距和块间距，使 SN、状态、字段标签和原始路径形成明确的三级层级。

验收标准：在 1366×768 和当前大屏分辨率下，展开两个设备的 RF/IPSec 结果后，无需逐行阅读完整 TR path
即可在 10 秒内判断每台设备的动作、请求/回读是否一致及失败参数；键盘操作时仍能明确识别当前焦点。

### 21.8 Issue #304 语义门禁修订与 2026-08-12 现场补证

21.3、21.6、21.7 的历史结论按当时 GF-16/GF-17 的 RF/IPSec 契约成立，但没有检查只读
`OpState`，不得继续引用为“真实小区去激活”通过证据。老需求文字写“去激活 IPSec 和射频”及
“下发激活/去激活 TR-069 指令”，但旧 `FenceClient/FenceController` 加密，189 也没有实际控制路径
和终态证据，因此不能证明新实现与老系统真实运行终态一致。

Issue #304 的 251 BLQ 现场形成反例：`X_COM_RadioEnable=false` 与 `FAPControl.LTE.OpState=true`
可同时存在，基站本机显示“射频关、已激活”，OMC 列表又因陈旧标准 RF 别名显示“射频开”。由此确认：

1. RF/IPSec-only 动作门禁属于设计和验收语义缺口，不是单一 BLQ 固件问题；
2. 新契约必须验证可写 Admin/AdminRF、RF、IPSec 和只读 OpState；
3. RF 与 OpState 必须独立投影；标准/私有 RF 别名按观测时间归一，最新私有 false 不得被陈旧标准
   true 覆盖；
4. 历史动作默认 `contract_version=1`，不追认为真实去激活，也不作为新契约自动恢复所有权。

同日 452 产品在 251 测试服务器补证：SN `120200055922C8B0068`（仓库设备清单归类为 MLN）在
17:48:01 对三个 FAPService 实例下发私有 `CellConfig.LTE.RAN.RF.AdminCellState=0`，随后设备列表
显示“未激活、射频关”。该证据证明 MLN/452 产品的 `AdminCellState` 可以作为 `AdminRF` 组合控制，
而不是要求每种产品物理上都存在两个不同参数；证据不得外推到 BLN、BM 或仅有同名路径的产品。
但正式 GF-16 签署仍必须补齐该动作的 GPV、目标有效小区 OpState=0、IPSec 和动作终态；历史
SPV 中出现三个实例不能替代 `InUse/NumOfCells` 有效范围证据。

产品能力矩阵和新状态机详见
`docs/superpowers/specs/2026-08-12-geofence-cell-deactivation-capabilities.md`。从本节起，GF-16/GF-17
只按新门禁签署。
