# PM 稀疏存储与小时聚合优化设计

## 状态

- 日期：2026-07-24
- 状态：已确认
- 范围：PM 明细入库、查询兼容、小时聚合、TimescaleDB 存储与运维默认值
- 部署约束：允许重新部署并重建 PM 时序库，不开发旧 PM 数据在线迁移器

## 背景

10000 基站压测运行一夜后，TimescaleDB 数据目录约 678 GiB，其中数据库逻辑大小约
571 GiB，`pm_metrics` 明细分区约 536 GiB，`pm_metrics_hourly` 约 35 GiB；对应的
PM 原始压缩文件只有约 5.7 GiB。

现场抽样和代码分析确认，主要原因不是数据库异常膨胀，而是当前数据模型主动把
“产品支持、但本次文件未报告”的指标补成 `NaN`，随后以 SQL `NULL` 物理入库。
约 70% 的 `pm_metrics` 行为空值。同时，每行还重复保存 UUID、设备字符串、指标路径、
四个时间字段和平均约 118 字节的 `extra JSON`，并维护多个大索引。每个原始指标最终
平均消耗约 314 字节（含索引），导致 5.7 GiB 压缩输入形成约 575 GiB 逻辑数据库。

数据目录比逻辑数据库额外多出的约 100 GiB，主要由以下内容构成：

- XFS speculative preallocation 约 98 GiB；
- 聚合查询当前临时文件约 15.3 GiB；
- WAL 约 4 GiB。

现场关系的死元组比例约 0.018%，TOAST 占用很小，因此不存在足以解释百倍放大的
普通表膨胀或损坏证据。

小时聚合还存在以下问题：

- 扫描大量人为补出的空值行；
- 单次查询持续时间长并产生大量临时文件；
- 对约 16 GiB 自然唯一索引执行海量 `ON CONFLICT` 探测；
- 一个小时任务运行过久后，后续小时任务持续排队；
- 压缩策略只按数据年龄执行，没有和聚合完成水位联动。

## 目标

1. 只物理保存 PM 实际报告的非空值。
2. 保留“测量确实发生、但支持指标没有报告”的完整业务信息。
3. 保持现有 PM API、页面、KPI、CSV 和 `fill_empty` 逻辑结果兼容。
4. 将小时聚合改为有界批处理和整桶版本发布，消除逐行冲突更新。
5. 将新明细及索引物理空间控制在旧方案的 20% 以内。
6. 10000 基站持续压测时，PM 队列不随运行时间增长。
7. 使压缩、保留和磁盘保护感知聚合水位及在途数据。

## 非目标

- 不迁移当前 TimescaleDB 中的旧 PM 压测数据。
- 不改变主库中的设备、配置、用户、告警等业务数据。
- 不用 TimescaleDB continuous aggregate 重写现有聚合语义。
- 不在生产路径长期双写新旧两套明细表。
- 不在本次调整 PM 原始文件和数据库数据的保留周期。
- 不把业务警告、错误和致命数据库日志全部关闭。

## 核心决策

采用“稀疏真实值 + 采集锚点 + 历史指标集版本”的双平面模型：

- 值平面只保存文件实际报告的非空指标值；
- 语义平面保存每次测量的锚点及其当时支持的完整指标集合；
- 查询时组合两个平面，恢复现有的空值和 `filled` 语义。

不采用只删除 `NULL` 行的最小改法，因为它无法区分：

- 测量已发生但指标未报告；
- 该时间完全没有采集；
- 指标在当时尚不属于产品支持集合。

也不优先采用 TimescaleDB continuous aggregate，因为现有聚合包含动态指标集、
迟到数据重算和自定义空值语义，直接改为 continuous aggregate 会增加兼容风险，
且不能解决原始明细的重复元数据问题。

## 业务兼容契约

### 缺失值语义

| 场景 | API 值 | `filled` |
| --- | --- | --- |
| 文件实际报告指标 | 实际值 | `false` |
| 采集锚点存在，支持指标未报告 | `null` | `false` |
| 没有采集，查询请求 `fill_empty` | `null` | `true` |
| 指标不属于采集当时的支持集合 | 不生成逻辑记录 | 不适用 |
| 文件报告了配置外的新指标 | 保存并返回实际值 | `false` |

### 必须保持的接口信息

- 设备 ID、OUI、序列号；
- `carrier`、`technology`；
- `counter_group`、`report_key`；
- `granularity`；
- 对象类型、对象层级、`object_ldn`；
- 指标路径、指标名称和单位；
- 开始时间、结束时间及已有时间字段；
- KPI、Counter、Dashboard 和 CSV 所需字段；
- 分页顺序和稳定的记录标识。

删除 `extra JSON` 后，上述字段分别从设备维度、指标字典、采集锚点和查询粒度推导。
API DTO 尽量不变，主要替换 repository 和聚合实现。

## 数据模型

### `pm_metric_dictionary`

每个指标路径只保存一次。

建议字段：

```text
metric_id       BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
metric_path     TEXT NOT NULL UNIQUE
report_key      TEXT
metric_name     TEXT
unit            TEXT
created_at      TIMESTAMPTZ NOT NULL
updated_at      TIMESTAMPTZ NOT NULL
```

主库已有指标配置同步到 TimescaleDB 时必须补齐当前镜像缺少的 `report_key`。文件中
出现未知指标时，在入库事务中登记最小字典记录，实际值不能被静默丢弃；后续配置同步
可以补齐名称、单位等元数据。

### `pm_metric_sets`

保存产品或测量组在某个历史版本支持的完整指标集合。

建议字段：

```text
metric_set_id   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
product_key     TEXT NOT NULL
counter_group   TEXT NOT NULL
content_hash    BYTEA NOT NULL
metric_ids      BIGINT[] NOT NULL
created_at      TIMESTAMPTZ NOT NULL
UNIQUE (product_key, counter_group, content_hash)
```

写入前对排序后的指标 ID 计算哈希。相同集合复用同一记录，白名单变化时生成新版本。
采集锚点始终引用采集当时的版本，查询历史数据时禁止使用当前白名单倒推。

如果真实压测证明超大数组展开影响查询，可改成集合头表加关联表，但这一变化不得改变
集合内容哈希和锚点引用语义。

### `pm_measurement_anchors`

每个“设备 + 对象 + 时间 + 测量组”保存一条采集锚点，表示测量确实发生。

建议字段：

```text
time            TIMESTAMPTZ NOT NULL
anchor_id       BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL
device_dim_id   BIGINT NOT NULL
object_type     SMALLINT NOT NULL
object_ldn      TEXT NOT NULL
counter_group   TEXT NOT NULL
metric_set_id   BIGINT NOT NULL
source_file_id  BIGINT NOT NULL
granularity     SMALLINT NOT NULL
ingest_batch_id BIGINT NOT NULL
PRIMARY KEY (time, anchor_id)
```

即使该锚点没有任何非空指标值，也必须保存。对象字段应根据现有查询计划决定是否继续
规范化；本设计不以牺牲对象筛选性能换取极限压缩。

锚点表和明细值表都按 `time` 建为 hypertable，并使用相同 chunk 边界。TimescaleDB
要求 hypertable 的唯一约束包含分区列，因此锚点主键使用 `(time, anchor_id)`，
值表使用 `(time, anchor_id, metric_id)` 唯一约束。两个 hypertable 之间使用逻辑引用
和入库事务保证一致性，不增加会限制 chunk 运维的跨 hypertable 外键。

### `pm_metrics`

只保存实际报告的非空值。

建议字段：

```text
time            TIMESTAMPTZ NOT NULL
device_dim_id   BIGINT NOT NULL
anchor_id       BIGINT NOT NULL
metric_id       BIGINT NOT NULL
metric_value    DOUBLE PRECISION NOT NULL
```

不再逐行保存：

- UUID；
- 完整指标路径；
- 设备 OUI、序列号和设备 ID 字符串；
- `extra JSON`；
- `granularity`；
- 可从粒度推导的结束时间；
- 产品、运营商和技术制式等维度文本。

内部稳定顺序使用：

```text
(time, device_dim_id, anchor_id, metric_id)
```

如果 API 必须返回 UUID 格式的 `id`，使用固定命名空间对 `anchor_id + metric_id`
生成确定性 UUID。分页游标保持为不透明字符串，内部编码上述稳定排序键。

### 小时表

小时结果使用同构模型：

- `pm_hourly_anchors` 保存小时内确实存在采集的设备、对象、测量组和指标集并集；
- `pm_metrics_hourly` 只保存聚合后非空的值。

小时内所有采样都缺失的指标不写值表，但通过小时锚点在查询时恢复为 `null`。

## 入库设计

单个 PM 文件按以下顺序处理：

1. 解析、标准化文件中的测量对象和指标。
2. 加载对应产品、测量组的支持指标集合。
3. 登记文件实际报告但字典中尚不存在的指标。
4. 将“配置支持指标 + 文件实际报告指标”规范化后生成指标集版本。
5. 为每个测量对象和采集时间创建锚点。
6. 丢弃仅为兼容语义生成的 `NaN`，批量写入真实非空值。
7. 在同一 TimescaleDB 事务中写入本地文件入库账本和批次提交状态。
8. TimescaleDB 提交后再确认外部工作队列；之后才允许归档或删除原始文件。

现有 `fillMissingSupportedCounters` 的“计算支持集合”能力保留，但不得再把缺失指标展开
成 `pm_metrics` 物理行。

### 幂等

- 原始文件使用来源标识加内容摘要建立唯一性；
- 同一文件重复投递不产生重复数据；
- 需要重新解析文件时，在事务中删除该文件旧批次并重新插入；
- TimescaleDB 本地入库账本、锚点和值必须共同提交或共同回滚；
- 主库工作队列与 TimescaleDB 无法共享本地事务，采用“先提交时序库、再确认队列”
  的至少一次投递；确认失败后的重复消费由本地入库账本幂等吸收。

### 异常

- 未识别设备、产品或不可恢复格式错误进入失败队列并产生可观测告警；
- 临时数据库错误保留原文件并重试；
- 未知指标动态登记，不能静默过滤实际报告值；
- 进程重启后从未完成状态恢复；
- 原始文件在数据库提交前不可删除。

## 查询设计

查询分为两个阶段：

1. 根据时间、设备、对象和测量组筛选锚点，并展开其历史指标集；
2. 左连接稀疏真实值，生成逻辑完整记录。

当调用方未请求完整指标集、只查询指定指标路径时，先将路径解析为 `metric_id`，
只展开匹配指标，避免为所有查询生成完整笛卡尔集合。

`fill_empty` 继续在查询层创建“完全没有采集”的设备、对象、时间骨架。物理锚点恢复
的空值统一标记为 `filled=false`，额外骨架生成的空值标记为 `filled=true`。

以下入口必须使用同一套语义函数或公共查询构造器，防止实现分叉：

- PM 明细和时间序列；
- Counter 查询；
- KPI 原始数据读取；
- Dashboard；
- CSV 导出；
- 小时数据查询。

## 小时聚合设计

### 聚合边界

- 只聚合已封闭小时；
- 保留可配置的迟到数据窗口；
- 每个小时桶使用数据库 advisory lock，避免多个 worker 重复处理；
- 迟到数据进入已完成小时后，把该小时标记为需要重算。

### 有界计算

一个小时按设备 ID 范围或稳定哈希分片计算：

1. 读取该批设备的原始锚点和真实值；
2. 计算小时指标集并集；
3. 仅对非空真实值执行 `SUM`、`AVG`、`MIN`、`MAX` 等现有聚合；
4. 将批次结果写入当前 `building` 版本；
5. 全部批次完成并校验后发布版本，同时提交聚合水位。

每个批次的大小可配置，并根据实际临时文件和内存峰值确定默认值。不得再用
`SET LOCAL work_mem=512MB` 作为处理无界聚合的主要手段。

### 整桶版本发布

增加 `pm_hourly_bucket_versions` 控制表，为每个小时保存当前活动版本。聚合按以下方式
发布：

1. 获取小时锁并创建新的 `building` 版本；
2. 将各设备分片结果带 `bucket_version` 分批写入小时锚点和值表；
3. 校验分片数、锚点数和值行数；
4. 在短事务中把新版本改为 `active`，同时把旧版本改为 `superseded`；
5. 更新聚合水位并提交；
6. 后台在安全窗口清理旧版本。

所有小时查询只读取控制表指向的 `active` 版本。构建期间继续看到完整旧版本，短事务
提交后统一切换到完整新版本，不会暴露半成品。任务失败时删除未发布版本或由清理任务
回收，可安全重试。

该设计替代当前逐行 `ON CONFLICT`，从而删除用于冲突探测的巨大自然唯一索引，同时
避免用一个超长事务承载整个小时的计算和写入。

## 索引设计

明细表的候选最小索引：

```text
(device_dim_id, time, anchor_id)
(metric_id, time, anchor_id)
(time, anchor_id, metric_id) UNIQUE
```

锚点按现有接口需要建立设备时间和对象时间组合索引。最终列顺序必须通过真实 API 的
`EXPLAIN (ANALYZE, BUFFERS)` 决定。

小时表所有查询索引均带上 `bucket_version`，并保留设备时间、指标时间和活动时间桶
发布所需索引，删除：

- UUID 主键；
- 当前没有实际扫描收益的 `object_ldn IS NOT NULL` 部分索引；
- 逐行 `ON CONFLICT` 所需的自然唯一索引；
- 经真实查询计划确认无收益的重复独立时间索引。

不能只根据 `idx_scan=0` 删除索引；必须覆盖 Dashboard、KPI、CSV、明细和小时查询后
再确定最终 DDL。

## Chunk 与压缩

使用同一批 10000 基站数据分别测试 4、12、24 小时 chunk，从以下指标选择默认值：

- 批量写入吞吐；
- 核心查询 P95；
- 压缩率；
- chunk 数量和规划耗时；
- 小时重算成本。

压缩资格由以下条件共同决定：

```text
超过迟到窗口
AND 对应小时聚合已成功
AND 不处于失败或重算状态
```

不能只按 `compress_after 7 days` 判断。压缩的 `segmentby` 和 `orderby` 通过设备查询、
指标查询两类真实负载比较后确定。

删除原始明细还必须确认小时结果完成。保留期本次不变。

## 资源和运维默认值

### CPU 与内存

沿用已经通过 10000 基站现场验证的 release 比例：

- 主库：宿主总核心数的三分之一；
- TimescaleDB：宿主总核心数的二分之一；
- worker：宿主总核心数的四分之一；
- worker 内存继续使用当前已验证默认值，不因本设计强制扩大到 2 GiB。

新聚合通过批次上限满足 worker 内存限制，不能依赖增加内存掩盖无界查询。

### 磁盘保护

- PM 接收背压阈值保持为 70%；
- 保护判断加入未处理原始文件、预计入库量、数据库临时文件、WAL 和文件系统预分配；
- 本次不改变已确认的删除顺序和保留周期；
- 新模型压测后重新计算原始文件到数据库的实际放大系数。

### 数据库日志

release 默认关闭高频诊断日志：

- checkpoint 明细；
- autovacuum 明细；
- SQL statement；
- 慢查询；
- 连接、断开；
- 临时文件逐条日志。

保留 warning、error、fatal，并配置容器日志轮转。现场已经确认数据库容器日志不足
100 KiB，不是当前磁盘占用来源。

## 测试策略

### 黄金样本双跑

使用固定 PM 原始文件分别运行旧实现和新实现，对归一化后的逻辑结果逐项比较：

- 逻辑记录数；
- 非空、空值和 `filled` 数量；
- 设备、对象、时间和指标路径；
- Counter、KPI、Dashboard；
- 小时聚合；
- CSV 字段、顺序和内容；
- 分页顺序及连续翻页结果；
- 历史指标集变更；
- 未知指标。

物理行数允许不同，逻辑结果必须一致。双跑工具只用于离线验证，不进入生产双写路径。

### 必测故障场景

- 支持指标缺失但测量存在；
- 整个测量组没有非空值；
- 完全没有采集并请求 `fill_empty`；
- 指标集合发生变更；
- 同一文件重复投递；
- 入库事务中途进程退出；
- 聚合中途数据库重启；
- 迟到数据触发小时重算；
- 未知指标动态登记；
- 多个 worker 争抢同一小时；
- 聚合临时文件或内存达到上限。

### 回归范围

- repository 单元和集成测试；
- PM API；
- Counter、KPI、Dashboard；
- CSV 导出；
- 前端 PM 页面；
- 主库到 TimescaleDB 指标和设备维度同步。

## 10000 基站验收标准

- 新明细及索引物理空间不超过旧方案的 20%；
- 连续运行一夜后，PM 队列长度和最老任务年龄不持续增长；
- 每个小时聚合在下一小时结束前完成；
- 单聚合任务临时文件峰值目标不超过 2 GiB；
- TimescaleDB 不长期顶满其二分之一总核心数配额；
- worker 不长期顶满其四分之一总核心数配额；
- worker 在现有内存限制内无 OOM；
- 核心 PM API P95 不高于旧实现；
- 黄金样本逻辑结果完全一致；
- 70% 磁盘背压在写满前生效；
- 无新增 flush 失败、超时、重复处理或 DLQ。

空间和性能目标如果未达到，先调整 schema、查询计划、批次和 chunk，不以放宽数据完整性
或业务兼容标准换取通过。

## 部署方案

1. 在独立环境用真实 PM 样本完成黄金双跑。
2. 保存当前镜像、配置、schema 和验收结果。
3. 停止 PM 消费，但继续安全保留接收目录中的原始文件。
4. 等待运行中文件事务完成或回滚。
5. 仅重建 TimescaleDB PM 时序库，保留主库全部业务数据。
6. 部署新镜像和新 schema。
7. 用小批原始文件验证 API、页面、KPI 和 CSV。
8. 恢复 PM 消费并逐步提升到 10000 基站压力。
9. 连续观察队列、CPU、内存、磁盘、临时文件和聚合水位。

删除现有 TimescaleDB 数据卷是破坏性操作，执行时必须再次确认服务器和精确卷名。

## 回退方案

1. 停止新 PM 消费。
2. 保留未处理和失败重试的原始文件。
3. 恢复旧镜像与旧 PM schema。
4. 从原始文件重新处理。

不开发新库到旧库的反向转换。因为 PM 时序库会重新创建，回退能力依赖原始文件在新库
提交成功前不被删除。

## 风险与控制

| 风险 | 控制 |
| --- | --- |
| 删除空值行后历史支持集合丢失 | 锚点绑定不可变的历史指标集版本 |
| 查询时展开指标集导致延迟 | 指定指标先解析 ID，只展开目标指标；用真实计划验收 |
| 去掉 `extra JSON` 导致字段缺失 | 建立字段来源清单并做 API、KPI、CSV 黄金对比 |
| 聚合批处理暴露部分结果 | 新版本构建完成后短事务切换活动版本 |
| 迟到数据导致小时结果过期 | 记录脏小时并幂等重算 |
| 未知指标被过滤 | 动态登记字典并保存真实值 |
| 新 schema 性能不及预期 | 在上线前比较索引、chunk 和压缩组合 |
| 重建时序库误删其他业务数据 | 只操作确认后的 TimescaleDB PM 目标并再次授权 |
| 回退时缺少数据源 | 数据库提交前不删除原始文件 |

## 结论

本方案不把缺失指标作为数十亿条 `NULL` 物理保存，而是将其语义压缩到可复用的指标集
和采集锚点中。它同时去掉每行 UUID、长字符串和 JSON，并把小时聚合从无界扫描加逐行
冲突更新改为有界计算加原子发布。

数据完整性的判断基准是现有业务可观察结果，而不是数据库物理行数。只有黄金样本、
业务回归和 10000 基站一夜压测全部通过，才允许重新部署。
