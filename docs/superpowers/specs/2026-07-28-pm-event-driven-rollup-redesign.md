# PM 事件驱动逐级汇聚重构设计

日期：2026-07-28

状态：已完成口头方案确认，待书面设计复核

## 1. 背景与结论

当前 PM 流式聚合已经具备“原始 Counter 逐级向上组合”的部分能力，但仍把聚合规则当作可运行任务处理：

- 主库播种 12 个全网、设备组、产品、频段 × LTE/NR/GSM 内置任务；
- worker 每 5 分钟把任务定义同步为流式版本；
- 全网任务额外派生 3 个页面不可见的“内置-设备-LTE/NR/GSM”任务；
- 运行时把一个任务的全部成员放进同一个窗口和 Redis Hash；
- 窗口恢复、完成和超时流程会读取完整 Hash。

在 10000 台 LTE 设备压测中，隐藏设备任务的单个小时窗口和单个日窗口均达到：

- 10000 台设备；
- 约 28 组有效 Counter 状态/设备；
- 每个状态保存 sum/count/min/max；
- 1,120,000 个 Redis Hash 字段；
- 约 626 MB/窗口。

设备小时、日、周、月 KPI 是必需业务能力，不能删除。需要删除的是“通过隐藏聚合任务生产设备基础多粒度数据”的实现方式。

本次重构采用以下最终模型：

1. 15 分钟 PM Counter 是唯一入口。
2. 设备小时、日、周、月由上一级原始 Counter 组合状态自动驱动。
3. 设备组、产品、频段、全网和自定义聚合由设备小时 Counter 状态自动驱动。
4. KPI 永远在目标窗口关闭时根据目标窗口原始 Counter 状态计算，禁止平均上一级 KPI。
5. 默认维度和自定义聚合只保存规则定义与不可变版本，不存在可调度、可运行的聚合任务。
6. 系统只运行固定数量的公共消费者、窗口关闭器、恢复器和结果写入器。

## 2. 目标

### 2.1 功能目标

- 保留单设备 15 分钟、小时、日、周、月 Counter/KPI。
- 保留设备组、产品、频段、全网的小时、日、周、月 Counter/KPI。
- 保留自定义聚合规则，规则创建后只处理生效时间之后的数据，不回算历史。
- 支持月粒度。
- 支持一个设备属于多个设备组。
- 没有显式设备组的设备进入系统默认“未分组设备”组。
- 规则可以更新；每次更新生成新的不可变规则版本，并从下一个自然桶边界生效。
- 所有目标窗口在子数据全部到达或超时后关闭和计算。

### 2.2 性能目标

- 设备数量增长只增加设备基础状态，不让分组结果状态随设备数线性增长。
- 同一份 15 分钟 PM 不再分别进入设备、设备组、产品、全网等多个完整累计器。
- 禁止对 PM 汇聚状态执行 `KEYS`、`HGETALL` 或其他无界全量读取。
- Redis 状态按设备数和预计状态大小自动分片。
- 单分片目标内存不超过 16 MiB，单次读取不超过 32 MiB。
- 10000 设备、当前指标规模下，全部活动 PM 汇聚状态目标控制在 512 MiB 以内。
- worker 在窗口最终计算期间保持有界内存，不依赖扩大 Redis/worker 内存掩盖问题。
- NATS 只保留恢复所需的紧凑 Counter 上卷事件，不保存重复 KPI 或重复完整定义。

### 2.3 正确性目标

- sum：逐级传递 sum。
- avg：逐级传递 sum + count，最终按总 sum / 总 count 计算。
- min/max：逐级传递 min/max。
- KPI：每一级都在该级 Counter 完成后重新套用公式。
- 不允许 `AVG(上一级 KPI)`、`SUM(百分比 KPI)` 等双层 KPI 聚合。
- 缺少某个 KPI 公式依赖只影响该 KPI，不把同窗口其他已正确计算的 KPI 标记为不完整。
- 数据完整性与公式可计算性分开记录。

## 3. 非目标

- 不回算规则生效前的历史数据。
- 不兼容旧聚合任务运行状态、旧 Redis `pmagg:*` 窗口或旧 NATS 聚合消息。
- 不迁移当前测试环境中的旧聚合结果。
- 不为旧 `oneshot/continuous/cron_expr/scheduled` 聚合任务语义保留兼容分支。
- 不通过增加 Redis 超时、扩大内存或缩短恢复数据保留时间规避架构问题。
- 不改变系统配置中 PM 时序数据保留策略；NATS 保留和时序数据库保留继续分别管理。

## 4. 领域概念

### 4.1 PM 基础汇聚流水线

常驻公共数据管线，负责所有设备基础时间粒度数据：

```text
设备 15 分钟 Counter
  → 设备小时 Counter/KPI
  → 设备日 Counter/KPI
  → 设备周 Counter/KPI
  → 设备月 Counter/KPI
```

它不是任务，不由 cron 启动，不存在一条“内置-设备-LTE”任务记录。

### 4.2 聚合规则

聚合规则只描述：

- 名称；
- 目标维度；
- 制式；
- 成员选择器；
- 指标选择器；
- 需要的粒度；
- 生效时间；
- 是否启用。

规则本身不运行。符合规则的设备小时 Counter 事件到达时，由公共规则匹配器自动累计。

### 4.3 规则版本

逻辑规则可以编辑，但已经生效的版本不可修改：

```text
逻辑规则
  ├── 版本 1：已生效，不可变
  ├── 版本 2：已生效，不可变
  └── 版本 3：当前版本，不可变
```

更新规则的含义是创建新版本。新版本默认从下一个小时自然桶边界生效，旧版本负责此前窗口。

### 4.4 窗口

窗口是数据状态，不是任务：

- 设备小时窗口：某设备在一个自然小时内的 4 个 15 分钟槽；
- 设备日窗口：某设备在一个自然日内的设备小时 Counter；
- 规则小时窗口：某规则版本在一个小时内的成员设备小时 Counter；
- 规则日窗口：某规则版本在一天内的规则小时 Counter；
- 周/月窗口：由日 Counter 驱动。

## 5. 总体架构

```text
PM 文件解析
  │
  ├─ 原始 Counter 入时序库
  ├─ 计算设备 15 分钟 KPI 并入时序库
  └─ 发布设备 15 分钟 Counter 事件
          │
          ▼
设备小时累计器（按设备/对象/Counter，自动分片）
          │ 全部 4 槽到达或超时
          ├─ 计算并写设备小时 KPI
          ├─ 上卷到设备日累计器
          └─ 发布紧凑设备小时 Counter 事件
                    │
                    ├─ 内置设备组规则
                    ├─ 内置产品规则
                    ├─ 内置频段规则
                    ├─ 内置全网规则
                    └─ 自定义聚合规则
                              │
                              ▼
                    规则小时累计器
                              │ 完整或超时
                              ├─ 计算并写规则小时 KPI
                              ├─ 上卷到规则日累计器
                              └─ 规则小时 Counter 事件

设备日 Counter ──→ 设备日 KPI ──→ 设备周 + 设备月
规则日 Counter ──→ 规则日 KPI ──→ 规则周 + 规则月
```

## 6. 数据驱动流程

### 6.1 15 分钟设备数据

每份 PM 文件解析成功后：

1. 原始 Counter 和 15 分钟 KPI 按现有 PM 配置入时序库。
2. 在同一可靠写入边界生成 `device.15m.counter` outbox 事件。
3. 事件包含设备、对象、Counter ID、数值、槽起止时间和源文件 ID。
4. 重复源文件和重复设备槽通过幂等键去重。

不得从数据库重新读取刚写入的 Counter 来驱动小时累计。

### 6.2 设备小时

每台设备的小时状态独立计算：

- 预期槽数：4；
- 收到 4 槽后立即关闭；
- 到 `hour_end + close_grace` 仍不完整时按超时关闭；
- 完整和超时路径使用同一最终计算代码。

关闭结果：

1. 基于该设备小时原始 Counter 状态计算小时 KPI。
2. 将设备小时 Counter/KPI 批量写入统一结果表。
3. 发布设备小时紧凑 Counter 上卷事件。
4. 删除该设备小时活动状态。

### 6.3 设备日、周、月

- 设备日只消费设备小时 Counter 状态。
- 设备周只消费设备日 Counter 状态。
- 设备月只消费设备日 Counter 状态。
- 每一级继续携带 sum/count/min/max 和源完整性信息。
- 每一级关闭时重新计算该级 KPI。

设备日预期 24 个小时子窗口，设备周预期 7 个日窗口，设备月预期自然月天数。

### 6.4 分析维度小时

设备小时 Counter 事件到达后，规则匹配器从版本快照解析维度归属：

- 设备组：一个设备可以命中多个组；
- 产品：按产品 ID；
- 频段：按设备/小区频段；
- 全网：统一 `network`；
- 自定义组：按规则版本成员快照。

匹配后只把 Counter 组合进目标维度状态，不传递设备 KPI。

规则小时窗口的预期子项来自窗口开始时的成员版本：每个应参与的成员设备应产生一个设备小时 Counter 子项。成员设备小时完整时立即上卷，缺失或不完整时由设备小时超时路径上卷完整性信息；规则窗口收到全部预期成员子项后立即关闭，或在规则小时宽限时间到达后按缺失成员数超时关闭。

如果 10000 台设备属于 10 个设备组，规则小时状态只保留：

```text
10 个设备组 × 对象 × Counter
```

而不是：

```text
10000 台设备 × 对象 × Counter
```

### 6.5 分析维度日、周、月

- 规则日只消费同规则版本的规则小时 Counter。
- 规则周和规则月只消费规则日 Counter。
- 不再次展开成设备数据。
- 不重新查询 15 分钟数据库。

## 7. 完整性、水位与超时

### 7.1 数据完整性

每个上卷状态携带：

- `source_expected_slots`
- `source_received_slots`
- `source_incomplete_slots`
- `children_expected`
- `children_received`

完整性的判定只描述数据到达情况：

```text
children_received >= children_expected
AND source_received_slots >= source_expected_slots
AND source_incomplete_slots = 0
```

### 7.2 公式完整性

每个 KPI 单独记录：

- `formula_complete`
- `missing_dependencies`

窗口数据完整但某个 KPI 缺依赖时：

- 已成功计算的 KPI 保持 `complete=true`；
- 缺依赖 KPI 不写入数值结果，并把指标 ID 与缺失 Counter ID 写入窗口诊断记录和指标；
- 不允许用一个全局 `formulaIncomplete` 把整个窗口全部标为不完整。

### 7.3 超时关闭

超时关闭器只做以下工作：

1. 从带索引的 due-window 集合中领取已过期窗口；
2. 发送窗口关闭请求；
3. 不查询原始 PM；
4. 不重新运行聚合任务；
5. 不扫描所有规则。

数据已收齐但即时最终计算失败的窗口仍保留“数据完整”事实；后续重试成功后不能因为走过超时恢复路径而错误标记为数据不完整。

## 8. 状态存储与自动分片

### 8.1 分片键

设备基础状态按稳定实体键分片：

```text
hash(device_id) % shard_count
```

规则状态按聚合实体分片：

```text
hash(rule_version_id + dimension_key + object_key) % shard_count
```

同一聚合实体的全部 Counter 必须进入同一分片，保证公式计算时不跨分片拉取。

### 8.2 分片数

分片数根据成员数、对象估计和 Counter 数自动计算：

```text
estimated_state_bytes =
  member_or_group_count × estimated_objects × counter_count × bytes_per_state

shard_count =
  next_power_of_two(ceil(estimated_state_bytes / 16MiB))
```

最少 1 个分片，最多由配置限制。规则版本保存时记录估算值和实际分片数。

### 8.3 Redis 表示

禁止把完整 `ContributionValue` JSON 编码进 Hash 字段名。

采用版本字典和短 ID：

- 设备/维度成员字典；
- 对象字典；
- Counter 字典；
- 指标公式字典。

活动状态使用短字段 ID，sum/count/min/max 分离为紧凑 Hash 或等价有界结构。定义元数据只在规则/目录版本中保存一次。

### 8.4 读取

- 存在性检查：`EXISTS meta-key`。
- 元数据读取：精确 `HMGET`。
- 状态读取：按分片 `HSCAN`/批量读取。
- 最终计算：一批实体一批实体处理。
- 删除：分片完成后 `UNLINK`，不在 Redis 主线程同步释放大对象。

禁止：

- `HGETALL` 活动状态；
- 把完整窗口装入一个 Go map；
- 单次生成完整窗口的全部 KPI 和上卷 Payload。

## 9. 事件契约

### 9.1 事件层级

至少保留以下领域事件：

- `pm.rollup.device.15m`
- `pm.rollup.device.hourly`
- `pm.rollup.device.daily`
- `pm.rollup.rule.hourly`
- `pm.rollup.rule.daily`
- `pm.rollup.rule.version.changed`
- `pm.rollup.window.close.requested`

事件主题名称可在实现计划中按现有 EventBus 命名约束落地。

### 9.2 Counter Payload

上卷 Payload 只包含：

- schema/catalog/rule version；
- 源粒度和窗口；
- 分片/批次编号；
- 实体短 ID；
- 对象短 ID；
- Counter 短 ID；
- sum/count/min/max；
- 完整性字段。

不得重复携带：

- 每个状态一份完整 JSON 定义；
- 已经计算好的 KPI；
- 可以由版本字典解析的设备名称、产品名称、规则名称等长字符串。

### 9.3 NATS 保留

沿用已确认的统一策略：

- 15 分钟源事件：保留 2 小时；
- 小时 Counter 事件：保留 48 小时；
- 日 Counter 事件：保留 40 天，设置硬容量上限并启用压缩；
- 周/月不需要作为下一层恢复源长期保留。

NATS 保留只服务状态恢复，不替代时序数据库 PM 保留配置。

## 10. 规则模型

### 10.1 不再使用任务语义

从聚合规则链路移除：

- `mode=oneshot/continuous`
- `cron_expr`
- `status=scheduled/pending/running`
- worker 抢任务；
- 连续任务调度器；
- 内置任务每 5 分钟恢复；
- 从全网规则派生隐藏设备任务。

### 10.2 内置规则

内置规则仍可在管理界面查看和编辑指标，但它们是规则，不是任务：

- 全网 × LTE/NR/GSM；
- 设备组 × LTE/NR/GSM；
- 产品 × LTE/NR/GSM；
- 频段 × LTE/NR/GSM。

设备基础汇聚不作为规则展示，由 PM 基础管线固定生产。

### 10.3 自定义规则

自定义规则保存：

- 目标聚合维度；
- 成员选择器或显式成员；
- 指标；
- 粒度；
- 生效起止时间；
- 可见性和创建者。

创建或更新规则后：

1. 生成不可变版本；
2. 计算成员和指标字典；
3. 估算状态大小并分配分片；
4. 从下一个自然小时桶生效；
5. 发布版本变更控制事件；
6. 不处理生效前历史。

## 11. 成员关系版本

- 设备组、产品、频段和自定义成员都必须使用窗口开始时的成员版本。
- 成员关系变化生成新版本，从下一个自然小时生效。
- 已打开窗口继续使用旧版本，避免一个小时内设备在两个版本间重复或丢失。
- 一个设备命中多个设备组时，分别贡献给每个设备组。
- 没有人工设备组的设备命中系统默认“未分组设备”组。

## 12. 结果写入与原子可见

设备粒度每小时约产生 10000 × KPI 数的结果行，这是必要业务数据，不能通过删除设备维度规避。

最终计算采用有界批处理：

1. 窗口进入 `finalizing`。
2. 按状态分片读取一批实体。
3. 计算该批实体 KPI。
4. 批量写入带 `window_id` 的暂存/结果记录。
5. 写入对应紧凑 Counter outbox。
6. 记录分片完成进度。
7. 所有分片完成后，在短事务内把窗口切换为 `published`。

查询视图只返回 `published` 窗口，保证用户看不到部分结果。

重试必须幂等：

- 结果业务唯一键包含窗口、维度、实体、对象和指标；
- Counter 上卷事件 ID 由窗口、版本、分片、批次稳定派生；
- 已完成分片不重复计算；
- 最后一个分片失败不回滚此前已安全落盘的暂存批次。

## 13. 恢复

恢复器每次只判断活动分片元数据是否存在：

```text
EXISTS meta-key
```

状态缺失时：

1. 根据源粒度选择 15 分钟、小时或日 NATS 保留流；
2. 只回放目标窗口；
3. 按当前 catalog/rule version 重新构造短 ID 状态；
4. 分片恢复；
5. 单窗口失败后记录错误并继续其他窗口。

恢复器不得：

- 用完整状态读取判断存在性；
- 因一个大窗口失败终止整轮恢复；
- 从时序数据库重新拉取 Counter；
- 对已发布窗口重新计算。

## 14. 背压与隔离

- 设备基础汇聚与规则汇聚使用独立消费者并发预算。
- 每级消费者设置最大待确认、批次大小和内存预算。
- Redis 达到内存压力阈值时暂停领取新批次，但不丢消息。
- 最终计算并发按预计分片内存控制，不只按固定 goroutine 数控制。
- 单规则状态估算超过预算时拒绝启用，并返回成员数、Counter 数、预计字节和建议分片。
- 规则数量少不能作为容量依据，容量以“成员/维度基数 × 对象 × Counter × 活动粒度”计算。

## 15. 可观测性

新增或调整以下指标：

- 各层事件 pending/ack/redelivery；
- 各粒度窗口 open/finalizing/published/failed；
- 每窗口预计/实际实体数；
- 每窗口预计/实际状态字节；
- 分片数、最大分片字节；
- 完整关闭/超时关闭数量；
- 数据完整但公式缺项数量；
- 每级上卷延迟；
- 最终计算批次耗时和结果行数；
- 恢复窗口数、恢复失败数和回放消息数；
- Redis 无界命令计数必须为 0；
- 规则版本变更和成员版本变更数量。

日志必须包含：

- pipeline/dimension/granularity；
- window start/end；
- catalog/rule version；
- shard/batch；
- expected/received/missing；
- state bytes；
- close reason。

## 16. 数据与部署策略

本次不兼容旧数据，重新部署时：

1. 停止 worker 写入；
2. 清理旧 `pmagg:*` Redis 状态；
3. 清理旧聚合窗口、结果、Counter rollup 和 outbox；
4. 清理旧聚合 JetStream 消息；
5. 移除旧内置任务和隐藏设备版本；
6. 应用重新整理后的基线 schema/seed；
7. 启动公共逐级汇聚流水线；
8. 从新收到的 15 分钟 PM 开始生成结果。

原始 PM、普通 15 分钟 KPI 和时序数据库保留策略不由 NATS 策略替代。

## 17. 测试策略

开发一次完成后统一执行测试，不采用“开发一个步骤、部署验证一个步骤”的方式。

### 17.1 单元测试

- sum/avg/min/max 组合律；
- KPI 只基于 Counter；
- 设备小时 4 槽完整和缺槽超时；
- 日/周/月自然桶和时区；
- 一设备多组；
- 默认未分组；
- 规则版本边界；
- 自动分片计算；
- 短 ID 编解码；
- 分片批量最终计算；
- 数据完整与公式完整分离；
- 幂等事件和重复槽。

### 17.2 集成测试

- 15 分钟 → 设备小时 → 设备日 → 设备周/月；
- 设备小时 → 设备组/产品/频段/全网小时 → 日 → 周/月；
- 新规则只处理生效后数据；
- 规则更新时新旧窗口不混合；
- Redis 分片丢失后从 NATS 恢复；
- 单窗口恢复失败不阻塞其他窗口；
- 最终计算中途失败后幂等续跑；
- 查询只看已发布窗口；
- NATS 保留配置；
- 不回读时序数据库 Counter。

### 17.3 10000 设备压测

统一验证至少一个完整日周期，并覆盖小时和日边界：

- 10000 台设备每 15 分钟上报；
- PM 文件解析和 15 分钟 KPI 正常；
- 设备小时结果完整生成；
- 设备组、产品和全网小时结果完整生成；
- 设备日结果在日边界生成；
- Redis 总状态、最大分片和增长趋势符合预算；
- worker/Redis/NATS 不发生 OOM、拒绝写入或持续超时；
- 无 `HGETALL pmroll:*`；
- 受保护消费者 pending/ack-pending/redelivery 回落为 0；
- CPU、磁盘 I/O、内存和数据库写入无持续饱和；
- 结果抽样与原始 Counter 手工计算一致。

## 18. 验收标准

1. 后台不存在 12/15 个 `scheduled` 内置聚合任务。
2. 不存在“内置-设备-LTE/NR/GSM”隐藏任务。
3. 单设备小时、日、周、月 KPI 仍可查询。
4. 设备组、产品、频段、全网小时、日、周、月 KPI 仍可查询。
5. 用户看到的是聚合规则及版本，不是运行任务。
6. 所有计算由 15 分钟 Counter 或上一级 Counter 事件驱动。
7. 没有任何一级平均上一级 KPI。
8. 不从时序数据库回读 Counter 执行正常上卷或恢复。
9. Redis 不存在无界大 Hash 和无界读取。
10. 10000 设备压测下，单分片、总状态和进程内存符合预算。
11. 窗口完整性与单 KPI 公式完整性正确区分。
12. 小时、日、周、月结果在完整或超时后自动生成，无 cron 聚合执行。
