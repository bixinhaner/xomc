# #36 V1 查询模板更新与详情设计

## 背景与根因

V1 指标查询页允许从左侧模板列表编辑模板。后端 `PATCH /pm/query-templates/:id`
会正确保存并返回更新后的模板，但前端 mutation 成功后只异步失效列表缓存：

- 当前查询表单仍保留编辑前的 payload；
- 已选模板从 `daily` 改为 `hourly` 后，下一次查询仍可能携带 `daily`；
- 模板列表项只展示名称和描述，没有完整配置详情入口。

本单只修复 V1（`omcmb/webcode`）。V2/V3 不在 #36 MR 中修改；#36 合入后另起独立
变更整体删除两套皮肤，避免缺陷修复与大范围删除混在同一个提交中。

## 方案

采用“更新响应作为唯一新状态”的方案：

1. `useUpdateQueryTemplate` 在成功后把 API 返回模板写回所有查询模板列表缓存，
   同时更新详情缓存；缓存无法精确命中时仍失效重取。
2. V1 保存编辑模板成功后，如果被编辑模板正是当前激活模板，则把更新响应中的
   payload 同步到主查询表单及自定义时间范围。
3. 不自动发起查询，也不覆盖当前已展示结果。用户再次点击“查询”后，才以新 payload
   创建 submitted snapshot；这保持现有“编辑表单与实际查询快照分离”的交互语义。
4. 模板列表增加详情入口，打开只读详情弹窗，展示名称、可见性、描述、设备类型、
   设备、指标、粒度、时间范围、创建与更新时间。编辑和删除权限规则保持不变。

## 状态与数据流

```text
编辑模板 -> PATCH 返回 updatedTemplate
         -> 更新 React Query 列表/详情缓存
         -> 若 activeTemplateId 相同：同步主表单 payload
         -> 保留 submittedPayload 和现有结果
         -> 用户点击查询：以新 hourly payload 重建查询快照
```

详情弹窗直接读取列表中当前模板对象；更新成功后该对象由缓存同步刷新，因此详情与
查询表单不会继续展示旧粒度。

## 错误与兼容

- 后端校验、权限与 409/403 错误处理不变。
- 旧模板指标显示名到指标编号的兼容映射继续只在“应用模板”时执行。
- 自定义时间范围仅在更新响应含完整起止时间时回填，否则清空选择器。
- 未激活模板被编辑时，不修改当前查询表单。

## 测试与验收

- Hook 单测：更新成功后列表缓存中的模板 payload 从 `daily` 变为 `hourly`。
- V1 组件/状态单测：编辑当前激活模板后主表单采用更新响应；编辑其他模板不影响当前表单；
  已提交查询快照不被自动替换。
- 详情展示测试：可见性、粒度、时间范围、设备与指标配置可见。
- 运行 V1 typecheck；按仓库现行完整验证要求运行 skin parity 和现存前端 typecheck，
  若 V2/V3 存在与本单无关的失败则如实记录。
- 重建 Docker web，真实创建 daily 模板、编辑为 hourly，确认数据库 payload、页面表单和
  下一次聚合查询参数均为 hourly；确认详情展示新值。
- 后端未改动，仍执行相关 API 测试或最小回归，确认模板 PATCH 返回完整更新对象。
