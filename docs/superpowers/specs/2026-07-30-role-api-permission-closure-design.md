# Issue #225 角色 API 权限闭环设计

## 背景

Issue #225 的用户流程是：管理员创建自定义角色，配置菜单权限和设备数据权限，
再把角色分配给普通用户。当前设备组过滤修复已经保证“默认二级设备组”同时覆盖：

- 真实绑定到默认二级设备组的设备；
- 为兼容历史数据而保留的未分组设备。

但当前角色配置链路存在另一处阻断：

- 运行时端点鉴权由 `role_api_permissions` 和 Casbin 执行；
- 新增、编辑角色页面只写入 `role_menus` 和 `role_device_groups`；
- `CopyRole` 没有复制 `role_api_permissions`；
- 自定义角色因没有端点授权，在进入设备数据过滤前就收到 HTTP 403。

因此，只有同时恢复角色 API 权限的配置、保存、复制和回显闭环，Issue #225
才能按真实用户流程完成验收。

## 设计目标

1. 保持后端端点级鉴权和默认拒绝，不增加鉴权旁路。
2. 恢复管理员可见、可审计的 API 权限配置入口。
3. 创建和编辑角色时准确保存 API 端点授权。
4. 复制角色时精确复制源角色的 API 权限，不扩大权限。
5. 任一权限绑定失败时不向管理员报告虚假成功。
6. 使用自动化测试和真实浏览器同时验证正向授权与负向拒绝。

## 非目标

- 不把自定义角色默认提升为 `operator` 或其他内置角色。
- 不根据角色名称、用户名称或设备组推断 API 权限。
- 不关闭或放宽 `RequireAPIPermission`。
- 不改变 `role_api_permissions`、`api_endpoints` 或 Casbin 的数据库结构。
- 不新增迁移文件。
- 不重构与 Issue #225 无关的角色、菜单或用户管理代码。

## 权限模型

角色权限继续由三个相互独立的维度组成：

| 权限维度 | 权威数据源 | 作用 |
|---|---|---|
| 菜单权限 | `role_menus` | 控制页面、菜单和按钮是否可见 |
| API 权限 | `role_api_permissions` | 控制 HTTP Method + 标准路由模板是否允许调用 |
| 数据权限 | `role_device_groups` | 控制设备组和网络制式的数据可见范围 |

请求必须同时满足相应的 API 权限和数据权限。拥有设备组权限不代表可以调用设备
接口；拥有设备接口权限也不代表可以绕过设备组过滤。

Casbin 继续从 `role_api_permissions JOIN api_endpoints` 加载端点策略。
`RequireAPIPermission` 继续使用 `c.FullPath()` 和 HTTP Method 校验，未授权端点继续
返回 HTTP 403。

## 角色配置界面

角色新增、编辑和查看抽屉恢复三个标签页：

1. 菜单权限；
2. API 权限；
3. 数据权限。

API 权限树按 `api_endpoints.api_group` 分组，叶子节点显示 Method、标准路由模板和
端点名称。保存值只包含叶子端点 UUID，不把分组节点写入数据库。

### 安全预选

创建角色时，系统可以根据已选择菜单预选能够可靠映射的 GET 只读端点：

- 只允许预选 `GET`；
- 映射必须来自代码中显式维护的菜单权限键到 API 分组映射；
- 不认识的菜单不自动产生任何端点授权；
- `POST`、`PUT`、`PATCH`、`DELETE` 永不自动授权；
- 管理员可以在保存前取消任何预选项或增加明确需要的端点。

编辑现有角色时，以数据库保存的端点 ID 为唯一回显来源。打开编辑抽屉、切换标签页
或重新加载页面都不得自动扩大已有角色权限。

### 表单约束

- 角色至少选择一个菜单权限；
- 角色至少选择一个 API 端点；
- 创建角色时至少选择一个数据权限目标；
- 编辑角色时沿用项目现有规则：允许在二次确认后清空数据权限；
- 校验失败时不发送角色创建或更新请求。

这些约束避免创建“菜单可见但所有业务接口均为 403”的不可用角色，同时保留项目
已有的“明确确认后清空数据权限”能力，并且不会通过隐式全量授权绕开最小权限原则。

## 创建与编辑的数据流

现有项目把角色主体和三个绑定关系拆成专项端点，本设计保留该边界：

1. 创建或更新角色主体；
2. 保存 `role_menus`；
3. 保存 `role_api_permissions`；
4. 保存 `role_device_groups`；
5. 所有步骤成功后刷新角色列表和当前用户菜单缓存；
6. 最后显示成功提示并关闭抽屉。

专项请求串行执行。任一步失败时：

- 立即停止后续步骤；
- 保持抽屉打开；
- 展示该请求返回的真实错误；
- 不显示成功提示；
- 不清空管理员已经选择的表单状态。

创建流程在角色主体已创建、后续绑定失败时可能留下未完成角色。前端必须明确报告失败，
不得将其视为成功。复制流程则由后端负责补偿清理，避免自动操作留下半成品副本。

## 复制角色

`CopyRole` 的行为契约是精确复制：

- 复制描述；
- 复制 `role_menus`；
- 复制 `role_api_permissions`；
- 复制 `role_device_groups` 及其 `network_types`；
- 新角色固定为非内置角色；
- 不复制源角色的 `code`、`created_by` 或 `updated_by`。

API 权限复制必须直接读取源角色的端点 UUID 集合，并写入副本，不执行菜单推断、不补
operator 基线、不扩大授权。

如果复制菜单、API 权限或设备组任一步失败：

1. 返回失败，不返回成功角色；
2. 删除刚创建的副本，依靠外键级联清理已写入的绑定；
3. 如果补偿删除也失败，将原始错误和清理错误共同包装到返回错误中，保留排障上下文。

API 权限保存成功后继续调用现有策略刷新机制，确保新角色授权无需重启服务即可生效。

## 错误处理与安全边界

- 后端新增错误必须使用 `fmt.Errorf("context: %w", err)` 包装上下文。
- API 权限仓储继续使用 Squirrel + pgx；不引入 ORM，不拼接动态 SQL。
- 空端点集合代表没有 API 权限，不转换为任何默认角色权限。
- 不因 Casbin 加载失败、策略刷新失败或菜单映射缺失而放行请求。
- 超级管理员现有明确旁路保持不变，不扩展到普通内置角色或自定义角色。
- 前端用户可见错误继续走现有 i18n 和统一错误映射，不硬编码新文案。

## 自动化测试

### 后端

测试必须覆盖以下行为：

1. 复制角色时副本获得与源角色完全相同的端点 UUID 集合；
2. 源角色没有 API 权限时，副本也保持空集合；
3. API 权限复制失败时返回错误并删除已创建副本；
4. 补偿删除失败时返回同时包含复制错误与清理错误上下文的错误；
5. API 权限持久化后触发现有 Casbin 策略刷新；
6. 未授权端点继续返回 HTTP 403。

### 前端

测试必须覆盖以下行为：

1. 菜单预选只加入显式映射的 GET 端点；
2. 写端点不会被自动预选；
3. 管理员显式选择的端点不会被菜单预选覆盖或删除；
4. 编辑角色严格回显后端保存的端点集合；
5. API 权限为空时阻止提交；
6. 创建和编辑请求向 API 权限专项端点提交准确的叶子端点 UUID；
7. 任一专项请求失败时不显示成功提示、不关闭抽屉。

## 真实浏览器验收

验收必须使用当前工作区启动的真实前后端服务，不通过手工 SQL 修改角色权限：

1. 使用管理员登录；
2. 新建自定义角色；
3. 选择仪表板、设备列表所需菜单；
4. 在 API 权限页选择对应只读端点；
5. 数据权限只选择 LTE、NR 和默认二级设备组；
6. 创建普通用户并只分配该角色；
7. 使用普通用户登录；
8. 验证仪表板汇总接口和设备列表接口返回 HTTP 200；
9. 验证默认设备组中真实绑定的 LTE、NR 设备可见；
10. 验证历史未分组设备仍按 Issue #225 的兼容规则可见；
11. 调用一个未授权写端点，验证返回 HTTP 403；
12. 复制该角色并验证副本的菜单、API 和数据权限均与源角色一致。

## 完成标准

- 不再需要手工向 `role_api_permissions` 插入测试数据；
- Issue #225 的普通用户真实流程通过；
- 严格端点鉴权和数据过滤同时生效；
- 自动化测试、前端类型检查和相关后端测试全部通过；
- 工作区只包含本设计范围内的代码、测试和文档变更。
