# PM Dashboard 快照全量扫描根治设计

## 目标

首页继续每 5 分钟读取既有小时、天、周聚合结果，并为当前天/周补充进行中覆盖率；任何首页请求不得扫描 `pm_aggregation_version_members`，无业务变化的内置任务校准不得导致目录快照失效。

## 根因

内置任务每 5 分钟执行保存。现有保存流程即使内容哈希一致，也先无条件更新 `pm_aggregation_tasks`，触发 `updated_at` 刷新。快照修订值又包含 `updated_at` 和任务整行 JSON，因此产生虚假修订。Dashboard 的天/周进度查询在首次看到虚假修订时重载通用匹配快照，连带读取全部任务版本成员。

## 设计

1. 保存任务时，任务主表更新增加 `IS DISTINCT FROM` 条件。只有名称、启用状态、可见性或计划结束时间真实变化时才执行 UPDATE。
2. 快照修订值移除 `updated_at` 和整行 JSON，改为只包含快照读取真正依赖的任务语义字段，并包含当前版本的有效时间和内容哈希，保证真实版本或时间变化仍可失效缓存。
3. 为 Dashboard/进度查询提供轻量任务目录加载器。它读取任务版本、指标规则和 Counter 规则，但明确跳过 `pm_aggregation_version_members`；worker 的匹配快照仍使用完整成员目录。
4. 保留现有 Dashboard 查询超时、并发保护、5 分钟轮询和 stale cache 行为，不改变小时/天/周业务结果语义。

## 验收标准

- 重复保存相同内置任务不更新任务主表，也不改变目录语义修订值。
- 名称、计划结束时间、当前版本、版本有效时间或内容哈希发生真实变化时，修订值变化。
- Dashboard 天/周进度快照可生成现有进行中结果，但其加载路径不查询成员表。
- 后端全量构建和测试通过。
- 清空目标 OMC 环境全部业务数据并部署最新构建后，全部服务健康；新数据进入后小时/天/周聚合与 KPI 正常。
- 连续跨过至少一个 5 分钟内置任务校准周期并多次请求首页，app/worker 均不再出现无变化导致的 336,186 行成员重载或对应慢查询。
