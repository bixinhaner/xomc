# Redis 终态任务压缩设计

## 背景与证据

20,000 设备启动恢复期间，`redis-core` 达到 2 GiB `maxmemory` 并以 `noeviction` 拒绝写入。现网抽样显示 `completed` 的 `acs:task:*` Hash 平均约 9.8 KiB；完成事件洪峰远高于旧容量模型中的 7,410 条/分钟，而终态详情保留 15 分钟。大量完整 `Params`/`Result` 在 Redis 中短期叠加，是写入 OOM 的直接原因。PostgreSQL 已是任务详情的持久化权威源。

## 目标与边界

- PostgreSQL 写入、跨槽索引清理及终态事件发布全部确认后，将 Redis 终态任务压成轻量墓碑。
- 墓碑保留现有 10 分钟下限、默认 15 分钟 TTL，用于拒绝迟到或重复 CWMP 结果。
- 用户查询终态任务详情时读取 PostgreSQL，不能把墓碑当成完整任务返回。
- 未完成补偿步骤的任务必须继续保留完整数据且保持持久化，保证可恢复性。
- 不迁移数据；删除动作仅允许作用于 OMC 数据。本修复不依靠清库掩盖问题。

## 方案选择

推荐在现有终态转换 Lua 原子收尾点压缩。`prepareTransition` 记录本次转换是否为终态；`finalizeTaskTransitionScript` 仅在 PG、索引清理和事件三个确认位全部清零后删除大 `data` 字段，保留 `status` 和 TTL。`GetByID` 能从这种 Hash 还原 `{ID, Status}` 墓碑；`TaskService.GetTask` 发现终态时回 PostgreSQL 读取完整任务。

未选择的方案：只提高 Redis 内存只能推迟复发；缩短 TTL 会削弱迟到响应防护；把全部终态任务立即删除会丢失幂等围栏。

## 数据流与失败语义

1. 活跃任务仍以完整 JSON 和 4 小时 TTL 入 Redis。
2. 终态转换先保存完整候选、`PERSIST` 并登记补偿索引。
3. PostgreSQL、队列/CWMP 索引及终态事件逐项确认。
4. 最后一个确认原子触发压缩和 15 分钟过期；任一步失败则不压缩，由 reconciler 使用完整数据恢复。
5. 迟到响应读取墓碑后看到终态并直接忽略；详情 API 回主库取得完整参数和结果。

## 验收

- 单测证明完成/失败/取消/过期均形成无 `data` 字段的终态墓碑，TTL 和幂等围栏不变。
- 单测证明事件未确认时仍保留完整 `data`，确认后才压缩。
- 单测证明详情服务遇到终态墓碑时返回 PostgreSQL 完整对象。
- 容量模型按 40,000 条/分钟、每墓碑不超过 512 字节计算，15 分钟终态工作集低于 512 MiB。
- 全量 Go 测试、发布门禁和线上健康检查通过；部署后 Redis 不再出现 OOM，ACS 503/拒绝为 0，任务与补偿队列持续收敛，小时/天/周 Dashboard 数据正常。
