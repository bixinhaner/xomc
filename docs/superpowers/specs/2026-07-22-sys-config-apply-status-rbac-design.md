# 内置角色 API 权限漂移修复设计

## 背景与根因

`2347187b` 恢复了基于 `(path, method)` 的严格端点权限校验，并通过一次性 seed 为当时已经登记的端点补齐内置角色权限。后续路由仍会在应用启动时由 `syncApiEndpoints` 自动写入 `api_endpoints`，但同步流程没有维护 `role_api_permissions`，因此新端点会进入“已登记、无角色授权”的状态。

本地数据库已经确认：740 个登记端点中有 71 个没有任何角色授权；324 个 GET 端点中 viewer 只获得 286 个。系统配置应用状态接口只是其中一个表现，单独补一个接口会在下次新增路由时再次复发。

## 业务不变量

沿用 !228 已确认的内置角色兼容策略，不重新设计权限模型：

- `users.source = 'builtIn'` 的超级管理员继续旁路权限检查。
- 固定内置 `admin`、`operator` 角色拥有全部已登记 API。
- 固定内置 `viewer` 角色只拥有全部 GET API。
- 内置角色在角色管理页面不可编辑或删除，因此启动期补齐其基线不会覆盖合法的人工配置。
- 自定义角色的 API 权限完全由管理员配置，本修复不得新增、删除或覆盖其授权。
- 保留 fail-closed 中间件，不把管理接口改为公开接口。

## 方案比较

### 方案 A：关闭严格 API 权限校验

可以快速消除 403，但会让所有登录用户绕过角色 API 权限，违反角色管理 PRD，拒绝采用。

### 方案 B：只增加一次性 seed

可以修复当前数据库，但下一次增加路由仍会漂移，只能作为存量修复，不能单独采用。

### 方案 C：seed 存量修复 + 路由同步后持续对账

采用该方案。seed 在应用启动前修复已经部署的数据库；运行时对账覆盖未来新增路由和手工触发的路由同步。两层逻辑都只执行幂等新增，不删除权限。

## 实现设计

### 1. 存量数据库修复

新增 seed `000002_repair_builtin_role_api_permission_drift.sql`：

- admin/operator 对全部 `api_endpoints` 执行 `INSERT ... SELECT ... ON CONFLICT DO NOTHING`。
- viewer 仅对 `method = 'GET'` 的端点执行同样的幂等插入。
- 使用三个固定内置角色 UUID，不按可能变化的展示名称关联。
- Down 为空操作，因为无法区分历史合法授权与本迁移新增授权，删除会破坏生产权限。

### 2. 持续对账

在 `PgRoleRepository` 增加内置角色基线对账方法：

1. 在一个事务中幂等补齐 admin、operator、viewer 三组权限。
2. 记录每个角色实际新增的授权数量。
3. 事务提交后，仅在确实新增权限时同步刷新当前 Casbin policy 并广播其他实例刷新。
4. 任一步骤失败均返回带上下文错误，不伪装成同步成功。

`ApiEndpointService.SyncApiEndpoints` 在完成端点登记后调用该对账器，因此启动自动同步和后台手工同步使用同一条路径。对账失败时同步请求返回失败；应用启动阶段不得把该错误静默忽略，以免服务表面健康但普通角色持续 403。

### 3. 非目标范围

- 不修改自定义角色权限。
- 不收敛 operator/viewer 的最小权限矩阵。
- 不修改菜单、设备分组或网络制式权限。
- 不修改文件上传 URL、PM 保留策略、ACS 配置应用语义或运营商识别。
- 不清理已经登记但当前未挂载的历史端点。

## 验证要求

- TDD 证明路由同步完成后一定执行内置角色对账，对账失败会向上返回。
- 仓储测试证明 admin/operator 覆盖全部端点，viewer 只覆盖 GET，自定义角色不参与 SQL。
- 测试证明只有实际新增授权时才刷新本实例并通知其他实例。
- seed 契约测试锁定固定角色 UUID、viewer GET 条件、幂等插入和无破坏 Down。
- 本地 PostgreSQL 应用 migration 后验证缺失授权数归零。
- 运行 `go build ./...`、admin/provider 相关测试以及 `go test ./...`。
