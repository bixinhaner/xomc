# PM 水位阻塞统计性能根治计划

## 线上证据

- TSDB 中出现持续超过 2 分钟的 `pm_aggregation_windows` 阻塞窗口计数查询。
- 查询对每一个到期窗口执行两组相关 `EXISTS`；同一小时约 2 万个设备窗口拥有完全相同的时间范围，却重复检查同一队列水位。
- 阻塞统计运行在每轮超时关闭前，慢查询会拖延小时窗口关闭并触发 `TSDBLongQueryActive`。
- 队列表已有针对未消费、可参与水位判断事件的部分索引，问题是重复探测次数，不是缺少基础索引。

## 修复

1. 先按 `granularity/window_start/window_end` 汇总到期窗口并保留窗口数量。
2. 对每个不同周期只执行一次队列水位 `EXISTS` 判断。
3. 对命中阻塞的周期汇总其窗口数量，保持原有“阻塞窗口数”指标语义不变。
4. 增加 SQL 结构回归测试，防止重新退化为逐窗口相关子查询。

## 验收

- 单元测试确认队列探测位于周期分组之后。
- 后端构建、全量测试、竞态测试、前端类型检查和发布门禁全部通过。
- 部署后不再出现该内部统计 SQL 的长查询。
- `TSDBLongQueryActive` 恢复正常，小时聚合队列最终清零，窗口正常发布。
