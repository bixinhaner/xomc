# PM 上报名分类根治实施计划

## 目标

修正 PM 白名单过滤的分类语义：设备上报名未进入当前产品路由时，先判断它是否已存在于该制式全局指标库。全局已知但未绑定当前产品的值计入 `known_but_disabled`，只有全局指标库也不存在的值才计入 `whitelist_miss`。两类值仍不写入时序库，且同一值只计数一次。

## 实施步骤

1. 先补 collector 失败测试，覆盖“路由命中、全局已知但未路由、全局未知”三类值，以及与启用指标过滤叠加时不覆盖既有计数。
2. 为指标仓储增加按制式读取全部 Counter `report_key` 的轻量查询及 SQL 测试。
3. 在 worker 增加五分钟缓存的全局上报名查询器并注入 collector，避免每个 PM 文件访问主库。
4. 修改 collector 分类和提交后指标记账：全局已知未路由归入 `known_disabled`，全局未知归入 `whitelist_miss`，启用过滤阶段使用累加而非覆盖。
5. 运行 collector、indicator、worker 定向测试与竞态测试，再运行全后端构建/测试、发布回归和前端类型检查。
6. 提交 MR、合入、构建并部署；跨越至少一个 15 分钟 PM 周期验证告警、KPI 入库、小时/天聚合、队列和资源。

## 验收标准

- 样本中 235 个“全局已知但 BLQ 未绑定”的上报名不再触发 `PMReportKeysMissingFromLibrary`。
- `known_disabled` 与 `whitelist_miss` 不重复计数，启用指标过滤的计数不会覆盖前一阶段结果。
- 真正未知的 51 个上报名仍保持告警，后续按明确别名或产品级忽略契约逐项处理，禁止伪造 Counter 编号。
- PM 文件处理成功、无新增 DLQ/队列积压；KPI 小时/天数据持续新鲜。
