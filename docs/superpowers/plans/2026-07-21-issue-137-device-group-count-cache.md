# Issue #137：设备移入回收站后设备组数量不一致

## 问题现象

设备从设备组移入回收站后，右侧实际设备列表已经减少，但左侧设备组及“全部”节点仍短时间显示删除前的数量。

## 根因

后端 `PgDeviceGroupRepository` 为设备组树及数量设置了 3 秒内存缓存。软删除 SQL 已正确排除 `deleted_at` 不为空的设备，前端在删除成功后也会重新请求设备组数据；但设备删除流程没有使这份后端缓存失效，因此重新请求仍得到删除前的数量。

这不是设备组成员关系删除失败，也不是前端 React Query 没有刷新，而是后端跨业务模块缺少缓存失效通知。

## 修复方案

- 保留 3 秒缓存，避免取消缓存后增加数据库分区查询和聚合开销。
- 在设备服务中定义最小化的 `DeviceGroupCountsInvalidator` 接口，避免 `device` 包反向依赖 `topology` 包。
- 只有批量软删除实际删除行数大于 0 时，才调用一次设备组计数缓存失效。
- 由应用 provider 将现有 `GroupRepo` 注入设备服务。
- 缓存失效时在互斥锁保护下同时递增缓存版本号，并清空缓存内容和缓存时间。
- 查询开始时记录缓存版本号；只有查询完成时版本号仍一致，才允许回填缓存，防止删除前已启动的查询在删除后把旧数量重新写回。

## 为什么这样修复

- 删除成功后下一次请求立即重新计算，用户无需等待固定的 3 秒过期时间。
- 不在前端增加延迟或重复轮询，避免掩盖后端一致性问题。
- 不改变设备软删除和设备组成员关系的现有数据模型，修复范围小且可回归验证。

## 验收标准

- 从任意设备组删除一台设备后，接口返回成功，左侧该设备组和“全部”数量立即各减少 1。
- 删除不存在或已经删除的设备时，不产生无意义的缓存失效。
- 刷新页面后数量与设备列表实际数量一致。

## 自动化验证

- 服务测试验证批量删除成功时恰好调用一次缓存失效。
- 并发回归测试验证失效前启动的旧查询结果不能在失效后重新写入缓存。
- topology 测试验证原设备组查询行为不受影响。
- 后端全量构建和测试用于检查跨模块注入关系。
