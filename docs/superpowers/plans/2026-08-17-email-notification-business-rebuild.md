# 邮件通知业务重建开发计划

**依据**：`docs/project/prd/F04-alarm-notification.md`
**分支**：`codex/email-notification-business-rebuild`

## 原则

- 只实现邮件，不扩展短信/Webhook/统一通知平台。
- 先打通 SMTP 通道，再做告警订阅，最后做 KPI 报表。
- 不沿用 `notify_email` 同步直发作为最终业务入口。
- 所有数据库变化折回三个 `000001` 基线文件。
- 用户可见流程必须用真实浏览器验证。

## 当前执行点

阶段 1 至阶段 3 的主链路已完成，代码复核后又收敛了以下阻断问题：

- 告警订阅按创建者隔离，非超级管理员不能使用空设备范围扩大到全量设备，也不能修改全局默认收件人；
- KPI Regular Report 保存前校验每个设备 SN 的真实存在性和当前用户数据权限；
- 告警聚合正文按 `text/html` 发送，重试复用稳定 `Message-ID`；
- 通知中心增加告警/KPI 邮件发送记录和逐收件人明细，并按业务所有者隔离；
- 新 API 补入基线端点权限；旧 `OMC_SMTP_*` 仅在新配置缺失时作为升级兼容兜底；
- 部署脚本不再把 SMTP 密码和请求正文放入子进程命令行参数；
- 告警设备选择改为服务端搜索，不再仅能使用固定前 200 条。
- 遗留 `alarm_filters.notify_email` 在基线协调时幂等转换为 Real Time 告警邮件订阅，保留旧收件人与筛选范围；无有效收件人或创建者时安全禁用。
- 告警任务入队时固化订阅与最终收件人，周期中途启用会保留首个部分窗口；KPI 定时报表启用态必须至少选择一个指标。

本地后端定向测试、前端 typecheck/生产构建、脚本语法、基线迁移测试和真实浏览器无写入回归均已通过。整库 `go test ./...` 仅剩两项与本需求无关的既有元数据数量差异：内置告警定义期望 442、实际 443；BLN XML 元数据期望 380、实际 329，本次不越界修改。104 环境的受控投递必须等待客户批准的 SMTP 凭据与测试收件人，不在本地阶段替代。评审通过前不更新 GitLab 状态，也不扩展短信、Webhook 或复杂降噪。
