# 设备异常重启日志功能流程规范文档

> **文档目的**：面向新系统（如 Go 语言开发）的开发人员，以功能规范的视角，完整描述"设备异常重启日志"从触发、收集、存储到展示、清理的全链路业务流程。  
> **适用范围**：4G 基站(eNB)、5G 基站(gNB)、2G 基站(BSC/BTS) 的异常重启日志处理。

---

## 一、功能概述

当网管平台管理的基站设备发生异常重启（死机/崩溃重启），设备会在重新上线时通过管理协议上报重启事件和故障原因。网管平台需要：

1. **识别**设备是否为异常重启（区别于正常重启）
2. 根据收集模式，**自动或受控**地通知设备上传异常重启日志文件
3. **接收并存储**设备上传的日志文件
4. 在 Web 管理界面**展示、下载、导出、手动收集、清理**异常日志记录
5. 按策略**定时清理**过期或超限的日志文件及数据库记录

---

## 二、核心术语定义

| 术语 | 说明 |
|------|------|
| **异常重启** | 设备非人为操作导致的重启，如死机崩溃后自动恢复。设备上报的故障主原因字段不为空即标识为异常重启 |
| **硬重启 (halt_reboot)** | 设备完全断电或硬件级重启，设备上线时上报"1 BOOT"事件 |
| **软重启 (soft_reboot)** | 5G 设备特有，子模块重启但设备本身不发生完整重启，通过"4 VALUE_CHANGE"事件上报 |
| **故障主原因 (faultLogMainReason)** | 设备上报的异常类型标识，如 `halt_reboot`、`soft_reboot`，或其他平台特定值 |
| **故障详细原因 (faultLogDetailReason)** | 设备上报的详细崩溃原因描述 |
| **收集模式** | 系统全局配置，分为"自动模式"(值=0)和"受控模式"(值=1) |
| **新版本设备** | 设备上报参数中包含故障原因字段路径的设备 |
| **旧版本设备** | 设备上报参数中不包含故障原因字段路径的设备（仅限4G） |
| **设备参数下发 (SetParameterValues)** | 通过管理协议向设备设置参数，此处指设置日志文件上传URL |
| **日志文件上传URL (FaultLogURL)** | 设备用于上传异常日志文件的服务端地址 |

## 三、系统配置项

以下配置项影响异常日志功能的行为，新系统需实现等效的配置机制：

| 配置项 | 含义 | 典型默认值 | 说明 |
|--------|------|-----------|------|
| `errorLogCollectionMode` | 收集模式 | `0`(自动) | 0=自动模式，1=受控模式 |
| `RebootLogSaveCount` | 单设备最大保留文件数 | `2` | 每台设备最多保留最近 N 次的异常日志文件 |
| `rebootLogDataSaveDays` | 日志数据保留天数 | `7` | 超过天数的记录可被清理 |
| `errorLogMaxNum` | 全局最大保留文件总数 | 可配置 | 4G和5G各自独立计数，超出后删除最早的文件 |
| `manualErrLogtimeout` | 手动收集超时时间(秒) | `300` | 手动触发收集后，设备在此时间内未上传则标记失败 |
| `rl.file.size.threshold` | 单文件大小上限(MB) | `500` | 超过此大小的文件不予存储 |

## 五、设备类型与触发条件对照表

| 设备类型 | 触发事件 | 故障主原因判断 | 说明 |
|----------|----------|---------------|------|
| **4G 基站 (eNB)** | 设备上报 `1 BOOT` 事件 | 新版本：故障主原因字段存在且不为空 → 异常重启；旧版本：字段不存在 → 直接下发参数
| **5G 基站 (gNB) - 硬重启** | 设备上报 `1 BOOT` 事件 | 故障主原因 = `halt_reboot` 
| **5G 基站 (gNB) - 软重启** | 设备上报 `4 VALUE_CHANGE` 事件 | 故障主原因 = `soft_reboot` | 子模块重启，设备不完整重启
| **2G 基站 (GSM)** | 设备上报 `1 BOOT` 事件 | 故障主原因字段不为空

## 六、全流程详细说明

### 6.1 阶段一：设备异常重启检测

**流程描述**：

当设备异常重启后重新上线，会通过管理协议向平台发送连接报文。平台解析报文中的事件类型和携带的参数。

**处理步骤**：

1. **接收设备上报报文**，解析事件列表（如 `1 BOOT`、`4 VALUE_CHANGE` 等）和携带的设备参数键值对
2. **获取设备标识信息**：设备编码、平台类型
3. **根据设备类型路由处理**：
   - 若事件为 `1 BOOT`：
     - 判断设备平台类型，排除不支持的设备类型
     - 分别路由到 **4G处理流程**、**5G硬重启处理流程**、**2G处理流程**
   - 若事件为 `4 VALUE_CHANGE`：
     - 仅5G设备：路由到 **5G软重启处理流程**

### 6.2 阶段二：异常重启判断与信息封装

对于每种设备类型，判断逻辑如下：

#### 6.2.1 4G 基站

```
输入：设备编码、平台类型、设备上报的参数集合
处理：
  1. 排除不支持的设备类型（5G设备、2G设备、异厂家设备等）
  2. 确认事件列表包含 "1 BOOT"
  3. 根据平台类型获取故障主原因和详细原因对应的参数路径
  4. 从系统配置读取当前收集模式 (errorLogCollectionMode)
  5. 从设备上报参数中提取故障主原因值和详细原因值
  6. 判断设备版本：
     - 若参数集合中包含故障主原因的路径键 → 新版本设备
       - 若故障主原因值不为空 → 标记为异常重启
       - 若故障主原因值为空 → 正常重启，不处理
     - 若参数集合中不包含故障主原因的路径键 → 旧版本设备
  7. 对于异常重启（新版本）或旧版本设备，封装信息写入消息队列
```

封装的消息体内容：

| 字段 | 说明 |
|------|------|
| cellCode | 设备编码 |
| platformType | 平台类型 |
| errorLogCollectionMode | 收集模式 (0/1) |
| isNewDeviceVersion | 是否新版本 ("true"/"false") |
| isAbnormalReboot | 是否异常重启 ("true"/"false") |
| faultLogMainReason | 故障主原因值 |
| faultLogDetailReason | 故障详细原因值 |

#### 6.2.2 5G 基站 - 硬重启

```
输入：设备编码、平台类型、设备上报的参数集合
处理：
  1. 仅处理5G特定平台类型的设备
  2. 确认事件列表包含 "1 BOOT"
  3. 根据平台类型获取故障主原因和详细原因对应的参数路径
  4. 从设备上报参数中提取故障主原因值
  5. 若故障主原因值 = "halt_reboot" → 确认为5G硬重启异常
  6. 封装消息写入消息队列（isNewDeviceVersion="true", isAbnormalReboot="true"）
```

#### 6.2.3 5G 基站 - 软重启

```
输入：设备编码、平台类型、设备上报的参数集合
处理：
  1. 仅处理5G特定平台类型的设备
  2. 注意：此处触发事件为 "4 VALUE_CHANGE"，不需要包含 "1 BOOT"
  3. 根据平台类型获取故障主原因和详细原因对应的参数路径
  4. 从设备上报参数中提取故障主原因值
  5. 若故障主原因值 = "soft_reboot" → 确认为5G软重启异常
  6. 封装消息写入消息队列（isNewDeviceVersion="true", isAbnormalReboot="true"）
```

#### 6.2.4 2G 基站

```
输入：设备编码、平台类型、设备上报的参数集合
处理：
  1. 仅处理2G设备类型（BSC/BTS）
  2. 确认事件列表包含 "1 BOOT"
  3. 根据平台类型获取故障主原因和详细原因对应的参数路径
  4. 从设备上报参数中提取故障主原因值
  5. 若故障主原因值不为空 → 确认为2G异常重启
  6. 封装消息写入消息队列（isNewDeviceVersion="true", isAbnormalReboot="true"）
```

### 6.3 阶段三：消息队列异步处理

**流程描述**：

阶段二中封装的消息通过消息队列（如 Redis List）异步传递给后端处理服务。处理线程从队列中持续消费消息。

**队列规范**：

| 项目 | 说明 |
|------|------|
| 队列名称 | `errorLogInfo2Queue` |
| 数据格式 | JSON 字符串 |
| 生产者 | 设备管理协议接收服务 |
| 消费者 | 方法执行处理服务中的专用线程 |
| 消费方式 | 循环 LPOP，空队列时休眠1秒 |

### 6.4 阶段四：收集模式路由处理

消息消费线程取出消息后，根据收集模式和设备版本执行不同逻辑：

#### 6.4.1 受控模式 (errorLogCollectionMode = 1)

**场景A：新版本设备 + 异常重启**

```
处理流程：
  1. 获取设备详细信息（序列号、运营商编码、主机名等）
  2. 检查单设备文件保留上限，超限则删除最早的文件（仅删文件，不删数据库记录，标记文件已删除）
  3. 向数据库插入一条异常日志基本信息记录（不含文件名，因为不自动收集文件）
  4. 通过 WebSocket 推送刷新通知给前端
  5. 不下发收集日志的参数指令给设备（由用户在界面手动触发）
```

**场景B：旧版本设备（仅4G存在此场景）**

```
处理流程：
  1. 向设备下发 SetParameterValues 指令，将文件上传URL设置给设备
  2. 设备收到指令后会触发日志文件上传
  3. 文件接收服务收到上传请求后，仅记录基本信息，不存储文件
     - 文件接收服务通过URL中的 mode=background 参数识别此场景
  4. 记录故障原因信息到数据库
```

#### 6.4.2 自动模式 (errorLogCollectionMode = 0)

```
处理流程：
  1. 若为新版本设备且非异常重启 → 直接返回，不处理
  2. 获取设备详细信息（序列号、运营商编码、主机名等）
  3. 检查单设备文件保留上限，超限则删除最早的文件（仅删文件，不删数据库记录，标记文件已删除）
  4. 【先入库】向数据库插入一条异常日志基本信息记录（不含文件名，记录已创建，即使后续文件上传失败也不会遗漏）
  5. 将故障原因信息暂存到中间缓存（供文件上传时使用）
  6. 通过 WebSocket 推送刷新通知给前端
  7. 【后下发】向设备下发 SetParameterValues 指令，设置文件上传URL
     URL格式：{服务根地址}/FileUploadService?fileType=RL&sn={序列号}&filename=
  8. 设备收到指令后会主动向该URL上传异常日志文件

设计说明：
  - 先入库再下发的目的是确保异常重启记录不遗漏
  - 即使设备因网络等原因未能成功上传日志文件，数据库中仍有该次异常重启的记录
  - 文件上传成功后，文件接收服务会更新该记录的 file_name、is_store 等字段
```

### 6.5 阶段五：设备上传日志文件的接收与存储

当设备向文件上传URL发送日志文件时，文件接收服务根据URL参数分发到异常日志文件处理逻辑。

**文件类型标识**：`fileType=RL` (Reboot Log)

处理流程按URL参数区分三种场景：

#### 场景1：受控模式 + 旧版本设备 (mode=background)

```
处理流程：
  1. 从URL获取设备序列号
  2. 通过序列号查询设备信息
  3. 检查单设备文件保留上限，超限则清理旧文件
  4. 从缓存获取故障主原因和详细原因
  5. 向数据库写入异常日志基本信息（不含文件名）
  6. 直接中断上传连接，不保存文件
```

#### 场景2：手动收集模式 (URL中带有 id 参数)

```
处理流程：
  1. 从URL获取设备序列号和任务记录ID
  2. 查询数据库中该记录的手动收集状态
     - 若状态为"已完成(0)"或"无状态" → 走自动模式逻辑
     - 若状态为"收集中(1)" → 继续手动模式处理
  3. 查询设备和运营商信息
  4. 删除该任务记录关联的手动收集超时标识（Redis key）
  5. 构造文件存储路径：{上传根目录}/{运营商编码}/rebootLog/
  6. 构造文件名：{序列号}_abnormalLog_{运营商时区时间}.{原始扩展名}
  7. 检查单设备文件保留上限，清理旧文件
  8. 检查磁盘使用率（超过90%则标记为不存储）
  9. 若该记录之前已有文件，先删除旧文件
  10. 检查文件大小是否超过上限
      - 超过 → 标记收集失败，记录失败原因
      - 未超过 → 更新文件名到数据库记录
  11. 更新数据库记录的结束时间、存储状态等
  12. 检查全局文件总数上限
  13. 通过 WebSocket 推送刷新通知
  14. 将文件写入磁盘
  15. 更新手动收集状态为"已完成(0)"
```

#### 场景3：自动模式（无特殊URL参数）

> **前置条件**：消息消费线程已在 6.4.2 阶段插入了异常日志基本信息记录，此处仅更新该记录。

```
处理流程：
  1. 从URL获取设备序列号
  2. 查询设备和运营商信息
  3. 根据序列号和故障原因查找已存在的异常日志记录（同一设备同一故障原因的最新一条未完成记录）
  4. 若未找到对应记录 → 作为新记录插入（兼容异常情况）
  5. 构造文件存储路径：{上传根目录}/{运营商编码}/rebootLog/
  6. 构造文件名：{序列号}_abnormalLog_{运营商时区时间}.{原始扩展名}
  7. 检查磁盘使用率（超过90%则标记为不存储）
  8. 检查文件大小是否超过上限
     - 超过 → 更新记录的 collection_fail_reason 字段，记录失败原因，不存储文件
     - 未超过 → 继续处理
  9. 更新数据库记录（而非插入新记录）：
     - file_name = 构造的文件名
     - op_end_time = 当前时间
     - is_store = "1"（已存储）
     - 若磁盘空间不足则 is_store = "0"
  10. 检查全局文件总数上限
  11. 通过 WebSocket 推送刷新通知
  12. 将文件写入磁盘（支持本地文件系统和FTP两种存储方式）
```

### 7.2 手动收集异常日志

**前置条件**：
- 设备当前必须在线（已连接管理平台）
- 该记录的手动收集任务未在进行中（防重复下发）

**处理流程**：

```
1. 检查设备是否在线
2. 检查该任务是否已在进行中（通过 Redis key 判断，key格式：{设备编码}_{记录ID}_manualErrorLog）
   - 若 key 存在 → 返回，不重复下发
3. 更新数据库记录的手动收集状态为"收集中(1)"
4. 在 Redis 中设置超时标识 key，过期时间为配置的超时秒数
5. 将超时检测任务信息推入超时检测队列
6. 向设备下发 SetParameterValues 指令，URL中携带记录ID
   URL格式：{服务根地址}/FileUploadService?fileType=RL&id={记录ID}&sn={序列号}&filename=
7. 等待设备响应
```

**手动收集超时处理**：

```
后台线程持续消费超时检测队列：
  1. 取出任务信息，检查 Redis 超时标识 key 是否还存在
     - key 存在 → 未超时，将消息放回队列尾部，继续等待
     - key 不存在（已过期） → 检查数据库中的手动收集状态
       - 若状态仍为"收集中(1)" → 更新为"收集失败(2)"，记录失败原因"手动日志收集超时"
       - 若状态已不是"1" → 说明已成功，不处理
```

### 7.3 删除异常日志

**参数**：记录 ID 列表（逗号分隔）、运营商编码

**处理流程**：
1. 根据记录 ID 查询对应的文件名列表
2. 删除物理文件（支持本地文件系统和FTP）
3. 删除数据库记录

### 7.4 下载异常日志文件

**处理流程**：
1. 根据记录 ID 查询文件名列表
2. 构造文件完整路径：`{上传根目录}/{运营商编码}/rebootLog/{文件名}`
3. 验证文件是否存在
4. 单文件：直接返回原始文件流
5. 多文件：打包为 ZIP 文件返回，文件名格式 `ErrorLogFiles_{UTC时间}.zip`

### 7.5 导出异常日志列表

**处理流程**：
1. 按查询条件分页查询异常日志记录
2. 以 CSV 格式流式写出
3. 每页1000条，逐页查询写出，避免内存溢出

## 九、数据清理策略

### 9.1 单设备文件数量限制

- 每台设备最多保留最近 `RebootLogSaveCount` 次的日志文件
- 清理策略：
  1. 查询该设备序列号下所有未被标记删除且有文件名的记录，按 ID 降序排列
  2. 从第 `RebootLogSaveCount` 条开始，将之后的记录标记为"文件已删除(is_file_deleted=1)"
  3. 删除对应的物理文件
  4. **注意**：仅删除文件和标记状态，不删除数据库记录本身

### 9.2 全局文件总数限制

- 4G 和 5G 各自独立计数
- 当有文件名且未被标记删除的记录数超过 `errorLogMaxNum` 时，触发清理
- 清理策略：
  1. 保留最新的 `errorLogMaxNum` 条记录
  2. 将超出的记录标记为"文件已删除"
  3. 删除对应的物理文件

### 9.3 定时清理任务

- 系统定时任务周期性执行全局文件数量检查
- 分别检查 4G（is_gnb != '1'）和 5G（is_gnb = '1'）的文件数量
- 超出上限的按 ID 升序（最早的优先）清理

### 9.4 磁盘空间保护

- 文件接收服务在存储文件前检查磁盘使用率
- 若异常日志目录所在磁盘使用率 ≥ 90%，标记为不存储，仅保留数据库记录

## 十二、完整流程时序

### 12.1 自动模式 - 新版本设备异常重启

> **设计改进**：先入库记录，再下发SetParameterValues，确保异常重启记录不遗漏。

```
设备            管理协议服务          消息队列         方法执行服务          文件接收服务         数据库
 │                 │                   │                │                    │               │
 │──1 BOOT上报──→│                   │                │                    │               │
 │  (含故障原因)   │                   │                │                    │               │
 │                 │──封装消息──→      │                │                    │               │
 │                 │                   │──消费消息──→   │                    │               │
 │                 │                   │                │──暂存故障原因→      │               │(缓存)
 │                 │                   │                │                    │               │
 │                 │                   │                │──【先入库】插入记录→│               │
 │                 │                   │                │  (基本信息，无文件名) │               │
 │                 │                   │                │                    │               │
 │                 │                   │                │──推送通知──→       │               │(WebSocket)
 │                 │                   │                │                    │               │
 │←──【后下发】SetParameterValues(设置上传URL)──         │                    │               │
 │                 │                   │                │                    │               │
 │──────────────上传日志文件──────────────────────→      │               │
 │                 │                   │                │                    │──更新记录──→   │
 │                 │                   │                │                    │  (file_name等) │
 │                 │                   │                │                    │──存储文件──→   │
 │                 │                   │                │                    │──推送通知──→   │(WebSocket)
```

**异常处理**：若设备未能成功上传日志文件（网络中断、设备离线等），数据库中仍有该次异常重启的基本记录，不会遗漏。

## 十三、关键设计要点总结

1. **设备类型区分处理**：4G、5G、2G 各有独立的判断入口和条件，但写入同一个消息队列，由统一的消费端处理
2. **异步解耦**：管理协议服务仅负责识别和封装消息，通过消息队列与实际处理逻辑解耦
3. **收集模式全局控制**：受控模式不自动下发收集指令，需用户手动触发
4. **新旧设备兼容**：4G 设备需兼容不上报故障原因字段的旧版本设备
5. **5G 软重启特殊性**：软重启不触发 `1 BOOT` 事件，而是通过 `4 VALUE_CHANGE` 事件上报，需独立监听
6. **多级清理策略**：单设备上限 → 全局上限 → 磁盘空间保护，三级保护防止存储溢出
7. **文件与记录分离**：清理文件时不删除数据库记录，仅标记文件已删除状态，保留历史追溯能力
8. **手动收集超时机制**：通过 Redis Key 过期实现超时检测，避免任务永远停留在"收集中"状态
9. **文件存储抽象**：支持本地文件系统和 FTP 两种存储后端，通过配置切换
10. **实时推送**：日志记录变化后通过 WebSocket 推送，前端无需轮询
11. **先入库后下发（自动模式）**：识别到异常重启时先入库记录基本信息，再下发 SetParameterValues 指令。即使设备因网络等原因未能成功上传日志文件，数据库中仍有该次异常重启的记录，避免遗漏
