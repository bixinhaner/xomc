## 5. 真实入库墙钟核验（不信工具看门狗）

记忆纪律："工具看门狗会提前放弃，真实入库耗时要看 pm_files marker 时间戳跨度才准"。

- copy 模式下 `pm_files.parsed_at` 为 NULL，**marker 时间戳是 `created_at`**（= 入库提交时刻，写在 COPY 同事务里）。
- **marker 跨度 = max(created_at) − min(created_at) = 14:02:06.3 → 14:04:24.9 = 138.7s**（权威）。
- 工具自报"排空 1m40.4s（收敛）"= 100.4s（从上传结束到入库收敛的纯排空，本次**未触看门狗**，6m 内收敛，故工具数字本身也可信）。
- 二者关系自洽：138.7s ≈ 上传重叠期 40s（worker 边收边写、被上传节流）+ 100.4s 纯排空。

## 6. 丢弃 counter 说明（非 bug）

丢弃 13.88M counter ≈ 原始 22.9M 行的一半，**绝大部分是 NR**：NR 每文件 3606 原始行只有 175 counter 落库（~95% 丢弃）。

根因（已记录在案，非产品缺陷）：**NR 真机样本是 QILIN 厂商，却被路由到 Baicells/BaiBNQ 指标库**，白名单命中率极低 → 海量孤儿 counter 被白名单丢弃。这是**测试样本厂商错配 + GNB 指标库待扩建**，不是入库 bug。LTE/GSM 对得上各自库（76%/96% 命中）。

> 白名单丢弃是正确行为（避免孤儿/重名 counter 撞库）；它**不产生失败、不进 DLQ**，只是纯解析浪费。

## 8. 与历史基线对比 + 诚实差异分析

| 版本 / 配置 | 运营规模 marker 跨度 | 说明 |
|------------|---------------------|------|
| 删主键前（随机 uuid 主键 + 7 索引）| **304s** | 历史 |
| 删主键 + autovacuum（实验室最佳记录）| **76.7s** | 记忆基线（~4×）|
| **本次（最新 main，durable copy，共享 VM）**| **138.7s** | 见下 |

**本次 138.7s 比删主键前 304s 快 ~2.2×**，方向正确、优化生效；但比实验室最佳 76.7s 偏高 ~1.8×。差异最可能原因：

1. **共享 VM CPU 争用**：本机 12.5G/16 核 VM **同时跑 boss 栈 ~20 容器**。本次 PG 后半段需打满 8 核但只拿到部分，运行被拖慢。76.7s 记录可能在 boss 栈更闲时测得。
2. **单次运行方差**：单点测量，未取多轮中位数；autovacuum 在本次末段触发 1 次（+~14s 高 CPU 尾巴）。
3. **测量窗口口径**：marker 跨度含 40s 上传重叠期；不同上传节奏会拉伸该重叠。

**排除代码回归**：写路径经 `copy_ingest.go` 源码核对与 main 一致（durable copy、无主键、3 索引、autovacuum 5M），功能 100% 正确。差异是环境/方差，非实现退化。

> 如需贴近 76.7s 的干净数字：在 boss 栈空闲时段重跑、取 3 轮中位数即可（每轮先 `drop_chunks` 起新 chunk）。本次因机器发热已暂停，未做多轮。

## 9. 结论与建议

**结论**：✅ 最新代码 + 重建镜像后，PM 入库链路**功能完全健康**（10030 文件 0 失败 / 0 DLQ / 0 迟到，10.79M 行无重复，全 10030 设备算出 KPI），durable copy 写路径与 schema 一致，吞吐 ~107K 行/s。性能方向正确（vs 删主键前 ~2.2×），绝对墙钟受共享 VM 争用影响偏高。

**下一步杠杆（若要再压墙钟，均需动 schema/部署，非本次范围）**：
1. PG 仍是单 chunk 索引维护墙（后半段打满 8 核）。最大头是 3 个 btree 随单 chunk 增大的维护成本 —— 生产真实文件按时间分散到多 chunk 会自然缓解（本测试单窗口=最坏情况）。
2. group-commit（批 K 文件一次 fsync，保 durable）天花板 ~20%，是最划算的非 schema 杠杆。
3. 共享 VM 上做性能基线不稳，建议固定测量时段或独占资源跑权威基线。

**测试数据**：本次留下 10030 个 `KPILT-*` 设备 + 10.79M 行（可在性能管理页看曲线）。清理：`cd omcgo && bin/kpiperf -mode cleanup -db <15432> -nats <14222>`（删 KPILT* + 清 NATS PM 流；会有一次 DELETE 负载，按需在机器凉时跑）。

## B. 五个关键结论

**1. 稳定性满分 —— 连续高压不掉链子。**
50,150 文件背靠背灌入、数据累积到 64.7M 行同一 chunk，**0 失败 / 0 DLQ / 0 迟到**，每轮 100% 成功。durable copy 写路径在持续压力下完全可靠。

**2. 吞吐平稳，无随 chunk 增大而塌方。**
chunk 涨了 6×（10.79M→64.7M），marker 跨度却在 217/194/137/173/165s 之间**上下波动而非单调上升** —— run5（最大 chunk）比 run1（最小 chunk）还**快**。说明**单个 daily chunk 撑到 65M 行仍不退化**，没有"越灌越慢"的渐进塌方。容量含义：一个 15min 采集周期 ~10k 设备入库占用 165–217s = 窗口的 ~18–24%，即使灌进已很大的 chunk 也跟得上（生产按时间散到多 chunk 会更轻）。

**3. 瓶颈坐实在 PG，worker 全程闲置。**
PG avg 468–654% / peak 850–928%（8 核打满甚至超额），**worker avg 仅 110–131%（4 核里只用 ~1.2 核）**、peak ~250%。worker 大量时间**阻塞等 PG**。→ **再加 worker 并发/副本毫无用**，墙在 PG 写侧（单 chunk 索引维护 + autovacuum）。

**4. 轮间方差 = autovacuum 触发时机，不是 chunk 大小。**
全程 autovacuum 触发 6 次（~1/轮，5M 阈值 + 每轮灌 10.78M）。**最慢的 run1（217s）恰是 PG avg 最高的（654%）** —— autovacuum 与 COPY 抢 CPU，CPU 烧得更多、行/s 反而更少（无效争用）；**最快的 run3（137s）PG avg 最低（468%）** —— 干净窗口无 autovacuum 叠加。即"PG CPU 越高 ≠ 干活越多"，高 CPU 是 autovacuum 内耗。

**5. fresh chunk 首灌快、续灌进大 chunk 慢 —— 一步台阶，非渐进。**
首轮 fresh chunk（0→10.79M）107K/s 是全场最快；之后续灌进**已有数据的 chunk**（索引已大，随机插入维护大 btree）均值降到 79.5K/s（~25% 惩罚）。但这是 fresh→populated 的**一次性台阶**，之后在 79.5K/s 附近**持平**，不继续恶化。

## C. 对第一部分假设的纠偏（诚实）

第一部分曾推测：首轮 138.7s 偏高是受同机 boss 栈 CPU 争用拖累。**本次 boss 全停后实测推翻了该假设** —— 续灌各轮（无 boss）反而更慢（均值 177s > 首轮 138.7s）。首轮快的真因是 **fresh chunk（空索引）**，不是 boss 没在抢。boss 争用即使存在，也不是首轮数字的主导因素。

## D. 遗留与建议

- **磁盘**：现剩 **13.8G（94% 已用）**，pm_metrics 已 18GB / MinIO pm-files ~10GB。再压前建议清理：
  `cd omcgo && bin/kpiperf -mode cleanup -sn-prefix KPILT -db <15432> -nats <14222>`（删全部 KPILT* 设备/行/marker + 清 NATS PM 流；DELETE 64M 行有负载，机器凉时跑）。MinIO 对象 cleanup 不删，需 `docker exec omc-minio-1 mc rm -r --force local/pm-files` 单独清。
- **若要再压性能杠杆**（均需动 schema/部署）：① 单 chunk 索引维护是墙 —— 生产真实文件按时间散到多 chunk 自然缓解；② autovacuum 仍周期性内耗，可评估对 PM chunk 进一步调度/手动 vacuum 窗口；③ worker 严重过剩（只用 1.2 核），资源可向 PG 倾斜。
