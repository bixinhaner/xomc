## 1. 概览

OMC 项目采用**分层多实现**的消息队列架构，不同队列服务于不同的耦合强度和持久化需求：

| # | 实现类型 | 库/协议 | 定位 | 持久化 | 跨进程 |
|---|---------|---------|------|--------|--------|
| 1 | **NATS JetStream** | `nats-io/nats.go` | 主事件总线 (app ↔ acs ↔ worker) | ✅ 文件 | ✅ |
| 2 | **Channel EventBus** | 纯 Go channel | 单进程内事件总线 (测试/开发) | ❌ | ❌ |
| 3 | **Redis Sorted Set 命令队列** | `redis/go-redis` | 每设备 TR-069 RPC 命令队列 | ✅ Redis | ✅ |
| 4 | **Redis 任务队列** | `redis/go-redis` | 新版统一任务队列（Redis + PG 双写） | ✅ Redis+PG | ✅ |
| 5 | **Redis Pub/Sub** | `redis/go-redis` | Casbin 策略热更新通知 | ❌ | ✅ |
| 6 | **SSE MessageHub** | 纯 Go channel + 可选持久化 | 浏览器 WebSocket/SSE 推送 | 可选 | ❌ |

**核心实现文件位置**：

## 2. NATS JetStream 流 (Stream) 定义

在 [nats.go](omcgo/internal/core/components/nats/nats.go) 中集中注册 **8 个 JetStream 流**，每个流以点分前缀捕获一类事件。保留策略均为 `WorkQueuePolicy`（处理后删除），存储为 `FileStorage`，最大存活 72 小时。

| Stream | Subject 模式 | 业务定位 |
|--------|-------------|---------|
| `DEVICE` | `device.>` | 设备入网、心跳、参数变更、告警、传输完成等 Inform 相关事件 |
| `COMMAND` | `command.>` | 下发类 RPC 命令（预留）+ RPC 响应事件 |
| `PM` | `pm.>` | PM 文件生命周期（收到 / 解析完成） |
| `MR` | `mr.>` | MR 文件生命周期（收到 / 解析完成） |
| `ALARM` | `alarm.>` | 告警生命周期（raised / cleared / acknowledged） |
| `OSS` | `oss.>` | 北向推送（告警、PM、配置快照） |
| `PROVISION` | `provision.>` | 自动开站任务状态 |
| `DATAMODEL` | `datamodel.>` | 数据模型 XML 上传/接收事件 |

## 4. Redis 队列

### 4.1 旧版命令队列 `acs:cmdq:{device_sn}` (Sorted Set)

**实现文件**: [cmdqueue/queue.go](omcgo/internal/acs/cmdqueue/queue.go)

**Key 前缀**: `acs:cmdq:` （定义于 [queue.go:34](omcgo/internal/acs/cmdqueue/queue.go#L34)）

**数据结构**:
- Redis **Sorted Set**
- Score = `priority × 1e12 + created_at_unix_nano`（支持优先级 + FIFO）
- Value = JSON 序列化的 `Command` 对象

**接口**（[queue.go](omcgo/internal/acs/cmdqueue/queue.go)）:
```go
type CommandQueue interface {
    Push(ctx, deviceSN, cmd) error
    Pop(ctx, deviceSN) (*Command, error)   // 原子 ZRANGEBYSCORE + ZREM
    Peek(ctx, deviceSN) (*Command, error)
    Len(ctx, deviceSN) (int64, error)
    Clear(ctx, deviceSN) error
}
```

**Push 位置**（向队列入队 RPC 命令）:
- [provision/orchestrator.go:78-80](omcgo/internal/provision/orchestrator.go#L78-L80) — 自动开站步骤入队
- [provision/sync.go:72](omcgo/internal/provision/sync.go#L72) / [154](omcgo/internal/provision/sync.go#L154) / [245](omcgo/internal/provision/sync.go#L245) / [301](omcgo/internal/provision/sync.go#L301) / [423](omcgo/internal/provision/sync.go#L423) — 参数同步命令
- [provision/model_upload.go:82](omcgo/internal/provision/model_upload.go#L82) — 数据模型 Upload RPC
- [device/device_service.go](omcgo/internal/device/device_service.go) — 任意 RPC 下发

**Pop 位置**（设备会话内出队）:
- ACS Handler 在 CPE 发送 `Inform` / `*Response` 后，通过 `Pop()` 拉取下一条命令写入 SOAP 响应：[acs/handler.go](omcgo/internal/acs/handler.go)

### 4.2 新版任务队列 `acs:taskq:{device_sn}` / `acs:task:{taskID}` / `acs:cwmp2task:{hash}`

**实现文件**: [task/redis_queue.go](omcgo/internal/task/redis_queue.go)

**Key 前缀**（[redis_queue.go:15-17](omcgo/internal/task/redis_queue.go#L15-L17)）:

```
acs:taskq:{device_sn}       — 每设备任务队列（Sorted Set，member=taskID）
acs:task:{taskID}           — 任务详情 Hash（TTL 24h）
acs:cwmp2task:{cwmp_id_hash} — CWMP ID → Task ID 映射（TTL 24h，用于响应回查）
```

**设计意图**（根据 [omcgo/CLAUDE.md §5.2](omcgo/CLAUDE.md) 和 [task/](omcgo/internal/task/) 模块结构）:
- Redis 负责高性能队列操作（入队 / 出队 / 查找）
- PostgreSQL `device_tasks` 表负责持久化与审计（[task/pg_repository.go](omcgo/internal/task/pg_repository.go)）
- 双写模式：业务层通过 `TaskService` 同步写入两者

**核心组件**:
- [task/service.go](omcgo/internal/task/service.go) — 统一任务服务（上层 API）
- [task/handler.go](omcgo/internal/task/handler.go) — HTTP API
- [task/bridge_queue.go](omcgo/internal/task/bridge_queue.go) — 向下兼容旧 `CommandQueue` 接口
- [task/cwmp_id.go](omcgo/internal/task/cwmp_id.go) — CWMP ID 生成与 Task 关联

**状态**：新旧两套队列当前**并存**。`cmdqueue` 仍在 provision/device 模块中使用，`task` 模块是统一化演进方向（bridge_queue 承担兼容层）。

### 4.3 Redis Pub/Sub — `casbin:policy:reload`

**实现文件**: [admin/casbin.go:140-157](omcgo/internal/admin/casbin.go#L140-L157)

**Channel**: `casbin:policy:reload`

**数据结构**: Redis Pub/Sub（Fire-and-forget，无持久化）

**用途**: RBAC 策略热更新。管理面改动角色权限后，[casbin.go:143](omcgo/internal/admin/casbin.go#L143) 的 `redisWatcher` 向该频道发布通知，所有 app/acs/worker 实例订阅后重新加载 Casbin 策略，实现多实例实时同步。

```
    → Hub.Publish(userID, msg)
    → Per-user Go channel

    → Browser EventSource 实时接收
```

**数据结构**:
```go
type SSEMessage struct {
    ID, Event, UserID string
    Data              json.RawMessage
}
```

**发布者**:
- [mml/service.go:80](omcgo/internal/mml/service.go#L80) — MML 命令执行状态推送

**订阅者**: 浏览器端通过 HTTP GET `/api/v1/events/stream` 建立长连接消费（handler 位于 [events/handler.go](omcgo/internal/events/handler.go)）

## 10. 交付保证与重试策略

### 10.1 NATS JetStream（[nats_bus.go](omcgo/internal/core/event/nats_bus.go)）

- **交付语义**: At-Least-Once（Durable Consumer + Explicit Ack）
- **重试策略**: 指数退避（1s / 2s / 4s / 8s），最多 5 次（[nats_bus.go:15](omcgo/internal/core/event/nats_bus.go#L15)）
- **超限处理**: `msg.Term()` 终止消息，避免死循环
- **Stream 保留**: `WorkQueuePolicy`（消费完删除）+ MaxAge 72h

### 10.2 Redis 命令队列 / 任务队列

- **原子 Pop**: `ZRANGEBYSCORE + ZREM` 组合保证并发安全
- **过期跳过**: 若 `Command.ExpiresAt` 已过期则直接丢弃
- **优先级 + FIFO**: Score 编码 `priority × 1e12 + timestamp`
- **持久化**: Redis AOF/RDB；任务队列额外双写 PostgreSQL `device_tasks`

### 10.3 Redis Pub/Sub

- Fire-and-forget，订阅者掉线会丢消息。
- 仅用于 Casbin 策略通知（最坏情况下订阅者重连时自动全量重载，可接受）。

### 10.4 SSE Hub

- 每用户独立 channel；channel 满时丢弃最旧消息
- 可选持久化（[events/store.go](omcgo/internal/events/store.go)）支持重连回放

## 13. 观察与建议

### 13.1 当前架构优点

1. **Subject 常量集中**：[subjects.go](omcgo/internal/core/event/subjects.go) 是唯一事实源，含 doc comment 标注发布/订阅方，维护成本低。
2. **实现分离**：NATS / Channel 双实现使得单进程测试和生产部署可共用业务逻辑。
3. **部署单元职责清晰**：发布者主要在 acs + app，订阅者多在 app + worker，工作负载分散合理。

### 13.2 潜在问题

1. **孤儿 Subject 比例偏高（约 65%，下调中）** ✅ 2026-04-22 打通 2 个
   - 应做一次审计：保留必要钩子，删除无计划消费的 Subject 避免腐蚀。
   - 建议对"有发布无订阅"的 Subject 至少加一个默认的审计日志订阅者，避免事件彻底丢失。
   - 已打通（2026-04-22）: `device.inform.reboot_complete` / `device.reboot.abnormal` 见 §7.15。

## 14. 三套 Redis 机制合并可行性分析

> **动机**: 希望项目中只保留**唯一一套**基于 redis/go-redis 的队列实现，降低维护与心智负担。本章评估三套现存 Redis 机制 —— 旧命令队列（`acs:cmdq`）、新任务队列（`acs:taskq` 族）、Casbin Pub/Sub —— 合并的技术可行性，给出分阶段迁移路线。

### 14.1 目标澄清

"唯一一套"需要先区分**合并**的两个层级：

1. **数据结构层统一** — 全部用同一 Redis 原语（ZSET 或 Stream 或 Pub/Sub）
2. **代码抽象层统一** — 共用同一 Go 封装（连接、序列化、指标、生命周期），底层可以是不同 Redis 原语

先说结论：

- **数据结构层强行统一不可取**。队列语义（单消费者 + 优先级 + 响应关联）与广播语义（多订阅者 + fire-and-forget）在 Redis 原语上没有单一最优选择（详见 §14.4）。
- **代码抽象层统一可取且必要**。应提炼出 `internal/core/components/redisx` 基础包，统一三套机制的公共横切关注（§14.7）。
- **业务上的简化** = cmdq 下线 + Casbin 脱离 Redis Pub/Sub，让"基于 redis/go-redis 的队列实现"最终**只剩 taskq 这一套**。

### 14.2 三套机制的本质语义对比

| 维度 | cmdq (旧) | taskq (新) | Casbin Pub/Sub |
|------|----------|-----------|----------------|
| **Redis 原语** | Sorted Set | ZSET + Hash + String | Pub/Sub Channel |
| **消费者模式** | 单消费者（acs Pop） | 单消费者（acs Peek/Pop） | **多订阅者广播** |
| **顺序语义** | 优先级 + FIFO | 优先级 + FIFO（纳秒精度） | 无序 |
| **持久化** | Redis AOF/RDB | Redis + **PG 双写** | 无持久化 |
| **响应关联** | 无 | `acs:cwmp2task` CWMP ID 反查 | 不需要 |
| **生命周期** | 无显式 TTL | 详情 Hash TTL 24h + 状态机 (pending/sent/completed/failed) | 连接存活期 |
| **重试语义** | 应用层决策 | `GetStaleSentTasks` 超时重发 | 丢失可容忍（周期刷新兜底） |
| **一致性要求** | 最终一致 | 强一致（Redis + PG 事务对齐） | 最终一致（松散） |
| **使用规模** | ≤10 万 device keys | ≤10 万 device keys + 瞬时任务数 | 1 个固定 channel |
| **典型调用方** | provision / device / software | task.Service（新接入点） | admin (casbin watcher) |

**关键观察**: cmdq 和 taskq 是**同一类问题的新老方案**，语义差异在于 taskq 引入了审计、响应关联、状态机。而 Casbin Pub/Sub 是**完全不同的问题**（广播通知），在数据结构和语义上与前两者正交。

### 14.3 cmdq ↔ taskq：严格超集关系

**taskq 是 cmdq 的严格功能超集**。具体差集：

| 能力 | cmdq | taskq |
|------|:----:|:----:|
| Push / Pop / Peek / Len / Clear | ✅ | ✅ |
| 优先级 + FIFO | ✅ Score=priority×1e12+ns | ✅ Score=priority×1e13+ns（精度更高）|
| `ExpiresAt` 跳过过期 | ✅ | ✅ |
| 任务状态机（pending/sent/completed/failed） | ❌ | ✅ |
| CWMP ID 反查 → 响应回调定位 | ❌ | ✅ |
| 任务详情独立 Hash（可部分更新） | ❌ | ✅ |
| PG 持久化（重启不丢 + 审计） | ❌ | ✅ |
| 僵死任务恢复（`GetStaleSentTasks`） | ❌ | ✅ |

**迁移风险**: **零语义损失**。cmdq 所有使用点（provision/sync.go、orchestrator.go、model_upload.go、device_service.go、backup/executor.go）都可以直接改用 taskq。

**迁移阻力**: 仅是工程成本（调用点替换 + 回归测试），无架构障碍。[bridge_queue.go](omcgo/internal/task/bridge_queue.go) 已经在做兼容层过渡。

### 14.4 广播 vs 队列：为何不应"硬合并"

Casbin Pub/Sub 的语义是**广播**：一条消息要被所有实例各自收到一份。而 cmdq/taskq 是**队列**：一条消息只能被一个消费者消费。

#### 若强行用队列承担广播 — 三种反模式

1. **每实例一队列**: 发布者要知道所有实例的 ID，N 个实例要 N 次 Push → 违反"发布者不关心订阅者"的解耦原则
2. **一个队列 + 每实例独立 offset**: 实际上就是 Redis Streams + consumer group（每消费者独立 group），但 Streams 的性能开销远高于 Pub/Sub
3. **每实例轮询共享队列**: 每实例都 Pop 会造成竞争消费 → 丢失广播语义

#### 若强行用 Pub/Sub 承担队列 — 更糟

- 无持久化：消费者重启就丢消息
- 无优先级 / FIFO 保障
- 无响应关联
- 无 ACK 重试

**结论**: 广播和队列是 Redis 层面的两种独立范畴，必须分别对待。

### 14.5 候选方案矩阵

| 方案 | 技术思路 | 改造成本 | 性能 | 语义完整度 | 运维 | 推荐 |
|------|---------|---------|-----|-----------|-----|:---:|
| **A. Redis Streams 统一三者** | 所有队列/广播都用 Streams + consumer group | 高 | 中（反向索引扫描成本高） | ⚠️ 优先级语义无法复现 | 10 万 Streams 巡检复杂 | ❌ |
| **B. cmdq→taskq 合并，Pub/Sub 保留** | 只下线 cmdq | 中 | 不变 | ✅ | 不变（仍需维护两种 Redis 用法） | ⚠️ 过渡 |
| **C. cmdq→taskq 合并 + Casbin 迁 NATS** | taskq 是唯一 Redis 队列；Casbin 改走 NATS 已有基础设施 | 中 | 提升（NATS 持久化） | ✅ | 减少一种 Redis 使用范式 | ✅ |
| **D. cmdq→taskq 合并 + Casbin 迁 PG LISTEN/NOTIFY** | 用 Postgres 的 NOTIFY 做策略通知 | 中（需新增 pg listener） | 延迟极低（<1ms） | ✅ | 运维需新增 PG listener 监控 | ⚠️ 次选 |

#### 为什么 A 方案（Streams 统一）不推荐

子代理已验证三个 hard blocker：

1. **优先级无法复现**: Stream 条目 ID 固定为 `{timestamp}-{seq}`，无法注入 `priority × 1e13` 这样的自定义 Score。要么在 payload 里编码优先级 + 应用层排序（破坏原子 Pop），要么放弃优先级。
2. **CWMP ID 反查成本不可接受**: 现方案 `GET acs:cwmp2task:{hash}` 一次命中 O(1)。Streams 方案要 `XRANGE` 扫描最近 N 条，10 万并发会话下延迟不可控。
3. **10 万 Streams 的运维负担**: Redis 支持无限 Stream，但 `XINFO` 遍历、清理、告警巡检相比 ZSET + SCAN 模式复杂度陡增。需要额外建立 Stream 名称索引表。

### 14.6 推荐方案：C —— 两层统一

```
┌─ 语义层 ─────────────────────────────────────────────┐
│                                                        │
│   TaskQueue                    BroadcastChannel        │
│   (每设备 RPC + 审计)           (系统事件广播)           │
│   ● 优先级 FIFO                 ● 多订阅者接收            │
│   ● 状态机                      ● 持久化（可重放）        │
│   ● CWMP 响应回查               ● Ack/重试              │
│                                                        │
└────────┬──────────────────────────┬───────────────────┘
         │                          │
         ▼                          ▼
┌─ 实现层 ─────────────────┐ ┌─ 实现层 ─────────────────┐
│  Redis ZSET + Hash + Str │ │   NATS JetStream         │
│  + PG device_tasks       │ │   Subject: sys.*         │
│  (internal/task)         │ │   (Casbin policy reload) │
└──────────────────────────┘ └──────────────────────────┘
         │                          │
         └──────────┬───────────────┘
                    ▼
┌─ 基础设施层（新增 internal/core/components/redisx）───┐
│  • 连接池（UniversalClient，单例）                      │
│  • Key 前缀常量（acs:taskq: / acs:task: / acs:cwmp2task:）│

│  • Prometheus 指标（Op counter / latency histogram）    │
│  • 错误处理与指数退避重试                                 │
│  • TTL & 扫描清理（SCAN + MATCH）                       │
└───────────────────────────────────────────────────────┘
```

**三句话说明**：

- **Redis 侧**: cmdq 下线，Redis 上只剩 taskq 一套队列实现。Pub/Sub 从 Redis 中彻底移除。
- **NATS 侧**: Casbin 策略通知改用 NATS subject（如 `sys.casbin.policy.reload`），走项目已有的 JetStream 基础设施，获得持久化 + 重连回放。
- **代码侧**: taskq 依赖新包 `redisx`，该包封装所有 Redis 相关横切关注，成为项目中"基于 redis/go-redis"的**唯一**入口。

```go
// 新增 internal/admin/casbin_nats.go
type natsCasbinWatcher struct {
    js      nats.JetStreamContext
    subject string      // "sys.casbin.policy.reload"
    cb      func(string)
}

func (w *natsCasbinWatcher) Update() error {
    _, err := w.js.Publish(w.subject, []byte("reload"))
    return err
}

func (w *natsCasbinWatcher) StartListener() error {
    _, err := w.js.Subscribe(w.subject, func(m *nats.Msg) {
        if w.cb != nil {
            w.cb(string(m.Data))
        }
        m.Ack()
    }, nats.Durable("casbin-reload-"+hostname()))
    return err
}
```
