# 参数树自动发现与管理方案

> 设备首次连接时自动识别参数模型，同步全量参数，并提供参数树可视化管理界面。

---

## 1. 需求概述

| 编号 | 需求 | 说明 |
|------|------|------|
| R1 | 自动匹配参数模板 | 设备首次 Inform 时，按 OUI + ProductClass + SoftwareVersion 三元组匹配已有 DataModel |
| R2 | 自动发现参数树 | 匹配不上时，通过 GetParameterNames RPC 自动提取设备完整参数树，生成 DataModel |
| R3 | 全量参数同步 | 用匹配/发现的参数树，通过 GetParameterValues 同步全量参数值到数据库 |
| R4 | 参数树管理界面 | 设备详情页新增「参数树」标签页，支持参数的树状浏览、搜索、编辑、刷新 |
| R5 | 功能开关 | 自动发现和自动同步作为可配置功能，默认关闭，可按需开启 |

---

## 2. 现有机制分析

### 2.1 现有 DataModel 工作流（手动导入）

当前系统中，DataModel 是**管理员手动导入**的，流程如下：

```
管理员 → POST /api/v1/config/datamodels (Import JSON)
       → DataModel 创建为 draft 状态
       → 管理员审核 → PUT /activate → 变为 active
       → DataModelRegistry 三级缓存自动更新
```

**三级回退解析**（现有）：
1. **product**: carrier + tech + OUI + ProductClass
2. **oui**: carrier + tech + OUI
3. **carrier_default**: carrier + tech

### 2.2 现有 Provisioning 流程（硬停止）

```go
// engine.go HandleBootstrap() 现有行为：
1. discovered → identifying:  调用 dmRegistry.ResolveForDevice()
   - dm == nil 时：不报错，继续（dm 只是信息参考）
   - dm != nil 时：记录日志

2. identifying → matching:    调用 templateService.Match()
   - tmpl == nil 时：★ 直接 failTask()，provisioning 终止 ★
   - tmpl != nil 时：继续

3. matching → configuring:    BuildProvisioningSteps(tmpl)
   - 固定生成 3 步：GetParameterValues → SetParameterValues → Reboot

4. configuring → verifying → completed
```

**关键发现**：现有系统中，**没有配置模板 = provisioning 直接失败**。DataModel 解析结果实际上没有被充分利用。

## 3. 功能开关设计

### 3.1 为什么需要开关

| 原因 | 说明 |
|------|------|
| **流量控制** | 自动发现会对每台新设备发起 GPN + 多轮 GPV，产生大量 TR069 流量 |
| **渐进上线** | 运营商环境下新功能需要灰度验证，不能一刀切 |
| **兼容现有流程** | 已部署环境中管理员可能仍习惯手动导入 DataModel |
| **资源保护** | 大批量设备同时上线时，自动发现可能导致 ACS 过载 |
| **安全审计** | 某些运营商要求参数树变更必须有人工审批流程 |

### 3.2 开关配置设计

#### YAML 配置（静态，随部署设定）

```yaml
# config.dev.yaml / config.prod.yaml
provision:
  # 是否启用自动开站（现有功能，默认 true）
  enabled: true

  # 自动发现开关：设备无匹配 DataModel 时，是否通过 GPN 自动发现参数树
  auto_discovery:
    enabled: false                    # 默认关闭
    max_concurrent: 10                # 同时进行自动发现的最大设备数
    gpn_timeout: 60s                  # GetParameterNames 超时时间
    gpv_batch_size: 50                # 每批 GetParameterValues 的参数数量
    gpv_timeout: 30s                  # 每批 GetParameterValues 超时时间
    auto_activate_model: false        # 自动发现的 DataModel 是否自动激活（建议 false）

  # 自动同步开关：设备有 DataModel 但无配置模板时，是否自动同步全量参数值
  auto_sync:
    enabled: false                    # 默认关闭
    sync_on_bootstrap: true           # 设备首次上线时自动同步
    sync_on_firmware_change: true     # 固件版本变化时重新同步
    max_concurrent: 20                # 同时进行同步的最大设备数
```

### 3.3 开关生效位置

```
HandleBootstrap()
    │
    ├── identifying: ResolveForDevice()
    │       ↓ dm 结果
    ├── matching: templateService.Match()
    │       ↓ tmpl 结果
    │
    ├── tmpl != nil → configuring（现有流程，不受开关影响）
    │
    ├── tmpl == nil && dm != nil
    │   └── if cfg.Provision.AutoSync.Enabled
    │       ├── true  → syncing（自动同步参数值）
    │       └── false → ★ failTask（现有行为：无模板则失败）★
    │
    └── tmpl == nil && dm == nil
        └── if cfg.Provision.AutoDiscovery.Enabled
            ├── true  → discovering → syncing → completed
            └── false → ★ failTask（现有行为：无模板则失败）★
```

**关闭所有开关 = 完全兼容现有行为**。这是最关键的设计原则。

## 4. 整体架构

### 4.1 扩展后的 Provisioning 状态机

```
              现有状态（不变）                     新增状态（开关控制）
  ┌─────────────────────────────────┐    ┌──────────────────────────┐
  │ discovered → identifying        │    │                          │
  │           → matching            │    │                          │
  │           → configuring         │    │  discovering → syncing   │
  │           → verifying           │    │     (GPN)       (GPV)    │
  │           → completed / failed  │    │                          │
  └────────────────┬────────────────┘    └────────────┬─────────────┘
                   │                                  │
                   └──────────── 合并 ────────────────┘

  discovered → identifying → matching ─┬─→ configuring → verifying → completed
                                       │      (有模板)                   ↑
                                       │                                │
                                       ├─→ syncing ─────────────────────┤
                                       │   (有DM无模板                  │
                                       │    + auto_sync=true)           │
                                       │                                │
                                       ├─→ discovering → syncing ───────┘
                                       │   (无DM无模板
                                       │    + auto_discovery=true)
                                       │
                                       └─→ failed
                                           (开关关闭时的默认行为)
```

#### HandleBootstrap 扩展（含开关逻辑）

```go
func (e *ProvisioningEngine) HandleBootstrap(ctx context.Context, evt bootstrapEvent) error {
    task := e.createTask(evt)

    // 1. identifying: 解析 DataModel（四级回退）
    dm, err := e.dmRegistry.ResolveWithFirmware(ctx,
        device.Carrier, device.Technology,
        device.OUI, device.ProductClass, device.FirmwareVersion)
    if err != nil {
        return e.failTask(ctx, task, fmt.Errorf("resolve data model: %w", err))
    }

    // 2. matching: 匹配配置模板
    tmpl, err := e.templateService.Match(ctx, device)
    if err != nil {
        return e.failTask(ctx, task, fmt.Errorf("match template: %w", err))
    }

    // 3. 四路分支（前两路是现有行为，后两路受开关控制）
    switch {
    case tmpl != nil:
        // 路径A: 有模板 → configuring（★ 现有流程，完全不变 ★）
        return e.startConfiguring(ctx, task, tmpl)

    case dm != nil && e.cfg.Provision.AutoSync.Enabled:
        // 路径B: 有 DataModel、无模板、auto_sync 开启 → 直接同步参数值
        e.logger.Info("auto sync: data model found, syncing parameters",
            zap.String("device_sn", device.SerialNumber),
            zap.String("data_model_id", dm.ID.String()))
        return e.startSyncing(ctx, task, device, dm)

    case dm == nil && e.cfg.Provision.AutoDiscovery.Enabled:
        // 路径C: 无 DataModel、auto_discovery 开启 → 先发现再同步
        e.logger.Info("auto discovery: no data model, starting parameter discovery",
            zap.String("device_sn", device.SerialNumber))
        return e.startDiscovering(ctx, task, device)

    default:
        // 路径D: 开关关闭 → failTask（★ 现有行为，完全兼容 ★）
        return e.failTask(ctx, task,
            fmt.Errorf("no provisioning template matched for device %s", device.SerialNumber))
    }
}
```

#### 自动发现流程 (discovery.go — 新文件)

```go
// startDiscovering 发送 GetParameterNames 发现参数树
func (e *ProvisioningEngine) startDiscovering(ctx context.Context,
    task *ProvisioningTask, device *Device) error {

    e.transitionTo(task, StateDiscovering)

    // 并发控制检查
    if !e.discoverySemaphore.TryAcquire(1) {
        return e.failTask(ctx, task, fmt.Errorf("auto discovery concurrent limit reached"))
    }

    // 创建发现日志
    log := &ParameterDiscoveryLog{
        DeviceID:        device.ID,
        DeviceSN:        device.SerialNumber,
        OUI:             device.OUI,
        ProductClass:    device.ProductClass,
        FirmwareVersion: device.FirmwareVersion,
        Status:          "discovering",
        StartedAt:       time.Now(),
    }
    e.discoveryLogRepo.Create(ctx, log)

    // 发送 GetParameterNames("Device.", nextLevel=false)
    params, _ := json.Marshal(map[string]interface{}{
        "path":       "Device.",
        "next_level": false,
    })

    _, err := e.taskService.CreateTask(ctx, &CreateTaskRequest{
        DeviceSN: device.SerialNumber,
        Method:   "GetParameterNames",
        Params:   params,
        Priority: 5,
        Source:   SourceSystem,
        Metadata: map[string]string{
            "provisioning_task_id": task.ID.String(),
            "discovery_log_id":    log.ID.String(),
            "purpose":             "auto_discovery",
        },
    })
    return err
}

// handleDiscoveryResult 处理 GetParameterNames 响应
func (e *ProvisioningEngine) handleDiscoveryResult(ctx context.Context,
    task *ProvisioningTask, device *Device, result json.RawMessage) error {

    defer e.discoverySemaphore.Release(1)

    // 1. 解析参数列表
    var paramInfos []struct {
        Name     string `json:"name"`
        Writable bool   `json:"writable"`
    }
    if err := json.Unmarshal(result, &paramInfos); err != nil {
        return fmt.Errorf("parse GPN response: %w", err)
    }

    // 2. 去重检查：同 OUI+ProductClass+FirmwareVersion 是否已有 DataModel
    existing, _ := e.dmRegistry.ResolveWithFirmware(ctx,
        device.Carrier, device.Technology,
        device.OUI, device.ProductClass, device.FirmwareVersion)
    if existing != nil {
        // 已有（可能另一台同型号设备先完成了发现），直接复用
        device.DataModelID = existing.ID
        e.deviceRepo.Update(ctx, device)
        e.transitionTo(task, StateSyncing)
        return e.startSyncing(ctx, task, device, existing)
    }

    // 3. 构建参数树并创建 DataModel
    paramTree := buildParameterTree(paramInfos)
    paramTreeJSON, _ := json.Marshal(paramTree)

    dm := &DataModel{
        Carrier:         device.Carrier,
        Technology:      device.Technology,
        OUI:             device.OUI,
        ProductClass:    device.ProductClass,
        FirmwareVersion: device.FirmwareVersion,
        Scope:           ScopeProduct,
        Status:          StatusDraft,
        SourceType:      "auto_discovered",
        RootObject:      "Device.",
        ParameterTree:   paramTreeJSON,
        Source:           fmt.Sprintf("auto-discovered from %s", device.SerialNumber),
        Description:      fmt.Sprintf("自动发现: %s %s (FW: %s)",
                            device.OUI, device.ProductClass, device.FirmwareVersion),
    }

    // 是否自动激活
    if e.cfg.Provision.AutoDiscovery.AutoActivateModel {
        dm.Status = StatusActive
        dm.IsActive = true
    }

    e.dataModelRepo.Create(ctx, dm)

    // 4. 关联设备
    device.DataModelID = dm.ID
    e.deviceRepo.Update(ctx, device)

    // 5. 进入同步阶段
    e.transitionTo(task, StateSyncing)
    return e.startSyncing(ctx, task, device, dm)
}
```

#### 参数同步流程 (sync.go — 新文件)

```go
// startSyncing 根据 DataModel 参数树，分批 GetParameterValues 同步参数
func (e *ProvisioningEngine) startSyncing(ctx context.Context,
    task *ProvisioningTask, device *Device, dm *DataModel) error {

    e.transitionTo(task, StateSyncing)

    // 从 DataModel 提取所有叶子参数路径
    leafPaths := extractLeafPaths(dm.ParameterTree)
    batchSize := e.cfg.Provision.AutoDiscovery.GPVBatchSize
    if batchSize <= 0 {
        batchSize = 50 // 默认值
    }

    totalBatches := (len(leafPaths) + batchSize - 1) / batchSize

    // 分批创建 GetParameterValues 任务
    for i := 0; i < len(leafPaths); i += batchSize {
        end := min(i+batchSize, len(leafPaths))
        batch := leafPaths[i:end]
        batchIndex := i/batchSize + 1

        params, _ := json.Marshal(map[string]interface{}{
            "names": batch,
        })

        e.taskService.CreateTask(ctx, &CreateTaskRequest{
            DeviceSN: device.SerialNumber,
            Method:   "GetParameterValues",
            Params:   params,
            Priority: 10 + batchIndex, // 按顺序执行
            Source:   SourceSystem,
            Metadata: map[string]string{
                "provisioning_task_id": task.ID.String(),
                "purpose":             "param_sync",
                "batch_index":         fmt.Sprintf("%d/%d", batchIndex, totalBatches),
            },
        })
    }

    task.TotalSteps = totalBatches
    task.CurrentStep = 0
    e.taskRepo.Update(ctx, task)
    return nil
}

// handleSyncResult 处理 GetParameterValues 批次响应
func (e *ProvisioningEngine) handleSyncResult(ctx context.Context,
    task *ProvisioningTask, device *Device, result json.RawMessage) error {

    // 1. 解析 GPV 响应
    var paramValues []struct {
        Name  string `json:"name"`
        Value string `json:"value"`
        Type  string `json:"type"`
    }
    json.Unmarshal(result, &paramValues)

    // 2. 批量写入 device_parameters
    deviceParams := make([]DeviceParameter, 0, len(paramValues))
    for _, pv := range paramValues {
        deviceParams = append(deviceParams, DeviceParameter{
            DeviceID:       device.ID,
            ParameterPath:  pv.Name,
            ParameterValue: pv.Value,
            ParameterType:  mapXSDType(pv.Type),
            Writable:       true,
            LastUpdatedAt:  time.Now(),
        })
    }
    e.paramRepo.BatchUpsert(ctx, device.ID, deviceParams)

    // 3. 推进进度
    task.CurrentStep++
    if task.CurrentStep >= task.TotalSteps {
        e.transitionTo(task, StateCompleted)
        e.deviceRepo.UpdateStatus(ctx, device.ID, DeviceActive)
    }
    e.taskRepo.Update(ctx, task)
    return nil
}
```

### 5.4 SOAP 响应解析器

**现状**：ACS handler 在 `handleRPCResponse()` 中仅检测 SOAP Fault，不解析具体内容。

## 8. 关键设计决策

### Q1: 为什么默认关闭自动发现？

**理由**：
- 自动发现对每台新设备产生额外 RPC 流量（1 次 GPN + N 次 GPV）
- 运营商环境对网管到基站的指令有审计要求，自动行为需要明确授权
- 已有手动导入 DataModel 的工作流，开关关闭时完全兼容
- 允许管理员先在测试环境验证，再在生产开启

### Q2: 开关关闭时手动操作仍可用？

**是的**。开关只控制 Provisioning Engine 的自动行为：
- `auto_discovery.enabled=false`: 设备 bootstrap 时不会自动 GPN
- 但管理员仍可通过 `POST /devices/:id/parameters/discover` 手动触发
- `auto_sync.enabled=false`: 设备 bootstrap 时不会自动 GPV
- 但管理员仍可通过 `POST /devices/:id/parameters/sync` 手动触发

### Q3: 为什么用 nextLevel=false（递归获取完整参数树）？

**理由**：
- nextLevel=true 只返回直接子节点，需要递归多轮 RPC（深度 5-8 层）
- 一次性获取虽然响应大（1000-3000 参数），但减少 RPC 往返
- 基站通常支持完整树导出，这是 TR069 标准行为

**降级方案**：CPE 不支持时降级为 nextLevel=true 逐层发现。

### Q4: 同时多台同型号设备上线怎么办？

**方案**：去重检查。`handleDiscoveryResult()` 在创建 DataModel 前先调用 `ResolveWithFirmware()` 检查是否已有同 OUI+ProductClass+FirmwareVersion 的 DataModel。如果另一台设备已先完成发现，直接复用。

### Q5: 自动发现的 DataModel 为什么默认 draft？

**理由**：
- 自动发现的参数树缺少人工审核（参数描述、约束、分类不完整）
- 管理员可审核后激活，或以此为基础完善
- 可通过 `auto_activate_model: true` 改为自动激活（如信任设备的参数报告）
- draft 状态的 DataModel **仍可用于参数同步**（通过 device.DataModelID 直接关联）

### Q6: 参数修改是同步还是异步？

**异步**。PUT /parameters 返回 202 + task_id：
- SetParameterValues 需要等设备下次连接才执行
- 设备可能离线，命令排队等待
- 前端通过 task_id 追踪执行状态

## 9. 风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| CPE 不支持递归 GPN | 中 | 发现失败 | 降级为逐层发现(nextLevel=true)，增加重试 |
| 参数树过大(>5000) | 低 | GPV 超时 | 减小 batch size，增加超时，分段处理 |
| 并发发现重复创建 DM | 中 | 冗余数据 | 去重检查 + OUI+PC+FW 唯一约束 |
| 设备离线无法同步 | 高 | 任务积压 | 任务设过期时间(24h)，状态标记为 pending |
| ACS 过载 | 中 | 影响正常业务 | MaxConcurrent 限制 + semaphore 控制 |
| SOAP 响应异常 | 中 | 解析失败 | 容错解析，记录原始响应，任务标记 failed |

## 11. 总结

### 核心设计原则

1. **开关控制，默认兼容** — 所有新行为受 `auto_discovery.enabled` 和 `auto_sync.enabled` 开关控制，关闭时完全等同现有行为
2. **手动能力不受限** — 即使开关关闭，管理员仍可通过 REST API 手动触发发现和同步
3. **增量扩展** — 在现有 Provisioning 状态机基础上新增 2 个状态，不修改已有状态转换
4. **去重保护** — 同型号设备并发上线时不会重复创建 DataModel
5. **并发控制** — MaxConcurrent + semaphore 防止 ACS 过载

```yaml

provision:

    enabled: false
  auto_sync:

  auto_discovery:
    enabled: false

    enabled: true

  auto_sync:

  auto_sync:
    enabled: true
```
