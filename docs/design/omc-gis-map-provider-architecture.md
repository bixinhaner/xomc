# OMC GIS 地图源与离线部署方案

> **文档状态**：方案决策稿
> **适用系统**：OMC 通信网管 GIS 基站地图
> **适用版本**：V1 主皮肤 + OpenLayers
> **更新日期**：2026-08-04

## 1. 背景与目标

OMC 面向通信运营商和小基站运维场景，地图页面不仅用于展示地理背景，还承担以下业务职责：

- 展示基站和设备的在线、离线、告警状态；
- 支持设备组筛选、聚合、搜索定位和设备详情查看；
- 支持内网、无外网、无 VPN 的生产环境；
- 支持国内部署，也为海外部署保留能力；
- 在底图服务不可用时，设备点位和运维操作仍然可用；
- 满足地图数据授权、版权、密钥、访问审计和数据安全要求。

本文只解决地图源、底图部署、中心点和故障降级问题。OpenLayers 作为渲染引擎继续保留，不因地图源变化替换前端地图框架。

## 2. 结论摘要

### 2.1 最终推荐

生产环境采用：

```text
合法授权的地图数据
    -> 内网地图瓦片服务
    -> OpenLayers 加载 XYZ 或矢量瓦片
    -> 设备数据作为独立 Vector/Cluster 图层
```

国内生产环境默认使用自建离线地图；海外生产环境可以使用合法授权的 OSM 数据生成离线地图，或使用当地合法商业地图服务。

高德、百度和 OSM 在线服务不作为 OMC 国内内网生产环境的基础依赖。它们可以作为开发环境、具备授权的在线部署环境或明确配置的备用源，但不能通过抓取、绕过 Key、隐藏版权或未经授权的代理方式使用。

### 2.2 中心点决策

中心点严格采用以下顺序：

```text
1. 离线地图元数据 center
2. 当前查询到的有效设备坐标计算中心点
3. 部署配置中的默认中心点
4. 代码内置默认中心点
```

离线地图元数据请求失败时，不能把历史地区的中心点伪装成有效离线元数据。失败应表示为“无离线地图元数据”，然后继续走设备数据或部署默认值。

### 2.3 底图不可用时的行为

底图瓦片加载失败不能导致白板。页面应保留：

- OpenLayers 地图容器；
- 设备点、聚合点、搜索定位和弹窗；
- 本地省界、行政区边界或网格背景（如已部署）；
- 明确的底图不可用提示；
- 地图源和版权说明。

## 3. 方案边界与基本概念

### 3.1 OpenLayers 不等于地图数据

OpenLayers 是地图渲染和交互引擎，负责：

- 地图视图、缩放和平移；
- Tile、Vector、Cluster、Overlay 等图层；
- 坐标投影转换和地图事件；
- 设备点位、聚合、扇区和测量等业务图层。

它不负责：

- 判断用户是否位于中国；
- 判断某个地图服务是否获得授权；
- 自动提供高德、百度或 OSM 数据；
- 自动处理各地图服务的 Key、配额、版权和坐标体系。

### 3.2 不按“是否国内”自动切换地图源

不建议通过浏览器 IP、VPN 状态或设备坐标判断国内外并自动切换地图源，原因包括：

- VPN、代理和企业出口会导致 IP 位置不可靠；
- 用户位置与设备部署位置可能不同；
- 自动切换会增加不可审计的外部依赖；
- 不同地图源的授权、Key、版权和坐标系不能动态假设；
- 自动切换失败时难以确定是网络、配额、授权还是坐标问题。

地图源应由部署配置、租户配置或后端许可证配置决定。浏览器只负责加载已经批准的配置。

## 4. 候选方案评估

| 方案 | 适合场景 | 主要优点 | 主要问题 | 结论 |
|---|---|---|---|---|
| 公共 OSM 在线瓦片 | 海外开发、小规模验证 | 接入简单、OpenLayers 兼容 | 依赖公网，公共服务有使用政策和流量限制 | 不作为 OMC 大规模生产依赖 |
| 高德在线服务 | 中国公网或有授权的在线环境 | 国内访问通常较好，数据和 POI 丰富 | Key、域名白名单、配额、商业授权、GCJ-02、版权要求 | 可选备用，不作为内网基础依赖 |
| 百度在线服务 | 已使用百度生态的项目 | 国内覆盖和 POI 能力 | Key、配额、BD-09、特殊瓦片体系、接入适配更复杂 | 不作为首选 |
| 国内自建离线瓦片 | 中国内网生产 | 不依赖公网和 VPN，性能和可控性最好 | 需要合法数据授权、制作、存储、更新和运维 | **首选** |
| 海外自建离线瓦片 | 海外内网或受限网络 | 统一架构，离线可用 | 需要各区域数据授权和更新流程 | 推荐 |
| 本地边界/网格背景 | 底图故障兜底 | 体积小、稳定、无白板 | 不是完整道路和 POI 地图 | 必须作为降级能力 |

### 4.1 高德和百度的隐性成本

接入在线地图并不只是替换一个 URL，通常还需要：

- 注册开发者或企业账号；
- 申请对应产品和调用权限；
- 配置 Key、域名白名单、服务端 IP 或应用标识；
- 评估每日和并发调用配额；
- 处理版权和数据来源展示；
- 处理服务条款、商业使用范围和数据合规；
- 将设备坐标转换到目标地图服务要求的坐标系；
- 设计 Key 泄露、配额耗尽、服务故障和续期流程；
- 为在线服务不可用准备离线或本地兜底。

因此，在线地图不能被视为“零运维底图”。

### 5.1 图层分层

1. **底图层**：离线 XYZ 或矢量瓦片；
2. **边界层**：省界、行政区界线或网格背景；
3. **设备业务层**：设备点、聚合点、告警样式；
4. **交互层**：高亮、弹窗、测量、扇区和搜索定位。

底图层发生故障时，不得清理或隐藏设备业务层和交互层。

## 6. 中心点与设备查询设计

### 6.1 中心点状态模型

离线地图加载结果应至少区分：

```text
loading       正在读取元数据
available     元数据有效且抽样瓦片可用
unavailable   元数据不存在、格式错误或瓦片不可用
```

`unavailable` 不应携带某个具体地区的历史中心点。

### 6.2 中心点决策流程

```text
页面初始化
    |
    +-- 离线元数据有效且瓦片可用？ -- 是 --> 使用 metadata.center
    |                                      并使用离线瓦片
    |
    +-- 否 --> 首次设备查询不依赖当前地图 bounds
                 |
                 +-- 有效设备坐标？ -- 是 --> 计算设备 bounds 中心
                 |
                 +-- 否 --> 使用 VITE_MAP_DEFAULT_CENTER
                              |
                              +-- 未配置 --> 使用代码默认中心
```

### 6.3 首次设备查询要求

无离线地图时，第一次 `/devices/geo` 查询不能使用一个可能错误的初始视口作为唯一过滤条件。推荐方式：

- 首次查询不传 `bounds`，或由后端提供全国/租户范围的摘要接口；
- 后续地图平移和缩放再按视口 bounds 查询；
- 设备数据返回后计算 bounds、中心点和合理 zoom；
- 设备坐标全部无效时才进入默认中心点。

否则会出现“初始中心点错误 -> bounds 错误 -> 查不到设备 -> 无法用设备计算中心点”的闭环。

### 6.4 空设备场景

没有有效设备坐标时：

- 使用 `VITE_MAP_DEFAULT_CENTER`；
- 没有配置时使用部署明确的代码默认中心；
- 国内 OMC 默认可以使用中国区域中心 `[104.0, 35.0]`、zoom 4；
- 海外部署必须通过环境变量或部署配置提供当地默认中心；
- 不得使用其他地区遗留配置作为通用默认值。

### 6.5 当前实现的时序分析

当前页面和地图 Hook 实际上是两个相互协作但初始化时机不同的状态机：

```text
GIS 页面
    -> 设备组树完成
    -> 启用 /devices/geo
    -> mapViewport 为空时首次请求不带 bounds
    -> 设备数据到达后计算 initialCenter

OpenLayers Hook
    -> 等待 /tiles-metadata
    -> 检查离线抽样瓦片
    -> 只初始化一次 Map/View
    -> 后续设备数据到达时由页面一次性自动纠偏
```

这意味着当前代码有以下事实和风险：

1. **首次设备请求目前不依赖错误视口**：`mapViewport` 初始为空，首个设备查询不传 `bounds`，可以为设备中心点计算提供数据基础。这一点应保留，并作为回归测试条件。
2. **地图初始化不是每次中心点变化都重建**：OpenLayers `Map` 和 `View` 创建后，新的 `initialCenter` 不会自动替换已经存在的 View。中心点变化必须通过明确的 `flyTo`/`fit` 完成，不能只依赖 React Props 变化。
3. **设备数据晚于地图初始化时依赖一次性纠偏**：当前页面使用 `hasAutoFittedRef` 只执行一次自动纠偏。它可以避免用户拖动地图后被数据刷新抢回，但如果首次设备响应只是分页结果、坐标不完整或后续才补齐数据，可能无法再次适配全部设备。
4. **设备数据早于地图初始化时依赖初始 Props**：如果设备数据在离线元数据和抽样瓦片检查完成前返回，地图初始化时可以拿到设备计算中心；但如果数据尚未返回，就会先使用环境或代码默认中心。
5. **元数据中心不等于设备中心**：离线地图的 `center` 是底图覆盖范围的推荐视图，不一定是当前租户设备分布中心。离线地图可用时应优先使用它，但设备到达后仍应验证当前视口是否包含设备；不包含时允许一次性纠偏。
6. **视口查询与中心点计算必须分阶段**：首屏阶段使用全量或租户范围设备摘要；地图稳定后才将 `bounds` 作为增量查询条件。不能用“当前视口内没有设备”直接推导“系统没有设备”。

### 6.6 建议的中心点状态机

建议将中心点处理明确拆成四个阶段：

```text
BOOT
    -> 先准备离线元数据和设备查询

PROVISIONAL
    -> 没有离线中心时使用部署默认中心
    -> 允许设备点到达后纠偏

RESOLVED
    -> 离线中心或设备中心已经确定
    -> 用户尚未操作时允许一次自动 fit

USER_CONTROLLED
    -> 用户完成拖动、缩放或搜索定位
    -> 禁止后台数据刷新再次覆盖用户视图
```

自动纠偏的判定建议如下：

- 只有设备坐标数量从 0 变为有效值，或首次权威设备数据完成时才触发；
- 当前视口没有任何设备时才纠偏；
- 用户已经拖动、缩放、搜索定位或点击聚合展开后不再自动纠偏；
- 设备数据为空不能触发纠偏，也不能把空结果当作“无设备”结论，必须区分请求失败、权限过滤、无坐标和确实无数据；
- 纠偏后更新 `mapViewport`，后续请求才使用新的 bounds；
- 设备跨越多个国家或区域时，优先 fit 全部设备 bounds，而不是只使用某一个设备或当前视口样本。

### 6.7 中心点问题的回归场景

至少应验证以下场景：

| 场景 | 元数据 | 设备数据 | 期望中心点 | 是否允许自动纠偏 |
|---|---|---|---|---|
| 国内离线地图正常 | 有效 | 有效 | `metadata.center` | 设备不在视口时一次性 fit |
| 无离线地图，国内有设备 | 失败/不可用 | 有效 | 设备 bounds 中心 | 是，直到进入用户控制状态 |
| 无离线地图，海外有设备 | 失败/不可用 | 有效 | 海外设备 bounds 中心 | 是 |
| 无离线地图，无设备 | 失败/不可用 | 空 | `VITE_MAP_DEFAULT_CENTER` | 否 |
| 环境变量缺失 | 失败/不可用 | 空 | 代码默认中心 | 否 |
| 元数据中心在海外，设备在国内 | 有效 | 有效 | 首屏先用元数据，设备不在视口时 fit 国内设备 | 是一次 |
| 首次请求失败后重试成功 | 失败后成功 | 有效 | 成功响应对应的设备中心或元数据中心 | 不覆盖用户已操作视图 |
| 用户已拖动后设备刷新 | 任意 | 有效 | 保留用户当前视图 | 否 |

### 6.8 风险修复方案

#### P0：统一中心点决策入口

当前中心点判断分布在页面 `GISMapView`、`GISMap` 默认 Props、`useOLMap` 配置和地图元数据 Hook 中，长期容易出现一处修改、另一处仍使用旧默认值的问题。

修复方式：

1. 新增纯函数 `resolveMapInitialView`，输入离线元数据状态、有效设备坐标、环境配置和代码默认值；
2. 只由该函数返回 `{ center, zoom, source }`；
3. 页面和 `useOLMap` 都消费同一个结果，不再各自解释优先级；
4. `source` 固定为 `metadata`、`device_data`、`env_config` 或 `default`，用于日志和测试；
5. 失败元数据必须是 `null/unavailable`，禁止返回带有历史地区坐标的伪默认对象。

验收重点：同一组输入在页面初始 Props、OpenLayers View 和自动纠偏判断中得到相同结果。

#### P0：把首屏设备查询和视口增量查询分开

当前首个 `mapViewport` 为空时不传 `bounds`，这已经避免了错误中心点导致的首查闭环。但这个行为依赖页面状态，缺少接口层契约，后续重构容易回归。

修复方式：

1. 增加明确的 `initialLoad` 或 `viewportReady` 状态；
2. `initialLoad=true` 时禁止构造 `bounds`，查询全量设备摘要或租户授权范围内的首屏设备；
3. 首次响应完成后设置 `initialLoad=false`，后续请求才使用 bounds；
4. 查询请求记录 `requestMode: initial | viewport`，便于排查空结果；
5. 后端返回 `total`、`items`、`hasMore`、`coordinateCount`，禁止把分页结果误当成完整设备集。

#### P0：区分空结果、失败、无权限和无坐标

`items=[]` 可能代表多种业务含义，不能直接触发默认中心或自动纠偏。

建议统一为：

```ts
type GeoQueryState =
    | { kind: 'loading' }
    | { kind: 'success'; items: DeviceGeo[]; total: number; hasMore: boolean }
    | { kind: 'empty'; total: 0 }
    | { kind: 'no-coordinate'; total: number; coordinateCount: 0 }
    | { kind: 'forbidden'; reason: string }
    | { kind: 'error'; retryable: boolean; message: string };
```

只有 `success` 且收到首屏权威数据时，才允许用设备计算中心；`error`、`forbidden` 和 `no-coordinate` 应保留当前中心并显示相应状态。

#### P0：增加用户控制状态，替代单一 `hasAutoFittedRef`

当前一次性 `hasAutoFittedRef` 能防止后台刷新反复抢回视图，但不能表达用户是否已经拖动、缩放、搜索定位或展开聚合。

建议维护：

```ts
type MapViewControlState = 'automatic' | 'user-controlled';
```

进入 `user-controlled` 的事件包括：

- 用户拖动或滚轮缩放；
- 点击放大/缩小；
- 搜索定位；
- 聚合展开或 fit bounds；
- 外部页面主动调用定位。

自动 fit 只允许在 `automatic` 状态、首个权威设备集到达且当前视口没有设备时执行。执行完成后保留 `automatic`，用户下一次操作再切换为 `user-controlled`。后台数据刷新不得重置该状态。

#### P1：处理分页和动态视口数据导致的错误 fit

如果首屏只返回第一页设备，使用第一页计算 bounds 会把地图定位到局部区域。

修复方式按规模选择：

- 设备数量较小：首屏返回全部有效坐标；
- 设备数量较大：增加后端 `geo/summary`，只返回全量 bounds、中心、zoom 和数量；
- 超大规模：使用后端聚合或矢量切片，中心点由摘要接口提供，明细点按视口加载；
- 禁止用当前分页 `items` 冒充全量设备集，除非响应明确标记 `complete=true`。

#### P1：增加元数据和瓦片健康状态

当前通过一个中心瓦片的 `HEAD` 检查离线地图可用性，存在以下局限：

- 某一张瓦片可用不代表整个 bounds 可用；
- 部分 Nginx 或对象存储不支持正确的 `HEAD`；
- 元数据可访问但瓦片路径、坐标方案或版本可能不匹配。

建议：

1. `/tiles-metadata` 返回地图版本、数据范围、瓦片方案和健康状态；
2. 发布验证阶段采样中心、边界和典型区域多张瓦片；
3. 前端使用 `GET` 小瓦片或后端健康接口作为兼容探测；
4. 运行时监听瓦片 `tileloaderror`，只标记底图不可用，不清除设备业务层；
5. 健康检查失败时显示底图状态提示和数据版本，便于现场定位。

#### P1：坐标转换集中到服务层

禁止在 GIS 组件内根据地图源散落 WGS84、GCJ-02、BD-09 转换逻辑。建议由后端或地图适配服务完成：

```text
原始设备坐标 + source_crs
        -> 地图适配层
        -> 当前地图源显示坐标 + display_crs
        -> OpenLayers EPSG:3857 显示
```

每个地图源至少增加北京、广州、乌鲁木齐和边界点的转换回归样例，确认点位偏移在可接受范围内。

#### P1：增加地图源配置和授权闸门

地图源不能只由 `VITE_MAP_TILE_URL` 任意覆盖。生产配置应包含：

```ts
interface MapProviderConfig {
    provider: 'offline' | 'osm' | 'amap' | 'baidu';
    tileUrl: string;
    metadataUrl: string;
    attribution: string;
    displayCrs: string;
    authorizationRef: string;
    enabled: boolean;
}
```

启动或发布前检查 `authorizationRef` 是否存在且有效；未通过时只允许 `offline` 或本地兜底层，不能静默切到未经批准的在线源。

#### P2：底图降级必须是独立能力

当前底图源失败时，设备图层仍应存在，但还需要明确的用户反馈和本地背景。

建议新增：

- 本地省界/行政区 GeoJSON 图层；
- 轻量网格或经纬线背景；
- `basemapStatus`：`available`、`degraded`、`unavailable`；
- 不阻塞设备点加载的底图错误提示；
- 禁止把在线 OSM 作为国内内网失败后的唯一兜底。

### 6.9 修复优先级与交付顺序

| 优先级 | 修复项 | 交付物 | 验证方式 |
|---|---|---|---|
| P0 | 中心点纯函数和失败状态 | 统一 resolver、单元测试 | 四级优先级测试 |
| P0 | 首屏/视口查询分离 | `initial`/`viewport` 请求契约 | 首查不带 bounds、后续带 bounds |
| P0 | 空结果状态分类 | GeoQueryState 和错误提示 | 空、失败、无权限、无坐标场景 |
| P0 | 用户控制状态 | 自动 fit 状态机 | 拖动后刷新不抢视图 |
| P1 | 全量摘要或 complete 标记 | geo summary API | 分页数据不错误 fit |
| P1 | 瓦片健康监控 | 多点探测、tileloaderror | 404/500/路径错误降级 |
| P1 | 坐标适配层 | CRS 转换服务和样例 | 国内外典型点位回归 |
| P1 | 授权配置闸门 | ProviderConfig 和发布检查 | 未授权源不能启用 |
| P2 | 本地边界/网格兜底 | 本地矢量背景层 | 底图异常仍可操作 |

## 7. 国内内网部署方案

### 7.1 生产主方案

```text
授权地图数据
    -> 离线瓦片制作
    -> 内网瓦片服务/Nginx
    -> /tiles/{z}/{x}/{y}.png
    -> /tiles-metadata
    -> OpenLayers XYZ source
```

瓦片服务可以与 OMC Web 服务同域部署，减少跨域和网络策略问题。

### 7.2 必备文件和接口

```text
/tiles/{z}/{x}/{y}.png
/tiles-metadata
/boundaries/china.json       可选，本地边界兜底
```

`/tiles-metadata` 应提供：

- `center: [longitude, latitude, zoom]`；
- `bounds: [minLongitude, minLatitude, maxLongitude, maxLatitude]`；
- `minzoom`、`maxzoom`；
- 数据版本；
- 数据来源和版权声明；
- 生成时间和更新批次。

### 7.3 生产环境禁止事项

- 不直接批量抓取高德、百度公共瓦片；
- 不使用来源不明的中国地图数据；
- 不把测试环境 Key 写入前端生产包；
- 不通过隐藏版权、修改 User-Agent 或绕过限制规避服务条款；
- 不把精确基站坐标暴露到无权限的地图接口；
- 不让公共 OSM 瓦片承担 10 万级设备系统的生产流量。

## 8. 海外部署方案

海外部署可以继续使用 OpenLayers，地图数据有两种选择：

### 8.1 推荐方式：当地合法离线数据

与国内部署保持相同架构，只替换地图数据包和元数据。优点是：

- 不依赖当地公网；
- 统一 OMC 软件行为；
- 更容易满足运营商内网和安全审计要求；
- 设备点位和底图服务均在本地控制。

### 8.2 在线 OSM 或商业源

适用于开发、演示或明确具备授权和网络条件的环境。需要：

- 遵守数据源版权和使用政策；
- 控制请求频率和缓存；
- 配置合法的瓦片服务；
- 准备离线或本地边界兜底；
- 在部署文档中记录地图来源、版本和责任人。

## 9. 坐标系治理

地图源切换前必须明确设备坐标的坐标参考系（CRS）和数据来源：

| 坐标系 | 常见场景 | 注意事项 |
|---|---|---|
| WGS84 | GNSS、通用地理数据 | 与部分国内地图存在偏移 |
| GCJ-02 | 高德等国内地图生态 | 不能直接当作 WGS84 使用 |
| BD-09 | 百度地图生态 | 需要额外转换，不能直接叠加其他坐标 |
| EPSG:3857 | Web Mercator 地图显示投影 | OpenLayers 常用显示投影，不等于原始经纬度 |

推荐原则：

1. 后端保存原始坐标和坐标系标识；
2. 服务层根据地图配置统一输出地图显示坐标；
3. OpenLayers 只负责显示投影转换，不在页面散落坐标算法；
4. 设备详情、导出和审计记录保留坐标来源；
5. 切换地图源必须配套坐标系测试样例。

## 10. 授权、安全和运维要求

### 10.1 授权清单

每个地图数据包和在线源都必须登记：

- 数据提供方；
- 授权类型和适用范围；
- 是否允许商业使用和内网部署；
- 是否允许缓存、切片和再分发；
- 版权声明要求；
- 有效期和续期负责人；
- 数据更新频率。

### 10.2 安全要求

- 地图和设备 API 复用 OMC 权限体系；
- 按租户、运营商、区域限制设备坐标查询范围；
- 对外导出时降低坐标精度或移除精确坐标；
- 记录地图数据访问审计；
- 在线地图 Key 不承担设备数据权限；
- 生产 Key 不写入 Git，不写入公共日志；
- 允许通过许可证或部署配置关闭在线地图源。

### 10.3 运维监控

建议监控：

- `/tiles-metadata` 成功率和响应时间；
- 瓦片 404、5xx 和超时数量；
- 瓦片缓存命中率；
- 地图数据包版本和磁盘占用；
- 设备点位 API 延迟和空结果率；
- 底图不可用期间设备业务层是否仍可用。

## 11. 实施分阶段计划

### 阶段一：修复当前中心点和降级逻辑

- 离线元数据失败返回无元数据状态；
- 移除历史地区中心点作为失败默认值；
- 首次设备查询不依赖错误视口；
- 增加设备中心点和默认中心点测试；
- 底图失败时保留设备图层。

### 阶段二：完善国内离线地图

- 确认数据来源和授权；
- 生成中国区域瓦片和 `tiles-metadata`；
- 部署同域瓦片服务；
- 增加本地省界或网格兜底层；
- 验证无 VPN、无外网、瓦片服务异常三种场景。

### 阶段三：完善海外部署配置

- 约定按部署包提供地图数据；
- 支持不同区域的中心点、bounds 和 zoom；
- 明确 OSM 或当地商业源的授权边界；
- 统一地图源、坐标系和版权配置。

### 阶段四：大规模性能治理

- 设备查询按视口和聚合级别分层；
- 10 万至 100 万设备使用后端聚合或矢量切片；
- 限制单次设备返回量；
- 对瓦片和设备数据建立缓存及容量监控。

## 12. 验收标准

### 功能验收

- [ ] 有离线地图时使用 `tiles-metadata.center`；
- [ ] 无离线地图但有设备时根据设备坐标定位；
- [ ] 无离线地图且无设备时使用部署默认中心；
- [ ] 不会落到历史地区或赞比亚等遗留中心点；
- [ ] 底图不可用时设备点、聚合、搜索和弹窗仍可用；
- [ ] 国内和海外部署只需更换配置和地图数据包，不改业务图层代码。

### 合规验收

- [ ] 地图数据来源和授权记录完整；
- [ ] 版权和数据来源按要求展示；
- [ ] 在线地图 Key、域名白名单和配额已登记；
- [ ] 未使用未经授权的瓦片抓取或代理；
- [ ] 设备坐标权限、审计和导出脱敏已验证。

### 可靠性验收

- [ ] `/tiles-metadata` 404、超时、错误 JSON 均可降级；
- [ ] 瓦片服务 5xx 时不会导致页面白板；
- [ ] 首次设备查询不因错误 bounds 返回空数据；
- [ ] 离线地图数据版本可查询、可回滚、可更新；
- [ ] 1000、1 万和 10 万设备规模完成性能验证。

## 13. 最终决策

OMC GIS 地图采用 **OpenLayers + 授权离线地图主源 + 本地边界/网格兜底** 的统一架构：

- 国内内网：默认使用授权的中国离线地图；
- 海外部署：优先使用对应区域的授权离线地图，必要时使用合法在线 OSM 或商业源；
- 高德、百度：仅作为具备明确授权、Key、配额、坐标和版权方案时的可选源；
- 浏览器不判断国内外、不自动猜测地图源；
- 中心点由离线元数据、设备数据、部署配置、代码默认值依次决定；
- 底图失败不影响设备业务图层；
- 地图数据、设备坐标、授权和运维都纳入 OMC 的部署和审计体系。

## 14. 离线地图部署实施步骤

本节是面向国内 OMC 内网生产环境的落地步骤。海外部署沿用相同流程，只替换地图数据包、授权材料、默认中心和区域边界。

### 14.1 确认部署范围和坐标系

在制作地图前先形成部署清单：

- 部署国家、行政区和覆盖范围；
- 需要的最小/最大 zoom；
- 预计设备数量和设备分布；
- 设备原始坐标系及坐标来源；
- OMC 服务部署方式（Docker、Nginx、裸机或 Kubernetes）；
- 是否完全断网，是否允许受控出口；
- 瓦片磁盘、缓存和备份容量。

国内场景尤其要先确认设备坐标是 WGS84、GCJ-02 还是其他坐标。地图数据和设备坐标必须在同一显示坐标体系下叠加，不能在部署完成后才临时修偏移。

### 14.2 完成地图数据授权

在使用任何数据前登记并审批：

1. 数据提供方和数据版本；
2. 是否允许商业使用；
3. 是否允许内网部署、缓存和切片；
4. 是否允许随 OMC 产品交付给客户；
5. 版权、署名和数据来源的展示要求；
6. 更新周期、有效期和续期责任人。

没有明确授权材料时，不得把在线高德、百度、OSM 或来源不明的瓦片批量下载后作为生产底图。

### 14.3 准备地图数据包

地图数据包至少包含：

```text
map-package/
├── tiles/                         # XYZ 瓦片，z/x/y.png 或约定的矢量格式
├── tiles.json                     # TileJSON/OMC 元数据
├── boundaries/                    # 可选，省界/行政区/网格 GeoJSON
├── LICENSE.txt                    # 授权和版权材料
├── source.txt                     # 数据来源、版本和生成时间
└── SHA256SUMS                     # 文件完整性校验
```

制作阶段应检查：

- `tiles.json.center` 位于实际覆盖范围内；
- `tiles.json.bounds` 与瓦片覆盖范围一致；
- `minzoom`、`maxzoom` 与实际目录一致；
- 中国区域经度、纬度方向没有写反；
- XYZ 的 `y` 方案与 OpenLayers `XYZ` source 一致；
- 关键省份和典型设备位置均有可用瓦片。

### 14.4 部署内网瓦片服务

推荐与 OMC Web 同域提供瓦片，避免跨域、证书和防火墙配置复杂化。服务至少提供：

```text
GET /tiles-metadata
GET /tiles/{z}/{x}/{y}.png
GET /boundaries/china.json          # 可选
```

部署要求：

- 只读挂载地图数据目录；
- 对瓦片设置长期缓存和版本化发布策略；
- 对 `tiles-metadata` 设置短缓存或版本缓存，保证更新可感知；
- 返回正确的 `Content-Type`、缓存头和压缩配置；
- 记录 404、5xx、超时和异常访问；
- 不允许通过路径穿越访问地图目录之外的文件；
- 地图服务与 OMC API 使用统一 TLS、认证边界和访问日志策略。

如果采用 Docker，建议将地图数据作为只读 volume 挂载到 Web/Nginx 容器，不把数 GB 或数十 GB 瓦片直接复制进应用镜像。

### 14.5 编写 `tiles.json`

示例结构如下，数值必须替换为实际地图数据：

```json
{
    "tilejson": "2.2.0",
    "name": "OMC China Offline Map",
    "description": "Authorized offline basemap for OMC internal deployment",
    "version": "2026.08.04",
    "attribution": "按授权协议填写地图数据来源和版权信息",
    "tiles": ["/tiles/{z}/{x}/{y}.png"],
    "minzoom": 3,
    "maxzoom": 15,
    "bounds": [73.0, 3.0, 135.0, 54.0],
    "center": [104.0, 35.0, 4]
}
```

`center` 是底图推荐中心，不应被写成某个历史客户或历史国家的固定值。设备中心仍由 OMC 页面按第 6 节规则进行校验和必要纠偏。

### 14.6 配置 OMC 前端

国内生产环境建议：

```env
VITE_MAP_TILE_URL=/tiles/{z}/{x}/{y}.png
VITE_MAP_DEFAULT_CENTER=104.0,35.0,4
VITE_MAP_METADATA_TIMEOUT_MS=2500
```

说明：

- `VITE_MAP_TILE_URL` 与 `tiles.json.tiles` 保持一致；
- `VITE_MAP_DEFAULT_CENTER` 只在无离线元数据、无有效设备时使用；
- 不把赞比亚或其他历史部署的中心点写入通用 `.env`；
- 环境变量进入前端构建产物，不能放置 Key、密码或其他秘密；
- 生产环境若不允许在线 OSM，应将在线源配置关闭或指向明确的内部备用源。

### 14.7 发布前验证

在无 VPN、无公网的国内测试网络中执行：

1. 访问 `/tiles-metadata`，确认返回 200 和合法 JSON；
2. 手工打开中国范围内的多个 `/tiles/{z}/{x}/{y}.png`；
3. 校验北京、上海、广东、新疆等代表区域；
4. 打开 GIS 页面，确认中心点来自离线元数据；
5. 禁用 `/tiles-metadata`，确认有设备时根据设备坐标定位；
6. 删除或隐藏设备坐标，确认使用 `VITE_MAP_DEFAULT_CENTER`；
7. 让瓦片接口返回 404/500，确认设备点和搜索仍可用；
8. 拖动地图后刷新设备数据，确认不会被自动纠偏抢回；
9. 检查版权和数据来源是否按授权要求显示；
10. 检查浏览器网络面板，确认没有请求未经批准的外部地图域名。

### 14.8 发布、回滚和更新

地图数据应独立于应用代码版本发布，并保留可回滚版本：

```text
/data/maps/omc-china/2026.08.04/
/data/maps/omc-china/2026.09.01/
/data/maps/omc-china/current -> 2026.08.04
```

推荐流程：

1. 在离线环境校验授权、SHA256 和 `tiles.json`；
2. 将新地图包上传到非当前目录；
3. 完成代表区域瓦片和中心点验证；
4. 原子切换 `current` 或容器 volume 版本；
5. 清理/刷新旧缓存；
6. 观察瓦片 404、5xx、延迟和前端空白指标；
7. 出现问题时切回上一个已验证版本。

地图数据更新不应改变设备原始坐标。若新数据要求改变显示坐标系，必须先完成坐标转换评审和设备点位回归测试。

- [ ] `/tiles-metadata` 的 center、bounds、zoom 与实际数据一致；
- [ ] 国内无 VPN、无公网时地图可以正常使用；
