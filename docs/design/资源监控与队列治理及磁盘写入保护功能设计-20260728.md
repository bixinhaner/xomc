# OMC 资源监控、队列治理与磁盘写入保护功能设计

> **文档版本**：v1.0  
> **创建日期**：2026-07-28  
> **文档状态**：开发设计  
> **适用项目**：OMC（Operations, Management and Control）  
> **前置分析**：[资源监控与磁盘写入保护需求分析-20260727.md](./资源监控与磁盘写入保护需求分析-20260727.md)

## 1. 设计目标

本设计将现场Grafana核验发现的所有“需优化”和“需新增”项转化为可开发功能，解决以下问题：

1. 资源指标已经采集但面板查询不匹配，导致容器面板可能无数据。
2. NATS、Redis设备任务和PostgreSQL持久化队列没有统一积压视图。
3. PM队列指标在现场不存在有效时间序列，无法判断是否积压。
4. MinIO和监控数据卷有容量指标或存储能力，但没有完整展示和治理闭环。
5. 磁盘告警存在，但没有通过OMC配置阈值并控制实际写入。
6. 数据保留期和清理结果分散在不同组件，缺少统一策略和容量视图。

## 2. 设计边界

### 2.1 纳入范围

| 领域 | 纳入内容 |
|---|---|
| 资源监控 | 主机、容器、App/ACS/Worker进程、PostgreSQL、TimescaleDB、Redis、NATS、MinIO和监控存储 |
| 队列监控 | NATS JetStream、Redis旧命令队列、新版设备任务队列、PostgreSQL任务和Outbox、PM/MR/备份/Trace持久任务 |
| Grafana | 现有面板修正、新增存储与队列仪表盘、Prometheus告警规则和数据源验证 |
| 写入保护 | 文件上报、MinIO对象、备份、报告、Trace、日志和业务数据处理入口 |
| 有效期治理 | MinIO、TSDB、日志、NATS、Redis、备份和监控数据保留及清理状态 |

### 2.2 排除范围

- 不监控应用进程内部Go Channel、Worker Channel、参数同步内存Channel和Trace本地Capture Queue。
- 不引入Kafka、RabbitMQ或其他新的消息中间件。
- 不使用Grafana统一告警替换现有Prometheus规则。Prometheus继续负责规则计算，Grafana负责展示，Alertmanager负责通知。
- 不通过业务页面直接承诺能够阻断PostgreSQL WAL、Docker daemon日志或监控组件内部写入；这些写入由底层磁盘告警、日志轮转和运维措施保护。

### 4.1 组件职责

| 组件 | 职责 |
|---|---|
| Prometheus | 抓取、保存和计算所有资源/队列/写入保护指标 |
| Alertmanager | 接收Prometheus告警并通知运维 |
| Grafana | 展示指标、趋势、告警状态和策略状态 |
| OTel Collector | 继续采集PostgreSQL、Redis、日志和Trace指标，不承担业务队列语义 |
| OMC指标生产层 | 暴露NATS、Redis、PostgreSQL和PM队列的业务语义指标 |
| StorageAdmissionEvaluator | 周期读取容量，计算保护状态，为写入入口提供缓存决策 |
| OMC管理页面 | 查看容量和状态、配置阈值、手动处理和查看审计 |

## 5. 指标设计

### 5.1 资源指标标签规范

现有现场cAdvisor目标在线，但容器样本主要以`id`等标签识别，不能继续假设存在`name`标签。开发时应先固定标签转换规则：

| 维度 | 来源 | 规则 |
|---|---|---|
| `service` | Prometheus scrape或Docker Compose标签 | 使用`app`、`acs`、`worker`、`postgres`等稳定服务名 |
| `container_id` | cAdvisor `id` | 仅用于排查和详情，不作为所有面板的唯一业务维度 |
| `instance` | exporter目标 | 用于主机/采集目标区分 |
| `mountpoint` | node-exporter | 用于文件系统容量和inode展示 |
| `namespace` | Kubernetes专用 | Docker Compose环境不使用，不得出现在通用面板查询中 |

所有Grafana面板和Prometheus规则必须经过“指标存在、标签存在、查询有结果”三项检查。新增或修改面板时，同时提供PromQL探针查询。

### 5.2 存储指标

#### 5.2.1 主机和数据卷

继续使用node-exporter指标，并新增或补齐以下计算：

```promql
# 文件系统使用率
1 - node_filesystem_avail_bytes / node_filesystem_size_bytes

# inode使用率
1 - node_filesystem_files_free / node_filesystem_files

# 预计耗尽时间
predict_linear(node_filesystem_avail_bytes[6h], 4 * 3600)
```

数据卷映射由部署配置提供，不从业务容器猜测。每个部署环境维护：

```yaml
storage_targets:
  - id: docker-data
    type: host_filesystem
    mountpoint: /var/lib/docker
    components: [pgdata, tsdbdata, redisdata, natsdata, miniodata]
  - id: monitoring-data
    type: host_filesystem
    mountpoint: /var/lib/docker
    components: [prometheusdata, lokidata, tempodata, grafanadata]
```

#### 5.2.2 MinIO

已有指标直接纳入新仪表盘：

- `minio_cluster_capacity_usable_total_bytes`
- `minio_cluster_capacity_usable_free_bytes`
- `minio_node_ilm_expiry_pending_tasks`
- MinIO上传失败、请求错误和对象清理指标

按桶容量需要新增定时采集，不能通过Prometheus动态创建无限标签。桶维度限定为系统已知桶：PM、MR、firmware、config-backup、logs、reports、exchange、UI assets、trace和备份扩展桶。

### 5.3 NATS JetStream指标

#### 5.3.1 指标来源

现场已有NATS exporter健康和JetStream总存储指标，但`nats_jetstream_consumer_num_pending`没有数据。因此新增OMC NATS观测器，使用已存在的JetStream连接查询StreamInfo和ConsumerInfo；不再依赖当前无效的旧PromQL。

#### 5.3.2 指标定义

```text
omc_nats_stream_messages{stream}
omc_nats_stream_bytes{stream}
omc_nats_stream_max_bytes{stream}
omc_nats_consumer_pending{stream,durable}
omc_nats_consumer_ack_pending{stream,durable}
omc_nats_consumer_redelivered_total{stream,durable}
omc_nats_consumer_oldest_age_seconds{stream,durable}
omc_nats_consumer_delivered_rate{stream,durable}
omc_nats_consumer_ack_rate{stream,durable}
omc_nats_observer_failures_total{operation}
```

约束：

- `stream`和`durable`只能使用配置中已注册的名称，不允许设备SN进入标签。
- 采集周期默认30秒，查询超时5秒。
- 查询失败时保留上一值并增加失败计数，同时暴露观测状态，不伪造为0。
- Consumer不存在、Stream不存在和连接失败分别记录原因。
- “最老消息年龄”无法直接从客户端API得到时，通过Stream序列查询计算；不能通过消费消息的方式探测。

### 5.4 Redis队列指标

当前Redis同时存在旧命令队列和新版设备任务队列，两者均纳入监控。

#### 5.4.1 聚合指标

```text
omc_redis_task_queue_length_total{queue_family}
omc_redis_task_queue_active_devices{queue_family}
omc_redis_task_queue_max_length{queue_family}
omc_redis_task_queue_oldest_age_seconds{queue_family}
omc_redis_task_queue_scan_duration_seconds{queue_family}
omc_redis_task_queue_scan_failures_total{queue_family}
omc_redis_task_queue_reconcile_total{outcome}
```

其中：

- `queue_family=cmdq`对应`acs:cmdq:{device_sn}`。
- `queue_family=taskq`对应`acs:taskq:{device_sn}`。
- 采集使用Redis `SCAN`，禁止使用`KEYS`阻塞生产环境。
- 总长度、活动设备数和最大队列长度作为Prometheus稳定指标。
- Top N设备只保留前20名，使用有限的`rank`和脱敏设备标识，禁止为所有设备创建Prometheus时间序列。
- 详细设备队列查询通过OMC管理API提供，Grafana总览只展示聚合和Top N。

#### 5.4.2 设备任务与PostgreSQL对账

Redis是运行时队列，PostgreSQL是持久化权威来源。需要增加：

```text
omc_task_queue_redis_pg_diff
omc_task_queue_recovery_action_total{action}
omc_task_queue_write_failures_total{operation}
```

对账差异不能直接阻断业务，但必须产生告警和可定位的修复记录。

### 5.5 PostgreSQL持久化队列指标

统一使用有限的`queue`和`status`标签：

```text
omc_persistent_queue_pending{queue,status}
omc_persistent_queue_oldest_age_seconds{queue,status}
omc_persistent_queue_failed_total{queue}
omc_persistent_queue_dead_letter_total{queue}
omc_persistent_queue_processed_total{queue,result}
omc_persistent_queue_observer_failures_total{queue}
```

纳入的队列名称：

- `device_tasks`
- `async_jobs`
- `parameter_sync_outbox`
- `northbound_outbox`
- `pm_kpi_export`
- `trace_export`
- `backup_tasks`
- `dead_letters`

#### 5.5.1 Task 1契约

以上指标的 `queue` 只能取本节列出的八个固定名称，`status` 只能取
`pending`、`sent`、`running`、`succeeded`、`failed`、`dead_letter`；
`processed_total` 的 `result` 只能取 `succeeded` 或 `failed`。标签中禁止出现
device SN、完整 Redis key、对象路径、数据库 row ID 和请求 ID，避免队列规模随业务
对象数量产生高基数时间序列。

指标单位和可用性语义固定为：`pending`、`dead_letter_total` 是条数，
`oldest_age_seconds` 是秒，`failed_total`、`processed_total` 和
`observer_failures_total` 是次数。成功采集到空队列必须暴露真实 `0`；查询失败或
观测样本过期不能伪造为 `0`，应保留上一次业务值并递增观测失败计数。

已有`omc_tasks_pending_total`、`omc_tasks_backlog_total`和`omc_async_jobs_queue_depth`继续兼容，新增统一指标逐步替代分散面板。

### 5.6 PM/MR/Trace任务指标

PM队列现有代码指标在现场没有有效时间序列，修复要求如下：

- `omc_pm_queue_pending`、`omc_pm_queue_ack_pending`、`omc_pm_queue_redelivered`、`omc_pm_queue_oldest_age_seconds`在Worker启动时注册并初始化为0。
- 成功采集为空队列时暴露0，而不是删除时间序列。
- 采集失败时保留不可用状态，增加`omc_pm_queue_sample_failures_total`。
- 增加`omc_pm_queue_sample_timestamp_seconds`，Grafana和告警先判断采集是否新鲜。
- MR和Trace增加待处理数量、最老任务年龄、失败数和存储写入失败数。

PM 指标的 `subject`/`durable` 仅使用已注册的 PM subject 和 durable；单位分别为
消息数、秒、JetStream sequence、Unix 秒和失败次数。Worker 启动及成功采集空队列
时的 0 是真实业务状态，采集失败时保留上次值并递增失败计数。

## 6. Grafana设计

### 6.1 现有仪表盘修正

| 仪表盘 | 修改内容 |
|---|---|
| `omcgo-nginx-host` | 保留主机CPU、内存、磁盘；增加inode、耗尽预测和挂载点筛选 |
| `omcgo-resources` | 修正cAdvisor标签，保留App/ACS/Worker进程和连接池指标，删除无效容器过滤 |
| `omcgo-infra` | 保留PG/Redis；增加MinIO容量、NATS Stream存储和监控存储容量 |
| `omcgo-ops` | 删除或改写`namespace="omcgo"`的Kubernetes遗留面板；移除无数据的旧NATS积压查询 |

### 6.2 新增仪表盘

新增 `OMC - 存储与队列治理` 仪表盘，分为五个Row：

1. **存储总览**：主机/数据卷、MinIO、数据库、Redis、NATS和监控存储使用率。
2. **NATS队列**：Stream消息数、Consumer pending、Ack pending、最老消息、重投递和消费速率。
3. **Redis队列**：cmdq/taskq总量、活动设备、最大队列、最老任务、Top 20设备。
4. **PostgreSQL队列**：任务、Outbox、死信、异步任务、PM/KPI、Trace、备份。
5. **写入保护与清理**：当前策略状态、阻断次数、拒绝写入、清理结果、释放空间和失败原因。

面板统一要求：

- 每个面板的PromQL必须能在Prometheus Explore中独立返回数据。
- 查询无数据时显示“指标不可用”，不能将采集失败显示成0。
- 使用统一时间范围和刷新周期，默认`now-1h`、30秒刷新。
- 不使用高基数设备标签作为普通时序；Top N使用受限标签或API数据。
- 面板JSON、PromQL和指标名变更必须同步提交并通过自动检查。

## 7. 告警设计

### 7.1 告警归属

- Prometheus规则文件是告警唯一计算来源。
- Grafana只展示Prometheus告警状态和历史。
- Alertmanager负责通知和分组。
- 新增规则统一放到`deployments/monitoring/alerts/storage-queue-alerts.yml`，避免继续扩大基础设施规则文件。

### 7.2 告警矩阵

| 告警 | 默认条件 | 严重级别 | 处理方向 |
|---|---|---|---|
| 主机CPU/内存/磁盘 | 复用现有90%、10%、5%和预测耗尽规则 | warning/critical | 保留并修正标签 |
| 容器CPU/内存/OOM | 复用现有规则，改为实际服务标签 | warning/critical | P0修复 |
| NATS Consumer积压 | pending或最老消息超过对应队列策略，持续10分钟 | warning/critical | 检查Consumer和Worker |
| NATS消费停滞 | 生产速率大于确认速率且pending持续增长 | critical | 检查服务、连接和Ack |
| Redis队列积压 | 总量、单设备Top N或最老任务超过策略 | warning/critical | 检查设备在线率和ACS消费 |
| PostgreSQL持久队列 | pending、最老年龄、死信或僵尸任务超过策略 | warning/critical | 检查Worker、Outbox和数据库 |
| PM队列指标过期 | sample timestamp超过2个采集周期 | warning | 检查PM观测器和Worker |
| MinIO容量 | 使用率超过80%/策略阈值，或ILM待处理持续增长 | warning/critical | 清理、扩容或阻断写入 |
| 存储写入阻断 | `omc_storage_admission_state=blocked` | critical | 检查容量并处理阻断 |
| 清理失败 | 清理连续失败或释放空间低于预期 | warning | 检查权限、对象和数据库元数据 |

策略阈值允许按队列或存储目标覆盖默认值，默认磁盘策略为：告警80%、阻断90%、恢复85%。

## 8. 磁盘写入保护设计

### 8.1 策略模型

新增存储保护策略，建议使用独立表而不是把多目标策略压入单个JSON配置：

```sql
storage_protection_policies
---------------------------
id                         uuid primary key
target_type                varchar(32)   -- filesystem/minio/database/redis/nats/monitoring
target_id                  varchar(128)  -- mountpoint、bucket或逻辑目标
write_scope                varchar(32)   -- upload/log/backup/report/trace/pm/mr/all
enabled                    boolean
warn_used_percent          integer
block_used_percent         integer
recover_used_percent       integer
check_interval_seconds     integer
unknown_behavior           varchar(32)   -- allow_with_alarm/block_new_uploads
created_at                 timestamptz
updated_at                 timestamptz
updated_by                 varchar(64)
version                    bigint
```

约束：

- `0 <= warn < recover < block <= 100`。
- 同一`target_type + target_id + write_scope`只能有一条启用策略。
- 默认策略为告警80%、阻断90%、恢复85%。
- 手动放行必须有过期时间，过期后自动恢复策略控制。
- 没有策略时只监控，不阻断写入。

### 8.2 状态机

```text
normal ── usage >= warn ──► warning
warning ── usage >= block ─► blocked
blocked ── usage <= recover ─► normal
任意状态 ── 指标过期/查询失败 ─► unknown
unknown ── 根据unknown_behavior ─► normal或blocked
```

状态变更需要滞回和去抖：

- 连续两个检查周期达到阈值才进入warning或blocked。
- 连续两个检查周期低于恢复阈值才恢复。
- 相同状态不重复发送告警。
- 状态变化记录目标、使用率、阈值、原因和时间。

### 8.3 运行时接口

新增内部接口：

```go
type WriteAdmission interface {
    Check(ctx context.Context, target StorageTarget, scope WriteScope) AdmissionDecision
}

type AdmissionDecision struct {
    Allowed       bool
    State         string
    Reason        string
    RetryAfter    time.Duration
    ObservedAt    time.Time
}
```

写入入口必须在创建对象、打开大文件或创建任务前检查，不在写入完成后才检查。

### 8.4 写入入口接入顺序

| 入口 | P阶段 | 阻断行为 |
|---|---:|---|
| PM/MR文件接收和MinIO上传 | P2 | 拒绝新上传或转入可恢复待处理状态，不生成孤儿对象 |
| 备份文件和配置快照 | P2 | 新任务暂停或返回容量保护错误 |
| 报告、交换文件和Trace导出 | P2 | 新任务不创建，已有任务进入paused |
| 固件、配置、证书和许可证 | P2 | 管理端上传拒绝，并给出剩余空间和恢复条件 |
| 应用/ACS/Worker文件日志 | P3 | 保留错误、安全和审计日志，限制普通日志并增加丢弃计数 |
| Docker daemon日志、PG WAL、Loki/Tempo内部写入 | 运维边界 | 通过文件系统告警、日志轮转、保留期和数据盘扩容处理 |

文件写入采用“先准入、后写对象、再写元数据”的顺序；任一阶段失败必须执行补偿，禁止留下无法追踪的对象或元数据。

### 8.6 OMC管理页面

页面建议放在“系统管理 / 资源与存储保护”，分为：

1. **容量总览**：目标、总量、已用、可用、使用率、趋势和当前状态。
2. **保护策略**：目标、写入范围、告警阈值、阻断阈值、恢复阈值、未知状态策略。
3. **当前阻断**：被阻断的写入类型、原因、开始时间、预计恢复条件。
4. **清理与有效期**：数据类型、保留期、清理状态、释放空间和失败原因。
5. **审计记录**：配置变更、手动放行、阻断和恢复事件。

## 9. 有效期和清理治理

### 9.1 统一策略对象

每种数据类型统一描述：

```text
data_class
storage_target
retention_days
max_bytes
max_objects
cleanup_schedule
cleanup_batch_size
delete_order
orphan_policy
enabled
```

### 9.2 当前策略纳入治理矩阵

| 数据类型 | 当前实现 | 设计处理 |
|---|---|---|
| MinIO PM/MR原始文件 | 原始文件默认生命周期 | 展示容量、对象数、ILM状态和清理失败 |
| TSDB PM/MR/Trace/告警 | 已有Hypertable保留策略 | 展示表/Chunk大小、保留天数和实际删除结果 |
| 应用/ACS/Worker日志 | 有文件轮转和保留天数 | 纳入磁盘策略和清理面板 |
| NATS消息 | Stream有MaxAge/MaxBytes | 展示策略与实际使用量，积压优先于过期删除 |
| Redis任务详情 | 有TTL | 展示过期失败、异常增长和队列数据量 |
| PostgreSQL任务元数据 | 状态清理分散 | 统一最老记录、死信和清理结果 |
| 备份 | 有时间、数量和容量策略 | 与MinIO对象删除和数据库元数据删除关联展示 |
| Prometheus/Loki/Tempo | 各自有保留配置 | 纳入监控存储容量和即将耗尽告警 |

删除顺序必须明确：对于文件类数据，先完成对象状态确认，再删除数据库元数据；对于时序数据，先执行压缩/归档策略，再执行保留期删除。清理失败不能静默吞掉，必须增加失败指标和审计事件。

## 11. 测试与验收设计

### 11.1 指标和面板

- Prometheus查询每个新增指标至少返回一个有效序列；空队列返回0而不是缺失。
- cAdvisor面板能显示App、ACS、Worker、PostgreSQL、Redis、NATS、MinIO实际容器。
- 面板不再依赖`namespace="omcgo"`或现场不存在的`name`标签。
- MinIO、主机文件系统和监控数据卷的使用率能在Grafana显示。

### 11.2 队列积压

- 停止一个NATS Consumer，验证pending、最老消息和告警。
- 向单个设备写入任务，验证Redis总量、Top N和最老任务。
- 插入PostgreSQL待处理任务，验证任务、Outbox和最老年龄面板。
- PM队列为空时验证指标为0；停止采集时验证采集过期告警。
- 恢复消费者或任务处理后，告警自动恢复。

### 11.3 磁盘写入保护

- 配置告警80%、阻断90%、恢复85%，验证状态按滞回规则变化。
- MinIO上传达到阻断状态后，新上传被拒绝且无孤儿对象。
- 备份、报告、Trace和文件上报按各自策略暂停或拒绝。
- 磁盘恢复后业务自动恢复，阻断状态和告警清除。
- Prometheus不可用或容量未知时，行为符合`unknown_behavior`配置。
- 配置修改、手动放行、阻断和恢复均有审计记录。

### 11.4 数据清理

- 执行清理后，Grafana能显示删除数量、失败数量和释放空间。
- 对象删除失败不会提前删除数据库元数据。
- 数据库元数据删除失败不会产生无法定位的对象孤儿。
- 每类数据的实际保留期与策略页面一致。
