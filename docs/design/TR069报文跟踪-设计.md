# TR069 报文跟踪功能 — 新 OMC 设计文档

> 状态：**已定稿**（10 项设计决策已确认，见 §10）
> 移植参考：老 OMC（OMCWebServer + TR069Server + cellHandler）— 仅作行为参考，新设计已与老实现解耦，§2 列出关键差异
> 适配目标：本工程当前架构（Go 模块化单体 + 独立 ACS 引擎，详见 `CLAUDE.md`）
> 关联功能域：F01 南向接口 / F06 OMC-R 运维

---

## 1. 背景与目标

老 OMC 的报文跟踪允许运维选定一台设备后实时抓取其 TR069 SOAP 报文，落库后可在线查看 / 下载，用于现场排障。功能在新 OMC 上需保留，但要适配新工程的：

- **进程划分**：管理面 `omcgo-app` ↔ 抓包面 `omcgo-acs` 跨进程协作
- **基础设施**：PostgreSQL/TimescaleDB、Redis、NATS JetStream、WebSocket 通知中心、统一任务队列
- **设备范围**：CPE、4G/5G 小基站；老 OMC 中的 eGW（企业网关）暂不纳入 RC（决策见 §10）

**功能边界（要做）：**
- 选定设备后启停抓包任务（含超时自动停止）
- 按设备 + 时间窗口 落库 SOAP 请求 / 响应报文
- Web 端在线查看（含 XML 格式化）、按时间段下载 XML 文件
- 任务状态变化实时广播给在线用户
- 多 ACS 实例采集的同一设备报文在中心库统一聚合查询（设备跨会话切换 ACS 实例时，运维仍能看到完整时间线）

**不做（明确非目标）：**
- 全网"全量录制"开关（老 OMC `tr069MsgEnbEnable`）— 新 OMC 默认仅对授权 SN 抓包，避免在 10 万级网中产生灾难性数据量
- 报文内容的语义解析 / 参数提取（这是 F02 配置同步的职责，不混入跟踪功能）

## 2. 与老 OMC 的核心差异

| 维度 | 老 OMC | 新 OMC 设计 | 改进收益 |
|---|---|---|---|
| 任务主键 | `device_code`（单设备单记录，开新任务先 DELETE） | 自增任务 ID，保留全部历史 | 支持"查看历史抓包"；操作可按 task_id 精准定位 |
| 报文存储 | MySQL 100 张哈希分表 + GZIP varbinary | TimescaleDB hypertable（按时间分块）+ 大报文外置 MinIO | 单表查询；过期清理用 retention policy 而非循环 DELETE |
| 跟踪缓存同步 | TR069Server JVM 内存缓存 + 10 秒扫库 | ACS 进程订阅 NATS 主题 + 启动加载 + 定时兜底 | 毫秒级生效；多 ACS 实例自动一致 |
| 超时停止 | 仅靠前端倒计时，后端不自动收尾 | 复用 `internal/task/` 的 ExpiresAt + worker 巡检 | 用户关浏览器后任务也会自动停止 |
| 查询接口 | 一次性拼全量字符串返回 | 分页 + 时间范围过滤；下载走异步文件准备 | 大窗口抓包不阻塞 RPC |
| stop / clear | 两个接口 | 单接口 + `purge` 参数 | 减少冗余 |
| 实时通知 | WebSocket 广播给全部在线用户 | 复用 `internal/notification/` Hub，按"运维组"订阅 | 减少无关推送 |
| 设备类型 | enb / gnb / cpe / egw | 复用 `device.device_type` 字段，不引入二级枚举 | 数据源单一；新增类型走设备表 |

### 3.2 关键数据流

**抓包链路（写）：**
1. 用户 → app → 创建任务 → 入库 + 发 `trace.task.started`
2. 所有 ACS 实例订阅事件 → 更新本地 SN 白名单
3. CPE 后续 SOAP 报文到达任一 ACS 实例 → 协议拦截器旁路投递到 `trace.message.captured`（含设备 SN、方向、时间戳、原始 XML）
4. worker 消费事件 → 批量落 hypertable；XML 大于阈值则只在 PG 存元数据，原文写 MinIO

**查询链路（读）：**
1. 用户 → app → 按 task_id 查任务详情（含起止时间、状态）
2. app 按 sn + 时间窗口 + 分页 查 hypertable；如果命中外置 MinIO 记录，按需 lazy 拉取
3. 下载：app 起一个生成任务（写入 MinIO `exchange` bucket）→ 完成后返回预签名 URL

**任务收尾链路：**
- worker 定时巡检 `trace_tasks`，把 `expires_at < now() AND status = running` 的任务置为 `stopped` 并发 `trace.task.stopped`
- ACS 实例收到事件 → 从白名单移除

## 4. 功能拆解

### 4.1 任务模型

- **复用 `internal/task/` 还是新建？**
  - **决策：新建 `internal/trace/` 模块，独立持久化任务表，不挤进 `task/` 队列。**
  - 理由：`task/` 是面向 "CWMP 指令派发 + 重试 + completion router" 的设备级任务队列；报文跟踪任务的语义是"开启/关闭一段时间内的抓包窗口"，不需要重试、不映射 CWMP ID、不需要 completion 路由。强行复用会污染 `task/` 的概念模型。
  - 但可复用 `task/` 的设计模式：状态机、ExpiresAt、定时巡检 closer。

- **任务状态**：`running` / `stopped`（含正常结束 + 手动停止） / `purged`（停止 + 数据已清理）
- **唯一性约束**：同一 SN 任意时刻最多一个 `running` 任务；新建时若有冲突，直接覆盖（关闭旧任务再开新的，与老 OMC 行为对齐）

### 4.2 ACS 侧的报文拦截

- **拦截位置**：在 `omcgo/internal/acs/handler.go` 现有 `protocolLogger` 附近增加 hook，命中白名单时旁路一份 XML 到 capture 通道
- **白名单缓存**：进程内 sync.Map，由 NATS 事件实时维护；进程启动时一次性从 PG 加载所有 `running` 任务的 SN
- **兜底**：每 30 秒拉一次 `trace_tasks` 与本地缓存对账，防 NATS 漏消息
- **零拷贝原则**：拦截 hook 必须在 happy path 上 < 1ms；耗时全部丢给 worker（NATS 异步）

### 4.3 报文存储

- **主表（PG/TimescaleDB hypertable）**：
  - 必备字段语义：`device_sn`、`task_id`、`direction`（in/out）、`captured_at`（时序列）、`rpc_method`（如 `Inform`、`GetParameterValues`）、`payload_inline`（小报文 inline）、`payload_object_key`（大报文外置 MinIO 的对象键，二选一）
  - 时间分块粒度：1 天 / chunk；retention：3 天（自动清理）；按 `device_sn` + `captured_at` 联合索引
- **大报文外置**：阈值默认 32KB。超过则 PG 只存元数据，原文 GZIP 后写入 MinIO `trace-bulk` bucket（key 含 task_id / sn / timestamp 三段）
- **压缩**：inline 报文不压缩，依赖 PG TOAST 自动压缩；外置走 GZIP
- **原文保真**：报文一律原样落库，不做任何字段擦除 / 替换

### 4.4 任务通知

- **事件主题**：`trace.task.started` / `trace.task.stopped` / `trace.task.purged`（NATS JetStream）
- **WebSocket 推送**：app 接到事件后通过 `internal/notification/` Hub 推送给"有运维权限且当前在线"的用户
- **不推送给所有用户**：与老 OMC 全员广播不同。理由：减少多租户/多团队场景下的噪声。订阅者范围由 RBAC 决定（用户权限包含 `trace:read` 即推送）

### 4.5 查询与下载

- **查询接口**：分页 + 时间范围过滤 + 方向过滤 + RPC 方法过滤
- **下载接口**：参数指定 task_id / 时间窗口 / 时区
  - 小批量（< 5MB）：服务器直接拼好 XML 流式返回，文件名 `{sn}_{startTime}-{endTime}.xml`
  - 大批量：异步生成到 MinIO，前端轮询任务状态，完成后给预签名 URL（复用 `internal/transfer/` 模式）
- **XML 美化**：服务端不做格式化，原文直接返回；前端用 monaco-editor 或 react-xml-pretty 渲染（与 MML 控制台一致风格）

## 5. 接口设计（RESTful，对齐新 OMC 风格）

> 路径前缀：`/api/v1/trace/`  | 鉴权：JWT；操作需 `trace:read` / `trace:write` 权限

| Method | Path | 说明 |
|---|---|---|
| POST | `/tasks` | 创建抓包任务（参数：device_sn、duration_minutes） |
| GET | `/tasks` | 列表查询（参数：device_sn、status、operator_code、分页） |
| GET | `/tasks/{id}` | 任务详情 |
| POST | `/tasks/{id}/stop` | 停止任务（参数：purge=bool） |
| GET | `/tasks/{id}/messages` | 查询任务下报文（分页、direction、rpc_method、时间窗口） |
| POST | `/tasks/{id}/export` | 触发异步下载，返回 export_job_id |
| GET | `/exports/{export_job_id}` | 查询下载任务状态，完成后返回 MinIO 预签名 URL |
| GET | `/devices/{sn}/active-task` | 给设备详情页用：查询该 SN 是否有进行中任务 |

**老 OMC 接口映射表**（迁移参考）：

| 老接口 | 新接口 |
|---|---|
| `POST /trace/start` | `POST /tasks` |
| `POST /trace/stop` | `POST /tasks/{id}/stop` (`purge=false`) |
| `POST /trace/clear` | `POST /tasks/{id}/stop` (`purge=true`) |
| `POST /trace/queryLatestMessageTraceDeviceInfo` | `GET /devices/{sn}/active-task` |

| `POST /trace/queryMessageTraceInfo` | `GET /tasks/{id}/messages` |
| `POST /trace/downLoadMessageTraceInfo` | `POST /tasks/{id}/export` + `GET /exports/{id}` |

## 6. 数据模型（概念层）

> 完整 DDL 在实施阶段产出，这里只列实体与关系。

- **trace_tasks**：任务表
  - 关键属性：id、device_sn、operator_code、status、start_time、expires_at、stopped_at、created_by、purged_at
  - 索引方向：(device_sn, status)、(operator_code, status, created_at)、(expires_at) 用于巡检
  - **关联设备**：仅冗余存 SN，不存 device_id。理由：设备记录被删 / 替换时不丢失跟踪历史；JOIN 设备信息时按 SN 实时关联即可

- **trace_messages**：报文表（TimescaleDB hypertable）
  - 时序列：captured_at
  - 关键属性：task_id（FK → trace_tasks）、device_sn、direction、rpc_method、cwmp_id、payload_inline、payload_object_key、payload_size_bytes
  - 索引：(device_sn, captured_at DESC)、(task_id, captured_at DESC)
  - retention policy：自动 drop 3 天前 chunk

- **MinIO bucket `trace-bulk`**：超阈值报文原文（与现有 PM/MR/firmware bucket 同级管理）

## 7. 跨进程协作细节

### 7.1 NATS 主题与消息体

| Subject | 发布者 | 订阅者 | 用途 |
|---|---|---|---|
| `trace.task.started` | app | acs（多实例）| 增加 SN 到本地白名单 |
| `trace.task.stopped` | app / worker | acs | 从本地白名单移除 |
| `trace.task.purged` | app | worker | 触发报文清理（DELETE + MinIO 对象删除） |
| `trace.message.captured` | acs | worker | 异步落库（JetStream 持久化，避免漏报） |

- **消息可靠性**：`task.*` 走普通 NATS（订阅者重启后通过启动加载+兜底对账恢复）；`message.captured` 走 JetStream（确保不丢报文）

### 7.2 ACS 实例水平扩展

- 同一台设备同一时刻只与某一个 ACS 实例建立 CWMP 会话（由前置负载均衡保证），因此 SN 白名单在每个实例都全量维护即可，不需要分片
- 新 ACS 实例启动时从 PG 全量加载 `running` 任务的 SN（< 1000 量级，无性能压力）

### 7.3 worker 职责

- 消费 `trace.message.captured` 并批量落库（批量大小、时间窗口与现有 PM/MR worker 一致）
- 定时巡检 `expires_at < now()` 的任务并发 stopped 事件
- 处理 `trace.task.purged` 的物理清理
- TimescaleDB retention 触发由数据库自身完成，worker 不参与

## 8. 可观测性、安全、容量

### 8.1 指标（Prometheus）

- `trace_active_tasks` — 活跃任务数
- `trace_messages_captured_total{direction}` — 累计采集报文数
- `trace_messages_dropped_total{reason}` — 因队列满 / 解析失败被丢弃的报文数（NATS 异常告警信号）
- `trace_storage_bytes_total{location=inline|minio}` — 存储量分布
- `trace_capture_latency_seconds` — 拦截 hook 在 ACS 内的耗时直方图（P99 必须 < 5ms）

### 8.2 审计

- 所有创建 / 停止 / 导出操作写审计日志，含操作者 + IP + 设备 SN + 时间窗口
- 报文一律按 CPE 原始上送 / ACS 原始下发的样子落库与展示，不做敏感字段 mask；查询 / 下载权限由 RBAC（`trace:read` / `trace:write`）控制

### 8.3 容量预估（10 万级 CPE）

- 同时跟踪任务数：< 100（运维场景，极少同时跟踪大量设备）
- 单设备每分钟报文：< 20 条（含 Inform、Get/SetParameterValues、TransferComplete）
- 单条报文平均：~2-8KB；峰值（带大参数列表的 Get/SetParameterValuesResponse）可达 100KB+
- 单次抓包窗口（默认 5 分钟）：~100-500 条报文，~500KB-2MB
- 3 天保留 × 平均 30 个并发任务：~5GB 量级，TimescaleDB hypertable + MinIO 外置完全可承载

## 10. 设计决策（已确认）

| 编号 | 决策点 | 最终方案 | 锚点 |
|---|---|---|---|
| D1 | inline 报文是否压缩 | 否，依赖 PG TOAST 自动压缩 | §4.3 |
| D2 | device_id 与 sn 是否都存 | 只存 sn，避免设备删除导致历史丢失 | §6 |
| D3 | 报文敏感字段处理 | 不 mask，原样落库与展示；权限由 RBAC 控制 | §8.2 |
| D4 | 是否纳入 eGW 设备类型 | 不纳入 | §1 |
| D5 | "全网全量录制"开关 | 不做 | §1 |
| D6 | 任务数据模型 | 独立 `internal/trace/` 模块，不复用 `internal/task/` | §4.1 |
| D7 | XML 美化位置 | 前端 | §4.5 |
| D8 | 默认 retention 周期 | 3 天 | §4.3 / §6 |
| D9 | 单 SN 报文限流 | 不做限流 | §4.2 |
| D10 | 单用户单日任务上限 | 不做上限 | §8.2 |
