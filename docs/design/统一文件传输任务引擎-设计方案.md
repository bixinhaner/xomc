# 统一文件传输任务引擎（UFTE）设计方案

> **文档版本**：v2.4  
> **日期**：2026-05-14  
> **目标**：消除 eNB 升级、日志收集等功能中大量重复的 TR-069 Download/Upload 交互代码，
> 将文件传输流程抽象为**配置驱动的通用引擎**，并提供**可视化配置管理页面**，
> 内置功能可查看，用户可在页面上自行新增和维护自定义文件传输类型，无需修改任何代码。

---

## 回答核心问题

**Q1：这个设计能做到文件传输类操作动态可配置吗？**

**可以，但有明确边界**。以下维度完全动态可配置（只改数据/配置，零代码）：
- TR-069 RPC 类型（Download / Upload）
- FileType 字符串、CommandKey 前缀、URL 模板
- 步骤执行顺序（step_chain 数组）
- 每步超时时长
- TransferComplete 之后等待哪个 Inform EventCode 以及成功/失败判定值
- 平台级差异覆盖（不同平台 FileType 不同）
- 前置校验规则（磁盘空间、文件数量等）

以下情况**仍需代码**（极少发生）：
- 全新的交互模式（如需要设备侧回调一个完全不存在的机制）
- 复杂的特殊业务前置校验（现有规则类型覆盖不了时，需实现新的 `PreValidateRule` 并注册）
- TR069Server 需要监听新的 EventCode，需注册一次（后续再来同类型 EventCode 则无需改代码）

---

**Q2：新增文件传输类型时，可以通过页面配置而非直接写数据库吗？**

**是的，这正是本方案的核心设计**。提供专用的「任务类型管理」页面：
- 系统内置类型（4G升级、5G升级、日志收集、回退、备份、恢复等）：**可查看、可局部调参、不可删除**
- 用户自定义类型：**可视化表单创建/编辑，支持复用已有业务 Tab 或输入新的 Tab 名称；删除建议放二期并增加“已有任务引用”校验**

## 一、现状问题分析

### 1.1 各功能共性流程

```
┌─────────────────────────────────────────────────────────────────┐
│  权限检查 → 在线检查 → 发送 TR-069 RPC → 等待响应 →            │
│  等待文件传输（进度监控）→ 等待 TransferComplete →              │
│  [可选] 等待附加事件（102 UPGRADE FINISH 等）→ 结束             │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 各功能差异点汇总

| 差异维度 | 4G 基站升级 | 5G 基站升级 | 日志收集（立即）| 日志收集（周期）|
|---------|------------|------------|--------------|--------------|
| **TR-069 RPC 类型** | Download | Download | Upload | SetParameterValues |
| **TR-069 FileType 字段** | `1`（Firmware Upgrade Image） | `1`（Firmware Upgrade Image） | `6/7/8/9`（运行/安全/故障/PCAP） | — |
| **CommandKey 前缀** | `Download Upgrade,` | `Download Upgrade,` | `Collect LOG,` | — |
| **URL 模板（逻辑值）** | `firmware/{minio_path}` | 同 4G | `/smallcell/FileUploadService?fileType={fileType}&filename={targetFileName}` | `/smallcell/FileUploadService?fileType={fileType}&filename={targetFileName}` |
| **等待文件下载进度** | ✅ 轮询 `DownloadingFlag` | ✅ 同 4G | ❌ 无（设备主动上传） | — |
| **等待 TransferComplete** | ✅ 是终态 | ✅ 非终态，继续等 | ✅ 是终态（文件到达即完成）| — |
| **附加事件等待** | ❌ 无 | ✅ 等待 `102 UPGRADE FINISH`| ❌ 无 | — |
| **TC 超时容错** | ✅ 版本比对 | ✅ 版本比对 | ❌ 直接失败 | — |
| **平台限制** | 全平台 | BBU-XSS/BBU-QSS | 部分平台不支持周期日志 | Intel_CR 等不支持 |
| **保留配置字段** | ✅ `rawMode` | ✅ `rawMode` | ❌ | — |
| **文件数量上限校验** | ❌ | ❌ | ✅（默认 5 个）| ❌ |

### 1.3 冗余代码量化

当前每新增一个类似功能，需要重复实现：
- **后端**：独立 Controller、Service、状态机、Redis Key 约定、超时处理（≈ 800~1500 行）
- **前端**：独立页面、任务列表、进度轮询、操作按钮（≈ 500~1000 行）
- **DB**：独立任务表（主任务 + 子任务两张表）
- **文档**：独立接口文档

## 二、设计目标

1. **配置驱动**：新增"新型升级"或"其他文件传输"功能时，只需在数据库新增一行任务类型配置，无需修改后端代码
2. **步骤链可组合**：将传输流程拆解为原子步骤，通过 JSON 配置自由组合
3. **事件等待可扩展**：通过配置指定 TransferComplete 之后需要等待哪个 EventCode，未来新的 EventCode 无需改代码
4. **平台差异可注入**：FileType、URL 模板、CommandKey 前缀等通过配置注入
5. **UI 泛化**：前端基于任务类型元数据动态渲染，无需为每个功能单独写页面
6. **业务分类动态化**：业务 Tab 由任务类型的 `category/category_label` 聚合生成；新增模板时可复用现有 Tab，也可直接新建 Tab 名称

---

## 补充：基于现有代码的后端落地决策

### A. 结论先行

**不建议再单独写一套“第四套执行链”。**

更合适的方案是：
- 新建 `internal/ufte/` 统一编排模块，承接 `/ufte/*` API、模板治理、统一任务/设备视图和任务创建入口
- 底层尽量复用现有能力，尤其是 `internal/task` 的设备命令下发、`internal/transfer` 的上传文件落盘桥接、`internal/software` 的升级文件资产与升级/回退编排、`internal/backup` 的备份/恢复执行能力
- 不直接复用 `internal/software` 的任务表和执行器作为 UFTE 主模型，因为它们是“升级专用模型”，无法自然覆盖 Upload、日志采集、配置备份、配置恢复和后续自定义场景

### B. 现有代码复用判断

#### 可以直接复用的基础设施

1. `internal/task.Enqueuer`
    - 现有 `task.CreateTask(ctx, *CreateTaskRequest)` 已经是多个模块共同复用的统一入口。
    - `software/executor.go`、`backup/executor.go`、`filemanager/service.go`、`provision/model_upload.go` 都是通过它下发 Download / Upload RPC。
    - 这说明 UFTE 不需要重新发明“设备任务队列”，直接复用 `internal/task` 即可。

2. `internal/transfer/bridge.go`
    - 现有 `TransferBridge` 已能订阅 ACS 的 AutonomousTransferComplete，下载 CPE 上传文件并落 MinIO，再向下游发布事件。
    - 这对 `station_log`、`config_backup`、后续 Upload 类 UFTE 任务是天然复用点。

3. `internal/software`
    - 前端最新 UI 已明确“升级文件”继续来自软件管理。
    - 后端也应保持同样原则：UFTE 升级类任务只引用 `firmware_id`，文件存储、MD5、版本元数据继续由 `software` 模块负责。

4. `internal/backup`
    - 备份已有任务模型、执行器、恢复接口与 restore service。
    - 因此 `config_backup`、`config_restore` 不建议在 UFTE 第一阶段重新写一套执行后端，应优先通过适配器复用现有服务。

#### 不建议直接复用为 UFTE 主体的代码

1. `internal/software` 的 `UpgradeTask` / `UpgradeSubTask` 与执行器
    - 当前模型字段明显是升级专用：`firmware_id`、`file_md5`、`is_keep_config`、`dest_version`、回退审计字段等都直接绑定升级语义。
    - `UpgradeExecutor` 也硬编码了升级流程：Download、DownloadingFlag、TransferComplete、5G `102 UPGRADE FINISH` 分支、版本比对等。
    - 这些能力应该被抽取复用，而不是让 UFTE 直接依赖升级模块的表结构和状态机。

2. `internal/ops` 的 `TaskExecutor`
    - 当前 `ops` 执行器仍以模板/占位执行和 inline-RPC fan-out 为主，适合运维任务框架演进，不适合直接承接文件传输主链路。
    - 它可以作为未来统一任务编排框架的收敛方向，但不适合当前 UFTE 首期交付直接压上去。

### C. 推荐总体架构

建议采用“UFTE 统一编排层 + 业务适配器层 + 公共基础设施层”三层结构。

```text
前端 /transfer/center / template-management
                     |
                     v
          internal/ufte (新模块)
  - Handler: /ufte/overview /task-types /tasks /devices
  - Service: 统一创建任务、统一查询、模板治理
  - Repository: ufte_task_types / ufte_tasks / ufte_sub_tasks
  - Adapter Router: 按 type_code / category 分发到具体执行适配器
                     |
        -----------------------------
        |             |             |
        v             v             v
 softwareAdapter  backupAdapter  genericTransferAdapter
        |             |             |
        v             v             v
 internal/software internal/backup internal/task + internal/transfer
```

### D. 为什么不是“一把梭全部迁移到新引擎”

- 升级、备份、恢复都已有在跑的后端代码和任务表，直接重写风险高。
- 当前最新 UI 已经先跑在 mock-first 预览模式，后端首期重点应是先让 UI 有真实接口和真实数据，而不是一次性替换所有历史执行链。
- 因此建议先做 UFTE 统一入口与读写编排，执行侧通过 adapter 复用；待统一模型跑稳后，再逐步把升级/日志等执行器抽成真正的通用 StepEngine。

## 三、核心设计

### 3.1 步骤原子化（Step 枚举）

将所有流程节点拆解为以下 9 个原子步骤：

| 步骤 ID | 步骤名称 | 说明 |
|--------|---------|------|
| `CHECK_PERMISSION` | 权限检查 | 按 permissionCode 校验用户功能权限 |
| `CHECK_ONLINE` | 设备在线检查 | 查 Redis 设备缓存；离线可配置等待/立即失败 |
| `CHECK_CONFLICT` | 并发冲突检查 | 防止同一设备同时执行多个同类任务 |
| `PRE_VALIDATE` | 前置校验 | 文件数量上限、磁盘空间等业务规则（可插拔） |
| `SEND_RPC` | 发送 TR-069 RPC | Download 或 Upload 或 SetParameterValues |
| `WAIT_RPC_RESPONSE` | 等待 RPC 响应 | 等待设备返回 DownloadResponse / UploadResponse |
| `WAIT_FILE_TRANSFER` | 等待文件传输 | 轮询 `DownloadingFlag`（仅 Download 场景）|
| `WAIT_TRANSFER_COMPLETE` | 等待 TransferComplete | 订阅 Redis 中 TR069 进程写入的 TC 结果 |
| `WAIT_INFORM_EVENT` | 等待 Inform 事件 | 等待指定 EventCode 的 Inform（102/其他）|

### 3.2 任务类型配置表（`file_transfer_task_type`）

> 以下 DDL 以 **PostgreSQL 16** 为准，面向当前 Go + pgx + JSONB 的项目实现，不再使用 MySQL / Java 风格定义。

```sql
CREATE TABLE file_transfer_task_type (
    type_code                  TEXT PRIMARY KEY,
    category                   TEXT        NOT NULL,
    category_label             TEXT        NOT NULL,
    display_name               TEXT        NOT NULL,
    description                TEXT,

    rpc_type                   TEXT        NOT NULL CHECK (rpc_type IN ('DOWNLOAD', 'UPLOAD', 'SET_PARAM_VALUES')),
    tr069_file_type            TEXT,
    file_type_label            TEXT,
    file_type_editable         BOOLEAN     NOT NULL DEFAULT TRUE,
    command_key_prefix         TEXT,
    url_template               TEXT,

    file_name_template         TEXT,
    file_size_field            TEXT,
    checksum_field             TEXT,
    raw_mode_default           TEXT,
    delay_seconds              INTEGER     NOT NULL DEFAULT 0,

    step_chain                 JSONB       NOT NULL,
    timeout_config             JSONB       NOT NULL DEFAULT '{}'::jsonb,
    post_tc_event              JSONB       NOT NULL DEFAULT '{}'::jsonb,
    tc_timeout_fallback        TEXT,
    permission_code            TEXT,
    platform_scope             JSONB       NOT NULL DEFAULT '[]'::jsonb,
    platform_overrides         JSONB       NOT NULL DEFAULT '{}'::jsonb,
    pre_validate_rules         JSONB       NOT NULL DEFAULT '[]'::jsonb,
```

### 3.3 附加事件等待配置（`post_tc_event` JSON 结构）

```json
{
    "enabled": true,
    "eventCode": "102 UPGRADE FINISH",
    "redisKeyTemplate": "{cellCode}_upgrade_finish",
    "resultField": "upgradeStatus",
    "successValues": ["1"],
    "failValues": ["2", "3"],
    "timeoutMs": 600000,
    "preClean": {
        "deleteRedisKey": "{cellCode}_upgrade_finish"
    }
}
```

- `enabled = false` 时（4G 升级、日志收集），WAIT_TRANSFER_COMPLETE 就是终态，不再等附加事件
- `preClean.deleteRedisKey`：5G 升级在 SEND_RPC 完成后需要预删除残留标识，通过此配置实现

### 3.4 前置校验规则（`pre_validate_rules` JSON 结构）

```json
[
    {

    {

]
```

### 3.6 统一任务表（`file_transfer_task`）

```sql
CREATE TABLE file_transfer_task (
    task_id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    type_code        TEXT        NOT NULL REFERENCES file_transfer_task_type(type_code),
    category         TEXT        NOT NULL,
    category_label   TEXT        NOT NULL,
    task_name        TEXT        NOT NULL,
    operator_scope   TEXT,
    create_user      TEXT,
    execution_mode   TEXT        NOT NULL CHECK (execution_mode IN ('immediate', 'scheduled', 'suspended')),
    scheduled_at     TIMESTAMPTZ,
    task_status      TEXT        NOT NULL CHECK (task_status IN ('pending', 'in_progress', 'suspended', 'ended')),
    task_result      TEXT        CHECK (task_result IN ('success', 'partial', 'failure', 'terminated')),
    current_step     TEXT,
    task_params      JSONB       NOT NULL DEFAULT '{}'::jsonb,
    total_count      INTEGER     NOT NULL DEFAULT 0,
    success_count    INTEGER     NOT NULL DEFAULT 0,
    fail_count       INTEGER     NOT NULL DEFAULT 0,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    started_at       TIMESTAMPTZ,
    ended_at         TIMESTAMPTZ
);

CREATE TABLE file_transfer_sub_task (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    task_id          UUID        NOT NULL REFERENCES file_transfer_task(task_id) ON DELETE CASCADE,
    type_code        TEXT        NOT NULL,
    category         TEXT        NOT NULL,
    category_label   TEXT        NOT NULL,
    device_id        UUID,
    device_name      TEXT,
    device_sn        TEXT        NOT NULL,
    product_type     TEXT,
    platform_type    TEXT,
    current_step     TEXT,
    step_status      TEXT        NOT NULL CHECK (step_status IN ('pending', 'in_progress', 'waiting', 'suspended', 'ended', 'failed')),
    step_result      TEXT        CHECK (step_result IN ('success', 'failure', 'terminated')),
    progress         INTEGER     NOT NULL DEFAULT 0,
    failure_reason   TEXT,
    step_context     JSONB       NOT NULL DEFAULT '{}'::jsonb,
    current_version  TEXT,
    target_version   TEXT,
    last_report_at   TIMESTAMPTZ,
    executed_at      TIMESTAMPTZ,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_file_transfer_task_category ON file_transfer_task(category);
CREATE INDEX idx_file_transfer_task_status ON file_transfer_task(task_status);
CREATE INDEX idx_file_transfer_sub_task_task_id ON file_transfer_sub_task(task_id);
CREATE INDEX idx_file_transfer_sub_task_category ON file_transfer_sub_task(category);
CREATE INDEX idx_file_transfer_sub_task_device_sn ON file_transfer_sub_task(device_sn);
```

- `category/category_label`：前端业务 Tab 的直接数据来源，不单独维护一张 `tab` 表；页面按任务类型聚合生成 Tab。
- `file_transfer_sub_task` 同时承载设备级执行明细，因此前端“设备列表”可直接基于该表聚合或分页查询，无需额外设备执行表。
- 对外 API 建议使用 camelCase 字段（如 `fileType`、`categoryLabel`），数据库层保留 snake_case。

## 五、后端统一引擎架构

### 5.0 首期实现原则

首期后端不追求“所有业务共享一个全新执行器”，而是分两步走：

1. 先统一编排与查询模型
    - 新建 `internal/ufte`，统一提供 `/ufte/*` API、模板元数据、任务创建入口、任务/设备聚合视图。
    - 首期 built-in 任务类型通过 adapter 路由到现有 `software` / `backup` / `task+transfer` 能力。

2. 再抽象执行器内核
    - 把 `software/executor.go` 中与升级强绑定但可泛化的步骤，逐步下沉到 UFTE `StepExecutor`。
    - 新增的真正“自定义类型”优先走 UFTE 通用执行器；历史成熟能力先复用旧模块，避免首期大面积迁移。

```go
type StepExecutor interface {
    StepID() string
    Execute(ctx context.Context, stepCtx *StepContext) (StepResult, error)
}

    TypeDef            FileTransferTaskTypeDef
    Task               FileTransferTask
    SubTask            FileTransferSubTask
    EffectivePlatform  string
    ResolvedParams     map[string]string
    StepData           map[string]any
}

const (
    StepContinue StepResult = "CONTINUE"
    StepWait     StepResult = "WAIT"
    StepSuccess  StepResult = "SUCCESS"
    StepFailure  StepResult = "FAILURE"
```

### 5.3 WAIT_INFORM_EVENT 步骤实现逻辑

```go
func (e *WaitInformEventStepExecutor) Execute(ctx context.Context, stepCtx *StepContext) (StepResult, error) {
    eventCfg := stepCtx.TypeDef.PostTcEvent
    if !eventCfg.Enabled {
        return StepSuccess, nil
    }

    if stepCtx.StepData["eventSubscribed"] == nil {
        redisKey := resolveTemplate(eventCfg.RedisKeyTemplate, stepCtx)
        if err := e.subscribeEvent(ctx, redisKey, stepCtx); err != nil {
            return StepFailure, err
        }
        stepCtx.StepData["eventSubscribed"] = true
        stepCtx.StepData["eventWaitStart"] = time.Now().UnixMilli()
        return StepWait, nil
    }

    waitStart, _ := stepCtx.StepData["eventWaitStart"].(int64)
    if time.Now().UnixMilli()-waitStart > eventCfg.TimeoutMs {
        return StepFailure, nil
    }

    redisKey := resolveTemplate(eventCfg.RedisKeyTemplate, stepCtx)
    result, err := e.redisClient.HGetAll(ctx, redisKey).Result()
    if err != nil {
        return StepFailure, err
    }
    if len(result) == 0 {
        return StepWait, nil
    }

    resultValue := result[eventCfg.ResultField]
    if contains(eventCfg.SuccessValues, resultValue) {
        return StepSuccess, nil
    }
    if contains(eventCfg.FailValues, resultValue) {
        return StepFailure, nil
    }
    return StepWait, nil
}
```

### 5.4 引擎主循环（简化伪代码）

```go
func (e *UnifiedFileTransferEngine) ProcessSubTask(ctx context.Context, subTask *FileTransferSubTask) error {
    typeDef, err := e.typeRepo.Get(ctx, subTask.TypeCode)
    if err != nil {
        return err
    }

    stepChain := typeDef.StepChain
    currentIdx := getStepIndex(stepChain, subTask.CurrentStep)
    stepCtx, err := e.buildContext(ctx, typeDef, subTask)
    if err != nil {
        return err
    }

    for index := currentIdx; index < len(stepChain); index++ {
        stepID := stepChain[index]
        executor := e.stepExecutors[stepID]
        subTask.CurrentStep = stepID

        result, execErr := executor.Execute(ctx, stepCtx)
        if execErr != nil {
            return e.markSubTaskFailed(ctx, subTask, execErr)
        }

        switch result {
        case StepWait:
            return e.subTaskRepo.Save(ctx, subTask)
        case StepFailure:
            return e.markSubTaskFailed(ctx, subTask, nil)
        case StepSuccess:
            return e.markSubTaskSuccess(ctx, subTask)
        case StepContinue:
            continue
        }
    }

    return e.markSubTaskSuccess(ctx, subTask)
}
```

## 九、风险与权衡

| 风险点 | 说明 | 应对方案 |
|--------|------|---------|
| 平台差异分支过多 | 不同平台 URL/FileType/行为差异可能超出配置能力 | `platform_overrides` 覆盖大多数差异；极端情况可注册平台专属 `StepExecutor` |
| 步骤间上下文依赖复杂 | 某些步骤需要前序步骤的特定数据（如 commandKey）| `StepContext.stepData` Map 规范化 key 约定；文档说明各步骤写入/读取哪些 key |
| 旧功能迁移风险 | 迁移过程中新旧并存，可能引入 Bug | 新旧引擎双写，按运营商灰度切换；充分回归测试 |
| DB 表结构变化 | 现有任务历史数据存在旧表 | 旧任务保留旧表只读展示；新任务走新表；提供历史数据归档脚本 |
| 配置错误导致任务异常 | JSON 配置出错可能导致引擎行为异常 | 配置入库前 JSON Schema 校验；步骤链合法性验证；引擎保护性兜底（未知步骤直接 FAILURE）|

## 十、与现有架构的兼容策略

```
当前：
    升级功能 → internal/software → 专用任务表 + 专用执行器
    备份/恢复 → internal/backup → 专用任务表 + 专用执行器
    Upload/Download 下发 → internal/task → device_tasks 队列

首期目标态：
    所有 UFTE 页面 → /ufte/* → internal/ufte
                                                             ├─ 统一模板配置
                                                             ├─ 统一任务/设备聚合查询
                                                             └─ 按 typeCode 分发到 software/backup/generic adapter

二阶段目标态：
    所有 UFTE built-in / custom 类型 → internal/ufte StepEngine
                                                                         └─ 仅底层继续复用 internal/task / internal/transfer / event bus

迁移期（新旧并存）：
    新 UI 统一走 `/ufte/*`
    首期执行复用旧模块，避免重写成熟链路
    随通用执行器成熟，逐类把 built-in 类型切出旧模块
```

> **核心原则**：UFTE 首期不是“全量重写执行链”，而是“统一入口 + 统一模型 + 渐进抽执行器”。先把用户看到的任务创建、模板治理、任务/设备视图统一起来；再把现有升级/备份/上传链路中真正通用的部分逐步下沉为 `StepExecutor`。
