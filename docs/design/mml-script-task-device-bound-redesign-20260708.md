# MML 脚本任务按设备编排设计方案

> 版本：2026-07-08
> 状态：产品设计方案，待评审
> 适用模块：MML 脚本库、MML 任务记录、MML 任务派发、MML 结果导出
> 关联文档：
> - `docs/design/mml-task-flow-design-20260424.md`
> - `docs/design/mml-script-task-integration.md`
> - `docs/design/mml-requirements-design.md`

## 1. 背景

当前 MML 脚本任务主要支持“选择一批设备，然后执行同一组命令”。这个模型适合公共查询、公共巡检和批量一致性配置，但不适合真实的现场维护。

实际业务中，一个脚本任务经常是一份多设备维护计划：不同设备执行不同命令，不同设备携带不同参数值，甚至同一设备内也需要先修改、再查询回读、再追加对象。此时“设备集合”和“脚本命令集合”不能再被看作两个独立输入，它们之间必须存在明确绑定关系。

因此，本方案将 MML 脚本任务从“批量设备 + 公共命令”升级为“按设备编排的执行计划”。

## 2. 现状问题

### 2.1 执行意图表达错误

现有任务模型可以概括为：

- `mml_tasks.device_sns[]` 保存目标设备集合。
- `mml_tasks.commands[]` 保存任务命令集合。
- 后端 fanout 按“设备 × 命令”生成 `device_tasks`。

这等价于把每条命令广播给每台设备。对于差异化维护来说，这不是用户的真实意图。

### 2.2 脚本文本和 SN 脱节

脚本模板中已经存在类似 `命令;{Serial Number}` 的书写方式，但当前产品入口仍要求用户额外选择设备。即使脚本行里写了 SN，系统也没有把 SN 作为该行命令的路由键使用。

这会导致用户以为脚本已经声明了目标设备，而系统实际仍按外部设备列表广播执行。

### 2.3 任务记录难以追溯

现有详情主要按设备结果和命令结果展示，但缺少“原始脚本行 -> 目标 SN -> 编译命令 -> device_task -> 响应结果”的完整链路。出现失败时，用户难以判断是哪一行脚本、哪个 SN、哪个参数值导致问题。

### 2.4 导出和审计粒度不足

对于按设备差异化执行的任务，审计对象应该是“某个 SN 执行了某一行命令，参数是什么，结果是什么”。如果只保留公共 commands 数组和 device_sns 数组，导出结果很难完整表达计划本身。

## 3. 设计目标

1. 支持一个脚本任务中不同 SN 执行不同命令。
2. 支持同一 SN 内多条命令按顺序执行，不同 SN 之间并行执行。
3. 支持脚本文本、表格导入和页面编辑三种方式生成执行计划。
4. 在执行前提供可预览、可校验、可编辑的 SN-命令关系。
5. 任务记录、审计日志、导出文件都能追溯到原始计划行。
6. 保留现有“批量设备执行公共脚本”模式，降低迁移成本。

## 4. 非目标

1. 不在本期引入复杂工作流编排，例如跨设备依赖、条件分支、循环、人工确认节点。
2. 不改变 TR-069 RPC 本身能力。
3. 不要求本期实现 Excel 高级公式或外部 CMDB 联动。
4. 不废弃现有公共脚本模式。

## 5. 核心概念

### 5.1 公共脚本模式

公共脚本模式保持当前语义：

> 一批设备执行同一组命令。

适用场景：

- 批量查询设备基础信息。
- 批量读取软件版本。
- 批量执行相同参数模板。

### 5.2 按设备编排模式

按设备编排模式是本方案的主模式：

> 一个任务由多条计划行组成，每条计划行明确指定目标 SN、命令和参数；同一 SN 的执行顺序由脚本中的原始行顺序决定，系统解析后自动生成内部顺序号。

示例：

```text
LST DEVICE_INFO;SN001
MOD DEVICE_INFO:USER_LABEL=Site-A;SN002
LST DEVICE_INFO;SN002
ADD EUTRANNFREQ:LTE_INTER_FREQ_DL_EARFCN=41390;SN003
```

## 6. 用户体验设计

### 6.1 新建任务入口

新建 MML 任务时，先选择任务模式：

| 模式 | 说明 | 默认建议 |
|------|------|----------|
| 统一脚本批量执行 | 选择多台设备，每台设备执行同一套脚本 | 作为快捷方式保留 |
| 按设备编排执行 | 每行命令绑定设备 SN；同一设备按脚本从上到下执行 | 作为推荐方式 |

如果用户导入的脚本或表格中已经包含 SN，系统自动切换到“按设备编排执行”。

模式选择使用整块可点击的说明卡，而不是只显示短标签或把解释隐藏在 Tooltip 中。每张卡始终展示“执行方式名称 + 一句话说明”；选中态通过边框、底色和单选标记共同表达，禁用态仍保留说明，让用户理解为什么当前方式不可选。

### 6.2 按设备编排页面结构

按设备编排模式不应只提供纯文本框，而应提供“执行计划表”。

表格字段：

| 字段 | 说明 |
|------|------|
| SN | 目标设备序列号 |
| 设备状态 | 在线、离线、不存在、产品型号不匹配等 |
| 顺序 | 同一 SN 内的执行顺序，由导入行序自动派生，可在页面中调整 |
| 命令 | MML 命令码或命令名称 |
| 参数摘要 | 本行参数和值的摘要 |
| 校验状态 | 通过、警告、错误 |
| 操作 | 编辑、复制、删除、查看编译结果 |

建议能力：

- 按 SN 分组折叠。
- 按校验状态过滤。
- 一键只看错误行。
- 复制某台设备的命令到其他设备。
- 批量替换参数值。
- 从设备列表追加 SN。
- 从 CSV、TXT、XLSX 导入执行计划。

### 6.3 执行前校验

提交任务前必须完成校验并展示结果：

| 校验项 | 错误级别 | 处理方式 |
|--------|----------|----------|
| SN 为空 | 阻断 | 不允许提交 |
| SN 不存在 | 阻断或警告，可配置 | 默认不允许提交 |
| 命令无法识别 | 阻断 | 不允许提交 |
| 参数格式错误 | 阻断 | 不允许提交 |
| 参数不可写但用于 MOD | 阻断 | 不允许提交 |
| 同一 SN 显式顺序重复 | 阻断 | 仅在表格或页面手动调整顺序时校验 |
| 设备离线 | 警告 | 允许结合离线重试策略提交 |
| 产品型号和命令不匹配 | 警告或阻断 | 默认警告，危险命令阻断 |

### 6.4 大数据量分页与任务上限

单个 MML 脚本任务按最多 200 台设备、2000 条计划行设计。前端和后端使用同一组硬限制：前端在解析、选择和提交前即时提示，后端在创建任务时再次校验，防止绕过页面提交超限数据。

| 场景 | 数据来源 | 分页策略 | 默认分页 |
|------|----------|----------|----------|
| 创建脚本的计划执行预览 | 浏览器本地解析结果 | 前端分页，不截断原数组 | 20 条/页，可选 20、50、100 |
| 下发任务的计划执行预览 | 浏览器本地解析结果 | 前端分页，不截断原数组 | 20 条/页，可选 20、50、100 |
| 可选设备列表 | 设备查询接口 | 服务端分页，跨页保留已选项 | 20 台/页，可选 20、50、100 |
| 已选设备列表 | 浏览器本地选择结果 | 摘要 + 可删除的前端分页列表 | 20 台/页，可选 20、50、100 |
| 任务执行结果 | 任务结果接口 | 服务端分页 | 沿用结果接口参数 |

交互要求：

- 始终显示总计划行数、总设备数和当前展示范围，例如“第 21–40 条，共 2000 条”。
- 已选设备不使用 200 个标签直接撑开表单；默认显示“已选 120/200 台”，展开后用分页列表查看、移除和清空。
- 三套皮肤使用相同的数据范围、每页数量和总数语义；不得用 `slice(0, 20)` 一类静默截断替代分页。
- 分页只改变可见数据，不重排 `line_no`、`order` 或原始数组；同一设备仍严格按脚本从上到下执行。
- 超过 200 台设备或 2000 条计划行时阻止提交，并明确显示当前数量和允许上限。

## 7. 脚本和导入格式

### 7.1 推荐表格格式

CSV/XLSX 推荐列：

```text
sn,command_code,parameters,remark
SN001,LST DEVICE_INFO,,
SN002,MOD DEVICE_INFO,"USER_LABEL=Site-A",
SN002,LST DEVICE_INFO,,
```

说明：

- 行顺序就是默认执行顺序；同一 SN 的多行命令按文件从上到下执行。
- 可选支持 `order` 列，主要用于从外部系统导入已经排好序的计划；页面编辑时也可以调整内部顺序。

### 7.2 推荐文本格式

```text
LST DEVICE_INFO;SN001
MOD DEVICE_INFO:USER_LABEL=Site-A;SN002
LST DEVICE_INFO;SN002
```

推荐使用旧模板风格作为文本主格式。它的好处是书写接近现场脚本习惯，用户只需要按计划从上到下写命令，不需要额外维护竖杠分隔符或 `1/2/3` 顺序号。

### 7.3 兼容显式顺序格式

为了兼容外部工具生成的计划，也可以接受显式顺序格式：

```text
SN001 | 1 | LST DEVICE_INFO;
SN002 | 1 | MOD DEVICE_INFO:USER_LABEL=Site-A;
SN002 | 2 | LST DEVICE_INFO;
```

解析规则：

1. 推荐文本格式中，如果行尾最后一个分号后的片段匹配已知 SN 或 SN 格式，则识别为 `device_sn`。
2. 分号前内容识别为命令和参数；命令内部仍可使用冒号和逗号表达参数。
3. 同一 SN 的执行顺序默认按原始脚本行号从小到大派生，系统写入 `order`。
4. 显式顺序格式中的 `order` 可作为导入顺序，但不作为推荐手写格式。
5. 如果行内没有 SN，则按公共脚本模式处理，或要求用户在页面中补充设备集合。

### 7.4 解析后的统一形态

无论用户通过文本、CSV、XLSX 还是页面表格编辑，提交前都归一化为执行计划行。

```json
{
  "line_no": 1,
  "device_sn": "SN001",
  "order": 1,
  "raw_line": "LST DEVICE_INFO;SN001",
  "command": {
    "command_code": "LST DEVICE_INFO",
    "operation_type": "LST",
    "parameters": {}
  }
}
```

## 8. API 契约建议

### 8.1 新建任务请求

建议在现有 `POST /api/v1/mml/tasks` 上扩展字段，而不是新增完全割裂的接口。

```json
{
  "task_name": "站点参数差异化维护",
  "execute_mode": "device_bound",
  "script_id": "optional-script-id",
  "plan_items": [
    {
      "line_no": 1,
      "device_sn": "SN001",
      "order": 1,
      "raw_line": "LST DEVICE_INFO;SN001",
      "command": {
        "command_code": "LST DEVICE_INFO",
        "operation_type": "LST",
        "parameters": {}
      }
    }
  ],
  "execute_type": "immediate",
  "offline_retry": false,
  "failed_retry": true,
  "failed_retry_count": 3,
  "failed_retry_interval": 5
}
```

### 8.2 兼容字段

为兼容现有列表、筛选和旧页面，可继续保留：

- `device_sns`：由 `plan_items.device_sn` 去重得到。
- `commands`：公共脚本模式继续使用；按设备编排模式可保存为摘要或编译后的命令集合。

但按设备编排模式下，真实执行源必须是 `plan_items`。

### 8.3 任务详情响应

任务详情应返回计划行和执行结果的关联视图：

```json
{
  "id": "task-id",
  "task_name": "站点参数差异化维护",
  "execute_mode": "device_bound",
  "device_sns": ["SN001", "SN002"],
  "plan_stats": {
    "device_count": 2,
    "plan_item_count": 3,
    "rpc_count": 3,
    "success_count": 2,
    "failed_count": 1
  },
  "plan_items": [
    {
      "line_no": 1,
      "device_sn": "SN001",
      "order": 1,
      "command_code": "LST DEVICE_INFO",
      "status": "completed",
      "device_task_ids": ["device-task-id"]
    }
  ]
}
```

## 9. 数据模型建议

### 9.1 最小演进方案

在 `mml_tasks` 上新增 JSONB 字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `execute_mode` | text | `common` / `device_bound` |
| `plan_items` | jsonb | 按设备编排模式的原始计划行 |

优点：

- 改动小。
- 与现有 `mml_tasks` 生命周期、调度、导出能力兼容。
- 适合先完成产品语义纠偏。

风险：

- 计划行查询和统计依赖 JSONB。
- 后续复杂报表可能不够方便。

### 9.2 结构化演进方案

如果后续需要大量按计划行检索、审计和重试，建议新增表：

```sql
CREATE TABLE mml_task_plan_items (
    id uuid PRIMARY KEY,
    task_id uuid NOT NULL REFERENCES mml_tasks(id) ON DELETE CASCADE,
    line_no integer NOT NULL,
    device_sn text NOT NULL,
    order_no integer NOT NULL,
    raw_line text,
    command jsonb NOT NULL,
    compiled_command jsonb,
    status text NOT NULL DEFAULT 'pending',
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);
```

同时在 `device_tasks` 中增加或复用扩展字段关联计划行：

- `source_id` 继续指向 `mml_tasks.id`。
- 新增 `source_item_id` 或在 params/metadata 中保存 `plan_item_id`。

首期建议采用最小演进方案，稳定后再结构化。

## 10. 后端执行语义

### 10.1 公共脚本模式

维持现有逻辑：

```text
device_sns × commands -> device_tasks
```

### 10.2 按设备编排模式

执行逻辑改为：

```text
plan_items -> group by device_sn -> sort by order -> device_tasks
```

规则：

1. 同一 SN 内按 `order` 严格串行；`order` 默认由原始脚本行顺序按 SN 分组自动生成。
2. 不同 SN 之间并行。
3. 每个 plan item 可以编译成一个或多个 RPC。
4. 编译后的每个 RPC 都必须能追溯到原始 plan item。
5. 如果某个 SN 的前置命令失败，默认停止该 SN 后续命令；可在后续版本支持“失败后继续”策略。

### 10.3 状态统计

任务统计需要从单一“设备数”扩展为：

| 指标 | 说明 |
|------|------|
| 设备数 | 去重后的 SN 数量 |
| 计划行数 | 用户提交的 plan item 数量 |
| RPC 数 | 编译后实际产生的 device_task 数量 |
| 成功行数 | 全部关联 RPC 成功的计划行 |
| 失败行数 | 任一关联 RPC 失败的计划行 |
| 部分成功行数 | 多 RPC plan item 中部分成功、部分失败 |

## 11. 任务记录与导出

### 11.1 任务详情

任务详情建议提供三层视图：

1. 总览：设备数、计划行数、成功数、失败数、执行耗时。
2. 按设备：展示每个 SN 的命令链路和状态。
3. 按计划行：展示原始脚本行、编译命令、RPC 方法、参数、响应和失败原因。

### 11.2 单设备详情

单设备详情应展示该 SN 的完整执行序列：

| 顺序 | 原始脚本行 | 命令 | RPC | 状态 | 响应摘要 | 失败原因 |
|------|------------|------|-----|------|----------|----------|

### 11.3 导出

支持两种导出：

- 汇总导出：一行一个 plan item，适合审计。
- 单设备导出：某个 SN 的全部命令和响应，适合排障。

汇总导出建议字段：

```text
任务ID,任务名称,行号,SN,顺序,原始脚本行,命令码,RPC方法,参数摘要,状态,失败原因,下发时间,响应时间
```

## 12. 前端三皮肤落地

涉及前端页面时必须覆盖三套皮肤：

- `webcode`：标准实现，优先完成。
- `webcode-v2`：保持路由、菜单和主能力一致。
- `webcode-v3`：保持路由、菜单和主能力一致。

共享能力应优先放到 `frontend-core`：

- 脚本解析器。
- 执行计划数据类型。
- API client。
- 导入文件解析。
- 校验规则。

三套 UI 壳只负责交互呈现，不重复实现业务解析。

## 13. 分阶段实施

### Phase 1：执行计划建模和导入预览

目标：

- 新增按设备编排模式。
- 前端支持文本/CSV 导入解析。
- 提供执行计划表格预览和校验。
- API 支持 `execute_mode=device_bound` 和 `plan_items`。

验收：

- 导入包含 SN 的脚本时，页面能正确识别每行目标设备。
- 错误行能在提交前阻断。
- 旧公共脚本模式不受影响。

### Phase 2：后端 fanout 支持 plan_items

目标：

- 后端按 `plan_items` 生成 `device_tasks`。
- 同一 SN 内串行，不同 SN 并行。
- 每个 `device_task` 能追溯原始计划行。

验收：

- SN001 只执行分配给 SN001 的命令。
- SN002 只执行分配给 SN002 的命令。
- 不再出现“所有设备执行所有命令”的误派发。

### Phase 3：任务记录和导出升级

目标：

- 任务详情按设备和计划行展示。
- 导出结果包含行号、SN、原始脚本行、命令、参数和结果。
- 审计日志能定位到计划行。

验收：

- 用户能从失败结果反查原始脚本行。
- 汇总导出和单设备导出都能表达差异化执行计划。

### Phase 4：高级编辑能力

目标：

- 复制某台设备命令到其他设备。
- 批量替换参数。
- 保存按设备编排模板。
- 支持失败后继续策略。

验收：

- 高频批量维护可以在页面内完成，不依赖外部手工改 CSV。

## 14. 兼容与迁移

### 14.1 旧任务

旧任务没有 `execute_mode` 时，按 `common` 处理。

### 14.2 脚本格式兼容

脚本行没有 SN 时，继续走公共脚本模式。

脚本行尾包含 SN 时，导入时提示：

```text
检测到脚本中包含设备 SN，已切换为按设备编排模式。请确认执行计划后提交。
```

### 14.3 API 兼容

现有 `device_sns + commands` 请求继续可用。

新增 `plan_items` 后，后端判断优先级：

1. 如果 `execute_mode=device_bound`，必须使用 `plan_items`。
2. 如果 `plan_items` 非空但 `execute_mode` 为空，可自动推断为 `device_bound`。
3. 否则使用现有公共脚本逻辑。

## 15. 测试策略

### 15.1 后端测试

覆盖：

- `plan_items` 请求校验。
- 按设备 fanout。
- 同 SN 串行。
- 跨 SN 并行。
- 计划行到 `device_tasks` 的追溯关系。
- 旧公共脚本模式回归。

### 15.2 前端测试

覆盖：

- 文本格式解析。
- CSV 格式解析。
- 推荐 `命令;SN` 格式解析。
- 可选显式顺序格式解析。
- 计划表校验。
- 错误行阻断提交。
- 三皮肤路由和菜单一致性。

### 15.3 集成验收

核心用例：

```text
LST DEVICE_INFO;SN001
MOD DEVICE_INFO:USER_LABEL=Site-A;SN002
LST DEVICE_INFO;SN002
```

预期：

- 只为 SN001 创建 1 条查询任务。
- 只为 SN002 创建 2 条任务。
- SN002 的第 2 条在第 1 条完成后才执行。
- 任务详情中每条结果都能回到原始脚本行。

## 16. 产品验收标准

1. 一个脚本任务可以包含多个 SN。
2. 每个 SN 可以有不同命令。
3. 每个 SN 可以有不同参数值。
4. UI 执行前预览和后端实际派发结果一致。
5. 任务详情可以从结果追溯到原始脚本行。
6. 导出文件可以表达 SN、命令、参数、结果之间的绑定关系。
7. 旧公共脚本任务仍可创建和执行。

## 17. 待评审问题

1. SN 不存在时是否允许保存为草稿，还是必须阻断提交？
2. 同一 SN 的某行失败后，默认是否继续执行后续行？
3. 首期是否需要支持 XLSX，还是先支持 TXT/CSV？
4. `plan_items` 首期存在 `mml_tasks` JSONB 中，还是直接新增结构化表？
5. 是否需要为危险命令增加逐行二次确认？

## 18. 推荐结论

MML 脚本任务应保留公共批量模式，但主模型应升级为按设备编排的执行计划。

这个改变能让产品语义贴近真实维护场景，避免误派发，也能让任务记录、审计和导出从一开始就具备可追溯性。
