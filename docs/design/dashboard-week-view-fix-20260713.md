# 首页 KPI 周视图修复方案

> 文档日期：2026-07-13
> 文档状态：已实现，待验收
> 代码基线：`ce479a0ff`
> 范围：仅 v1 首页 KPI 折线图的“周”视图
> 对应 Issue：首页周视图改用 daily 数据并展示最近七个完整自然日
> 前置依赖：[首页 KPI 时序接口粒度对齐方案](./dashboard-kpi-granularity-api-20260713.md)
> 本文只给出分析与方案，不包含业务代码修改。

## 0. 2026-07-13 验收补充（以 PM 口径为准）

根据 GitLab [xomc#53](http://192.168.10.16/netmanager/xomc/-/issues/53) 的验收反馈以及性能仪表盘（PM）现行实现复核，首页周视图必须优先与 PM 的 daily 数据口径和出点时机保持一致，不能为了提前显示今天而自行用 hourly 数据拼接 partial 日点。

### 0.1 时间与数据口径

假设系统业务时区为 `Asia/Shanghai`，当前时间为 `2026-07-13 14:20`：

```text
daily 窗口：[2026-07-06 00:00+08:00, 2026-07-13 00:00+08:00)
横轴：      07/06 ... 07/13（07/13 为今日普通日期占位）
```

历史点直接读取与 PM 相同的 `pm_metrics_daily`。当天尚未结束时横轴仍显示当天的普通日期，但不显示当天点、不补零、不连线；待自然日结束并由 PM daily 聚合链生成对应日期的日点后，下一次周窗口才将该日期显示为真实点。以 2026-07-13 为例，13 日白天保留 `07/13` 标签但没有点；14 日完成 daily 聚合后，13 日成为真实点，14 日成为新的占位日期。

### 0.2 日期归属修复

daily 桶起点 `2026-07-12 00:00+08:00` 经 JSON 序列化可能成为 `2026-07-11T16:00:00Z`。前端不得再使用 `point.time.slice(0, 10)`，必须使用系统时区日期格式化函数生成 `2026-07-12` 键。测试必须覆盖 UTC `Z` 字符串跨日映射。

### 0.3 样式与图例

- 周主线颜色改为系统主蓝 `#1677FF`，与 PM 图表和 #53 验收要求一致。
- 周模式系列名称使用实际指标名称，不再使用“周”或“本周”。
- 单指标周模式隐藏冗余图例；多指标周模式保留指标名称图例。
- Tooltip 使用指标名称，缺值仍显示 `-`；真实缺口不跨点连线。

### 0.4 范围边界

GSM/2G 制式入口及 `network_type` 字典大小写分别由 xomc#50、xomc#58 跟踪，本轮不修改。

## 1. 范围约束

本次只解决以下周视图问题：

1. 周视图需要稳定展示最近 7 个完整自然日的数据。
2. 图例中的“本周”改为“周”。
3. 周视图不再叠加“今日”系列，只显示“周”这一条醒目的亮色趋势线。
4. 周视图日点与性能仪表板 `daily + network + 当前制式` 的计算口径一致；同一自然日、同一指标、同一统计范围应显示相同值。

明确不改：

- “天”视图的今日/昨日取数、颜色、横轴和交互。
- 首页 KPI 指标选择、布局配置和多指标模式。
- KPI 公式、既有小时/日聚合任务或数据库表结构。
- 首页设备、告警、UE、状态分布等其他卡片。
- 性能管理页面以及 v2/v3 页面。
- 性能仪表板的取数和展示逻辑。

## 2. 老系统实现还原

老系统首页代码位于：

```text
omcmb/original-omc/OMCWebServer/src/main/webapp/WEB-INF/content/home/home.jsp
```

### 2.1 Day/Week 是粒度切换

老系统用 `periodTypeData[code]` 保存每个 KPI 图表的 `min/week` 状态：

- Day：小时粒度，显示昨日和今日两条线。
- Week：日粒度，显示最近 7 个完整自然日的一条指标线。

`periodTypeChange()` 只重新加载当前 KPI 图表，不影响其他卡片。

### 2.2 Week 查询范围

老代码在 Week 分支执行：

```text
statisPeriod = 1440
startTime = 7 天前 00:00:00
endTime = 今天 00:00:00
lineLength = 1
```

该窗口是 `[7天前零点, 今天零点)`，恰好包含最近 7 个已经结束的自然日，不包含尚未结束的今天。

`getDays()` 同样生成连续 7 个日期。Week 模式关闭小时 timeline，X 轴名称切换为“天”，日期格式为 `MM/DD`。

### 2.3 老系统可复用的原则

- 周不是自然周，也不是“本周一到现在”。
- 周不依赖星期几，星期一进入时仍有 7 个完整日点。
- X 轴由时间窗口生成，不由接口返回了哪些日期决定。
- 缺少某天数据时保留日期槽位，不能压缩横轴。

## 3. 当前实现与根因

### 3.1 当前数据流

```text
DashboardKPIModules
  -> useMultiKPITrendComparison(metrics, 'last_week')
  -> GET /api/v1/dashboard/kpi-time-series
  -> LayoutKPIPanel
  -> buildSeries(..., 'last_week')
  -> LineChart
```

### 3.2 周范围使用了自然周

`frontend-core/src/hooks/api/useDashboard.ts` 当前把 `last_week` 计算为：

```text
current：本周一 00:00 到现在
compare：上周一 00:00 到上周日 23:59:59
```

因此星期一切换到周视图时，`current` 天然只有今天一个日期点。这是“只能打今日的点”的直接原因。

### 3.3 图例和颜色绑定错误

`LayoutKPIPanel.tsx` 当前在周视图中仍把主线命名为“今日”，把 `compare` 数据命名为“本周”。

`LayoutKPIPanel.helpers.ts` 又把所有 compare 线固定设置为：

```text
color = #999999
dashed = true
```

所以界面中的灰色“本周”实际承载的是上周数据，并继承了历史对比线样式。数据语义、图例和颜色三者没有对齐。

### 3.4 X 轴依赖数据日期并集

当前周分支把 `current` 和 `compare` 中出现过的日期取并集再排序。结果会随数据完整性变化：

- 星期一可能出现 8 个日期：上周 7 天 + 今日。
- 星期二可能出现 9 个日期：上周 7 天 + 本周 2 天。
- 某天无数据时，该日期可能直接从 X 轴消失。

这不是稳定的“周”视图。

### 3.5 现有测试固化了错误预期

`LayoutKPIPanel.buildSeries.test.ts` 当前明确断言周模式输出：

```text
主线 = 今日
compare 线 = 本周
compare 线 = 灰色虚线
X 轴 = current/compare 实际日期并集
```

因此现有测试通过并不能证明周视图符合业务要求，测试本身需要随周语义修正。

### 3.6 首页与性能仪表板的日值计算口径不一致

性能仪表板选择日粒度时，通过 PM Aggregator 查询 `pm_metrics_daily`，按自然日汇总基础 counter 后再代入 KPI 公式重算。以 `KGNB0516 上行用户平均速率` 为例：

```text
(sum(C010020001) - sum(C010020006)) * 8 / sum(C010020008)
```

首页周视图当前仍查询 hourly 数据，然后在 `LayoutKPIPanel.helpers.ts` 的 `aggregateToDays()` 中对同一天的小时 KPI 做算术平均：

```text
(hourKPI1 + hourKPI2 + ... + hourKPIN) / N
```

“全天 counter 汇总后重算”与“小时 KPI 简单平均”并不等价。尤其对速率、成功率、利用率等分式指标，各小时分母权重不同，因此不仅某一天会不一致，周内每个日点都可能与性能仪表板不同。

此外，首页 hourly 链路使用桶的 `end_time` 作为展示时间，再由前端按该时间归属日期。`07/13 00:00` 实际代表 `07/12 23:00～07/13 00:00`，却会被归入 `07/13`，导致首页日窗口与性能仪表板的自然日窗口发生一小时偏移。

因此，周视图不能继续由前端对 hourly KPI 求日均，必须直接使用 PM Aggregator 的 daily 自然日结果。

## 4. 目标行为

### 4.1 文案

切换按钮保持：

```text
天 | 周
```

周视图图例调整为：

```text
周
```

不再显示“今日”或“本周”。“周”在本页面中的定义是“最近 7 个完整自然日”。指标名称已由卡片右上角选择器明确展示，图例只需表达当前时间粒度。

### 4.2 时间窗口

假设当前时间为 `2026-07-13 10:00`：

| 系列 | 查询范围 | X 轴位置 |
|---|---|---|
| 周 | `[2026-07-06 00:00, 2026-07-13 00:00)` | `07/06`～`07/12` |

完整周视图横轴为连续 7 个日期：

```text
07/06  07/07  07/08  07/09  07/10  07/11  07/12
```

其中：

- 无数据使用 `null`，不使用 `0`，避免把未采集误认为真实零值。
- 每个日点直接使用后端 daily 聚合值，前端不再对 hourly KPI 二次平均。
- 相同 KPI、相同制式和相同全网统计范围下，日点数值应与性能仪表板一致。

该设计严格复用老系统“周 = 最近 7 个完整自然日”的口径。今日小时趋势属于“天”视图；周视图不再混入不同粒度的孤立今日点。

### 4.3 颜色和线型

| 系列 | 颜色 | 线型 | 说明 |
|---|---|---|---|
| 周 | `#FA8C16` | 实线 | 亮橙色，浅色/深色主题均清晰可见 |

周不再使用灰色和虚线，因为它不是“上一周期辅助线”，而是当前周视图的主要历史趋势。

图例标记与 Tooltip marker 必须使用相同颜色。周线无数据时可以断开，不能通过 `connectNulls` 跨越真实缺口。

### 4.4 Tooltip

每个日期只显示周系列，缺值显示 `-`：

```text
2026-07-11
周：3.77 Mbps
```

本次不修改 Tooltip 的单位和小数位规则。

## 5. 推荐实现

### 5.1 复用前置 Issue 的 daily 查询能力

本 Issue 不重复修改后端粒度路由。前置 Issue 已为 `/api/v1/dashboard/kpi-time-series` 提供 `granularity=daily`，并保证 daily 复用 PM Aggregator 的 `DimensionNetwork + GranularityDaily` 计算口径。

周视图只负责使用该能力，不在前端实现 KPI 日聚合公式。

### 5.2 周分支只发起一次 daily 请求

首页周分支计算：

```text
todayStart = 今天 00:00
weekStart = todayStart - 7 天

weekParams = {
  start_time: weekStart,
  end_time: todayStart,
  granularity: daily
}
```

“天”分支现有参数完全不动。

周分支不再构造 `today + compare` 两组数据，只请求一组 rolling week 数据。推荐新增专用的 `useMultiKPIWeekSeries()`，避免继续借用语义错误的 `last_week` 对比结构；该 Hook 内使用系统业务时区生成边界，并把 daily 响应映射为每个 KPI 的单一 week 序列。

如果为控制改动量暂时复用现有响应类型，也必须保证 `compare` 为空，并在代码中明确：

```text
week = rolling 7 complete days
```

时间边界必须通过项目现有 `systemTimezone`/Day.js 时区工具计算，不能使用浏览器本地 `new Date().setHours(...)` 推导业务日。

### 5.3 固定生成日期轴

新增或复用纯函数生成：

```text
[weekStart, weekStart+1d, ..., todayStart-1d]
```

共 7 个连续日期槽位。不能再从返回数据的日期集合反推 X 轴。

daily 返回行的桶起点对应自然日，数据映射规则：

```text
daily point -> 按系统业务时区日期写入7个槽位
missing    -> null
```

### 5.4 日值计算口径

周视图不再调用 `aggregateToDays()` 对 hourly KPI 求平均。每个日点直接采用 daily network 查询返回的 KPI 值：

```text
daily counter 聚合 -> network 维度汇总 -> KPI 公式重算 -> 首页周日点
```

这与性能仪表板日粒度的核心计算链路一致。前端只负责七天日期槽位映射、缺值补 `null` 和单位换算，不再参与 KPI 日值计算。

### 5.5 周系列样式

新增周系列专用颜色常量，例如：

```text
KPI_WEEK_LINE_COLOR = '#FA8C16'
```

仅周视图使用。现有 `KPI_COMPARE_LINE_COLOR = '#999999'` 继续服务“天”视图的昨日线，不作修改。

## 7. 测试方案

### 7.1 时间窗口

1. 星期一进入周视图，周窗口仍覆盖此前 7 个完整自然日。
2. 星期日进入周视图，周窗口仍是此前 7 个完整自然日，不按自然周截断。
3. 跨月场景，例如 08/03，正确生成 07/27～08/02，不包含尚未结束的 08/03。
4. 跨年场景，例如 01/01，正确生成上一年 12 月日期。
5. 使用系统业务时区计算边界，不因 UTC 序列化偏移一天。

### 7.2 Series 与 X 轴

1. X 轴始终为连续 7 个日期。
2. 周系列 7 个槽位映射正确。
3. 中间某天无数据时日期仍存在，对应值为 `null`。
4. 接口返回乱序数据时，最终仍按日期升序显示。
5. daily 接口返回一个自然日点时，前端直接使用该值，不进行小时平均或二次聚合。

### 7.3 与性能仪表板口径一致性

1. 对 `KGNB0516 上行用户平均速率`，准备各小时业务时长不同的数据，验证首页周日点等于 daily counter 重算值，而不是小时 KPI 算术平均值。
2. 同一自然日、同一 K/C 指标、同一制式、同一 network 范围下，首页周日点与性能仪表板 daily 点一致。
3. 验证 `07/12 23:00～07/13 00:00` 的小时数据归入 `07/12` daily 桶，不发生按 `end_time` 错归 `07/13`。
4. daily 数据缺失时展示断点，不回退到 hourly 简单平均，避免同一图表混用两种统计口径。

### 7.4 文案和样式

1. 周视图图例仅为“周”，不出现“今日”或“本周”。
2. 周为 `#FA8C16` 亮橙色实线。
3. “天”视图今日/昨日颜色和虚实线完全不变。
4. 浅色和深色主题下，图例、折线、点和 Tooltip marker 颜色一致且可辨识。

## 8. 验收标准

1. 任意星期切换到周视图，周系列都有 7 个连续日期槽位。
2. 有完整数据时周系列展示 7 个日点；缺数时保留日期并断点。
3. 周使用亮橙色，不再呈灰色，不再使用虚线。
4. 周视图不显示今日孤立点，图例只显示“周”。
5. 切回天视图后，现有今日/昨日行为与修改前一致。
6. 首页周视图与性能仪表板在相同指标、制式、network 范围和自然日下数值一致。
7. 周接口只请求一次 daily 数据，不再同时请求“今日”和“上周”两组 hourly 数据。
8. 其他首页卡片、其他页面和后端接口没有行为变化。

## 9. 实施顺序

1. 先补周时间窗口和固定日期轴的失败测试。
2. 修改周请求窗口，使其覆盖最近 7 个完整自然日。
3. 修改周 Series 映射、文案和颜色。
4. 运行目标单测、v1 typecheck、lint 和 `skin-parity`。
5. 在浅色/深色主题分别验证星期一场景和缺一天数据场景。

该顺序可以把改动严格限制在周分支，避免影响已经正常的“天”模式和其他首页功能。
