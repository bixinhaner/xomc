# 首页 GSM KPI 与网络制式字典统一设计（#50 / #58）

## 目标

修复首页仪表板缺少 GSM（2G）KPI 制式，并把 `network_type` 字典的机器值统一为
`lte`、`nr`、`gsm` 小写枚举，确保新部署、历史环境和后续人工维护都遵循同一契约。

## 已确认的根因

1. 部署 baseline 中 `network_type` 只有 `lte`、`nr` 两项；没有 `gsm`，因此新环境不会
   出现 GSM 页签。
2. 字典明细新增、编辑没有按字典类型校验机器值。人工创建 `GSM` 后，首页
   `useTechnologyDictionary` 的严格小写枚举过滤会丢弃该项。
3. GSM KPI 默认布局和 PM 内置任务已存在，不是缺少 KPI 面板定义。
4. 首页 KPI 时序请求当前没有传递所选 `technology`。即便 GSM 页签恢复，也没有形成与
   PM 性能仪表盘一致的制式过滤契约。

## 契约

| 语义 | 规范值 |
| --- | --- |
| 字典类型 | `network_type` |
| 机器值 | `lte`、`nr`、`gsm`（严格小写） |
| GSM 展示值 | `GSM` |
| Dashboard / PM 聚合制式参数 | `lte`、`nr`、`gsm`（严格小写） |

展示名和机器值必须分离：`GSM` 只可作为显示文本，不能作为字典值或接口制式参数。

## 修复设计

### 1. 数据迁移与 baseline

新增 seed 前向迁移，而不是修改已应用的 `000001_init_seed.sql`：

- 已有小写 `gsm` 时保留该记录；
- 仅有历史大写 `GSM` 时把它改为 `gsm`；
- 两者都没有时插入启用状态、排序第三的 GSM 项；
- 两者同时存在时保留小写规范项，软删除大写历史项，避免违反活跃明细唯一索引；
- 迁移按字典 `type = 'network_type'` 查找字典 ID，不能写死 ID。

同时更新 baseline，使全新数据库也从第一天就具备 GSM 项。

### 2. 字典写入约束

在字典明细创建和编辑服务中，先解析所属字典类型。仅当类型为 `network_type` 时，
拒绝 `lte`、`nr`、`gsm` 以外的机器值；其他字典保持原有自由值行为。这样不会把
通用字典服务变成设备制式专用接口，也杜绝再次写入 `GSM`。

### 3. 首页与时序数据

- 首页继续严格消费小写机器值，不在前端静默纠正错误数据；数据问题应由迁移与后端校验
  消除。
- 选择的制式必须从 Dashboard 组件传给 KPI 时序 hook、前端 API、后端 handler/service，
  最终填入 PM Aggregator 查询的 `Technologies` 条件。
- GSM 继续复用既有布局和 KPI 定义；不增加静态兜底页签，避免掩盖字典缺项。

## 验收与回归

1. 新库 seed 后 `network_type` 返回 `lte`、`nr`、`gsm`，首页显示 eNB、gNB、GSM。
2. 历史仅含 `GSM` 的环境迁移后返回小写 `gsm`；同时存在大小写两项时只保留一个可见 GSM。
3. 字典 API 对 `network_type=GSM` 返回校验错误，对 `gsm` 成功；其他字典不受影响。
4. 首页 GSM 页签的 hourly、daily 请求均带 `technology=gsm`，后端 PM 聚合请求也包含 GSM
   过滤。
5. LTE、NR 页面、禁用字典项和既有周/日时序测试继续通过。

## Issue 归属

- #58：字典规范、历史数据迁移和输入防回归。
- #50：首页 GSM 页签、GSM 布局可见性与 GSM 范围 KPI 数据。

两个 Issue 可关联同一个 MR，但不得使用自动关闭语法；测试环境验收完成后再手工关闭。
