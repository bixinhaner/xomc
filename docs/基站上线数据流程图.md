# 基站上线全链路数据流程图

> 当 CPE（基站）首次上电、重启、或周期性心跳连接 OMC 系统时，系统内部触发的完整事件链路和数据流。
> 包含：基站上线开通、心跳保活与重同步、PM/KPI 采集入库、MML 批量命令执行、告警管理、固件升级、配置备份全链路。

## 4. 详细阶段拆解

### 阶段一：ACS 接收 Inform

```
┌──────────────────────────────────────────────────────────────────────┐
│ CPE → ACS (:7547)  HTTP POST  Content-Type: text/xml               │
│                                                                      │
│  SOAP Envelope                                                       │
│  ├─ Header: <cwmp:ID>50027</cwmp:ID>                                │
│  └─ Body: <cwmp:Inform>                                             │
│       ├─ DeviceId                                                    │
│       │   ├─ Manufacturer: "COMMON"                                  │
│       │   ├─ OUI: "48BF74"                                          │
│       │   ├─ ProductClass: "FAP/BU1810"                              │
│       │   └─ SerialNumber: "1202000588233HB0039"                     │
│       ├─ Event                                                       │
│       │   ├─ EventCode: "0 BOOTSTRAP"  ← 首次上电                    │
│       │   ├─ EventCode: "1 BOOT"       ← 重启                       │
│       │   └─ EventCode: "2 PERIODIC"   ← 周期性心跳                  │
│       ├─ CurrentTime: "2026-03-24T19:13:24"                          │
│       ├─ RetryCount: 0                                               │
│       └─ ParameterList (41-43 个参数)                                 │
│           ├─ Device.DeviceInfo.HardwareVersion                       │
│           ├─ Device.DeviceInfo.SoftwareVersion                       │
│           ├─ Device.ManagementServer.ConnectionRequestURL             │
│           ├─ Device.DeviceInfo.SerialNumber                          │
│           └─ ... (厂商私有参数 X_COM_*)                               │
└──────────────────────────────────────────────────────────────────────┘
                                │
                                ▼
                    ┌───────────────────────────┐
                    │  ACS handler 处理流程       │
                    │  (internal/acs/handler.go) │
                    │                           │
                    │  1. parseSOAPEnvelope      │
                    │  2. 速率限制检查(per-device) │
                    │  3. 清理同设备孤儿会话       │
                    │  4. 准入控制(slot分配)       │
                    │  5. 创建 Redis 会话         │
                    │     · SessionID (UUID)     │
                    │     · State: INFORM_RECEIVED│
                    │     · TTL: 5 分钟          │
                    │  6. 缓存 STUN + ConnReqURL │
                    │  7. 发送 InformResponse     │
                    │  8. publishInformEvents()  │
                    └───────────────────────────┘
```

**触发的事件**（根据 Inform 中的 EventCode 按优先级分发）：

| EventCode | 发布的 NATS 主题 | 说明 |
|-----------|-----------------|------|
| `0 BOOTSTRAP` | `device.inform.bootstrap` | 首次上电，触发设备注册+开通 |
| `1 BOOT` | `device.inform.bootstrap` | 重启，同样触发注册+开通 |
| `2 PERIODIC` | `device.inform.periodic` | 周期性心跳（见第 8 节详解） |
| `4 VALUE CHANGE` | `device.inform.value_change` | 参数值变化通知 |
| `6 CONNECTION REQUEST` | `device.inform.connection_request` | 响应网管侧连接请求 |
| `7 TRANSFER COMPLETE` | `device.inform.transfer_complete` | 文件传输完成 |
| `8 DIAGNOSTICS COMPLETE` | `device.inform.periodic` | 诊断完成（降级为 periodic） |
| Alarm 相关 | `device.inform.alarm` | 告警上报 |
| Reboot Complete | `device.inform.reboot_complete` | 重启完成 |

> **注意**：事件分发采用优先级匹配，BOOTSTRAP/BOOT 优先级最高。当 Inform 同时携带多个 EventCode 时，按代码中 switch-case 顺序取第一个匹配的主题发布。

> **关键说明：路径 D "任务失败"**
>
> 当设备无匹配模板、无数据模型、且所有 feature toggle 均关闭时，开通任务标记为 `Failed`。
> 此时设备状态停留在 `discovered`，**不会**自动通知设备上传模板。
> 需要运维人员手动操作：
> 1. 为该设备类型创建数据模型和配置模板
> 2. 通过管理界面手动触发重新开通
> 3. 或等待设备下次 BOOT/BOOTSTRAP 时自动重试

**Post-Session Wake 机制**：

当一次会话中命令数达到 `maxRPCPerSession` 上限但队列仍有剩余命令时：

1. 会话正常结束，释放 admission slot
2. 延迟 1s（等待 RPC 订阅者可能入队新命令）
3. 检查组合队列深度（TaskService + CommandQueue）
4. 如果队列非空，检查连续唤醒计数器（防无限循环）
   - Redis key: `acs:continuous_wake:{deviceSN}`
   - 上限可配，默认 200 次
   - 冷却期默认 5 分钟
5. 发送 Connection Request 唤醒设备（HTTP 或 UDP/STUN）
6. 设备发起新 Inform → 新会话 → 继续分发命令

## 8. 心跳消息（PERIODIC Inform）流程

> 周期性心跳是 CPE 按 `PeriodicInformInterval`（通常 60-300 秒）定时发送的 Inform，
> EventCode 为 `2 PERIODIC`。除了保活，心跳会话也是命令分发的重要通道。

### 8.2 心跳的命令分发作用

心跳会话的 Empty POST 阶段与 BOOTSTRAP 完全一致 — ACS 会检查命令队列并分发 RPC：

| 场景 | 心跳时的行为 |
|------|------------|
| 管理员手动下发配置 | 配置命令入队 → 下次心跳会话分发 SPV |
| 固件升级任务 | Download 命令入队 → 心跳会话分发 |
| 参数查询请求 | GPV 命令入队 → 心跳会话分发 |
| 告警清除指令 | 命令入队 → 心跳会话分发 |
| 队列为空 | 空响应，正常结束会话 |

### 8.3 OMC 升级/替换场景

当 OMC 系统升级或整体替换时，现有设备持续发送心跳 Inform。系统处理策略：

```
OMC 升级/替换后，设备发送 PERIODIC Inform
        │
        ▼
  handlePeriodic() 查找设备
        │
        ├─── 设备在新 OMC 中不存在（数据库为空/已迁移）
        │    │
        │    ▼
        │    RegisterFromInform()  ← 自动注册
        │    发布 device.registered
        │    │
        │    ▼
        │    ProvisioningEngine.HandleBootstrap()
        │    · 四路径路由（同首次 BOOTSTRAP）
        │    · 自动同步参数 / 下发配置
        │    ★ 设备无需重启即可被新 OMC 纳管
        │
        └─── 设备在新 OMC 中已存在（数据已迁移）
             │
             ▼
             UpdateFromInform()  ← 仅更新状态
             不触发开通流程
             （如需重新同步，管理员手动入队命令，
               下次心跳会话分发）
```

**关键设计要点**：

1. **零重启纳管**：设备无需感知 OMC 更换，PERIODIC Inform 中的自动注册机制确保新 OMC 能自动发现并纳管所有在线设备
2. **渐进式纳管**：每台设备按各自的心跳周期逐个被发现，10 万台设备在一个心跳周期（通常 5 分钟）内全部纳管
3. **命令管道**：即使没有触发开通流程，管理员也可随时通过管理界面入队命令，在下次心跳会话中执行
4. **限制**：PERIODIC 自动注册**不会**对已存在的设备重新触发开通流程，避免不必要的参数同步风暴

### 9.4 KPI 计算

```
┌────────────────────────────────────────────────────────────────────┐
│  KPI Engine (internal/pm/kpi/engine.go)                            │
│                                                                    │
│  启动时加载:                                                        │
│  · 按 carrier + technology 分组的所有 KPI 公式                      │
│  · 公式解析为 AST (internal/pm/kpi/formula.go)                     │
│  · 支持 +, -, *, / 运算符，递归下降解析器                            │
│                                                                    │
│  公式示例:                                                          │
│  · RRC连接建立成功率 = (rrc_setup_success / rrc_setup_attempt) * 100 │
│  · E-RAB建立成功率 = (erab_setup_success / erab_setup_attempt) * 100│
│                                                                    │
│  计算触发: PM 文件解析完成后，对每个 cellID 执行                      │
│                                                                    │
│  计算流程:                                                          │
│  1. 确定时间窗口: collectTime ± granularity (默认 15 分钟)          │
│  2. 查询计数器:                                                     │
│     counterRepo.QueryForKPI(deviceID, cellID, counterNames, window)│
│     → 返回 map[counterName]float64                                 │
│  3. 公式求值:                                                       │
│     formula.Evaluate(counterValues)                                │
│     · 缺少必需计数器 → 跳过该公式 (warn 日志)                       │
│     · 除零保护 → 返回 0                                             │
│  4. 批量写入:                                                       │
│     kpiRepo.BatchInsert() → kpi_values 表 (TimescaleDB hypertable) │
└────────────────────────────────────────────────────────────────────┘
```

### 9.7 PM 采集触发方式

设备上传 PM 文件有两种触发方式：

```
方式一: 设备自主上传 (AutonomousTransfer)
═══════════════════════════════════════════
  设备按内部配置的周期(通常15分钟)采集 PM 数据，
  自动上传到预配置的 ACS 文件服务器地址。

  CPE ──HTTP PUT──→ ACS /smallcell/FileUploadService
  CPE ──SOAP──→ ACS AutonomousTransferComplete


方式二: ACS 主动请求上传 (Upload RPC)
═══════════════════════════════════════════
  管理员或定时任务通过 ACS 下发 Upload RPC 命令，
  指示设备上传 PM 文件。

  1. 命令入队:
     管理面 → TaskService/CommandQueue → Upload 命令
     · FileType: "4" (PM)
     · URL: http://acs:7547/smallcell/FileUploadService?fileType=4&filename=...
     · 含 JWT Token 认证

  2. 命令分发:
     下次心跳/会话 → ACS Pop 命令 → 发送 Upload SOAP RPC

  3. 设备执行:
     CPE 收到 Upload → 上传文件到指定 URL → 发送 TransferComplete

  4. 处理:
     同方式一的后续流程 (MinIO → Worker → 解析 → 入库)
```

### 12.3 告警生命周期

```
  [新告警] ──→ active ──→ acknowledged ──→ cleared
                  │                              │
                  └──→ cleared (自动清除)         │
                                                  │
                                                  ▼
                                          归档到 alarms_history
                                          (TimescaleDB hypertable)
                                          + 删除 Redis 缓存
                                          + Prometheus 指标 -1
                                          + Publish alarm.cleared
```

| 操作 | 方法 | 状态变更 | 事件 |
|------|------|---------|------|
| 确认 | `Acknowledge()` | active → acknowledged | `alarm.acknowledged` |
| 清除 | `Clear()` | active/acknowledged → cleared | `alarm.cleared` |
| 自动清除 | `AutoClear()` | 按设备SN+告警码查找 → Clear() | `alarm.cleared` |
| 批量确认 | `BatchAcknowledge()` | SQL 批量更新 | — |
| 批量清除 | `BatchClear()` | SQL 批量更新 + 归档 | — |

### 13.2 升级任务状态机

```
  pending → downloading → rebooting → verifying → completed
    │           │             │            │
    │           │             │            └──→ failed
    │           │             └──→ suspended / terminated
    │           └──→ failed / suspended / terminated
    └──→ failed / terminated

  终态: completed, failed, terminated (不可逆转)
```

| 操作 | 方法 | 说明 |
|------|------|------|
| 暂停 | `PauseUpgrade()` | 保存当前状态到 ErrorMessage |
| 恢复 | `ResumeUpgrade()` | 从保存的状态恢复，发送 Connection Request |
| 终止 | `TerminateUpgrade()` | 转到 terminated |
| 批量升级 | `BatchUpgrade()` | 共享 batchID, 信号量控制并发 (默认5) |
