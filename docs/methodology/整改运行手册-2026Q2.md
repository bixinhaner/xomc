## 第 2 章 · 日常节奏（4 类仪式）

### 2.1 每天 — Daily Standup（5 分钟）

**时间**：每个工作日 09:00（或团队约定时间）
**地点**：线上/线下均可
**议程（每人 3 问，60 秒）**：
1. 昨天我推进了 W1.X 的什么？
2. 今天我打算推进什么？
3. 我有什么阻塞？

**每天必做的硬动作**：
- [ ] 09:00 站会
- [ ] 09:10 看 GitHub Actions 状态（昨晚 push 是否绿）
- [ ] 上午聚焦 1 个 W1.X 任务
- [ ] 下午写测试 / review / 文档
- [ ] 18:00 daily commit + push（**任务未完也要 commit + push**，避免单点丢失）

**每天禁止做的**：
- ❌ 同时进行 ≥ 2 个新 W1.X 任务
- ❌ 长时间不 commit（超过半天）
- ❌ 跳过 CI 红灯
- ❌ AI 写完不本地跑测试

### 2.2 每周 — Weekly Cadence

**周一 10:00 规划会（30 分钟）**
- 议程：
  1. 上周完成情况盘点（5 min）
  2. 本周每人挑 1-2 个 W1.X 子任务（10 min）
  3. 阻塞项清理（10 min）
  4. CI 状态 + 测试覆盖率回顾（5 min）
- 产出：本周每人的任务清单 + Owner

**周三 中途检查（15 分钟）**
- PgM 私聊每个 owner：进度如何？需要帮助吗？

**周五 16:00 finishing day + 复盘（60 分钟）**
- 16:00-17:00 finishing day：
  - 把本周 in-progress 推进到 done 或 staging
  - **禁止开新任务**
- 17:00-17:30 周五复盘：
  - 本周完成 vs 计划
  - 测试覆盖率变化
  - E2E 用例数变化
  - 风险登记更新
  - 下周重点

### 2.3 每两周 — Sprint 边界

**Sprint 开始日 09:00（30 分钟）**
- Backlog Triage：处理 Proposed → Triaged
- 选 Wave Block 中下一批任务进 Sprint
- Risk register 复盘

### 2.4 月度 — 健康度审计

每月最后一个周五 14:00（60 分钟）：
- CI 通过率统计
- 测试覆盖率轨迹
- E2E 用例数轨迹
- 整改路线图进度对比
- AI 协作有效性回顾（哪些 AI 写的 PR 出过问题？）

## 第 3 章 · 一个 W1.X 任务的完整生命周期

走 `/dev-pipeline` S0-S7 简化版：

| 阶段 | 时长 | 动作 | 输出 |
|------|------|------|------|
| **S0 出队** | 5 min | `/dev-pipeline pick W1.3` 或在 backlog 选下一个 | 任务卡进 in-progress |
| **S1 立项** | 30 min | 写 1 段验收标准（Given/When/Then）+ Verify 命令 | PR 草稿 description |
| **S2 设计** | 30 min - 2h | 读相关代码、列实现要点（不超过 5 条） | 实现纲要（写在 PR description） |
| **S3 实现** | 0.5d - 3d | 分批 commit（每批 < 200 LOC） | 代码 + 单元测试 |
| **S4 自测** | 30 min | 本地 `go build && go test` + curl 自测 | 测试输出贴 PR |
| **S5 PR + Review** | 30 min - 2h | 开 PR，至少 1 人 review，DoD 全勾 | merge 进 main |
| **S6 部署 staging** | 30 min | merge 后部署 staging，跑 E2E | E2E 通过截图 |
| **S7 收尾** | 15 min | `/commit` 关闭 backlog 任务、更新进度表 | Done |

**关键纪律**：
- 任务超过 1 周未进 S5 = 强制重新评估范围
- DoD 缺一项 = 不允许 S5（merge）
- E2E 缺断言 = 不允许 S6（部署）

## 第 4 章 · 与 AI（Claude）协作模式

### 4.1 该让 AI 做的事

✅ **代码实现**：明确范围、明确接口的 W1.X 子任务
✅ **测试用例**：单元测试、E2E 断言扩展
✅ **文档**：runbook、PR description、commit message
✅ **代码审查**：跑 `/review` 或 `/security-review`
✅ **重复性巡检**：跑 `/loop` 周期检查

### 4.2 不该让 AI 做的事

❌ **决定优先级**——这是 PgM 的工作
❌ **改架构方向**——架构专家+人讨论后再让 AI 实现
❌ **跨多任务大改**——一次一个 W1.X，超过 200 LOC 必须拆
❌ **绕过流程**——AI 也要走 PR + DoD + review
❌ **"顺便加一个"**——拒绝，记 backlog

### 4.3 AI 协作工作流

每次开 AI session 的标准三段式：

```
1. 给 AI 一个具体任务（含 W1.X 编号 + 验收标准）
2. AI 实现 → 本地跑测试 → commit
3. 你 review AI 的输出 + 对比 DoD 清单
```

**反模式**（看到立刻打断）：
- AI 说 "顺便我把 X 也改了" → 打断，要求只做指定任务
- AI 写了 500 行代码 → 打断，要求拆
- AI 跳过测试 → 打断，要求补
- AI 改了不相关文件 → 打断，git checkout 撤销

### 4.4 Slash Commands 使用清单

| 时机 | 命令 | 用途 |
|------|------|------|
| 出队任务 | `/dev-pipeline pick T-NNNN` | 走 S0-S7 流水线 |
| 提交前 | `/commit` | 智能审查 + commit |
| PR 前 | `/review` | 代码审查 |
| 涉及鉴权/输入/文件 | `/security-review` | 安全审查 |
| 切片上线前 | `/e2e` | E2E 验证 |
| 关键 PR / 发布前 | `/ultrareview` | 多 agent 云端审查 |
| 周期任务 | `/loop` | 周期巡检 |

## 第 5 章 · 决策协议（5 类高频决策）

### 5.1 CI 红灯

```
红 → 1. 看哪个 job 红
   → 2. 本地复现
   → 3. 修代码或测试（不修阈值、不加 // nolint:all）
   → 4. 24h 内出 fix PR
   → 5. 连续 3 次跳过 = 升级到团队复盘
```

### 5.2 任务卡住（3 次失败规则）

```
第 1 次失败 → 换思路
第 2 次失败 → 缩小范围
第 3 次失败 → STOP
   → 1. 记录失败情况
   → 2. 研究 2-3 个替代方案
   → 3. 求救（同事 + AI + 文档）
   → 4. 必要时降级或推迟
```

### 5.3 外部插队请求（客户/老板要新功能）

**统一回复模板**：
> "已记入 backlog（ID：T-NNNN）。当前处于整改期（2026-04-27 ~ 2026-08-03 W14），新功能统一在 GA 后处理。
> 若紧急 P0（数据丢失/完全宕机/安全漏洞），请说明业务影响并由 PgM 评估是否批准例外。"

**P0 例外严格定义**（满足任一即可）：
- 生产数据正在丢失或损坏
- 服务完全不可用 ≥ 30 分钟且无法恢复
- 已被利用的安全漏洞
- 监管/法律合规强制要求

不满足 = 排队，无例外。

### 5.4 测试覆盖率下降

CI 检测到 → 自动阻塞 merge

**解锁条件**（必须满足其一）：
- 在同 PR 内补足测试
- PR description 写明 "本 PR 仅删除/重构生产代码，不引入新逻辑"（PgM 复核）

### 5.5 冻结令例外申请

申请人 → PgM → 决策

PgM 决策标准：
- ✅ 满足 5.3 P0 严格定义
- ✅ 修复 W1.X 任务的阻塞依赖
- ❌ 其他全部驳回

批准的例外必须文档化在 `docs/project/backlog.md` FREEZE 块下方。

4. 不修 CI 阈值

### 情景 C · F04 webhook 写不出（W1.5 卡住）
1. 读 `internal/notification/` 现有结构
2. 读 `docs/expert-review-report-20260322.md` 了解约束
3. 模仿 `internal/transfer/` 等模块的 channel 模式
4. 单元测试用 `httptest.NewServer` 做 webhook 接收端
5. 仍卡住 → 求救（同事 + `/ultrareview`）

### 情景 D · NATS 改造遇阻（Block E 卡住）
1. 立刻回滚到 ChannelBus（不阻塞 Wave 3 其他 Block）
2. 写技术 spike 文档：哪里卡住、3 个备选方案
3. 重新规划，不让 Block E 拖死整个 Wave 3
4. 实在不行 → R-004 风险升级，Wave 4 处理

### 情景 E · 团队成员说 "冻结令我接受不了"
1. PgM 一对一沟通
2. 引用整改路线图第 1 章五大致命问题 + R-INT-01
3. 不接受 = 升级到决策层
4. **不让步**——铁律破一次后面就破 100 次

### 情景 F · 整改期间紧急 hotfix
1. 走 dev-pipeline 快速通道（hotfix lane）
2. fix → unit test → merge → deploy
3. 24h 内补 postmortem 到 `docs/operations/`
4. **不计入新功能**，但计入 hotfix 累计数（>3 次/周 = R-INT-02 升级）

### 情景 G · AI 写的代码看起来不对
1. 跑 `/review` 让 AI 自审
2. 在 staging 跑一遍真实流程
3. 仍不对 → git checkout 撤销，自己写
4. 记录到 `docs/operations/ai-postmortem.md`（哪些任务 AI 不擅长）
