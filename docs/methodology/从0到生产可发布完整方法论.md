# 从 0 到生产可发布：一份不留半拉子工程的完整方法论

> 这份文档是一份**反"半拉子工程"**的工程哲学+操作手册。
> 不是"敏捷介绍"，不是"DevOps 综述"，是给自己和团队一份**今天就能照着做**的可执行剧本。
> 适用：个人项目、小团队 SaaS、运营商级网管系统（如本仓库 OMC）通用。

---

## 第 0 章 · 先承认问题：为什么你的项目总是半拉子

绝大多数 AI 辅助开发的项目（也包括纯人手项目）烂尾在 70%-85% 完成度。死法可枚举：

| 死法 | 症状 | 根因 |
|------|------|------|
| **横向开发病** | "先把所有 API 写完再做前端 / 先把数据库设计完再写代码" | 把"层"当切片，导致没有任何一个功能闭环可用 |
| **永远在加新功能病** | 看板上 30 个 70% 完成的任务，0 个 100% | 没有"完成定义"，新功能比收尾爽 |
| **DoD 缺失病** | "做完了"没人能验收 | 完成 = 模糊的"我感觉差不多了" |
| **部署后置病** | 第 6 个月才第一次部署，撞墙 | 本地能跑 ≠ 生产能跑，越晚发现成本越高 |
| **可观测性后置病** | 出了问题靠 SSH + grep | 监控、日志、告警当作"将来再说" |
| **硬化后置病** | 认证、限流、备份"等功能稳定再加" | 永远不稳定，永远不加 |
| **Mock 永生病** | 第一周 mock 数据，第十周还是 mock 数据 | 真接口才暴露真问题，mock 是技术债 |
| **重构永远做不完病** | "等我把 X 重构完再加新功能" | 重构应与功能并行，不能阻塞交付 |
| **AI 加东西病** | AI 助手不停"顺便补一下"，scope 失控 | 没人按住"够了"按钮 |
| **文档幻觉病** | 文档写"功能 X 已支持"，实际跑不通 | 文档与代码漂移，没有自动验证机制 |

**核心洞察**：半拉子的反面不是"做得多"，而是**"每一步都能交付一个完整的、最小的、有用的东西"**。

## 第 1 章 · 五条铁律（贯穿始终）

下面五条不是建议，是不可让步的工程纪律。如果违反任何一条，工程会以可预测的方式失败。

### 铁律 1 · 垂直切片，不做水平开发
- ❌ 错：第 1 周建模、第 2 周写所有 CRUD、第 3 周写所有前端表单
- ✅ 对：第 1 周做"用户登录 + 看到自己名字"端到端跑通；第 2 周做"创建一个订单"端到端跑通

**判定标准**：每周结束时问自己——*"这周新增了一个用户能完整使用的功能吗？"* 如果答案是"半个"，立刻停下重新规划。

### 铁律 2 · 走路骨架（Walking Skeleton）日 1 上线
- 第 1 天：哪怕只有一个 `GET /hello → 返回时间戳 → 前端显示`，也要部署到**真正的云上**（Fly.io / Railway / 1 台 VPS 都行）
- 必须自动部署（CI/CD），不能手动 scp
- 必须有一条监控告警通到你手机

为什么：**部署痛苦是永远不会自动消失的，越早遇见越便宜**。第 6 个月才第一次部署，等同于把所有部署债务复利累加。

### 铁律 3 · 写 README 先于写代码
开新功能前，先写：
1. 这个功能解决了什么问题（一句话）
2. 用户怎么用（命令 / 截图 / 接口示例）
3. 验收标准（Given / When / Then）
4. 不做什么（明确边界）

写不出来 = 想不清楚 = 不要写代码。这是最有效的防止半拉子工具，因为**代码写一半没事，README 写一半你自己都受不了**。

### 铁律 4 · DoD 是合同，不是建议
DoD（Definition of Done）必须是**清单形式、可勾选、缺一不可**。最低 DoD：

- [ ] 编译/类型检查通过
- [ ] 单元测试覆盖成功 + 失败两条路径
- [ ] E2E 用例能跑通（用户可见功能）
- [ ] 部署到 staging 自测通过
- [ ] 日志 + 指标已加
- [ ] 回滚方案明确（怎么撤销这次变更）
- [ ] 文档已更新（README / API / runbook）
- [ ] PR 描述含 What / Why / How / Verify

**没勾完不算完成**。即使老板催、即使自己想偷懒。

### 铁律 5 · 完成 = 用户能用 + 生产有数据 + 文档齐全
"代码合入"不是完成。"功能上线"才是完成。
"功能上线"也不是完成。"用户在生产环境用过、监控有数据、文档新人能照着用"才是完成。

## 第 2 章 · 阶段化路线图（Phase 0 → Phase 5）

每个 Phase 都有**入口条件、产出物、退出条件**。不达退出条件不进下个 Phase。

### Phase 0 · 立项（1-3 天，不是 1-3 周）

**目的**：搞清楚要做什么、为什么做、什么算做完。

**核心动作**：
1. 写一份 **PRD v0**（一页纸够）：
   - 一句话价值主张（"帮 X 在 Y 场景下达到 Z"）
   - 真实用户画像（最好有 3 个真实姓名 + 3 个真实场景）
   - 验收标准（5-10 条 Given/When/Then）
   - 非目标（明确不做什么）
   - Kill criteria（什么情况下我会主动停掉这个项目？）
2. 写一份 **ADR-0001 技术选型**：
   - 语言/框架/DB/部署平台 各一句话理由
   - 至少列 1 个"考虑过但没选"的方案 + 不选理由
3. 建立 **backlog.md**（唯一任务清单），先列前 3 个垂直切片

**产出物**：
- `README.md`（含 v1 范围 + 不做什么）
- `docs/adr/0001-tech-stack.md`
- `docs/backlog.md`

**退出条件**：能用 30 秒向另一个人说清楚"我们做什么、给谁用、什么算 v1 上线"。说不清楚 = 不要进 Phase 1。

> 在 OMC 这种已有项目里，Phase 0 等价于"拿到一个新需求时先写 PRD"，对应 `docs/project/prd/`。

---

### Phase 1 · 走路骨架（3-7 天）

**目的**：建立**真实的、端到端的、自动的**交付管道。

**必须包含**：

| 项 | 最低标准 |
|----|---------|
| 仓库 | Git + main 分支保护 + PR review 流程 |
| CI | push → 自动跑测试 + 构建 docker 镜像 |
| CD | merge to main → 自动部署到 staging（最低）；手动一键部署到 prod |
| 部署目标 | **真实云环境**（Fly.io / Railway / Render / 一台 5 美元 VPS） |
| 端到端通路 | 一个 API + 一个前端页面 + 一个 DB 查询都跑通 |
| 健康检查 | `/health` 端点 + 上层探针 |
| 监控 | 至少一条告警："服务挂了 5 分钟" → 通到你手机 |
| Runbook | 哪怕只有 3 行："怎么看日志 / 怎么重启 / 怎么回滚" |

**典型一周时间分配**：
- Day 1-2：仓库 + CI + Hello World 部署到云
- Day 3-4：DB 接入 + 一个迁移 + 一个 CRUD 端点
- Day 5：前端骨架 + 调通这个端点
- Day 6：监控 + 告警 + runbook
- Day 7：演练一次"故意挂掉" → 收到告警 → 按 runbook 恢复

**退出条件**：你今天合入一行无害改动，10 分钟内会自动跑到 staging，30 分钟内你能把它推到 prod，并且如果它挂了，5 分钟内你会收到告警。

**为什么这一周不能省**：你以后**每一天**都在用这条管道，省下来的每一天都是后面的连本带利。

---

### Phase 2 · 第一个完整业务垂直切片（1-2 周）

**目的**：把走路骨架变成**有真实业务价值**的最小产品。

**选切片的标准**：
- 选最关键、最能验证假设的 1 个功能
- 不是"最容易"的，是"最重要"的
- 一个完整切片 = 用户能完成一个真实任务

**实施模板**（每个切片都按这个流程）：

```
S1 立项（半天）
  - 写 PRD（一页纸）
  - 拆任务到 backlog（3-7 个子任务）

S2 设计（半天）
  - 数据模型（哪些表 / 字段）
  - API 契约（OpenAPI / Proto）
  - 前端线框（手画或 Figma）

S3 后端实现（2-4 天）
  - 迁移 + Repository + Service + Handler
  - 单元测试（成功 + 失败）
  - 部署到 staging，curl 自测通过

S4 前端实现（1-3 天）
  - 类型定义（与后端契约一致）
  - 服务层（API 调用）
  - Hook + Store
  - 页面 + 组件
  - 在 staging 跑一遍真实流程

S5 E2E + 验收（半天）
  - 写 1-3 条 E2E 用例（关键路径）
  - 用户验收（哪怕用户就是你自己，也走一遍真实流程）

S6 上线（半天）
  - 部署到 prod
  - 监控数据正常 30 分钟
  - 文档更新（README + runbook）

S7 收尾（半天）
  - 关闭 backlog 任务
  - 写一条用户变更日志
  - postmortem（如果有任何意外）
```

**退出条件**：用户在生产环境完成了一次完整任务，监控有数据，文档可读。

> 这个流程对应本仓库的 `/dev-pipeline` skill 的 S0-S7 七阶段，已经成熟可用。

---

### Phase 3 · 切片迭代（每周 1-2 个，持续 N 周）

**目的**：在不打破已上线功能的前提下，持续交付新切片。

**核心原则**：
- **每个切片独立可发布**：合入即可上线，不依赖其他未完成切片
- **不做并行半成品**：A 切片 100% 完成上线后才开始 B 切片，不要同时做 3 个 70% 的
- **上一个切片有反馈数据再做下一个**：监控/用户反馈会改变下一个切片的优先级

**节奏建议**：
- 每周一规划（基于上周数据决定本周做哪个切片）
- 每周五回顾（上线了什么、学到了什么、下周改什么）
- 每两周一次 **finishing sprint**（专门收尾，禁止开新功能）

**警告信号**：
- backlog 里 "进行中" 任务超过 3 个 → 强制收尾
- 连续两周没有切片上线 → 检查是不是又开始横向开发了
- 出现"等 X 完成才能 Y"的依赖链 → 重新拆切片，让 Y 不依赖 X

---

### Phase 4 · 生产硬化（与 Phase 3 并行，但有专项预算）

**目的**：让系统从"功能能跑"到"生产能用"。

**关键认知**：硬化**不能等到所有功能做完再做**。每两周抽 1-2 天做硬化项，永不跳过。

**硬化清单**（按优先级排序，前几项必须 Phase 1-2 阶段就做）：

| 项 | 何时做 | 最低标准 |
|----|--------|---------|
| HTTPS / TLS | Phase 1 | Let's Encrypt 自动续期 |
| 认证 | Phase 2 | 哪怕只有 1 个用户，也用真 token |
| 输入校验 | 每个 API 一开始 | 边界值 + 类型 + 长度 |
| 结构化日志 | Phase 1 | 含 request_id，可关联 |
| 指标 | Phase 1 | 至少 RED（Rate / Errors / Duration） |
| 错误追踪 | Phase 2 | Sentry 或等价物 |
| 数据库备份 | Phase 1 | 自动 + **演练过恢复** |
| 限流 | Phase 3 | 每用户 + 全局两级 |
| RBAC | 多用户场景 Phase 2 | 至少 admin / user 两个角色 |
| 链路追踪 | Phase 3 | 跨服务可关联 |
| 安全扫描 | Phase 3 | gosec / npm audit / Trivy 进 CI |
| 性能基线 | Phase 3 | 关键路径 p95 + 压测脚本 |
| 容量规划 | Phase 3 | 知道当前能撑多少用户/QPS |
| 灾难恢复 | Phase 4 | RTO/RPO 定义 + 演练 |
| 合规审计 | 商用前 | 数据保留、日志审计、隐私 |

**判定标准**：每两周问自己——*"硬化清单上有几项是 ✅ 状态？"* 比例下降就是技术债在积累。

---

### Phase 5 · Beta → GA（发布与运营）

**目的**：从"功能完成"到"用户用得起、用得稳、付得起"。

**Soft launch（Beta）**：
- 邀请 5-20 个真实用户
- 提供专属支持渠道（微信群 / Slack / 邮件）
- 每天看监控、每天问反馈、每周回顾
- SLA 暂不承诺，但出问题 24h 内响应

**GA 前的 Release Gate**：

- [ ] 全部 P0 切片上线且稳定运行 ≥ 4 周
- [ ] 关键路径 E2E 用例 100% 通过
- [ ] 性能基线达标，无回退
- [ ] 安全扫描无 high/critical
- [ ] 备份恢复演练通过
- [ ] 监控告警 100% 覆盖关键指标
- [ ] runbook 完整（新人能照着处理 P0 故障）
- [ ] 用户文档完整（新用户能 30 分钟上手）
- [ ] 计费/合同/隐私政策（商业项目）
- [ ] 客户支持流程（工单 / SLA / 升级路径）
- [ ] 回滚预案 + 已演练
- [ ] 法律 / 合规审查通过（如适用）

**GA 后**：
- on-call 轮值（哪怕一个人，也要明确"现在是不是我的班"）
- 每月一次"火灾演习"（故意制造 staging 故障）
- 每季度一次容量评估
- 每年一次架构回顾

## 第 3 章 · 工具栈推荐（精简版，反工具大全）

> 原则：**用最少的工具能跑就用最少的**。每加一个工具就多一个学习成本、运维成本、故障源。

### 必备（任何严肃项目）

| 用途 | 推荐 | 理由 |
|------|------|------|
| 版本控制 | Git + GitHub | 不用 GitLab/Bitbucket 除非有强制要求 |
| CI/CD | GitHub Actions | 与仓库一体，免运维 |
| 容器 | Docker + docker-compose | 本地一致性 + 部署一致性 |
| 部署平台（小） | Fly.io / Railway / Render | 免 k8s 运维，几分钟上线 |
| 部署平台（大） | AWS / GCP + Terraform | 等真的需要时再用 |
| 数据库 | PostgreSQL | 默认选项，没强理由别换 |
| 缓存 | Redis | 同上 |
| 错误追踪 | Sentry | 免费额度足够个人项目 |
| 监控 | Grafana Cloud（免费层）/ Prometheus + Grafana 自建 | 看规模 |
| 日志 | Loki / 云厂商日志服务 | 别再 SSH grep 了 |
| 域名/DNS | Cloudflare | 免费 + CDN + DDoS 防护 |
| 密钥管理 | 1Password / Doppler | 比 .env 文件强 |

### 进阶（按需）

| 用途 | 推荐 | 何时引入 |
|------|------|---------|
| 消息队列 | NATS JetStream / Redis Streams | 真的有异步任务时 |
| 对象存储 | S3 / MinIO（自建） | 文件上传场景 |
| 时序数据库 | TimescaleDB（PG 扩展） | 监控/IoT/金融场景 |
| 搜索 | Meilisearch / Elasticsearch | 全文搜索需求时 |
| 任务调度 | 自建 cron + 数据库锁 | 比上 Airflow 简单百倍 |
| 链路追踪 | OpenTelemetry + Tempo / Honeycomb | 跨服务调试时 |

### 不要被诱惑

- ❌ 不需要 Kubernetes，直到你有 50+ 服务或 5+ 团队
- ❌ 不需要微服务，直到单体真的扛不住
- ❌ 不需要 GraphQL，除非 REST 真的不够用（90% 情况都够用）
- ❌ 不需要事件溯源 / CQRS，除非你做的是金融/审计系统
- ❌ 不需要服务网格（Istio/Linkerd）
- ❌ 不需要把自己的项目搞成"云原生 demo"

## 第 4 章 · Claude Code 工具链（本仓库已有 + 推荐增补）

### 已经在用，必须充分利用

| Skill | 用途 | 触发时机 |
|-------|------|---------|
| `/init` | 给新仓库生成 CLAUDE.md | 项目启动 |
| `/dev-pipeline` | 七阶段开发流水线 S0-S7 | **每个新功能强制走** |
| `/commit` | 智能审查 + 提交 | 每次提交 |
| `/review` | 代码审查 | 重要 PR 合入前 |
| `/security-review` | 安全审查 | 涉及鉴权 / 输入 / 文件操作的 PR |
| `/e2e` | E2E 验证 | 切片上线前 |
| `/loop` | 周期任务 | 监控、巡检、报表 |
| `/schedule` | 调度后台 agent | 灰度后清理、定期回顾 |
| `/ultrareview` | 多 agent 云端审查 | 关键 PR / 发布前 |

### 推荐补强

| 工具 | 价值 |
|------|------|
| **GitHub MCP** | 让 Claude 直接读 issue、写 PR 评论、看 CI 状态 |
| **WebFetch / WebSearch** | 查最新文档（避免引用过时 API） |
| **Memory（你已经在用）** | 跨会话保留偏好、术语、决策 |
| **数据库 MCP（只读）** | 让 Claude 直接查生产 schema，避免凭印象写 SQL |
| **Sentry MCP** | 让 Claude 直接看错误日志、关联代码 |

### 与 AI 协作的反半拉子守则

1. **永远先让 AI 写 PRD/README，再让它写代码**——它会暴露需求里的洞
2. **每个迭代结束强制跑测试**——别相信"应该没问题"
3. **拒绝 AI 的"顺便加一个"**——记到 backlog，**绝不当场加**
4. **用 TodoWrite 强制阶段化**——AI 容易跑飞，让它每完成一项打勾
5. **PR 合入前必跑 `/review` 或 `/ultrareview`**——别相信"我看着没问题"
6. **每个会话结束检查 DoD**——清单不全的不算结束
7. **AI 写的代码要去 staging 跑过再合入**——AI 不知道环境差异
8. **不要让 AI 一次写超过 200 行代码**——超过就拆任务

## 第 5 章 · 直接可抄的模板与清单

### 5.1 一页 PRD 模板

```markdown
# F0X-feature-name

## 一句话价值
帮 [谁] 在 [什么场景] 下 [完成什么]，比 [现有方案] 好 [几倍/为什么]。

## 用户故事
作为 [角色]，我要 [操作]，以便 [价值]。

## 验收标准
- Given [前置条件]，When [动作]，Then [期望结果]
- ...（5-10 条）

## 非目标（不做什么）
- ❌ ...
- ❌ ...

## 运营商差异（如适用）
- CMCC: ...
- CTCC: ...
- CUCC: ...

## 依赖
- 阻塞项：...
- 上游：...

## 度量
上线后看哪个指标证明成功？目标值？
```

### 5.2 一页 ADR 模板


## 第 6 章 · 反模式 × 救药对照表

| 反模式 | 救药 |
|--------|------|
| "等我把 X 重构完再加新功能" | 重构永远做不完。**并行做**：新功能在新代码里写，旧代码渐进重构。 |
| "这个先 mock 后面再接真接口" | **先接真接口最简实现**。mock 是债，债是要还利息的。 |
| "认证我们最后加" | **第二天就加 token**。哪怕硬编码一个 admin token，也比裸跑强。后面替换成真鉴权很容易；先裸跑后加鉴权要重写一半代码。 |
| "本地能跑就行" | **本地能跑 ≠ 生产能跑**。Phase 1 必须真部署。 |
| "测试以后补" | **以后永远不补**。测试与代码同 PR，没补的 PR 不合入。 |
| "等设计完了再写代码" | **边写边设计**，每次小步对齐。设计文档与代码同步演进。 |
| "这个 bug 先记着不影响主流程" | 记 1 个可以，记 10 个就是泥潭。每周一次"还债日"。 |
| "我们是创业公司，先跑起来再说质量" | **质量底线**（测试、监控、回滚、备份）不可让步；其他可以让步。 |
| "AI 写的代码看一眼应该没问题" | **必须跑过 + review**。AI 错得比你想的频繁，且错得很自信。 |
| "文档以后再写" | 写代码时就在 PR 里改文档。**一次合入两件事**比"以后专门写文档周"高效 10 倍。 |

## 第 7 章 · 给本仓库（OMC）的具体建议

OMC 项目已经具备绝大多数本方法论要求的设施：
- ✅ `/dev-pipeline` 七阶段流水线
- ✅ `docs/project/backlog.md` 唯一任务清单
- ✅ `docs/project/dod.md` 与 `release-gate.md`
- ✅ `docs/project/risk-register.md`
- ✅ E2E 脚本（226 断言）+ CPE 模拟器
- ✅ 三大运营商 Carrier 适配接口
- ✅ Prometheus 指标 + Zap 日志 + OTel 追踪
- ✅ 多专家 persona 自动激活

**容易踩坑的点**：

1. **PM/MR 等长链路功能容易横向开发**——表设计完 → 接收完 → 解析完 → 才开始想 UI。建议拆成"端到端解析 1 类型 + UI 看到结果"为切片，而不是按"接收/解析/UI"分阶段。
2. **Backlog 任务进行中超过 3 个**——观察 `docs/project/backlog.md` 的 in-progress 数，超 3 强制 finishing sprint。
3. **E2E 用例数月不增**——每个切片必须为它写至少一个 E2E 断言，进 CI。
4. **运营商差异通过 Carrier 接口**——任何 `if carrier == "cmcc"` 出现就是技术债，立刻重构。
5. **跨域基础设施（task / notification / transfer / events）改动**——必须激活架构专家审视，避免局部优化破坏全局一致性。

**强制流程**（建议写进 CLAUDE.md）：
- 任何新切片：必须先 PRD（`docs/project/prd/`）→ 进 backlog → 走 `/dev-pipeline`
- 任何 PR 合入：必须 DoD 全勾 + `/commit` + 关键 PR 走 `/review`
- 任何发布：必须 Release Gate 全勾 + 演练回滚

## 第 8 章 · 长期心法

最后留四句话给自己（也是写给所有半拉子工程的解药）：

1. **完成胜过完美**——80% 完成且上线，比 99% 完成放抽屉强 100 倍。
2. **每周交付一个真实价值**——没交付价值的一周，就是负价值的一周。
3. **痛苦越早遇见越便宜**——部署、监控、备份、合规，都是越拖越贵。
4. **做减法比做加法难十倍，但回报百倍**——能砍的功能/工具/抽象，全砍。
