# 开发方式 · 多任务批量 + 无人值守串行推进

> 性质：开发方法论母本（新增）。**不入 git**，放 notes。
> 一句话：有**一批互不相关的独立任务**（多个 bug / 小改）时，让一个总调度**无人值守逐单串行**推进——每单内部由**开发 / 检查 / 运行栈** 三 agent 回合接力（死判+自判+对抗检查），每单**独立分支 + 独立提交 + 独立 PR**，**失败即跳过继续**（不连累整批），支持**软出口**（已修不改 / 需人工决策）；全部跑完回主会话做**收口自核**。
> 配套脚本（可运行）：`~/Documents/notes/workflows/batch-task-loop.workflow.js`
> **姊妹母本**：`知识库/开发方式-三agent回合制-无人值守多阶段.md`（旧）—— 用于**一个功能的多个相互依赖阶段**。本法用于**多个不相关任务**。两者内循环一致，外壳相反（见 §2）。
> **触发**：我说「**按多任务批量串行推进这几单**」/「**batch 串行跑 #A #B #C**」，或把本文递给你 → 按本法执行。

---

## 1. 何时用 / 何时不用

**适合**：**一批互相独立**的任务——多个不相关的 bug 修复 / 小增强，每个范围清晰、根因偏明确、能用命令自证（单测死判）或运行栈取证（自判留证）。典型：从 issue 列表挑出的一批就绪单，逐个清掉。

**不适合**：
- 多个**相互依赖**的阶段（后阶段建立在前阶段上）——用**旧母本**（三 agent 多阶段），它的"账本传上下文 + 失败即停 + 合成提交"才对。
- 还没锁根因 / 还要设计的单（先 brainstorming / grill / triage，别丢进无人值守）。
- 单行 hotfix / 纯探查（直接做）。
- **首次或大改脚本后**：先拿**一个最干净的单**小规模试跑，跑顺再放全批。

**判别口诀**：这些任务**谁也不依赖谁** → 本法；它们是**一个功能拆出来的连续步骤** → 旧法。

---

## 2. 与旧母本（三 agent 多阶段）的对照

| 维度 | 旧：多阶段（依赖） | 新：多任务批量（独立） |
|------|------------------|---------------------|
| 任务关系 | 后阶段依赖前阶段 | 互相独立，无跨任务依赖 |
| 账本 | 跨阶段传上下文（后阶段要读前阶段） | 每单自成一体，账本只在单内 开发↔检查↔运行栈 传话 |
| 失败处理 | **整条停**（烂地基不往上盖），留现场 | **标记后跳过、继续下一单**（一单不连累整批） |
| 收口提交 | 末尾 `git reset --soft` **合成一个**功能提交、一个分支 | **每单一分支一提交一 PR**，互不相干 |
| push | 不推，等人工 | **允许 push 开 PR**（由 args.push 控制，默认 true） |
| 软出口 | 无 | 有：done-no-change / needs-input（见 §5） |
| 内循环 | 开发→检查→运行栈→存档点 | **完全一致**（存档点并入收尾交付 agent） |

**复用边界**：每单内部那套 开发→检查→运行栈 + 死判/自判 + 对抗式检查 + 账本，与旧法逐字一致，是经首跑验证的精华，原样搬。**只有外壳变了**：依赖串行→独立串行、失败即停→失败即跳、合成提交→每单 PR。

---

## 3. 整体形状：多任务串行 + 单内三 agent 回合 + 两头 git agent

总调度读 `tasks` 数组**按顺序串行**走，每单走五步：

```
任务 N（issue #X）：
  ① 分支 agent     从干净 main 切出 <type>/X-slug（核工作树干净，不被上一单带脏）
  ②..④ 回合 1..maxRounds（默认 4）：
       ② 开发 agent    读账本+spec → 实现/修 → 自跑 build/test → 写账本
                       （若开了 gate，可提"软出口"：判这单不该硬改 → kind=done-no-change/needs-input）
       ③ 检查 agent    对抗复核 build/test + 核 spec 符合性 + 反推风险
                       （若开发提了软出口 → 对抗式核实证据，confirmed 才认；驳回则退回正常修复）
            ├ 软出口确认 → 跳出，进 ⑤ 走对应收尾
            ├ verdict=fail → 下一回合
            └ pass ↓
       ④ 运行栈 agent  needsDeploy=true：部署→取证；false：只跑相关单测取死判值
            脚本死判：全部 hardChecks 实测==预期 且 全部 softChecks 判 pass
            ├ fail → 下一回合
            └ pass → 跳出（innerOutcome=passed）
  ⑤ 收尾交付 agent  按内循环结局分流（见 §4）→ 回干净 main → 下一单
  到 maxRounds 仍未过 → 标 blocked、留半成品分支、跳过 → 下一单
全部跑完 → 收口汇总（✅PR / 🟰无需改动 / ✋待人工 / ⛔阻塞）→ 交主会话自核
```

关键设计：
- **检查 gate 住运行栈**：build/test/符合性没过不白部署（同旧法）。
- **两头 git 由 agent 做**：脚本是 JS 沙箱跑不了 git，开分支（①）和提交+PR（⑤）交给能跑 Bash 的 agent。
- **运行环境独占靠串行天然满足**：本法只串行，不存在两单抢同一套 docker 栈/端口的问题（这正是旧法 §7 拒绝并发的根因，本法不碰）。

---

## 4. 单的四种结局（收尾交付 agent 分流）

| 内循环结局 | 收尾动作 | outcome |
|-----------|---------|--------|
| **passed**（三环节全过）| 规范提交（footer `Closes #X`）→ push → `gh pr create` → 回干净 main | `pr-opened` |
| **soft-done-no-change**（开发判已修/不复现 + 检查核实）| 留 issue 评论贴证据建议关单（**不自己关**）；有零星改动才提交，无改动不造提交 → 回 main | `closed-no-change` |
| **soft-needs-input**（遇只有人能定的设计取舍）| 能干完的部分提交到分支 + issue 贴方案选项请人定夺 → 回 main | `left-for-human` |
| **failed**（maxRounds 仍没过）| 半成品提交到分支保命（不丢码）+ issue 留卡点 → 回 main | `blocked` |

四种都**回干净 main 再进下一单**——这是不污染下一单的命门（§7）。

---

## 5. 软出口（本法独有，把"条件式闸门"收编成机制）

无人值守不等于"必须改出代码"。有些单的正确产出不是 diff：

- **diagnose-first**（gate）：先复现再决定。**确实复现**→正常修；**复现不了/已被它单修掉**→开发填 `softExit.kind='done-no-change'` + 复现命令真实输出作证。检查 agent 会**自己再复现一次**核实，confirmed 才认（防开发偷懒报"已修"）。典型：#205 强制退出（可能已被相邻单顺带修）。
- **design-decision**（gate）：遇到只有人能拍板的取舍（多实现各有利弊、涉及数据库迁移口径），不替用户擅自定。能干的先干完，把取舍点填 `softExit.kind='needs-input'` + 2-3 个方案选项。典型：#189 子问题②（"同步别覆盖手改"怎么标记）。

不开 gate 的单（缺省）没有软出口——要么修通过、要么 blocked。**软出口都要过检查 agent 对抗核实**，开发单方面说了不算。

---

## 6. 死判 + 自判（同旧法，本法核心验收）

- **死判项 `hardChecks`**：每条带业务描述 + **预期值**。运行栈 agent 只回**实测值 + 原始证据**，脚本代码做 `实测==预期`，agent 不下结论 → 不破"判断留主线"铁律（把肉眼比对换成代码比对）。
  - 纯单测单（needsDeploy=false）：死判值来自 `go test -run <用例> -v` 的 PASS/FAIL 或断言真实数值，**不部署**。
  - 起栈单（needsDeploy=true）：死判值来自部署后查库/接口/DOM 实测。
- **自判项 `softChecks`**：机器没法数的视觉/交互项，agent 判 pass/fail 但**强制配真实原始证据**（DOM 真实文字 / 接口真实 JSON），编不出过不了 schema。
- **写验收纪律**：能转死判的尽量写死判。"退出码=0""用例 PASS""库里 count=1"这类本就该是 hardCheck；softChecks 只留真正数不出来的视觉项。

---

## 7. 不污染下一单（独占工作树，由串行 + 回干净 main 保证）

本法默认**调度独占当前 git 工作树 + 那套唯一 dev 运行环境**，靠两条保证不串味：
1. **每单从干净 main 切新分支**：分支 agent 开工先核 `git status --porcelain` 为空；非空说明上一单收尾没干净 → 报告并 `git switch main`（不 stash 不丢码）。
2. **每单收尾必回干净 main**：四种结局的收尾 agent 都以 `git switch main` + 工作树干净（backToMainClean=true）收尾。下一单分支 agent 再核一次兜底。

**用户人工保证**：执行期间同一时间只有一个会话在改这棵树 / 用这套环境（同旧法 §7，2026-06-05 拍板）。

---

## 8. 部署护栏（needsDeploy=true 的单，写死进运行栈 agent prompt）

运行栈 agent 是空白上下文，**读不到个人记忆**，prompt 显式写死（同旧法 §6）：
- 部署**只跑** `bash /Users/shangyingbin/project/omc-docker/docker-run.sh`。
- **绝不碰** `goomc/deployments/docker`（碰错会删运行栈网络致全栈断网）。
- 部署后验证 `docker compose ps`（omc-docker 目录）+ `curl healthz`（:8081 / :7557）。
- 端到端走前端 :3000 + playwright（admin/admin123）；明文 curl 登录被禁、内部 X-API-Key 对受限接口无权。
- 纯单测单（needsDeploy=false）：**不起 docker、不碰部署目录**，只跑相关测试取死判值。

---

## 9. 三处 git 分工（脚本跑不了 git）

1. **开分支（① 分支 agent）**：每单从干净 main 切 `<type>/X-slug`。
2. **提交+PR（⑤ 收尾交付 agent）**：按结局提交（规范 message + `Closes #X`）、push、`gh pr create`；blocked/部分完成则提半成品保命。
3. **回退锚点**：每单各自从 main 切，main 本身即基线；无需旧法的合成提交/全局 reset。

**铁律**（写进 agent prompt）：绝不 `--force`、绝不 `--no-verify`、绝不直接动 main（只在单的 feature 分支提交）。

---

## 10. 失败即跳 + 留现场（与旧法相反）

一单到 maxRounds 仍没过 → **不停整批**：半成品提交到该单分支（不丢码）+ issue 留卡点 + 回干净 main + 标 `blocked` + **继续下一单**。批量结束汇总里列出 blocked 单供人工接手。
> 这是与旧法最大的语义差：旧法依赖阶段，一阶段塌了往下全是烂地基所以整条停；本法各单独立，一单塌了不该连累其它单。

---

## 11. 主会话收口自核（全批跑完，主会话亲自做）

流水线 return 后，主会话**亲自**（不下放）：
1. **抽样重跑** build/test/typecheck（别全信 agent 报喜）。
2. **校迁移版本号连续**（若有单动了迁移）。
3. **抽验关键自判项证据**（图有没有画、内容对不对，亲自看一眼）。
4. **按"UI 打到最终呈现层"过一眼**要起栈单的最终呈现。
5. 确认无误 → 通知用户人工验收：✅PR 待 review、🟰无需改动单待确认关、✋待人工单需决策、⛔阻塞单需接手。

## 12. 输入结构 + 怎么调用

```js
Workflow({
  scriptPath: '/Users/shangyingbin/Documents/notes/workflows/batch-task-loop.workflow.js',
  args: {
    batchId, title,
    repoRoot,        // 仓库根（git 操作目录），缺省 /Users/shangyingbin/project/goomc
    ledgerPath,      // 账本绝对路径，放 ~/Documents/notes/tmp/
    maxRounds,       // 每单回合上限，默认 4
    push,            // 是否 push 开 PR，默认 true
    deployCmd,       // 默认 omc-docker/docker-run.sh
    tasks: [
      {
        id,            // 展示用 '#191'
        issue,         // 191（gh comment / Closes 用）
        name, branchType, slug,     // 分支 <branchType>/<issue>-<slug>
        specDocs:[...], scope,
        workdir,       // 该单 build/test 目录，缺省 repoRoot
        buildCmd, testCmd,
        hardChecks:[{id,desc,expected}],
        softChecks:[{id,desc}],
        runSegments,
        needsDeploy,   // true 起栈 / false 纯单测，缺省 false
        gate,          // 'diagnose-first' / 'design-decision'（可选软出口）
      },
      // ...
    ],
  },
})
```

**调用前主会话两件事**：① `mkdir -p` 账本目录（脚本不碰文件系统，账本由 agent 写）；② 确认无其他会话在改这棵树（§7）。无需取 startHead（每单各自从 main 切）。

## 14. 一句话

旧法管"一条多阶段实施计划无人值守跑完"，本法管"一批不相关任务无人值守逐单清掉"——内循环同一套较真机制，外壳从"依赖+合成+失败停"翻成"独立+各 PR+失败跳"，再加"软出口"接住"不该硬改代码"的单。
