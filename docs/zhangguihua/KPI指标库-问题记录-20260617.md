## 🟢 修复记录（2026-06-18）

**根因已定位为误删，并已恢复**：分组树原在 seed（`b0d65afc` 功能集树治理灌入），2026-06-08 `dd991a44`「init_seed 拆分纯部署 baseline，字典走 XML」时按"字典走 XML"的理由删了三张表的种子——但 XML 只携带 groupId 引用、不含组定义，dictloader 启动只插 1 个 `default`，导致分组丢失。

经全量比对，被删种子的 45 个组 id 与当前 XML/指标引用的 group_id **一一对齐**（同源 seed/000027）。已新增迁移 `omcgo/migrations/seed/000002_restore_indicator_groups.sql` 按原样恢复 22+8+15=45 节点（幂等 `ON CONFLICT DO NOTHING`，不动 XML、不动指标）。

**浏览器复测结果**：
- 问题 1（裸 hash）→ ✅ 已解决：分组列显示 PDCP/ERAB/HO/RRU/MAC… 真名，裸 hex 残留 0。
- 问题 3（筛选下拉空）→ ✅ 已解决：「按分组筛选」下拉填充 22 个功能集。
- 问题 2（chip 溢出盖级别列）→ ✅ 实质消失（真名短，不再溢出）；仍建议补 `ellipsis` 兜底防超长自定义组名。
- DB 侧 JOIN：enb 指标 group_name 解析率 100%（unresolved=0）。

> 注：该迁移对全新库 goose 顺序应用 1→2；本地已被 baseline stamp 到 seed v4 的存量 dev 库，已直接幂等应用同一 SQL 生效。

## 一、根因综述（贯穿多个表象问题）

KPI 指标的「分组（功能集）」数据存在**设计断层**：

- XML 字典（`omcgo/data/indicator-library/*.xml`）里每条指标只带 `groupId` 引用（32 位无横杠 hex），**不含分组名定义**。
- 启动期 Loader 只建 1 条 `default` 占位组（`loader.go:325` `ensureDefaultGroups`），**从不把 XML 的 groupId 物化为命名分组**（`service.go:438-441` #134 注释明确坐实）；seed 文件里 `indicator_group_*` 段为空。
- 运行库实测：`indicator_group_enb` 仅 1 行（`default`），而 `perf_indicators_enb` 引用了 **20** 个不同 group_id；全三制式合计 **41** 个组（enb 20 / gnb 14 / gsm 7）**全部无名**。
- 列表查询 `LEFT JOIN indicator_group_* ON g.id = i.group_id` 几乎全部 JOIN 不到 → `group_name` 为空 → 前端 `groupName || groupId` 回退**裸 hash**。
- 雪上加霜：UI 建组用 `uuid.New().String()`（**带横杠**），XML 是**不带横杠** hex，两套 id 空间永不相等，靠 UI 建组也对不回 XML 指标。

> 详细数据链与 41 组清单见此前分析（可另附）。下列「分组」相关问题（#1/#2/#3/#5）均源于此根因。

## 二、问题清单（按严重度）

### 🔴 P0 / 高严重度

#### 问题 1：「分组」列把 32 位裸 hash 直接展示给用户
- **现象**：BLQ 详情页一屏 50 行，分组列全是紫色 chip 显示 `f4e7edd6102544ca99c864798ec6328d` 之类 hash，本页出现 11 种 hash，零可读性。点进单条**指标详情抽屉**（截图 T6），分组字段同样是裸 hash。
- **证据**：截图 `T2-detail.png` / `T6-edit-modal.png` / `09-groupcell.png`；前端 [IndicatorsByTech.tsx:77-80](../../omcmb/webcode/src/pages/product/kpi-library/IndicatorsByTech.tsx#L77-L80)、[IndicatorDrawer.tsx:141](../../omcmb/webcode/src/pages/product/kpi-library/IndicatorDrawer.tsx#L141)
- **根因**：见第一节。
- **影响**：用户无法理解指标归类，专业网管系统观感差。

#### 问题 2：「分组」chip 溢出列宽 100px，覆盖「级别」列
- **现象**：chip 不截断，横穿进相邻「级别」列，`device` 文字直接压在 hash 上。
- **证据**：几何实测 chip 右边缘 1361px > 「级别」列左边缘 1261px，溢出 100px；截图 `11-cols-clean.png`（无下拉遮挡也复现）。
- **根因**：分组 chip 未设 `max-width` / `ellipsis`，长文本不收口。**即使分组名正常，长名也会错位。**
- **影响**：表格渲染错位，多列文字重叠。

#### 问题 3：「按分组筛选」下拉为空（暂无数据），但列里满是分组
- **现象**：详情页工具栏有「按分组筛选」下拉，点开是「暂无数据」。用户看得见一堆分组却一个都筛不了，筛选器形同虚设。
- **证据**：截图 `T3-groupfilter.png` / `10-groupdropdown.png`；后端 [pg_group_repository.go:45-66](../../omcgo/internal/pm/indicator/pg_group_repository.go#L45-L66) `ListByPlatform`。
- **根因**：下拉走 `ListByPlatform`，按平台 JOIN `indicator_group_*`（只有 default）→ 对 BLQ 返回 0 项。
- **影响**：核心过滤维度不可用。

### 🟡 P1 / 中严重度

#### 问题 4：三皮肤业务深度严重不对等（违反三皮肤铁律）
- **现象**：v2(shadcn) / v3(HUD) 的 KPI 库是**只读阉割版**，缺：删除/编辑指标、公式 CRUD、分组筛选、导入/管理 XML、新建/删除分组；且 v2/v3 大量**硬编码中文未走 i18n**。裸 hash 问题三皮肤都有。
- **证据**：代码审计 `webcode-v2/src/pages/product/KpiIndicators.tsx`、`webcode-v3/src/pages/kpi-library/index.tsx`。
- **影响**：违反 CLAUDE.md §8.3「前端三皮肤铁律」。

#### 问题 5：搜索结果触顶被分页截断，无提示
- **现象**：详情页搜 `DRB` 返回 50 条，正好等于 page_size 上限；结果其实更多但被截断，用户以为只有 50 条。
- **证据**：截图 `T4-search-DRB.png`；API 实测 page_size 上限行为。
- **影响**：误导用户，以为搜全了。

#### 问题 6：一级列表缺排序与制式筛选
- **现象**：平台指标数差异极大（ALL 68 / BLQ 1094 / MLN 1162），但无排序、无按制式（ENB/GNB/GSM）筛选，找平台只能靠搜索。
- **影响**：大数据量下定位平台效率低。
