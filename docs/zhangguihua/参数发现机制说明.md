## 一、基站接入后如何记录支持的参数

### 流程概述

基站接入后，系统通过 TR-069 Upload RPC 让基站主动上报自己的参数列表，再与系统预置的标准模型取交集，将结果持久化到数据库。

### 完整步骤

**第一步：系统主动下发上传指令**

基站与 ACS 建立会话后，系统通过 TR-069 下发 `Upload` RPC（`FileType=11`），要求基站把本地的参数模型 XML 压缩包推送到指定 URL。

**第二步：基站上传，ACS 存档并通知**

基站将 XML 文件 HTTP 上传到 ACS；ACS 将文件存入 MinIO 对象存储（bucket: `omc-exchange`，路径前缀: `datamodel/`），然后发布内部事件 `datamodel.file.received`，携带设备 SN、MinIO 路径等信息。

**第三步：App 服务处理事件（核心逻辑）**

App 服务的 `ProvisioningEngine` 订阅该事件，由 `ModelUploadService.HandleModelFileReceived` 处理：

1. 从 MinIO 下载 XML，解析出基站上报的全部私有参数路径（`[]CPEEntry`）
2. 根据设备 `ProductClass` + `FirmwareVersion` 找到对应产品（详见第三节）
3. 调用 `IntersectService.IntersectCPEModel` 执行交集计算：
   - 取出该产品的全量默认参数映射（`param_mappings` 表）
   - 与基站上报参数取交集（以 `privatePath` 为键匹配）
   - 不在交集内的条目（基站有但标准模型没有）直接丢弃
   - 不在基站上报中的条目（标准模型有但基站没有）保留默认，不写 discovered
4. 交集结果写入 `discovered_param_mappings` 表（以 `product_id + software_version` 为键，先 DELETE 再 INSERT，单事务）
5. 失效该 `(product_id, software_version)` 对应的 Redis 缓存

**第四步：记录发现日志**

全程在 `parameter_discovery_log` 表里维护一条状态记录，从 `discovering` → `completed` 或 `failed`。

### discovered_param_mappings 表的意义

这张表是"该产品型号 + 该固件版本的设备，实际支持哪些参数"的运行时台账：
- 以 `product_id + software_version` 为联合键，同一产品不同固件版本单独维护
- 后续所有参数读写（标准路径 ↔ 私有路径翻译）优先查此表

## 二、基站不支持 FileType=11 时的处理

有三种"不支持"情况：

### 情况一：产品级别关闭（`enable_filetype11=false`）

`products.xml` 中该产品配置了 `<enableFileType11>false</enableFileType11>`，系统**压根不下发**上传指令，直接将发现日志标为 `completed（reason: skipped）`，跳过整个 XML 上传流程。

### 情况二：指令下发但基站返回错误

基站不认识或不支持该指令，返回 SOAP Fault 或 TransferComplete Fault。系统调用 `HandleUploadFailed`，将发现日志标为 `completed（reason: used_default: xxx）`，不做任何参数写入。

### 情况三（两种情况的统一结果）：discovered 表无记录时的自动降级

无论是 skip 还是 failed，`discovered_param_mappings` 里都没有该设备的条目。后续 `ParamRegistry.GetByProduct` 查询时：

```
查 discovered（L1缓存 → Redis → DB）→ 空 → 自动降级 → 查默认模型（param_mappings）
```

对上层完全透明，只是翻译精度略低（基站实际不存在的参数，系统仍会尝试读写）。

## 三、如何找到默认模型

### 数据来源

`data/param-mappings/` 目录下有一批 XML 文件，每个文件对应一种基站型号的参数列表：

```
BLQ.xml       MLQ.xml       MLN.xml       BM.xml
BaiBNQ.xml    ENB_DEFAULT_098.xml         ENB_DEFAULT_181.xml  ...
```

系统启动时，`parammodel.Loader` 扫描该目录，将每个 XML 全量写入 `param_models`（模型定义）和 `param_mappings`（参数明细）两张表。

### 运行时查找——三步链路

**第一步：基站报 ProductClass**  
基站每次 Inform 都携带 `ProductClass` 字段（如 `FAP/BS31SC/SC`），这是基站的"型号指纹"。

**第二步：正则匹配找产品**  
`products.xml` 定义了"正则 → 产品"的路由表（按 `sort_order` 优先级排序），`ProductRegistry` 加载后缓存为编译好的正则列表，用基站上报的 `ProductClass` 挨条匹配，命中第一条即确定产品。

示例（`products.xml` 片段）：
```xml
<product name="QRTB 系列">
  <paramModel>BLQ</paramModel>
  <enableFileType11>true</enableFileType11>
  <patterns>
    <pattern globalOrder="12">FAP/\w+(BS31)\w+/SC</pattern>
  </patterns>
</product>
```

**第三步：产品 → 参数模型**  
产品配置里的 `<paramModel>BLQ</paramModel>` 指向模型名称，系统通过 `param_model_id` 去 `param_mappings` 表取 BLQ.xml 那批参数——这就是该基站的默认模型。

### 特殊情况：孤儿设备

若基站的 `ProductClass` 不匹配任何正则，`ProductRegistry` 返回 `ErrOrphan`，设备被标为"孤儿"，需运维人员在管理界面手动补充正则路由规则后才能正常处理。

```
基站 Inform（携带 ProductClass + FirmwareVersion）
       │
       ▼
ProductRegistry.MatchProductClass
（正则匹配 product_class_patterns）
       │
       ▼
找到 Product → ParamModelID
       │
  ┌────┴────────────────────────────┐
  │ enable_filetype11=true          │ enable_filetype11=false
  ▼                                 ▼
下发 Upload(FileType=11)          直接用默认模型（param_mappings）
  │
  ▼
基站上传 XML → MinIO
  │
  ▼
IntersectService.IntersectCPEModel
（CPE上报参数 ∩ 默认模型）
  │
  ▼
写入 discovered_param_mappings
（product_id + software_version 索引）
  │
  ▼
后续翻译：discovered 优先，无记录时降级 default
```

## 五、缓存设计

整套机制涉及两个独立的 Registry，各自维护三层缓存（L1 进程内 + L2 Redis + DB）。

### 5.1 ParamModel Registry（参数映射缓存）

**L1 — 进程内 `sync.Map`**

| 字段 | 键 | 缓存内容 |
|---|---|---|
| `defaultByModel` | `paramModelID` | 默认参数映射全量（对应某个 XML 文件的全部条目）|
| `discoveredByDevice` | `(productID, swVersion)` | 交集计算后的发现映射 |
| `cacheVersion` | atomic 整数 | 本进程已采纳的 L2 版本号快照 |

**L2 — Redis**

| Key 模式 | 内容 | TTL |
|---|---|---|
| `param:model:default:{paramModelID}` | 默认映射 JSON | 24h |
| `param:model:discovered:{productID}:{swVersion}` | 发现映射 JSON | 24h |
| 版本号 key | 整数，BumpVersion 自增 | 永久 |

**失效时机**：
- `IntersectService` 写完 `discovered_param_mappings` 后立即调 `InvalidateProduct`：先删 L1 的 `discoveredByDevice` 条目，再 DEL Redis key
- 管理员重导入 XML 后 `BumpVersion` 推进版本号，其他进程热路径 `ensureFresh` 检测到版本变化，丢弃全量 L1

---

### 5.2 Product Registry（产品路由缓存）

**L1 — 进程内**

| 字段 | 结构 | 缓存内容 |
|---|---|---|
| `patterns` | `atomic.Pointer<[]compiledPattern>` | 全量正则快照（整体替换，**零锁**，热路径无竞争）|
| `productByID` | `sync.Map` | 产品详情（`UUID → *Product`）|
| `productClassL1` | `sync.Map` | ProductClass 字面量 → 路由结果 |

**L2 — Redis**

| Key 模式 | 内容 | TTL |
|---|---|---|
| `product:id:{uuid}` | 产品详情 JSON（内嵌版本号） | 24h |
| `product:class:{productClass}` | ProductClass 路由结果 | 命中 **1h**，孤儿 **5min** |
| 版本号 key | 整数 | 永久 |

孤儿 TTL 故意比命中短（5min vs 1h）——新增一条正则规则后，原孤儿设备最坏等 5 分钟就能被正确路由，不需要手动失效。

**失效时机**：
- 管理 API 修改产品/规则 → `BumpVersion` → 其他进程 `ensureFresh` 发现版本前进，drop 全量 L1 重建
- `patterns` 不按条目失效，每次 Refresh 原子替换整个 slice

---

### 5.3 跨进程一致性（BumpVersion 协议）

两套 Registry 用同一套协议：写操作完成后在 Redis 原子递增全局版本号，每个进程的热路径（每次查询前都会调 `ensureFresh`）对比本地 `cacheVersion` 与 Redis 版本号，版本号前进就丢弃 L1，使 ACS 进程和 App 进程各自的本地缓存都能感知到对方的写变更。

```
写操作（任意进程）
       │
       ▼
BumpVersion（Redis INCR）
       │
       ▼  （下次热路径调用）
其他进程 ensureFresh：本地版本 ≠ Redis版本
       │
       ▼
drop 全量 L1 → read-through DB/L2 重建
```
