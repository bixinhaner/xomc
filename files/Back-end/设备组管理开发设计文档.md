## 一、需求概述

### 1.1 功能需求

| 编号 | 需求 | 说明 |
|------|------|------|
| R1 | 两级树状结构 | 设备组分为一级设备组和二级设备组 |
| R2 | 默认设备组 | 系统内置 Default Level Group / Default Level Group，不可修改删除 |
| R3 | 新增设备组 | 创建一级设备组时可选择同时创建二级子组和分配设备 |
| R4 | 修改名称 | 修改设备组名称（默认组除外） |
| R5 | 删除设备组 | 删除时若有设备，提示并将设备移至默认组 |
| R6 | 设备归属 | 设备只能归属二级设备组，一个设备只属于一个二级组 |
| R7 | 功能权限 | 通过角色管理分配设备组的操作权限（增删改查） |
| R8 | 数据权限 | 角色关联设备组，用户登录后只能看到角色关联的设备组及其设备 |

### 1.2 现有基础

当前系统 `topology/` 模块已有 `device_groups` 表和 `device_group_members` 表，提供基础的分组树功能，但缺少：
- 两级树约束和默认组
- status、remark、created_by、updated_by 字段
- 设备唯一归属二级组的约束
- 基于设备组的数据权限控制

## 二、数据库设计

### 2.1 device_groups 表改造

新增迁移 `000036_alter_device_groups.up.sql`，在现有表上追加字段：

```sql
-- 追加字段
ALTER TABLE device_groups ADD COLUMN status VARCHAR(16) NOT NULL DEFAULT 'active';
ALTER TABLE device_groups ADD COLUMN remark TEXT;
ALTER TABLE device_groups ADD COLUMN is_default BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE device_groups ADD COLUMN level SMALLINT NOT NULL DEFAULT 1;
ALTER TABLE device_groups ADD COLUMN created_by VARCHAR(64);
ALTER TABLE device_groups ADD COLUMN updated_by VARCHAR(64);

-- 层级约束：只允许1和2
ALTER TABLE device_groups ADD CONSTRAINT chk_dg_level CHECK (level IN (1, 2));

-- 层级与父子关系一致性：一级无父，二级必有父
ALTER TABLE device_groups ADD CONSTRAINT chk_dg_level_parent
    CHECK ((level = 1 AND parent_id IS NULL) OR (level = 2 AND parent_id IS NOT NULL));

-- 同一父节点下名称唯一（一级组用 COALESCE 处理 NULL parent_id）
CREATE UNIQUE INDEX idx_dg_name_parent ON device_groups (name, COALESCE(parent_id, '00000000-0000-0000-0000-000000000000'::uuid));
```

| 字段 | 类型 | 默认值 | 说明 |

### 2.2 device_group_members 表约束

```sql
-- 一个设备只能归属一个组（已有 PRIMARY KEY (group_id, device_id)，需追加唯一约束）
ALTER TABLE device_group_members ADD CONSTRAINT uq_dgm_device UNIQUE (device_id);
```

应用层校验：添加设备到组时，校验目标组的 `level = 2`。

### 2.3 角色数据权限表（新建）

新增迁移 `000037_create_role_device_groups.up.sql`：

```sql
CREATE TABLE role_device_groups (
    role_id    UUID NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
    group_id   UUID NOT NULL REFERENCES device_groups(id) ON DELETE CASCADE,
    PRIMARY KEY (role_id, group_id)
);

CREATE INDEX idx_rdg_role ON role_device_groups(role_id);
CREATE INDEX idx_rdg_group ON role_device_groups(group_id);
```

**含义**：角色被分配了哪些设备组的数据可见权限。角色关联的是**一级或二级设备组**（关联一级组 = 可见其下所有二级组的设备）。

## 三、模型设计

### 3.1 DeviceGroup 模型

修改 `omcgo/internal/topology/model.go`：

```
type DeviceGroup struct {
    ID          uuid.UUID         // 主键
    Name        string            // 名称
    ParentID    *uuid.UUID        // 父组ID（NULL=一级组）
    Level       int               // 层级：1=一级, 2=二级
    Status      string            // 状态：active / disabled
    IsDefault   bool              // 是否默认组
    Carrier     model.CarrierCode // 运营商（可选）
    Description string            // 描述
    Remark      string            // 备注
    SortOrder   int               // 排序
    CreatedBy   string            // 创建人
    UpdatedBy   string            // 更新人
    Children    []DeviceGroup     // 子组（树查询时填充）
    DeviceCount int               // 设备计数（查询时计算，不持久化）
    CreatedAt   time.Time
    UpdatedAt   time.Time
}
```

### 3.2 请求结构

**CreateDeviceGroupRequest** — 创建设备组：

| 字段 | 类型 | 必填 | 说明 |

| 字段 | 类型 | 说明 |

| 字段 | 类型 | 说明 |

| 字段 | 类型 | 说明 |
|------|------|------|
| can_delete | bool | 是否可以删除 |

## 五、核心业务逻辑

### 5.1 新增设备组

```
CreateDeviceGroup(ctx, req, operator):
  1. 判断层级：parent_id 为空 → level=1，非空 → level=2
  2. 如果 level=2：
     - 校验 parent 存在且 parent.level=1
     - 校验 parent 未被禁用
  3. 校验同级同父下名称不重复
  4. 事务开始 —
     a. 创建设备组，设置 created_by = operator
     b. 如果是一级 + 提供了 sub_groups：
        - 逐个创建二级子组
        - 为每个子组分配对应的设备（移出设备原归属组）
     c. 如果是二级 + 提供了 device_ids：
        - 将设备从原归属组移出
        - 将设备加入新创建的组
  5. 事务提交
```

### 5.2 修改设备组

```
UpdateDeviceGroup(ctx, id, req, operator):
  1. 查询目标组
  2. 校验 is_default=true → 返回错误"默认设备组不可修改"
  3. 校验新名称不与同级其他组重复
  4. 更新 name/remark，设置 updated_by = operator
```

### 5.3 删除设备组

**删除前检查：**
```
CheckDelete(ctx, id):
  1. 查询目标组
  2. is_default=true → 返回 { can_delete: false, message: "默认设备组不可删除" }
  3. 统计该组及其子组下的设备总数
  4. 如果 device_count > 0：
     返回 { can_delete: true, has_devices: true, device_count: N,
             message: "删除后 N 个设备将移动到默认设备组" }
  5. 否则：
     返回 { can_delete: true, has_devices: false, device_count: 0 }
```

**执行删除：**
```
DeleteDeviceGroup(ctx, id, operator):
  1. 校验 is_default=true → 拒绝
  2. 事务开始 —
     a. 收集该组及所有子组的ID列表
     b. 查询这些组关联的所有设备ID
     c. 将这些设备的 group_id 更新为默认二级组 ID
     d. 删除设备组记录（CASCADE 自动清理 device_group_members 和子组）
  3. 事务提交
  4. 清除相关缓存
```

### 5.4 设备归属规则

| 场景 | 处理逻辑 |
|------|---------|
| 新设备注册（TR069 Inform） | 自动归入默认二级设备组 |
| 添加设备到二级组 | 先从原组移除，再加入新组（事务） |
| 删除设备 | 自动清理 device_group_members（CASCADE） |
| 删除设备组 | 组下设备移至默认二级组 |

**约束：**
- 设备只能归属 level=2 的设备组
- 每个设备同一时刻只属于一个二级组（`UNIQUE(device_id)` 约束）
- 添加设备到组时使用 `INSERT ... ON CONFLICT (device_id) DO UPDATE SET group_id = ...` 保证原子性

### 5.5 设备组树查询（含数据权限）

```
GetTree(ctx, userID):
  1. 获取用户可见的设备组ID列表（见第六章数据权限）
  2. 查询所有设备组（flat list），附带 device_count：
     SELECT dg.*, COUNT(dgm.device_id) AS device_count
     FROM device_groups dg
     LEFT JOIN device_group_members dgm ON dg.id = dgm.group_id
     GROUP BY dg.id
     ORDER BY dg.sort_order, dg.name
  3. 如果用户非超管：
     - 过滤：仅保留可见的二级组 + 这些二级组的父一级组
  4. 组装为树结构返回
```

## 六、数据权限设计

### 6.1 权限模型关系

```
用户(User) ──N:M── 角色(Role) ──N:M── 设备组(DeviceGroup)
              via user_roles         via role_device_groups
```

**数据权限传递链：** 用户 → 所有角色 → 角色关联的设备组 → 设备组下的设备

### 6.2 角色管理集成

在角色的创建/编辑页面中新增**数据权限**配置项：

- 展示设备组树，允许勾选一级或二级设备组
- 勾选一级组 = 该角色可见其下所有二级组的设备
- 勾选二级组 = 该角色仅可见该二级组的设备
- 不勾选任何组 = 该角色无设备数据可见权限（需要提示）

在 admin 模块扩展：
- `CreateRole / UpdateRole` 请求中增加 `device_group_ids []uuid` 字段
- 角色详情返回中增加 `device_groups` 列表
- 存储到 `role_device_groups` 表

### 6.3 数据权限查询逻辑

```
GetUserVisibleGroupIDs(ctx, userID) → (groupIDs []uuid, isAll bool):
  1. 查询用户信息（获取 carrier 字段）
  2. 如果 carrier=NULL（超管）→ return nil, true（全部可见）
  3. 查询用户所有角色ID：
     SELECT role_id FROM user_roles WHERE user_id = $1
  4. 查询这些角色关联的设备组：
     SELECT DISTINCT group_id FROM role_device_groups
     WHERE role_id = ANY($roles)
  5. 展开一级组 → 包含其下所有二级组：
     SELECT id FROM device_groups
     WHERE parent_id = ANY($level1_group_ids) AND level = 2
  6. 合并所有二级组ID → return groupIDs, false
  7. 缓存到 Redis：
     key: "user:visible_groups:{userID}"
     TTL: 5分钟
```

### 6.4 设备查询集成

在 `device` 模块的查询流程中注入数据权限：

```
DeviceFilter 新增字段:
  GroupIDs []uuid.UUID  // 数据权限过滤（nil=全部可见）

Repository SQL 改造:
  如果 GroupIDs 不为 nil 且长度 > 0：
    追加 WHERE 条件：
    AND d.id IN (
      SELECT device_id FROM device_group_members
      WHERE group_id = ANY($N)
    )
  如果 GroupIDs 不为 nil 且长度 = 0：
    // 角色未���配任何组，返回空结果
    AND FALSE
```

**Handler 调用流程：**
```
DeviceHandler.List(c):
  1. 从 JWT context 获取 userID
  2. groupIDs, isAll := GetUserVisibleGroupIDs(ctx, userID)
  3. if !isAll { filter.GroupIDs = groupIDs }
  4. 调用 service.ListDevices(ctx, filter) → 正常查询
```

### 6.5 缓存策略

| Key | TTL | 失效时机 |
|-----|-----|---------|
| `user:visible_groups:{userID}` | 5分钟 | 角色数据权限变更时主动清除 |

**缓存失效触发：**
- 修改角色的 device_group_ids → 清除该角色下所有用户的缓存
- 用户角色变更（分配/移除角色）→ 清除该用户的缓存
- 设备组删除 → 清除所有用户的缓存（简单起见）

### E2E 测试场景

1. 创建一级设备组 + 同时创建 2 个二级子组，每个子组分配 3 个设备
2. 修改二级设备组名称 → 成功；修改默认组名称 → 403
3. 删除有 5 个设备的二级组 → check-delete 返回设备数 → 确认删除 → 设备出现在默认组
4. 删除一级组（含 2 个二级子组、共 10 个设备）→ 设备全部移至默认组
5. 角色 A 分配设备组 X → 用户用角色 A 登录 → 只能看到组 X 的设备
6. 超管登录 → 可看到所有设备组和设备

## 十、注意事项

1. **向后兼容**：现有 `/api/v1/groups` 路由暂时保留，新增 `/api/v1/device-groups` 路由
2. **性能考虑**：数据权限使用 `IN (SELECT ...)` 子查询，10 万设备规模需确认索引命中。`device_group_members.device_id` 已有索引
3. **缓存一致性**：角色数据权限变更时需清除相关用户的 Redis 缓存（`user:visible_groups:*`）
4. **事务安全**：删除设备组 + 移动设备必须在同一 DB 事务中
5. **新设备注册**：TR069 Inform ���册的新设备自动归入默认二级组，确保所有设备都有归属
6. **已有数据迁移**：迁移脚本需将现有未归组的设备自动加入默认二级组
