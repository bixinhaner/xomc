## 一、概述

### 1.1 现有流程分析

当前系统处理基站上线的流程：

```
基站 Bootstrap/Boot Inform → ACS 解析 → NATS 事件 → InformHandler 注册/更新 → ProvisioningEngine 自动开通
```

**现有问题：**

| 问题 | 说明 |
|------|------|
| Inform 入库字段不足 | 仅提取 SoftwareVersion、ConnectionRequestURL、IP，未提取 TR069 报文中的主表字段 |
| 无参数同步流程 | Bootstrap 后直接进入 Provisioning，缺少"先从设备读取完整参数"的同步阶段 |
| 无同步状态管理 | 设备表无 sync_status 字段，无法追踪参数同步进度 |
| 设备状态跳跃 | RegisterFromInform 直接设为 active，跳过了完整生命周期 |

### 1.2 优化后的完整生命周期

```
基站重启上线
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段一：Inform 报文解析入库                                │
│ → 提取主表字段写入 devices 表                               │
│ → 全量参数写入 device_parameters 表                        │
│ → 设备状态 = registered，sync_status = pending             │
└────────────────────┬────────────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段二：参数分批同步（数据库驱动 + 插件化处理）               │
│ → 从 DB 读取该设备适用的同步批次定义                         │
│ → ���序执行 GetParameterValues                              │
│ → 每批结果经对应的 ParamProcessor 插件处理                   │
│ → 全部完成 → sync_status = synced                          │
│ → 某批失败 → sync_status = sync_failed，终止                │
└────────────────────┬────────────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────────────┐
│ 阶段三：自动开通（Provisioning，已有，改为监听 sync 事件）    │
└─────────────────────────────────────────────────────────┘
```

## 三、阶段二：参数分批同步（核心设计）

### 3.1 设���目标

| 目标 | 实现方式 |
|------|---------|
| 批次定义可配置 | 存储在数据库中，不同运营商/制式/型号可用不同批次 |
| 批次顺序可调整 | 通过 sort_order 字段控制执行顺序 |
| 特殊参数处理优雅 | ParamProcessor 插件接口，按批次绑定处理器 |
| 不硬编码 | 新增参数批次只需 INSERT 数据库 + 注册处理器（如需特殊处理） |

### 3.2 同步批次定义表

```sql
CREATE TABLE param_sync_batches (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name          VARCHAR(128) NOT NULL,          -- 批次名称（如"射频状态"、"GPS 经纬度"）
    carrier       VARCHAR(4),                     -- 运营商（NULL=通用）
    technology    VARCHAR(4),                     -- 制式（NULL=通用）
    product_class VARCHAR(64),                    -- 产品类型（NULL=通用）
    sort_order    INT NOT NULL DEFAULT 0,         -- 执行顺序（小 → 大）
    param_paths   JSONB NOT NULL,                 -- 要查询的参数路径列表 ["path1","path2",...]
    processor     VARCHAR(64) NOT NULL DEFAULT 'default',  -- 结果处理器名称
    is_active     BOOLEAN NOT NULL DEFAULT TRUE,  -- 是否启用
    description   TEXT,                           -- 说明
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_psb_carrier_tech ON param_sync_batches(carrier, technology);
CREATE INDEX idx_psb_sort ON param_sync_batches(sort_order);
```

**字段说明：**

| 字段 | 说明 |
|------|------|
| carrier | NULL=所有运营商通用，"cmcc"=仅移动适用 |
| technology | NULL=所有制式通用，"lte"=仅 LTE 适用 |
| product_class | NULL=所有型号通用，"BaiBLQ"=仅该型号适用 |
| param_paths | JSON 数组，该批次要 GetParameterValues 的 TR069 路径 |
| processor | 对应 ParamProcessor 注册名，如 "default"、"gps"、"mme_pool" |

### 3.3 批次匹配规则（三级回退，复用 DataModel 模式）

为设备查找适用的同步批次时，采用与数据模型相同的三级回退策略：

```
优先级从高到低：
1. carrier + technology + product_class  （最精确）
2. carrier + technology                  （运营商+制式级）
3. carrier = NULL AND technology = NULL  （通用批次）
```

**批次合并逻辑：**

```
GetBatchesForDevice(device) → []Batch:
  1. 查询所有 is_active=true 的批次
  2. 按三级匹配过滤：
     - 精确匹配：carrier=device.carrier AND technology=device.tech AND product_class=device.product_class
     - 运营商级：carrier=device.carrier AND technology=device.tech AND product_class IS NULL
     - 通用级：carrier IS NULL AND technology IS NULL AND product_class IS NULL
  3. 同一 sort_order 下，精确匹配的覆盖通用的（higher specificity wins）
  4. 按 sort_order ASC 排序返回
```

## 四、ParamProcessor 插件体系（核心架构）

### 4.1 设计理念

参照项目中 Carrier 接口 + CarrierRegistry 的模式，设计 ParamProcessor 接口 + ProcessorRegistry：

- **接口定义行为** — 每个处理器实现同一个接口
- **Registry 管理注册** — 按名称注册处理器，运行时按名称查找
- **默认处理器兜底** — 大部分批次使用 default 处理器（直接存 device_parameters）
- **特殊处理器按需注册** — GPS、MME 池等特殊逻辑各自一个处理器

### 4.2 ParamProcessor 接口

```go
// ParamProcessor defines the interface for processing a batch of parameters
// returned from GetParameterValues.
//
// Each processor handles a specific type of parameter processing logic.
// The "default" processor simply stores parameters to device_parameters table.
// Special processors (gps, mme_pool, etc.) extract and transform data
// before storing.
type ParamProcessor interface {
    // Name returns the processor's registered name (matches param_sync_batches.processor).
    Name() string

    // Process handles a batch of GetParameterValues results.
    // It receives the device, batch metadata, and raw parameter values.
    // It should:
    //   1. Store parameters to device_parameters table (via paramRepo)
    //   2. Optionally update device main table fields (via returned DeviceFieldUpdates)
    //   3. Return any errors encountered
    Process(ctx context.Context, input ProcessorInput) (*ProcessorOutput, error)
}

// ProcessorInput contains all data a processor needs.
type ProcessorInput struct {
    Device     *model.Device
    BatchName  string
    Parameters []tr069.ParameterValueStruct   // GetParameterValues 的原始结果
}

// ProcessorOutput contains the results of processing.
type ProcessorOutput struct {
    // DeviceFieldUpdates contains fields to update on the devices main table.
    // Key = column name, Value = new value. Empty map = no main table updates.
    DeviceFieldUpdates map[string]interface{}

    // StoredCount is the number of parameters stored to device_parameters.
    StoredCount int
}
```

### 4.3 ProcessorRegistry

```go
// ProcessorRegistry manages ParamProcessor registrations.
// Follow the same pattern as CarrierRegistry.
type ProcessorRegistry struct {
    mu         sync.RWMutex
    processors map[string]ParamProcessor
}

func NewProcessorRegistry() *ProcessorRegistry { ... }

// Register adds a processor. Called at application startup.
func (r *ProcessorRegistry) Register(p ParamProcessor) { ... }

// Get returns the processor by name, or the "default" processor if not found.
func (r *ProcessorRegistry) Get(name string) ParamProcessor { ... }

// MustGet returns the processor or panics (for startup validation).
func (r *ProcessorRegistry) MustGet(name string) ParamProcessor { ... }
```

### 4.4 内置处理器清单

| 处理器名称 | 文件 | 职责 |
|-----------|------|------|
| `default` | `proc_default.go` | 直接存入 device_parameters，不做特殊处理。大部分批次使用此处理器 |
| `device_field` | `proc_device_field.go` | 存入 device_parameters + 按参数路径映射回写 devices 主表字段 |
| `gps` | `proc_gps.go` | 解析 LockedLatitude/LockedLongitude，度分秒→十进制转换，回写 devices.latitude/longitude |
| `mme_pool` | `proc_mme_pool.go` | 将 16 组 MME 参数（Status/IP/PlmnId）组装为 JSON 数组，回写 devices.mme_pool |
| `sync_source` | `proc_sync_source.go` | 拼接 tfcsManagerPrimsrc + tfcsSyncState，回写 devices.sync_source |
| `multi_cell` | `proc_multi_cell.go` | 多小区参数展开（FAPService.1/2/3），根据设备载波模式动态处理 |
| `current_alarm` | `proc_current_alarm.go` | 解析 FaultMgmt.CurrentAlarm.*，转换为告警记录，触发 alarm.raised 事件 |

### 4.5 各处理器详细设计

#### 4.5.1 DefaultProcessor（默认处理器）

```
Process(ctx, input):
  1. 将 input.Parameters 转换为 []model.DeviceParameter
  2. 调用 paramRepo.BatchUpsert(ctx, deviceID, params)
  3. 返回 { StoredCount: len(params) }
  // 不更新主表字段
```

适用场景：射频启用状态、系统备份版本、许可证信息、以太网速率等无需特殊处理的参数。

#### 4.5.2 DeviceFieldProcessor（主表字段回写处理器）

```
Process(ctx, input):
  1. 存入 device_parameters（同 default）
  2. 遍历参数，按路径映射表查找对应的设备主表字段：
     映射表（可配置在 processor 的 config 或数据库中）：
       "Device.DeviceInfo.AntennaInfo.Height" → "height"
       "Device.DeviceInfo.X_COM_MODULE_TYPE"  → "model_name"
       "Device.IP.Interface.1.IPv4Address.1.IPAddress" → "ip_address"
  3. 返回 DeviceFieldUpdates
```

适用场景：单个参数直接映射到 devices 表字段的情况。

#### 4.5.3 GPSProcessor

```
Process(ctx, input):
  1. 存入 device_parameters
  2. 从参数中提取 LockedLatitude 和 LockedLongitude
  3. 格式转换：
     - 如果是度分秒格式（如 "31°12'36.5\"N"）→ 转为十进制（31.2101389）
     - 如果已是十进制字符串 → 直接解析为 float64
     - 解析失败 → 不更新，记录 warning 日志
  4. 返回 DeviceFieldUpdates: { "latitude": lat, "longitude": lng }
```

#### 4.5.4 MMEPoolProcessor

```
Process(ctx, input):
  1. 存入 device_parameters
  2. 解析 16 组 MME 参数：
     遍历 input.Parameters，按 MmePoolConfigParam.{N}.{Field} 分组：
       N = 1~16
       Field = Status, MMEIP, PlmnId
     过滤 Status != "0"（无效条目）
  3. 组装为 JSON 数组：
     [{"index":1, "status":"1", "ip":"10.0.0.1", "plmn":"46000"}, ...]
  4. 返回 DeviceFieldUpdates: { "mme_pool": jsonArray }
```

#### 4.5.5 SyncSourceProcessor

```
Process(ctx, input):
  1. 存入 device_parameters
  2. 提取 tfcsManagerPrimsrc（同步源）和 tfcsSyncState（同步状态）
  3. 拼接为 "GPS(locked)" 或 "1588v2(acquiring)" 等格式
  4. 返回 DeviceFieldUpdates: { "sync_source": combined }
```

#### 4.5.6 MultiCellProcessor

```
Process(ctx, input):
  1. 检测设备载波模式：
     - 从设备参数或 ProductClass 推断 cell_count（1/2/3）
  2. 展开多小区参数：
     对于 cell_count=2，param_paths 中的 FAPService.1 自动扩展为 FAPService.1 和 FAPService.2
  3. 存入 device_parameters（每个小区独立的参数行）
  4. 返回 DeviceFieldUpdates（如需要）
```

#### 4.5.7 CurrentAlarmProcessor

```
Process(ctx, input):
  1. 存入 device_parameters
  2. 解析 FaultMgmt.CurrentAlarm.{N}.* 参数
  3. 对每个有效告警：
     - 通过 CarrierRegistry 获取运营商适配器
     - 调用 carrier.AlarmSeverityMapping() 映射告警级别
     - 发布 alarm.raised 事件（交给 AlarmEngine 处理去重和入库）
  4. 返回 { StoredCount: N }
```

### 4.6 处理器注册（启动时）

在 `cmd/app/router/router.go`（或 worker 的初始化代码中）：

```go
// 创建 ProcessorRegistry
procRegistry := paramsync.NewProcessorRegistry()

// 注册所有处理器
procRegistry.Register(paramsync.NewDefaultProcessor(paramRepo))
procRegistry.Register(paramsync.NewDeviceFieldProcessor(paramRepo, deviceRepo))
procRegistry.Register(paramsync.NewGPSProcessor(paramRepo, deviceRepo))
procRegistry.Register(paramsync.NewMMEPoolProcessor(paramRepo, deviceRepo))
procRegistry.Register(paramsync.NewSyncSourceProcessor(paramRepo, deviceRepo))
procRegistry.Register(paramsync.NewMultiCellProcessor(paramRepo, deviceRepo))
procRegistry.Register(paramsync.NewCurrentAlarmProcessor(paramRepo, carrierRegistry, eventBus))

// 注入到 ParamSyncEngine
syncEngine := paramsync.NewParamSyncEngine(syncTaskRepo, batchRepo, deviceService, procRegistry, cmdQueue, eventBus, logger)
```

### 4.7 新增处理器的扩展流程

当需要新增一种特殊参数处理逻辑时：

```
步骤 1: 创建处理器文件 proc_xxx.go，实现 ParamProcessor 接口
步骤 2: 在 router.go 中注册 procRegistry.Register(paramsync.NewXxxProcessor(...))
步骤 3: 在 param_sync_batches 表中 INSERT 新批次，processor 字段设为 "xxx"
完成。无需修改 ParamSyncEngine 核心代码。
```

## 五、ParamSyncEngine 编排引擎

### 5.1 数据模型

**同步任务表：**

```sql
CREATE TABLE param_sync_tasks (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    device_id       UUID NOT NULL,
    device_sn       VARCHAR(64) NOT NULL,
    status          VARCHAR(16) NOT NULL DEFAULT 'pending',
    total_batches   INT NOT NULL DEFAULT 0,
    current_batch   INT NOT NULL DEFAULT 0,
    failed_batch    INT,
    error_message   TEXT,
    batch_details   JSONB,        -- [{"batch_id":"...","name":"...","status":"done/failed","params_count":5}]
    started_at      TIMESTAMPTZ,
    completed_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 5.2 引擎核心流程

```
ParamSyncEngine:
  依赖: SyncTaskRepo, BatchRepo, DeviceService, ProcessorRegistry, CmdQueue, EventBus

  handleDeviceRegistered(ctx, evt):
    1. device = DeviceService.GetDevice(evt.DeviceID)
    2. batches = BatchRepo.GetBatchesForDevice(device)  ← 从 DB 读取，三级回退匹配
    3. 如果 batches 为空 → 直接标记 sync_status=synced，发布 device.sync.completed
    4. 创建 ParamSyncTask:
       - total_batches = len(batches)
       - batch_details = 初始化每个批次的状态为 pending
    5. 更新 device.sync_status = syncing
    6. 入队第一个批次的 GetParameterValues 到 Redis CmdQueue

  handleGetParamResponse(ctx, deviceSN, method, params, success, errMsg):
    1. 查找活跃的 ParamSyncTask
    2. 获取当前批次的 batch 定义
    3. 通过 ProcessorRegistry.Get(batch.Processor) 获取处理器
    4. 如果 success:
       a. output = processor.Process(ctx, {Device, BatchName, Parameters})
       b. 如果 output.DeviceFieldUpdates 不为空 → 更新 devices 主表
       c. 记录批次完成到 batch_details
       d. current_batch++
       e. 如果还有下一批次 → 入队下一批的 GetParameterValues
       f. 如果全部完成:
          - task.status = completed
          - device.sync_status = synced
          - device.last_sync_at = now
          - 发布 device.sync.completed
    5. 如果 !success:
       a. task.status = failed, task.failed_batch = current_batch
       b. device.sync_status = sync_failed
       c. device.sync_message = "批次 '${batch.name}' 同步失败: ${errMsg}"
       d. 终止，不继续后续批次
```

### 5.3 批次入队细节

```
enqueueBatch(ctx, deviceSN, batch):
  cmd = cmdqueue.Command{
    ID:         uuid.New().String(),
    Method:     "GetParameterValues",
    Params:     json.Marshal({ "parameter_names": batch.ParamPaths }),
    Priority:   100,                    // 高优���级，在普通命令之前
    CommandKey: "param_sync:" + batch.ID.String(),  // 去重
    ExpiresAt:  time.Now().Add(30*time.Minute),
  }
  return cmdQueue.Push(ctx, deviceSN, cmd)
```

## 六、Provisioning 对接调整

ProvisioningEngine 改为监听 `device.sync.completed` 事件（替代 `device.registered`）。

好处：
1. 同步完成后设备信息更完整（model_name, latitude, longitude 等），模板匹配更准确
2. 避免同步和配置下发在命令队列中交错

## 十二、设计决策说明

| 决策 | 理由 |
|------|------|
| 批次定义存 DB 而非硬编码 | 不同运营商/型号的基站参数差异大，需要灵活配置。运维人员可通过 API 管理批次定义 |
| ParamProcessor 用 Go 接口而非脚本引擎 | 保持类型安全和性能，Go 接口是项目已有的扩展模式（参考 Carrier 接口） |
| Registry 而非 map[string]func | Registry 提供线程安全、缺省处理器（fallback to default）、启动时校验等能力 |
| 三级回退匹配批次 | 复用 DataModel 的成熟模式，避免发明新的匹配逻辑 |
| processor 字段是字符串而非外键 | 处理器在代码中注册，DB 只存名称引用，避免 DB 和代码的循环依赖 |
| 同步失败即终止 | 后续批次可能依赖前面批次的数据（如 GPS 依赖模块类型），失败后继续没有意义 |
